# monetail WinUI 3の画面構造とライフサイクル

本Skillは**画面構造・責務・寿命の判断**を扱う。仕様承認は`AGENTS.md`、画面・操作は`UI_DESIGN.md`、現状と分離候補は`docs/architecture-winui.md`、業務契約は対象機能の正本を参照する。WinUI API/標準UI/LOB/コード品質/実行テストは既存`winui-*`・`windows-lob-xaml` Skillを併用し、本Skillへ複製しない。

## 画面遷移・生成の原則

以下は**新規実装と変更対象に適用する到達目標**。既存の全画面常駐実装を適合済みとは扱わず、無関係な画面まで同一PRで作り直さない。

1. **単一Window・標準ナビゲーション**：`MainWindow`は共通ナビゲーションとWindow寿命を担当する。遷移先の機能画面は原則`Page`、再利用部品は`UserControl`とし、画面遷移は`Frame.Navigate`へ集約する。管理画面の左メニュー等には必要に応じて`NavigationView`を使用する。新しい独自ナビゲーション基盤は作らない。
2. **使用時に生成**：起動時や`MainWindow.InitializeComponent`で、未表示の機能画面・入力画面をまとめて生成しない。初めて開く時に対象`Page`を生成し、閉じた画面のインスタンスを次回表示のために常駐させない。共有ヘッダーや現在表示する画面など、常時必要なUIはこの禁止対象ではない。
3. **通常離脱時に解放**：`NavigationCacheMode.Disabled`を原則とし、独自のPageキャッシュや使い回し用の参照リストを追加しない。不要になったViewへの強参照・イベント購読・非同期処理を整理する。再表示時はPageを新しく作り、必要な業務状態・共通検索条件等は画面の外の既存正本から受け渡す。単なる再生成を理由に状態のコピーを増やさない。
4. **画面と画面内表示を区別**：画面全体を多数XAMLに並べて`Visibility`で切り替える方式を新規に追加・拡大しない。画面内のエラー、進行状態、入力欄等の条件付き表示には`Visibility`を使用してよい。
5. **ダイアログも必要時に生成**：確認・編集に`ContentDialog`を使う場合は開く時に作り、終了後に不要な参照を保持しない。画面遷移の代用品としてダイアログを乱用せず、専用画面かダイアログかは`UI_DESIGN.md`の確定仕様に従う。

## 責務の境界

| 所有者 | 担当すること |
| --- | --- |
| `MainWindow`／共通シェル | 共通ナビゲーション、家計簿・アカウント切替、共通検索条件、画面間の未保存離脱確認、Windowと画面の寿命 |
| 各`Page`・`UserControl` | 画面固有のXAML・操作、実コントロール、表示、フォーカス・IME・スクロール等の一時的UI状態 |
| 既存の`Monetail.Windows.Presentation`（対象画面で使用する場合） | 表示行・選択・画面用Command・取得世代など既存ViewModelの状態 |
| `Monetail.Windows.Client` | 業務モデル、API通信、認証・権限、保存、競合と復旧の契約 |

`MainWindow`に画面固有イベント・入力検証・行選択を集積せず、Windowから画面内部の`x:Name`を直接操作しない。ViewからWindowや他画面の内部コントロールを参照しない。連携は必要な表示データと操作通知・最小限の公開操作に限定し、Window/Client全体をViewへ渡さない。`partial`のファイル移動だけでは責務分離とみなさない。

状態は**既存の正本を一つだけ**持つ。Clientの下書き・更新版・401復帰、Presentationの行・選択・カーソル等を別層へ複製しない。画面固有の生入力・キャレット・IME・表示位置など実コントロールに依存する情報だけ、必要に応じてViewが保持する。ViewModel、Service、DIやイベント層の追加は実際に責務が減る場合だけ採用する。

## 未保存・401復帰の例外

- 遷移は共通の未保存離脱判定を**画面の破棄やナビゲーション選択変更より先**に実施する。取消時は元のPage・入力・選択・フォーカスを保つ。
- 401後の再認証など、既存仕様が**同じ実コントロールやIME/キャレットを含む入力状態の維持**を要求する間は、**一度使用時に生成した**Page/Viewを復帰完了まで一時的に保持してよい。これは起動時の事前生成や無期限キャッシュの許可ではない。保持する所有者・解除条件を明示し、復帰または破棄後に参照・購読を整理する。
- 将来、Viewを破棄して下書きから再生成する方式に変える場合は、既存の401復帰・未保存保護・不正生入力・選択範囲・IME等を同等に保つテストが先に必要。単に`NavigationCacheMode.Disabled`を指定して既存の復帰契約を壊さない。
- 非同期処理は画面離脱・家計簿変更・再表示後に古い応答を新画面へ反映しない。取消・要求世代や既存の寿命管理を利用し、重複する状態管理を追加しない。

## 実装・レビュー・検証

1. 対象の`MainWindow.xaml`領域・partial・Page/View・Client/Presentationと関連スモークを調べ、生成時点、参照・購読、状態とイベントの所有者、離脱・復帰の経路を確認する。
2. 変更前に「残す共通責務／移す画面責務」「生成・解放時点」「未保存・401時の例外」「検証する契約」を短く整理する。確定済み画面仕様は変えない。
3. **1 PRで1画面境界を基本**とし、構造変更へ無関係のUI仕様変更や抽象化を混ぜない。既存コードに残る違反を理由に新規違反を追加しない。
4. PRでは画面の遅延生成と通常離脱後の解放、再表示、ダイアログ寿命、未保存取消、401復帰、選択・スクロール・キー操作・IME、古い応答の破棄を影響範囲に応じて確認する。既存テスト・Windows製品/スモークは`tests/README.md`に従い実行し、未実施は明示する。
5. 直接参照の削減、フィールド・フラグ・イベント・抽象化の増減、状態の二重管理、総コード量を比較する。行数の減少やCI成功だけで構造・操作の正しさを主張しない。

**自動検査の導入方針**：今後、XAMLの機能画面常駐配置、画面全体の`Visibility`遷移、起動時の不要Page生成、画面間の内部コントロール参照、不許可のキャッシュを構造検査で検出し、生成・復帰・解放はWindowsスモークで検証する。導入前はPRレビュー項目とし、既存違反は段階的に移行して**新規違反を先に禁止**、移行完了後に全画面を厳格検査する。検査の実装・CI必須化を未実施のまま完了扱いしない。

分離の検討順序は[`docs/architecture-winui.md`](../../../docs/architecture-winui.md#winuiの責務棚卸しと段階的分離検討順序未実装)に置き、このSkillに複製しない。
