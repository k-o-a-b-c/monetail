## 共通HTTP境界・認可

参加者の追加・人物対応の契約は[参加者API](specs/api/features/members.md)を正本とする。任意のアカウントID指定による直接追加APIは設けない。

- 対象家計簿を指定して操作するAPIは、対象家計簿の現在の参加・roleを要求ごとにDBで確認する。Cookieの全体Adminやクライアントのroleを信用しない。
- 未認証・セッション失効・利用停止は401。指定した家計簿の未参加と不存在は同じ404、参加済みで役割不足は403、古いrevision・対応の重複・要求IDの競合は409。人物・参加者・招待の操作にも適用する。
- 全体のアカウント検索・一覧・存在照会を家計簿管理者へ追加しない。人物名・表示名からの照合も行わない。
- 書込時はDBの最新の参加・権限・対象所属をトランザクション内で再確認する。最後の有効な管理者の同時降格・除外は、同じ書込ロック内で確認し、片方しか成立させない。
- 全体のアカウント停止と家計簿管理者保護の関係、緊急時の家計簿管理者復旧は別途具体化する。既存の全失効コマンドへ、今回新しい家計簿参照を加えない。
- 業務APIは共通HTTP境界に従う。家計簿に依存しない共通税区分・税率履歴の認証・認可は[共通税区分・税率履歴API](specs/api/features/tax-rates.md)に従う。ログイン、固定HTTPS・ホスト検証・no-store、認証／保存障害時503を適用する。POST・PATCH・PUT・DELETEには本文64 KiB上限を適用し、Cookie認証ではOrigin・CSRFを検証する。有効なBearer認証の業務API要求はCookie用のOrigin・CSRF検証の対象外とする。認証方式ごとの詳細は[セッション保護](auth-session-security.md)・[Windows認証](auth-windows-oauth.md)に従う。GETは追加の本人再確認を要求しない。認証APIの既存のIP単位の回数制限は維持する。

### 共通の検証原則

機能別API正本に適用する共通のエラー優先順位。必要な段階だけを適用し、各段階の内部処理・クラス構成や同一段階内の個別項目の順序は規定しない。機能固有の認可・再送・状態競合について正本で明示した例外は維持する。各機能別APIの第6節には、共通原則を適用した操作別の具体的な検証・処理の流れを記載する。共通原則は検証段階の意味を定め、個別仕様書は各操作の適用段階・固有条件を示す。

| 順序 | 検証内容 |
| --- | --- |
| 1 | ルーティング・共通HTTP境界・受付時の認証 |
| 2 | JSONメディアタイプ・構文・トップレベルのオブジェクト／許可キー（本文のある操作） |
| 3 | 現在の認証・対象家計簿への参加・基本操作権限 |
| 4 | 入力の必須項目・JSON型・配列要素の構造と許可キー・UUIDの形式と空UUID等、要求を解釈するための検証。クエリもこの段階で検証する |
| 5 | 再送対象操作の要求同一性の照合（各機能の再送契約に従う） |
| 6 | 対象の存在・個別操作権限 |
| 7 | 更新版の一致 |
| 8 | 入力値の範囲・業務制約・マスタ・参照整合性・計算等 |
| 9 | 原子的な保存・応答／確定前の認証・権限等の再検証 |

- 認可に必要な項目や対象情報、再送同一性の判定に必要な正規化・入力検証は、その判定に必要な範囲で前倒しできる。対象の存在を確認する前に認可できる場合は先に認可し、権限のないデータ・競合時の最新情報を公開しない。家計簿の不存在と未参加は区別しない。
- 更新版照合のある操作では、通常の入力項目の型・必須項目の検証を版一致より先に行い、業務値・参照制約の検証は版一致後に行う。再送照合を版照合より先に行う操作は、各機能で定めた成功済み要求の再送保証を維持する。
- 失敗時は最初に該当する段階のエラーを1件返す。同一段階で複数の不備がある場合は、個別契約に明示された優先条件を除き、そのうちいずれか1件の適切なエラーを返せばよい。クライアントはその順序やメッセージの文言に依存しない。
- 更新版競合の最新情報・取得結果を返す前、書込を確定する前には、操作に必要な最新の認証・認可を再検証する。認証失効・参加喪失・権限不足時には許可されないデータを返さず、未確定の書込を取り消す。対象行自身の削除等に関する例外、成功済み再送の応答は各機能の契約に従う。

#### 検証項目の分類

本文を解釈できるかという検証（段階4）と、解釈した値が業務上許されるかという検証（段階8）を区別する。

| 検証項目 | 段階 |
| --- | --- |
| 必須キーの欠落、許されない `null`、JSON型の不一致、配列・要素の構造不備、子オブジェクトの未知・重複キー | 4：版照合前 |
| UUIDの形式不正・全桁ゼロ（本文・クエリ）、日付・日時の形式不正や実在しない暦日・時刻、Decimal文字列の形式不正・正確にDecimalで表現できない値、整数として解釈できないJSON数値・整数の表現可能範囲超過（下記） | 4：版照合前 |
| 文字数、空文字の可否、数値の業務上の範囲（Int32等の保存値制約・率の許容範囲を含む）、列挙値の可否、開始日と終了日の前後関係、項目間の組み合わせ | 8：版照合後 |
| 配列の件数・IDの重複・ID集合の過不足、同名判定、入力で参照するマスタ・子要素の存在と所属、有効期間、参照制約、計算結果 | 8：版照合後 |

整数入力は、機能別契約で定める整数の入力表現として解釈できるかを段階4で検証する。解釈済みの整数に対する保存値のInt32範囲、正値・非負・列挙値等の業務制約は段階8で検証する。計算結果の範囲検証も段階8とする。入力表現の範囲と業務上の範囲を混同しない。

トップレベルのJSON形式・未知／重複キーは段階2で検証する。パスUUIDの形式はルーティング段階の契約に従う。操作対象自体の存在と個別操作権限は段階6で確認する。入力の参照IDであっても認可・再送同一性の判定に必要な検証は例外とし、各機能の固有契約に従う。版照合のない操作では段階7を省略する。上表はエラーの分類であり、解析の実装方式や解析回数を指定しない。

#### 複数の不備がある場合の代表例

各例は、明記した不備以外の先行条件を満たし、個別契約の例外が適用されない場合を示す。

| 同時に成立する不備・状態 | 優先する結果 |
| --- | --- |
| 受付時の認証失効と入力不備 | 401（共通HTTP境界の認証結果） |
| 有効な受付時認証、基本書込権限不足、必須項目欠落（JSON構造・許可キーは正常） | 403 `forbidden` |
| 対象家計簿への未参加と個別項目の型不備 | 404 `not_found` |
| 古い更新版と数量の文字列指定、許されない `null`、不正UUID、実在しない日付または数値として解釈できないDecimal文字列 | 400 `invalid_input`（不備の項目） |
| 古い更新版と、正しい型だが範囲外の数量・0〜100の範囲外の率値引・長すぎる名前・不正な列挙値・期間の前後逆転 | 409 `revision_conflict` |
| 古い更新版と対象行の個別操作権限不足（要求の形式は正常） | 403 `forbidden`。最新情報は返さない |
| 正常な同一要求の成功再送と対象行・版の変化 | 個別の再送契約に従った応答。書込を再実行しない |
| 競合応答の確定前に操作権限を喪失 | 403 `forbidden`。最新情報は返さない |
| 同一段階に複数の入力不備 | 固有の優先条件がなければ、そのいずれかの適切なエラー1件 |

失敗した書込で業務データ・更新版・成功再送記録を変更しないことも確認する。全ての組み合わせのテストや特定の実装順を必須にはしない。

### アカウント単位の回数制限（DEC-049）

認証済みの業務APIは原則として同じアカウントで、作成・更新・削除・順序保存等の書込を合わせて固定1分20回、参照・家計簿を開く操作を合わせて固定1分120回の別枠とする方針を確認済み（DEC-069。DEC-068の全操作を共有120回とする方針から変更）。機能ごとに書込枠や参照枠を追加せず、新しい別枠は必要な理由と対象を示して確認してから追加する。

| 対象 | 共通枠 |
| --- | --- |
| 家計簿・人物・科目・支払方法・参加者・招待・レシートの作成・更新・削除・順序保存・参加確定 | 同一アカウントで共有20回／分 |
| 家計簿の参照・開く、人物・科目・支払方法・参加者・招待の一覧、共通税率履歴の全件取得、招待preview、レシートの一覧・詳細取得、履歴候補検索・基本情報自動補完 | 同一アカウントで共有120回／分 |

認証後の検証済みアカウントIDで数え、端末・セッション・IPや対象家計簿が違っても同じ枠の要求は合算する。別アカウントの枠と、書込・参照の2枠は独立。更新後一覧の取得等のAPI内部処理は別のHTTP要求として二重計上せず、書込要求は書込枠だけを使う。既存の指定家計簿・最後の家計簿を開く要求は、最終選択の更新を含めても従来どおり参照枠とする。HTTPメソッドだけで書込・参照を判定しない。制限判定を通る要求は入力不備等も数え、超過は待機させず429とする。Cookie検証で未認証・失効と判断した要求はアカウント枠を使わず401等の認証結果を返す。認証APIは[セッション保護](auth-session-security.md)の既存のIP単位の制限を維持する。DBにカウンターや列を追加しない。
