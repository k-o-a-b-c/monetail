# 52 認証処理の再利用と機能別の境界

**アカウントはアプリごとに独立させ、認証処理のコードを流用しやすい構成を目指す（DEC-036）。** 日用品在庫管理などを別アプリとして作る際に、パスキー・セッション等の実装を再利用する想定とする。現時点では、アプリ間の共通アカウント・共通ログインは採用しない。

## 責務

| 領域 | 扱うもの |
| --- | --- |
| 再利用を目指す認証処理 | 認証アカウント、パスキー、セッションとその失効。「誰がログインしたか」を扱う処理をアプリ固有の処理から区別する |
| Monetail固有の処理 | 家計簿の人物、レシート、振替、計算など。人物と認証アカウントの対応・人物とアカウントを組み合わせる管理もここに属する |
| 将来の別アプリ | 在庫など、そのアプリのデータと利用権限。独立した認証アカウントを持ち、Monetailの人物マスタを利用者マスタとして流用する前提を置かない |

再利用するのはコードであり、アカウント・登録済みパスキー情報・セッション・権限等の認証データはアプリ間で共有しない。ログイン状態の引継ぎや単一の認証サービスへの接続も今回の方針に含めない。

ログインの成功と家計簿の利用許可を区別する。現在のアカウント管理用`Admin`ロールを将来の別アプリの権限として扱わず、各アプリの人物・権限モデルはその実装時に決める。

## 今回の整理

```text
src/Monetail.Api/
├─ Authentication/                  認証と既存の認証DB構成
├─ Features/
│  └─ Monetail/
│     └─ Accounts/                 人物とアカウントを組み合わせる管理
│        ├─ AdminAccountEndpoints.cs
│        ├─ AdminAccountService.cs
│        └─ MonetailAccountPersonLookup.cs
└─ Program.cs                      認証と各機能の登録・起動
```

管理者一覧APIの2ファイルを`Features/Monetail/Accounts`へ移し、名前空間を`Monetail.Api.Features.Monetail.Accounts`に合わせる。サービスとURLの登録は`Program.cs`で行い、認証基盤の`PasskeyWeb`からMonetailの一覧APIを直接登録しない。[51 API契約](51-admin-account-list.md)のURL・JSON・管理者条件・エラー応答は維持する。

将来の在庫管理をMonetailと同じAPIへ追加することは前提にしない。今回は別アプリの作成や認証ライブラリの別プロジェクト化は行わず、既存API・プロジェクト・DBの名称や配置も変更しない。

## 現在残る依存と後続作業

新規導入はアカウントと人物を別に管理する方針が確定した（DEC-039、[56](56-new-user-onboarding-policy.md)）。以下は現行コードの依存を記録したものであり、新規導入時の人物との対応付け・認証条件は実装前に具体化する。今回の文書更新だけで依存を解消したり、認証条件を変更したりしない。

現行の登録・ログイン・セッション検証・再確認等は、Monetailの人物と認証アカウントの対応を必須としている。`AuthDbContext`、`AuthUserLink`、`LegacyPerson`、人物指定の管理コマンドも現行構成を維持する。**今回のフォルダ整理だけで、認証部分をそのまま別アプリへ持ち出せる状態になったわけではない。**

人物照合・表示名取得は[53](53-account-person-lookup.md)で`IAccountPersonLookup`とMonetail側の実装へ分離した。認証の5経路がこの窓口を使い、同じDBスコープ・トランザクションで現在の人物を確認する。別アプリでは独自の人物対応へ差し替える箇所となるが、人物コードを持つ現在の認証データ・DBモデル・人物指定のアカウント発行や管理コマンドには依存が残る。ライブラリ化等は必要になった段階で検討し、現在の人物確認を単に削除してアクセスを許可する変更は行わない。

家計簿分割・同じアカウントの複数家計簿参加はDEC-035を引き継ぐ。人物・業務マスタは家計簿ごと、アカウントはMonetail全体、参加と権限は家計簿ごとに管理する方針が確定した（DEC-040、[57](57-ledger-data-ownership.md)）。DBはSQLite 1ファイルとし、家計簿IDで所属を区別してAPI側で参加と操作権限を確認する（DEC-041）。具体的なスキーマと人物との対応付け等の詳細は保留する。今回、EF移行・DB変更・新しい依存パッケージは不要で、Windows版・業務値・保存済み`receipt.total`・本番設定・実データを変更しない。

Monetail内で同じアカウントが複数の家計簿へ参加できる方針と、別アプリとのアカウント共有は別の話として扱う。共通アカウント案は利用者の変更により今回取り下げ、アプリごとの独立アカウントと認証コードの再利用へ方針を修正した。

検証結果・件数・CIは[tests/README.md](../tests/README.md)を参照する。
