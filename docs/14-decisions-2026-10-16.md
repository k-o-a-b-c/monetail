# 14 仕様決定記録：店舗別税端数とオーケーの現行割引額入力

更新日: 2026-10-16。以下は、利用者の明示した運用方針をまとめた決定記録。**プログラムと実DBには未反映**。

## 決定事項

| 分野 | 決定した方針 |
| --- | --- |
| 既存のDBデータ | 外部キーの整合性は取れている**前提**で進める。データ検査を実施済みとは扱わない |
| 消費税 | **税率ごとに課税対象額を合算**した後で税の端数を処理 |
| 端数処理 | **切り捨て／四捨五入を店舗ごと**に設定できるようにする |
| 金額の個人配分 | 金額は参考値。端数は**四捨五入**し、個人別参考額の合算と伝票総額が一致しなくてもよい |
| オーケーの3/103割引 | **従来どおり、既存の明細の「割引額」欄に手入力する** |
| オーケー専用機能 | **不要**。新規入力欄、分数割引の自動計算、追加DBテーブルは作らない |

## オーケー方針の変更理由

オーケーの会員割引は単品ごとに税抜本体価格の`3/103`を計算して1円未満を切り捨てる。買い物した食品を商品1点ごとに登録せずに分類等へまとめると、**商品ごとの丸めを再現するための元の単価情報がない**。

そのため「レシートの会員割引合計を別欄へ転記する」**前回の設計案は採用しない**。今まで利用していた`ReceiptDetail.DiscountFee`（DBでは`t_receipt_details.discount_fee`）に必要額を入力する運用を維持する。

### 既存の「割引額」の意味（重要）

`Receipt.Total` 等のソースの計算式は以下。

```text
基礎額 = (fee - discount_fee) × quantity
率割引 = Ceiling(基礎額 × discount_rate / 100)
税計算前金額 = 基礎額 - 率割引
```

したがって、食品を1つのまとめ明細として登録するなら、通常は**数量1の行に対して**レシートに印字された割引合計を`discount_fee`へ入力する。`quantity>1`では割引額も数量倍される。実際に値引された税率・費目に属する明細へ割引を割り当てる必要がある。

負の「会員割引」明細を追加する方法は採らない。現行コードでは負の明細を収入として認識するため。

詳細・税のテスト例: [08 改修仕様](08-requested-enhancements.md)。

## 2026-10-17 追加の設計決定（優先）

- **毎回店のマスタを作る運用にはしない**。マスタ未登録のレシートでも税端数処理を選べる。
- `m_shop.tax_rounding_mode`は**任意の初期値**。レシートの計算は常に`t_receipts.tax_rounding_mode`を参照。
- **`t_receipts.shop_code`や店舗マスタFKは追加しない**。
- 旧レシートは`floor`、新規レシートはその伝票ごとに選択・上書きできる。
- [15 詳細設計](15-shop-tax-rounding-design.md)と[移行SQL案](migrations/20261017_01_shop_tax_rounding.sql)を参照。

## 継続して実装するもの

**店舗別の消費税端数処理のみ**を新たな計算機能として追加する。

- 税率ごとに合算してから切り捨て／四捨五入。
- 店舗の既定丸め方式を設定できるようにし、レシートには適用した方式を残す案。
- 過去の伝票は今までの切り捨て計算を維持する。
- 現行のSQLiteとVB.NETの読込・保存への影響はテストしてから実装する。

## 今回の決定によって不要になった開発

- オーケークラブ3/103の自動計算。
- 専用の「会員割引合計」入力欄や専用のテーブル。
- 商品の割引対象フラグ・会員カード提示判定・分数パラメータの保存。
- オーケー割引だけを目的とした新しいDBマイグレーション。

## 技術的に残る確認

- レシートごとの方式保存は2カラム追加で設計済み。**店舗マスタへの紐付けは必須にしない**。UIの初期値適用・例外条件の実機検証は残る。
- マイナス金額・返品時の四捨五入方式。
- 金額配分の四捨五入をどの集計表示へ適用するか。
- 現行`discount_fee`の単価・数量への適用を説明したテストの追加。

> **外部キーについて**: 既存データは整合している前提とする。一方、`DataAccess.DeleteReceiptGroups` の削除順はFKがONの接続では違反し得る。実際のデータの整合性の話とは別のコード課題として扱う。

**2026-10-18対応（LEG-004）**: レシート更新・削除の削除順を、対象者割当→明細→グループ→レシート親に修正する。更新時は子だけを削除・再登録する。既存のトランザクションと操作手順を維持し、FK ON/OFFのテストDBで成功・失敗時の巻き戻しを確認する。DB定義・接続時の外部キー設定・ポイント機能は変更しない。
