# 14 決定済み業務ルールとオーケー省入力方式（2026-10-16）

この文書は、ユーザーが決めた運用ルールと、実装方法についての提案を区別して記録する。**現在のVB.NETコードやSQLiteのDDLを変更したものではない**。

## A. 決定した業務ルール

| 対象 | 決定事項 | 状態 |
| --- | --- | --- |
| DBの外部キー | **既存データは整合している前提で作業を進める** | 前提。実データ検査済みという意味ではない |
| 消費税 | **税率ごとに合算してから丸める** | 確定 |
| 消費税の端数 | **店舗ごとに切り捨て／四捨五入**を設定できる | 確定 |
| 対象者への配分 | 参考・目安として扱う。端数は**四捨五入** | 確定 |
| オーケー | 食品を全部1点ずつ登録することは現実的ではない | 利用上の要件 |

※外部キーの既存行の整合性という前提と、現在のDELETE文が**親側から削除**するためFK ON環境では失敗し得るという**コード上の問題**は別。後者は修正検討事項。

## B. オーケーに関する推奨設計

**結論：レシートに印字された会員割引の合計額を、購入明細とは別に入力する方式を先に実装する。**

オーケーの公式説明では、オーケークラブ会員が現金払いの際、対象食料品（酒類を除く）について、税抜本体価格の `3/103` を**単品ごとに**割引し、レシートにはその割引額の**合計**を表示する。商品を費目別にまとめた金額に一度だけ `3/103` を掛ける方法では端数切り捨てが再現できない。

公式説明:
- https://ok-corporation.jp/feature/okclub.html
- https://ok-corporation.jp/feature/okclub_app.html

### 登録操作の設計案

1. 利用者は現行のように「食品」「日用品」「家庭用品」など必要な粒度で明細を登録する。必要なら個別商品も登録できる。
2. レシート上の**会員割引合計**（例: 76円）を**正の割引額**として別入力欄に転記する。値引前の税抜金額を入力していることが前提。
3. 会員割引は対象の**8%食品の税抜小計から差し引く**。その後は**税率ごとに合算**し、店舗設定の「切り捨て／四捨五入」により税額を確定する。
4. 10%課税の商品等、割引対象外には控除しない。割引後の食品金額を既に入力したときは**二重割引**を防ぐ。
5. **支払合計はこの会計計算が正本**。明細別・分類別・対象者別の値引の割付けは参考値とし、必要なら対象金額の比率で按分して四捨五入する。
6. 将来的に商品を個別登録した場合に限り、`floor(税抜単価 × 3 / 103) × 数量` による自動計算を選択できるようにする。ただし集約入力には適用しない。

### 具体例（仮データ）

税抜入力、税端数は切り捨ての場合。

| 項目 | 金額 |
| --- | ---: |
| 8% 食品割引前小計 | 3,000円 |
| 10% 日用品小計 | 1,000円 |
| オーケー会員割引（レシートから転記） | 76円 |
| 8% 課税対象額 | 3,000 − 76 = 2,924円 |
| 8% 消費税 | floor(2,924 × 0.08) = 233円 |
| 10% 消費税 | floor(1,000 × 0.10) = 100円 |
| **支払合計** | **4,257円** |

### なぜ負の購入明細として入れないか

現在の `Receipt.Incomes` は**金額が負の明細を収入**とみなす。たとえば「会員割引 -76円」という明細を通常の商品明細として増やすと、収支集計が**76円の収入**と誤認する可能性がある。

従って、**会計割引は商品明細・収入・返金とは区別した属性**として保持し、`Receipt.Total` と `Receipt.Expenses` 等に一貫した減額処理を加える。

### DBの実装方針（未決定）

- 最低限必要な項目: **割引種別、金額、適用税率区分、入力方式（手動合計／個別自動）、適用時のルール**。
- レシート単位の単一カラムで始める案と、複数割引を表現する**子テーブル**を設ける案がある。ほかの店舗・混合割引も考えるなら子テーブルが拡張しやすい。
- **現行の `m_shop`・`t_receipts`・`t_receipt_details` には該当列が存在しない。** 正式DDLやマイグレーションは別途設計する。
- 店舗マスタの**税端数モードは新規レシートの初期値**。保存時にレシートへ丸めモードをスナップショットし、店舗設定が後から変更されても過去の金額を変えない。
- 現在の `Receipt.Total`・`Receipt.Incomes`・`Receipt.Expenses`・分類集計・残高推算への影響を一緒にテストする。

## C. 人への金額配分（確定事項）

- 対象者別金額は厳密な精算残高ではなく、**家計の参考値**。
- 人数で割った結果の小数は**四捨五入**。例えば100円を3人で割るなら**33円／人**、合計99円でも許容する。
- 端数1円を特定の人へ強制して配分しなくてよい。
- **会計のレシート総額は100円のまま**であり、人別に丸めた額を足し上げて会計を修正しない。
- 現在の `GetGroupStatisticsList` はグループ単位で税・丸めを行っており、新方式の表示や集計でどこまで変えるかは実装時にテストする。
