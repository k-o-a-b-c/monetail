# 14 仕様決定記録：レシート単位の税端数と既存データの扱い

初回決定: 2026-10-16 / 更新日: 2026-10-18。利用者の明示した運用方針と、その後の変更・実装を記録する。**PR #1〜#3はmainへ反映済み。実ユーザーDBへの移行適用・実データ照合は未確認**。

## 採用済みの決定事項

| 分野 | 決定した方針 |
| --- | --- |
| 既存のDBデータ | 外部キーの整合性は取れている**前提**で進める。データ検査を実施済みとは扱わない |
| 消費税 | **税率ごとに課税対象額を合算**した後で税の端数を処理 |
| 端数処理 | **切り捨て／四捨五入をレシートごと**に選択・保存する。保存済みの方式を履歴や店舗マスタで上書きしない |
| 店舗ごとの初期選択 | 同じ店名・現在の利用者の直近レシートを使う。履歴なしは`floor`。マスタ未登録・自由入力も同じ動作で、マスタ値は使わない |
| 店舗マスタ編集 | 作成を見送る。設定ボタン・更新APIを追加しない。既存の`m_shop.tax_rounding_mode`列は移行互換性のため残す |
| 編集中の税設定 | 内税／外税と端数方式は独立したラジオボタンで選択し、登録確認まで画面側だけで保持。`Receipt.GetTotal(taxType, taxRoundingMode)`で合計を計算する |
| 流用登録 | 従来どおり確認後に画面の内容を即時保存して閉じる。画面上の税設定を使い、追加の登録操作は求めない |
| 金額の個人配分 | 金額は参考値。新しい`half_up`の個人配分の最終端数は**四捨五入**。既存`floor`の参考額は互換性を維持し、個人別参考額の合算と伝票総額が一致しなくてもよい |
| 負額の端数処理 | `floor`は旧`Double`式を維持。新`half_up`は`Decimal`・`MidpointRounding.AwayFromZero`（税額−0.5円→−1円）を採用し、自動回帰テストを追加 |
| オーケーの3/103割引 | **従来どおり、既存の明細の「割引額」欄に手入力する** |
| オーケー専用機能 | **不要**。新規入力欄、分数割引の自動計算、追加DBテーブルは作らない |

## オーケー方針の変更理由

オーケーの会員割引は単品ごとに税抜本体価格の`3/103`を計算して1円未満を切り捨てる。買い物した食品を商品1点ごとに登録せずに分類等へまとめると、**商品ごとの丸めを再現するための元の単価情報がない**。

そのため「レシートの会員割引合計を別欄へ転記する」**前回の設計案は採用しない**。今まで利用していた`ReceiptDetail.DiscountFee`（DBでは`t_receipt_details.discount_fee`）に必要額を入力する運用を維持する。

### 既存の「割引額」の意味（重要）

`Receipt.Total` 等のソースの計算式は以下。

```text
基礎額 = (fee - discount_fee) × quantity
率割引 = Ceiling(基礎額 × discount_rate / 100)
税計算前金額 = 基礎額 - 率割引
```

したがって、食品を1つのまとめ明細として登録するなら、通常は**数量1の行に対して**レシートに印字された割引合計を`discount_fee`へ入力する。`quantity>1`では割引額も数量倍される。実際に値引された税率・費目に属する明細へ割引を割り当てる必要がある。

負の「会員割引」明細を追加する方法は採らない。現行コードでは負の明細を収入として認識するため。

詳細・税のテスト例: [08 改修仕様](08-requested-enhancements.md)。

## 2026-10-17以降の設計変更と最終形

- **毎回店のマスタを作る運用にはしない**。マスタ未登録のレシートでも税端数処理を選べる。
- **旧案（置き換え済み）**: `m_shop.tax_rounding_mode`を任意の初期値にする設計を検討した。利用者がマスタメンテナンス画面の作成を見送り、支払い方法の入力補助と同様の履歴利用を希望したため、**現在はマスタ値を初期選択に使用しない**。
- **採用した初期選択**: `DataAccess.GetTaxRoundingMode(shopName)`で同じ店名・`Environment.UserName`に一致する支払方法の利用者に絞り、`date DESC, seq DESC`の先頭を取得。登録済み店舗・履歴候補・自由入力で同じ処理を使う。手動選択後と保存済みレシートの編集では履歴で上書きしない。
- 保存済みレシートの計算は`t_receipts.tax_rounding_mode`を参照する。画面の合計プレビューだけは未確定の選択値を引数で渡す。
- **`t_receipts.shop_code`や店舗マスタFKは追加しない**。
- 旧レシートは`floor`、新規レシートはその伝票ごとに選択・上書きできる。
- 移行は`m_shop.tax_rounding_mode`と`t_receipts.tax_rounding_mode`の2列追加のみ。いずれも`TEXT NOT NULL DEFAULT 'floor'`で、値を`floor`／`half_up`に制限する。店舗側の列は既存移行設計との互換性のため残すが、初期選択・編集には使わない。
- **旧方式（置き換え済み）**: 編集中にReceiptの税設定を更新し、取消時に元へ戻す方式から変更した。現在は店名などと同様に、**すべての登録確認後にだけ画面の内税／外税・端数方式をReceiptへ転記**する。保存確認の取消では転記しない。Receipt全体のディープコピー案は検討したが、利用者の判断で採用せず現方式を維持する。
- 流用に登録し直しを求める案は採用しない。従来の`RegisterReceipt(True)`で確認後に即時保存し、画面の税設定をそのまま引き継ぐ。保存直前の履歴再取得はしない。
- [15 詳細設計](15-shop-tax-rounding-design.md)と[移行SQL](migrations/20261017_01_shop_tax_rounding.sql)を参照。

## 実装・main反映済みの改修

### PR #1: レシート単位の税端数処理（LEG-019）

- 税率ごとに合算してから切り捨て／四捨五入。
- レシートの方式と合計を同じトランザクションで保存し、一覧・残高推算の両読込経路へ方式を復元する。
- 過去の伝票は今までの切り捨て計算を維持する。移行SQLは既存`total`・明細・対象者割当を更新しない。
- 履歴による初期選択、内税／外税・税端数の独立したラジオボタン、編集中のReceiptの両設定の保持、従来の流用操作を自動テストで検証する。
- [PR #1](https://github.com/k-o-a-b-c/monetail-legacy/pull/1)。オーケーの入力方法・値引計算は変更しない。

### PR #2: レシート更新・削除時の外部キー対応（LEG-004）

- **対象者割当→明細→グループ→レシート親**の順に削除する。更新時は子だけを削除・再登録する。
- 既存のトランザクションと画面操作を維持し、FK ON/OFFの実SQLiteテストで更新・削除の成功、別レシートの保持、途中失敗時のDB巻き戻しを検証した。
- DB定義・製品接続時の外部キー設定・ポイント機能は変更していない。実ユーザーDBの整合性検査やFK一律有効化を実施したという意味ではない。
- [PR #2](https://github.com/k-o-a-b-c/monetail-legacy/pull/2)。

### PR #3: レシートのNULL文字列読込（LEG-024の対象範囲）

- レシートの所在地・タグ、グループと明細のタグの**4列・6読込箇所**にNULL判定を追加し、NULLを空文字として扱う。一覧・残高の両読込経路と子データの再読込を対象とする。
- NULL・空文字・日本語・空白、金額・対象者割当の保持、画面取消後の同じReceiptの再表示を自動テストで検証した。
- 読込・画面取消ではDB内のNULLを更新しない。後から明示的に保存した場合は、既存の保存処理により空文字を保存する。
- 全テーブル・全列のNULL対応やDBデータの一括正規化は行っていない。[PR #3](https://github.com/k-o-a-b-c/monetail-legacy/pull/3)。

## 今回の決定によって不要になった開発

- オーケークラブ3/103の自動計算。
- 専用の「会員割引合計」入力欄や専用のテーブル。
- 商品の割引対象フラグ・会員カード提示判定・分数パラメータの保存。
- オーケー割引だけを目的とした新しいDBマイグレーション。

## 検証済みの範囲と残る確認

- main反映済みの自動テストは計算20件・移行5件・Windows保存／画面15件の**計40件**。既存ソリューションのNuGet復元・Windowsビルドも成功している。実行方法と対象は [tests/README.md](../tests/README.md) 参照。
- 旧`floor`の負額・浮動小数点境界、新`half_up`の負額・正負混在、`discount_fee`の単価・数量適用、個人別の参考配分は自動回帰テスト済み。採用した負額方式を未決定とは扱わないが、実際の返品レシートとの照合は未実施。
- 実ユーザーDBのバックアップ・テスト用コピーへの移行適用、実レシート金額の照合、Windowsの手動画面確認は別途必要。自動UIテストの成功を実運用確認済みとはしない。
- FKの一律有効化、ポイント保存・読込、マスタメンテナンス画面は今回の実装対象外。採番・支払方法の有効期間などの未決定事項は [13 仕様判断](13-glossary-decisions.md) に残す。
- 割引率の小数保持（LEG-005）と支払メモ一括保存のトランザクション化（LEG-012）は未対応。次の機能改修に先立ち、利用者の依頼で全ドキュメントの整合性を確認する。
