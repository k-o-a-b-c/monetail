# 06 テスト計画・回帰テストケース

更新日: 2026-10-19 / 実装済み改修の自動テストと、今後のテスト計画を区別して記載。自動テストの構成・件数・最新CI結果は[tests/README.md](../tests/README.md)を参照する。実データでの検証・手動E2Eは未実施。

目的: レガシー版の「実際の期待動作」をテストで固定し、将来のオンライン版・別言語版と同じ入力で比較する。差異は変更理由を記録してから解消する。

## テスト実施上の原則

- 実データDBを直接用いず、**バックアップから複製したテスト専用DB**を使う。
- テスト前にアプリのDB接続先を確認し、クラウド同期フォルダや本番DBに誤接続しない。
- 「現行コードから予測できる結果」と「望ましい業務上の結果」は別列で記録する。
- 日時／ユーザー／通貨／税率／割引率／入力順序と期待表示額を固定する。
- 実装済み／要確認／失敗を記録する。実行環境・DBスキーマ・テストデータ版も記録する。

## B-2. 実装済みのレシート単位税端数と既存割引

税率ごとに合算後、レシートに保存した`floor`／`half_up`を適用する。計算20件には両方式、混在税率・非課税・税込、旧`floor`の負額／浮動小数点境界、手入力の`discount_fee`と`Ceiling`による率値引を含む。

オーケー3/103の自動計算は実装・受け入れ対象に含めない。会員割引は現行の`discount_fee`へ手入力し、数量乗算を含む既存の計算を維持する。

## B-3. 計算互換性の追加契約

[12-calculation-contract.md](12-calculation-contract.md)の**CAL-001〜007**を参照。旧`floor`の税抜10%・`+19円`と`−1円`では式から`Total=19 / Expenses=20 / Incomes=−2`となり、合計と収支列の総和は一致しない。

自動テストでは同じ性質を`+5円`と`−1円`で確認し、`floor`は`Total=4 / Expenses=5 / Incomes=−2`、`half_up`は`Total=4 / Expenses=6 / Incomes=−1`。小数率のDB往復には新規・更新の回帰を追加した。CAL全条件の網羅は未実施。月末・年跨ぎ・振替等の現行境界は実SQLite回帰を追加したが、対象者フィルタの全組合せ、同一日時の複数残高・別形式の日時、為替は残る。[21 日末残高](21-end-of-day-balance.md)参照。

## B-4. オーケーの既存割引の受け入れ条件

[14 決定記録](14-decisions-2026-10-16.md)と[08 改修要件](08-requested-enhancements.md)の**現行`discount_fee`入力、数量への乗算、収入誤計上・二重割引の回避**を維持する。自動計算テストで手入力値引・率値引・正負を確認済み。専用欄・分数計算は作っていない。

## B-5. レシート単位の端数処理の受け入れ条件

[15 詳細設計](15-shop-tax-rounding-design.md)の**RT-001〜014**を使用する。マスタ未登録店でも方式を選択・保存でき、新規入力の初期値は同じ店舗・現在の利用者の直近レシート（日付降順・同日時はseq降順）を使う。店舗マスタの値は初期選択に使用せず、編集画面の追加は見送った。

- Windows自動テストで、店舗履歴と利用者の範囲、自由入力・未登録店、保存済み設定と手動選択の保持を確認済み。
- 端数方式は独立したラジオボタンで選択する。内税／外税と互いの選択を解除しないことを確認済み。
- 内税／外税・端数方式は登録確認まで画面だけに保持し、`Receipt.GetTotal(taxType, taxRoundingMode)`で合計をプレビューする。編集・確認取消中に元Receiptの両設定・合計が変わらず、登録確認後に転記されることを確認済み。キャンセル時の設定復元や編集用のディープコピーは導入していない。
- 流用は確認ダイアログ後に画面の設定で即時新規保存して閉じ、追加の登録操作は不要。実際の流用ボタン・確認ダイアログによる保存と取消を確認済み。
- 負の`half_up`は税額を`AwayFromZero`で丸める実装を採用し、負額・正負混在を自動テスト済み。返品の実運用期待値の確認は導入前の別作業。

[JSON](tests/tax-rounding-cases.json)の全11件は`tests/CalculationTests`から実際のVBコードへ入力して実行される。JSONには全テストは収録しておらず、保存／画面／負額などはコード側にも定義する。

### C-016 金額の範囲超過

単価×数量・値引額との差・税込額・既存明細との合計が範囲外なら、明細反映前に警告し、入力・明細・DBを保持する。修正後は通常保存できる。内税／外税切替時の範囲超過表示、登録・流用の確認前の中止とSeq／更新版の保持、修正後の即時流用も自動回帰で確認する。[25 検証範囲](25-receipt-amount-overflow.md)。

## C. 自動テスト整備の残作業

1. 画面の明細反映・登録前の金額範囲確認を実装済み（[25 仕様](25-receipt-amount-overflow.md)）。分類・収支の月年集計は範囲超過表示・条件変更での復帰を回帰化した（[26 仕様](26-statistics-amount-overflow.md)）。残高集計など残る範囲のオーバーフローを検討する。両欄の加減算・乗算・不正式と式の途中の桁あふれは回帰化済み（[24 仕様](24-integer-money-expressions.md)）。数量0以下・率100%超などは画面で自動補正し、既存の範囲外値の読込・計算を維持する回帰を追加済み（[23 仕様](23-detail-input-validation.md)）。対象者0人とA・B・C・無関係者Dの全16選択集合、完全一致／部分一致と按分の組合せ、正負・税率・端数・グループ境界は回帰化済み（[22 検証範囲](22-person-group-statistics.md)）。重複対象者・重複選択は未網羅。小数率のDB往復（LEG-005）は新規・更新の回帰を追加済み。
2. 振替・残高登録など、残る保存／読込・途中失敗の結合テストを整える。支払メモ一括保存は3チェック、残高削除は成功・親削除失敗からの復元と再削除の2チェックで自動化済み。残高・振替タグのNULL読込は3チェックで検証済み。確認ダイアログを含む画面の手動E2E・実DBでの障害復旧とは区別する。
3. 同一日時の複数残高の優先順位の仕様確認、別形式の日時・為替換算の回帰が残る。日末残高の境界修正と推算の共通化は実装・回帰追加済み。
4. 複数プロセス・共有フォルダー・WAL・利用者環境の起動案内など、残るE2Eを整える。接続先不正・移行不足の拒否は自動回帰を追加した。ローカル2接続の採番・ロック・古い編集の検証は自動化済み。更新版照合と競合時の画面保持を実装した。レシート更新／削除と残高削除の途中失敗時のDB復元もFK ON/OFFで自動化済み。
5. 別言語へ移る前に、コード側だけにある計算契約も共有可能な入力→期待値のフィクスチャへ拡充する。
