# 08 改修要件：店舗別の消費税端数処理・オーケー割引の運用

更新日: 2026-10-24

レシート単位の税端数処理は [PR #1](https://github.com/k-o-a-b-c/monetail-legacy/pull/1) で実装・mainへ反映済み。**新規入力の初期選択は同じ店舗・現在の利用者の直近レシートから取得し、店舗マスタの値は使用しない。** 店舗マスタ登録や店コードFKは不要。マスタメンテナンス画面の作成は見送る。[詳細設計](15-shop-tax-rounding-design.md)参照。

**オーケーの3/103割引は現在の「割引額」欄への手入力を継続し、自動計算・専用入力欄・割引用DB列を追加しない。** 以前検討した「会計割引合計の専用入力欄」案は採用しない。方針変更の記録は [14 決定記録](14-decisions-2026-10-16.md)参照。

## 1. 今回の確定事項

| 対象 | 方針 | 状態 |
| --- | --- | --- |
| 税の計算単位 | **税率ごとに課税対象額を合算してから端数処理** | 実装済み |
| 税額の端数処理 | **切り捨て／四捨五入**を各レシートで選択・保存する | 実装済み |
| 店舗ごとの初期選択 | 同じ店舗・現在の利用者の直近レシートから取得。履歴なしは切り捨て | 実装済み |
| 店舗変更と過去の伝票 | 保存したレシートの税端数方式を保持し、履歴やマスタで上書きしない | 実装済み |

## 2. 店舗別の消費税端数処理（LEG-019）

### 必須の動作

1. これまでどおり**レシート内の同一税率の課税対象額を合算**して計算する。異なる税率を混在させない。
2. 税額の端数処理を**レシートごとに自由に選べる**切り捨て／四捨五入で計算する。新規入力の初期選択は同じ店名・現在の利用者の直近レシートから取得し、店舗マスタの設定は使わない。**税率別に合算した後で丸める**ことは固定。
3. **店舗マスタが未登録でも**レシート上で端数方式を選べる。同じ店舗・現在の利用者の履歴がなければ、初期値は従来の切り捨て。
4. 保存したレシートには適用した丸め方式を記録し、後から同じ店舗の新しいレシートが登録されても、過去の金額・方式を変えない。保存済みレシートの店名変更でも履歴を再適用しない。
5. **旧レシートは従来の切り捨て**として扱い、移行だけで既存レシートの金額を変更しない。

### 採用した保存・入力設計

- `m_shop`: `tax_rounding_mode`（`floor`／`half_up`）は以前の移行設計との互換性のため残す。**現実装の初期選択・店舗編集には使用しない**。
- `t_receipts`: `tax_rounding_mode`を**レシートごとに確定・保存する正本**として持つ。**店コード列を追加しない**。
- 両列は`TEXT NOT NULL DEFAULT 'floor'`、値を`floor`／`half_up`に制限する。元DDLは移行前の構造を記録しており、[移行SQL](migrations/20261017_01_shop_tax_rounding.sql)で2列だけを追加する。適用はバックアップしたテスト用DBに一度だけ行い、既存金額・対象者割当を更新しない。
- 登録済みマスタ候補・履歴候補（`Code=0`）・自由入力は同じ履歴検索を使う。`m_payment_classification`と`m_user`を介して`Environment.UserName`に一致する利用者に絞り、`date DESC, seq DESC`の先頭を採用する。手動選択後は店名を変えても選択を保持する。
- 内税／外税と端数方式は独立したラジオボタンで選択する。編集中は画面に値を持ち、`Receipt.GetTotal(taxType, taxRoundingMode)`で合計を表示する。**両設定はすべての登録確認を通過してからReceiptへ反映**し、キャンセル時の復元処理は不要。レシート全体のディープコピーは採用していない。
- 流用は従来どおり確認後に画面の内容を即時保存して閉じる。表示中の税設定を使用し、追加の登録操作や保存直前の履歴再取得は行わない。
- `floor`も合算・税計算をDecimalとし、負の方向への切り捨てを維持してDouble境界の1円誤差を修正する。保存済みtotalは変更しない（[40 Decimal税計算](40-decimal-tax-calculation.md)）。`half_up`の税額は`Decimal`と`MidpointRounding.AwayFromZero`で計算する（税額−0.5円→−1円）。負額・正負混在の自動回帰テストは実装済み。実運用の返品との照合は導入前の確認として残る。

### 受け入れテスト例（税抜・課税対象）

| ID | 条件 | 期待 |
| --- | --- | --- |
| TAX-001 | 10%・19円の商品2件・税率別合算・切り捨て | `floor(38×1.10)=41円` |
| TAX-002 | 同じ条件・四捨五入 | `round_half_up(38×1.10)=42円` |
| TAX-003 | 8%・7円・切り捨て | `floor(7×1.08)=7円` |
| TAX-004 | 8%・7円・四捨五入 | `round_half_up(7×1.08)=8円` |
| TAX-005 | 同じ店舗で別の方式の新しいレシートを保存 | 保存済みの過去レシートの適用方式・合計が変わらない |
| TAX-006 | 8%と10%の商品が混在 | 税率を分けて集計し、それぞれの合算金額に丸める |

## 3. オーケー：現行の割引額入力を継続（LEG-020）

### なぜ3/103の自動計算をしないのか

オーケークラブの対象商品の割引は、公式案内によれば**税抜本体価格×3/103を商品1個ごとに円未満切り捨て**し、その割引額を合算する。商品を分類単位にまとめた場合、各商品の単価と数量が失われるため、まとめた金額に3/103を掛けても同じ合計になるとは限らない。

**例（税抜単価100円×2個）**:

- 個別計算: `floor(100×3÷103)×2=4円`
- 合算後の計算: `floor(200×3÷103)=5円`

そのため、**実際のレシートに記載された割引合計を手入力**する現在の運用を続ける。オーケー専用の新しい計算ロジックは設けない。

公式参照:
- https://ok-corporation.jp/feature/okclub.html
- https://ok-corporation.jp/feature/okclub_app.html

### 現行コードの割引額の意味に注意

`Receipt.Total` や集計メソッドの現行の演算は以下の順序である。

```text
基礎金額 = (fee - discount_fee) × quantity
率割引額 = Ceiling(基礎金額 × discount_rate / 100)
税計算前金額 = 基礎金額 - 率割引額
```

**`discount_fee` は「その明細の単価から差し引く金額」**で、レシート全体の割引総額専用の列ではない。

- 例: 食品を税抜3,000円として**1行・数量1**でまとめ、レシート記載の会員割引が76円なら、その明細の`割引額=76円`で、税計算前の金額は2,924円。
- 同じ明細を**数量3**にすると、`(3,000 - 76) × 3`となり、値引額が**228円**扱いになる。複数個の入力へ割引合計をそのまま指定しない。
- 商品を複数の分類に分けて入力する場合は、**割引の全額を8%対象の食品の明細へ適切に割り当て**、同じ割引を複数行へ重複入力しない。費目別・対象者別の詳細精度は入力方法に依存する。
- **割引後の金額を既に`fee`に入力した場合**、同じ割引を`discount_fee`に重ねると二重割引になる。
- 「会員割引 -76円」という**負の新しい明細を追加しない**。現行`Receipt.Incomes`は負額の明細を収入と解釈する。既存の`discount_fee`欄なら費用の減額として扱われる。
- レシート税区分が**税込／税抜**のどちらかによって計算対象が異なる。ここに記載した食品割引前小計の例は**税抜入力**が前提。税込価格入力のレシートは実レシートと計算結果を照合する。

### 数値例（税抜入力・税率別合算・消費税切り捨て）

| 入力項目 | 金額 |
| --- | ---: |
| 8%食品グループ・`fee`（割引前） | 3,000円 |
| 同じ明細の`discount_fee`・`quantity=1` | 76円 |
| 8%食品の税計算前金額 | 2,924円 |
| 10%日用品グループの金額 | 1,000円 |
| 8%消費税 | `floor(2,924×0.08)=233円` |
| 10%消費税 | `floor(1,000×0.10)=100円` |
| **レシートの支払合計** | **4,257円** |

この例は**利用手順の例**であり、実ユーザーのレシートの再現テスト結果ではない。入力例では実装済みの`floor`を選択する。既存の値引計算と税率別合算は自動回帰テストでも検証している。

## 4. レガシー版で実装した範囲

**実装済み**: **すべてのレシートで独立して選べる**税端数の切り捨て／四捨五入、方式の保存・両読込経路への復元、同じ店舗・現在の利用者の直近レシートによる初期選択。マスタ編集機能は追加していない。

**実装しない**: オーケー専用の割引計算、3/103分子分母管理、会員割引合計の専用欄、会員割引専用テーブル、明細の割引対象判定。既存`discount_fee`を利用する。

**参考集計**: 人別の配分は参考値とする。`half_up`の個人配分の最終端数は四捨五入し、floorの参考集計は切り捨て規則を維持し、共通税計算はDecimalを使う。会計総額との完全一致は求めない。実装箇所・詳細は[計算契約](12-calculation-contract.md)参照。

## 5. 残る確認事項

- 実ユーザーDBのバックアップ・テスト用コピーへの移行適用と、実レシート金額の照合。自動テストでの旧金額保持は検証済みだが、実データへの適用を実施済みとはしない。
- Windowsの手動操作と実運用の返品期待値との照合。自動テストでは登録画面の操作・保存・取消・流用と採用済みの負額の丸めを検証済み。
- オーケーの現行入力方法で税抜／税込や複数分類に分けた場合の手入力運用の確認。**機能追加の前提にはしない**。

## 後続のWeb化に関する方針

まずWindows版を進める。後続のWeb化は必須とし、Web版の入力機能はレシート、次に振替を優先する。APIはASP.NET Coreを採用し、同じリポジトリにC#／.NET 10のAPI、`/health`、Docker・CIの土台を実装した（[42](42-api-foundation.md)）。認証DBの接続・追加移行まで実装した（[44](44-auth-database-foundation.md)）。サーバー上のDocker＋SQLiteを想定するが、ログインと本人再確認は実装済みで、業務機能・実配置は未実施。XMLのUserCode指定は採用せず、APIの利用者はログイン結果から確定する。認証はパスキー中心とし、初回登録・一般利用者の利用再開は管理者画面の登録コード発行で行い、利用停止・紛失時の全失効とは別操作とする。初期管理者と緊急復旧は管理コマンドを使う方針（[43 設計](43-passkey-authentication-design.md)）。各機能の詳細範囲は未決定で、現行の税・割引・保存契約を互換性の基準とする。[33 方針](33-windows-first-web-input-priorities.md)。
