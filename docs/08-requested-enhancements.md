# 08 改修要件: 店舗別の端数処理と3/103割引

- 起案: 2026-10-15
- 状態: **要件・設計案（未実装）**
- 対応課題: [LEG-019 / LEG-020](05-issues.md)
- 方針: レガシー版で必要な計算機能を先に完成させ、計算互換性をテストで固定してからオンライン化する。

## 1. 要望

1. 店ごとに、消費税等の端数が**四捨五入**か**切り捨て**かを設定して記録したい。
2. **3/103割引**など、単純な「何%引き」ではない割引を正しく計算したい。

現在の `Receipt.Total`、`Calculation.GroupCalculatedFee`、`Calculation.DetailCalculatedFee` は概ね `Math.Floor` を固定使用する。割引率は `Double` で持ち、`Math.Ceiling` によって割引額を丸める実装がある。**店ごとの税端数モードや分子・分母の割引率は未実装**である。

## 2. 店舗別の端数処理（LEG-019）

### 必要な設定（提案）

| 項目 | 値の例 | 理由 |
| --- | --- | --- |
| `tax_rounding_mode` | `floor`, `half_up` | 税額・税込変換の1円未満を店舗に合わせる。将来必要なら `ceil` |
| `tax_rounding_scope` | `line`, `tax_rate_subtotal`, `receipt` | **どの金額をまとめてから**丸めるかで合計が異なる |
| `discount_rounding_mode` | `floor`, `half_up` | 割引額の端数規則。税端数と**別にする** |
| `discount_rounding_scope` | `unit`, `line`, `receipt` | 商品1個ごとか品目行ごとか合計ごとかを区別する |

初期画面では「消費税の端数処理: 切り捨て／四捨五入」を選択可能とする案。既存レシートとの互換性を守るため、**未設定は旧計算と同じ値**にする。ただし、従来コードの「税率ごとに合算してから切り捨て」を崩さないため、単なるモード追加だけではなく、対象単位も併せて仕様化する。

- 店舗マスタは**入力時の初期値**として使い、レシート保存時に適用モード・単位をレシート側へ**スナップショット保存**する。あとで店舗の設定を変えても過去取引の金額を変えない。
- 現行の `t_receipts` は店名・店舗名を文字列で保存し、店舗マスタのIDを持たない。**マスタ紐づけをどう特定するか**（選択時のID保持、既存文字列とのマッピング）を設計し、同名店舗や店舗名変更による誤適用を防ぐ。
- 既存のレシートは原則「legacy（既存と同じ計算経路）」として解釈し、**自動で過去分を再計算しない**。
- 負数・返金では `Floor(-1.2)=-2` となる点に注意。対称の丸め規則（例: 負数は絶対値で丸め、符号復元）を別途決定し、仕様とテストに固定する。
- 端数処理のルールは税額、値引額、対象者按分の端数と混同しない。

### 丸め粒度による違いの例

税抜価格19円の商品が2件、税率10%の場合:

- **明細ごと切り捨て**: `floor(19×1.1)×2 = 40円`
- **税率別合計に切り捨て**: `floor((19+19)×1.1) = 41円`
- **明細ごと四捨五入**: `round_half_up(19×1.1)×2 = 42円`

「切り捨て or 四捨五入」だけでは店舗のレシートを再現できないため、**丸める対象単位**を仕様に含める。

## 3. 3/103割引（LEG-020）

### 計算式

`割引額 = 対象価格 × 3 ÷ 103`。一般的な `3%引き` の `×3÷100` とは異なる。

対象価格が税抜100円なら:

- 3%引き: 3円
- 3/103引き（割引額の円未満切り捨て）: `floor(100×3÷103)=2円`

**分数は分子 `3`・分母 `103` の整数として保持**し、近似値 `2.912621…% ` を `Double` に変換して計算しない。レシート金額が整数円である前提なら整数／有理数演算にできる。

### 実例: オーケークラブ

公式には、会員カード利用かつ現金払いで、**対象の食料品（酒類などは除外）**に対して**単品ごとに本体価格×3/103**の割引を行うと案内されている。割引額の円未満は切り捨て。

- 公式会員制度: https://ok-corporation.jp/feature/okclub.html
- 公式会員アプリ案内（単品ごと）: https://ok-corporation.jp/feature/okclub_app.html
- 公式レシート説明（割引計算・対象商品・丸め・消費税の計算単位）: https://ok-corporation.jp/media-download/1333/b64f0c13cb9da512/PDF/

オーケー公式のレシート解説では「単品ごとに割引額を計算してから合計する」ことが明示され、**単価98円×3個を割引額2円×3個とする**実例がある。消費税は税率別の税抜本体価格の小計を基に切り捨てると案内されている。これはオーケーのルールの根拠であり、他店へ自動適用しない。

**注意**: これは対応すべき方式の実例。Monetailが対象とする「3/103割引の店」がオーケーであると断定しない。対象条件・商品複数個の計算粒度・税計算との順序は手元の実レシートで確認する。

### 最小実装案

- 店舗側に `discount_formula_kind`（`none`, `percent`, `fraction`）、`discount_numerator`、`discount_denominator`、`discount_rounding_mode`、`discount_rounding_scope` を持たせ、**レシート作成時のデフォルト**とする。
- 対象商品・決済手段を判定するため、レシート登録画面で「会員割引を適用する」選択と**明細ごとの割引対象フラグ**を用意する案。対象商品を分類だけで自動確定しない。
- 適用したルールと各明細の最終割引額（または再計算に必要な確定スナップショット）を保存して履歴を再現できるようにする。**DBカラム名・テーブル構造は実DDL確認後に決定**。
- 既存の `discount_fee` と `discount_rate` に、会員割引を**どの順序で重ねるか**はレシートで検証して決める。税抜本体価格・割引後課税標準・税込合計の順序を明文化する。
- 店舗が未登録でも、レシート単位で税と割引の設定を変更できるようにする案。

### 数量による差（検証必須）

税抜価格100円の商品を2個購入した場合:

- 1個ずつ割引を算出: `floor(100×3÷103)×2=4円`
- 同じ品目行の小計から算出: `floor(200×3÷103)=5円`

**オーケーについては**公式レシート解説の `98円×3個 → 2円×3個` が確認できるため、1個ずつ割引算出が根拠を持つ。他店や汎用モードは商品単位か品目行単位かを**実レシートで検証**する。

## 5. 実装前に決める点

1. 端数処理の対象は**消費税だけ**か、値引・按分も含むか。
2. 税の丸めは明細ごとか、税率別小計か、レシート全体か。
3. 3/103割引は**1個単位**か、商品行単位か。
4. 割引対象品目・決済手段の判定、通常値引との適用順序。
5. 過去のレシートの計算方式を変えないための保存方法とDB移行。
