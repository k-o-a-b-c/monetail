# 08 改修要件：店舗別の消費税端数処理・オーケー割引の運用

更新日: 2026-10-16

> **最新方針**：店舗別の消費税端数処理のみを機能改修の対象とする。**オーケーの3/103割引は現在の「割引額」欄への手入力を継続し、自動計算・専用入力欄・割引用DB列を追加しない。** 以前検討した「会計割引合計の専用入力欄」案は採用しない。詳細な意思決定は [14 決定記録](14-decisions-2026-10-16.md)。

## 1. 今回の確定事項

| 対象 | 方針 | 状態 |
| --- | --- | --- |
| 税の計算単位 | **税率ごとに課税対象額を合算してから端数処理** | 確定 |
| 税額の端数処理 | **切り捨て／四捨五入**を店舗ごとに選べる | 確定・未実装 |
| 店舗変更と過去の伝票 | 保存したレシートの税端数方式を保持する | 提案・詳細未決定 |
| オーケー会員割引 | **従来の明細「割引額（discount_fee）」を使って手入力** | **運用確定・新機能不要** |
| 3/103自動計算 | 商品を1個ごとに登録しない場合、正確な割引合計を復元できない | **開発対象から外す** |
| 個人別の金額配分 | 参考値。端数は四捨五入し、配分合計の完全一致を求めない | 確定 |

既存データの外部キー整合性は取れている前提で進める。ただし、現行のレシート削除処理のDELETE順とFKの相性は**別のコード上の課題**として扱う。

## 2. 店舗別の消費税端数処理（LEG-019）

### 必須の動作

1. これまでどおり**レシート内の同一税率の課税対象額を合算**して計算する。異なる税率を混在させない。
2. 税額の端数処理を、店舗の既定設定に応じて**切り捨て／四捨五入**する。1円未満の端数をどのタイミングで丸めるかを決める機能ではなく、**税率別に合算した後で丸める**ことは固定。
3. 未登録の店でもレシート側で端数方式を選択できるようにする案。
4. 保存したレシートには適用した丸め方式を記録し、後から店舗の既定値を変更しても過去の金額が変わらないようにする。
5. **旧レシートは従来の切り捨て**として扱い、移行だけで既存レシートの金額を変更しない。

### 設計案（SQLite）

- `m_shop`: `tax_rounding_mode`（`floor`／`half_up`）など、税端数方式の**既定値**。
- `t_receipts`: `tax_rounding_mode`等、レシート登録時の**適用モード**。
- 実際の列名・DEFAULT・NULL・既存レコードの移行SQLは別途定義する。現在のDDLにはこれらの列はない。
- `t_receipts` は `m_shop.code` を持たず店名文字列で照合しているため、店設定の選択方法を設計する。名前を自動一致させるだけでは同名店舗への誤適用の可能性がある。
- 四捨五入は金額が正の場合の通常の0.5切り上げを想定。**マイナスの課税対象額／返品時の丸めの扱い**は確認してテスト化する。

### 受け入れテスト例（税抜・課税対象）

| ID | 条件 | 期待 |
| --- | --- | --- |
| TAX-001 | 10%・19円の商品2件・税率別合算・切り捨て | `floor(38×1.10)=41円` |
| TAX-002 | 同じ条件・四捨五入 | `round_half_up(38×1.10)=42円` |
| TAX-003 | 8%・7円・切り捨て | `floor(7×1.08)=7円` |
| TAX-004 | 8%・7円・四捨五入 | `round_half_up(7×1.08)=8円` |
| TAX-005 | 店舗の設定を変更 | 保存済みのレシートの適用方式・合計が変わらない |
| TAX-006 | 8%と10%の商品が混在 | 税率を分けて集計し、それぞれの合算金額に丸める |

## 3. オーケー：現行の割引額入力を継続（LEG-020）

### なぜ3/103の自動計算をしないのか

オーケークラブの対象商品の割引は、公式案内によれば**税抜本体価格×3/103を商品1個ごとに円未満切り捨て**し、その割引額を合算する。商品を分類単位にまとめた場合、各商品の単価と数量が失われるため、まとめた金額に3/103を掛けても同じ合計になるとは限らない。

**例（税抜単価100円×2個）**:

- 個別計算: `floor(100×3÷103)×2=4円`
- 合算後の計算: `floor(200×3÷103)=5円`

そのため、**実際のレシートに記載された割引合計を手入力**する現在の運用を続ける。オーケー専用の新しい計算ロジックは設けない。

公式参照:
- https://ok-corporation.jp/feature/okclub.html
- https://ok-corporation.jp/feature/okclub_app.html

### 現行コードの割引額の意味に注意

`Receipt.Total` や集計メソッドの現行の演算は以下の順序である。

```text
基礎金額 = (fee - discount_fee) × quantity
率割引額 = Ceiling(基礎金額 × discount_rate / 100)
税計算前金額 = 基礎金額 - 率割引額
```

**`discount_fee` は「その明細の単価から差し引く金額」**で、レシート全体の割引総額専用の列ではない。

- 例: 食品を税抜3,000円として**1行・数量1**でまとめ、レシート記載の会員割引が76円なら、その明細の`割引額=76円`で、税計算前の金額は2,924円。
- 同じ明細を**数量3**にすると、`(3,000 - 76) × 3`となり、値引額が**228円**扱いになる。複数個の入力へ割引合計をそのまま指定しない。
- 商品を複数の分類に分けて入力する場合は、**割引の全額を8%対象の食品の明細へ適切に割り当て**、同じ割引を複数行へ重複入力しない。費目別・対象者別の詳細精度は入力方法に依存する。
- **割引後の金額を既に`fee`に入力した場合**、同じ割引を`discount_fee`に重ねると二重割引になる。
- 「会員割引 -76円」という**負の新しい明細を追加しない**。現行`Receipt.Incomes`は負額の明細を収入と解釈する。既存の`discount_fee`欄なら費用の減額として扱われる。
- レシート税区分が**税込／税抜**のどちらかによって計算対象が異なる。ここに記載した食品割引前小計の例は**税抜入力**が前提。税込価格入力のレシートは実レシートと計算結果を照合する。

### 数値例（税抜入力・税率別合算・消費税切り捨て）

| 入力項目 | 金額 |
| --- | ---: |
| 8%食品グループ・`fee`（割引前） | 3,000円 |
| 同じ明細の`discount_fee`・`quantity=1` | 76円 |
| 8%食品の税計算前金額 | 2,924円 |
| 10%日用品グループの金額 | 1,000円 |
| 8%消費税 | `floor(2,924×0.08)=233円` |
| 10%消費税 | `floor(1,000×0.10)=100円` |
| **レシートの支払合計** | **4,257円** |

この例は**利用手順の例**であり、実レシートの再現テスト結果ではない。店別の税端数処理が実装されるまでは現行の切り捨て計算を適用する。

### 追加の受け入れ条件（現行機能の回帰テスト）

| ID | 条件 | 期待 |
| --- | --- | --- |
| OK-001 | 税抜食品3,000円・数量1・割引額76円 | 8%課税前金額2,924円（値引率0の場合） |
| OK-002 | 税抜食品3,000円・数量3・割引額76円 | **割引総額228円**として処理。操作マニュアルでは数量への注意喚起 |
| OK-003 | 割引76円を`discount_fee`で処理 | `Receipt.Incomes`には76円の収入を作らない |
| OK-004 | 同じ割引を割引後単価にも反映 | 二重割引となるため、入力手順で注意喚起する |
| OK-005 | オーケー専用の割引テーブル・入力欄・3/103自動計算 | **レガシー版の開発対象外** |

## 4. レガシー版で実装する範囲

**実装する**: 店舗ごとの税端数の切り捨て／四捨五入、およびレシートへの計算方式保存。

**実装しない**: オーケー専用の割引計算、3/103分子分母管理、会員割引合計の専用欄、会員割引専用テーブル、明細の割引対象判定。既存`discount_fee`を利用する。

**現状維持**: 人別の配分は参考値として四捨五入する方針。実装箇所・詳細な表示ルールは[13 仕様決定](13-glossary-decisions.md)参照。

## 5. 残る確認事項

- 店舗マスタとレシート文字列店名の紐づけ方。
- 税端数の半端な値・マイナスの返金時の四捨五入動作。
- 過去レシートの丸め方式の保存と既存金額への影響。
- オーケーの現行入力方法で税抜／税込や複数分類に分けた場合の手入力運用の確認。**機能追加の前提にはしない**。
