# Windows版の継続開発とWeb版の入力優先順位

更新: 2026-10-24。APIはASP.NET Coreを採用し、同じリポジトリにC#／.NET 10の土台・`/health`・DockerとCI、認証DBの接続・追加移行を実装した。ログインは実装済みで、Web業務入力と実環境への配置は未実施。[42 起動方法](42-api-foundation.md)、[44 認証DB](44-auth-database-foundation.md)参照。

## 確定した進め方

1. **まずWindows版を進める。** 日常の入力・保存・表示を改善し、計算とデータ保全の互換性を維持する。
2. **後続のWeb化は必須とする。** 単なる検討候補として扱わず、Windows版の改修でもWeb版へ引き継げる仕様とテストを整える。
3. **Web版はレシート（receipt）の入力を最優先し、次に振替（transfer）の入力へ進む。** 各入力機能の初期範囲はWeb版の詳細設計で決める。新規・編集・流用・削除の採否まで確定したものではない。

マスタメンテナンス画面の作成見送り、オーケーの既存割引額への手入力、正常な流用の操作回数を増やさない方針は継続する。

Web版の導入設計は新規利用を基本とする。既存DB移行は一度きりの運用手順・必要最小限の専用スクリプトで対応し、常設の移行画面・APIは作らない。通常のDBスキーマ更新は維持する。新規アカウント登録は全体管理者からの招待を必須とする（DEC-038）。家計簿の管理者であることだけでは新規アカウントを招待できない。入力開始までの画面・状態の整理は[56 導入方針](56-new-user-onboarding-policy.md)にまとめ、実装済みの既存DB向けコマンドと区別する。

## Windows版で積み上げるもの

- SQLは既存のDataAccessに集約した構成を維持し、必要性を確認しながら改善する。LEG-026の[月次／年次のSQL数・読込時間](34-receipt-read-performance.md)を基準に、[GetReceiptsの一括読込](35-batch-receipt-reads.md)を比較する。[残高推算向けGetPaymentReceipts](36-batch-payment-receipt-reads.md)も共通組立で一括化する。子再読込や振替・残高等の他経路は今回の対象に含めない。
- 計算、入力補正、税率別合算と端数、保存の更新境界を文書と固定期待値で残す。ブラウザー固有の処理を現行の計算モデルへ混在させない。
- 既存の計算テストの入力・期待値をWeb版の互換性の基準に使う。WinFormsの画面テストをそのままブラウザーへ流用できるという意味ではない。
- 既存Windows版のAPI接続への切替は未実施。認証・APIの設計時に段階と互換性を確認し、全面書換えや本番DBの移動を先行させない。

## 後続のWeb版で設計する境界

想定する構成はブラウザーからAPIを経由してDBへアクセスし、SQL・保存時の検証・確定計算をサーバー側で行うもの。Windows版の直接SQLite接続は現行のままとする。

レシート入力では、店舗・日時・支払方法、内税／外税、税端数、グループ・明細・対象者、割引・タグを現行仕様と照合する。入力候補となるマスタや店舗履歴の参照も整理する。振替入力では、移動元／移動先、名称・日時・整数金額・タグ、同一口座の拒否と現在の整数許容範囲を引き継ぐ。

## APIと認証の方針

- **APIはASP.NET Core／.NET 10 LTSを採用する。** 標準のMinimal APIや認証関連の資料・部品を使いやすいC#とし、Windows版のVB／.NET Framework 4.8とは独立したプロジェクトにする。Goは比較候補だったが、現時点では採用しない。将来の言語変更は実測したメモリ・保守負担を基に判断し、計算の固定期待値とAPI契約を移行の基準にする。
- **Windows版のXMLに利用者コードを設定する方式は採用しない。** UserCode設定のPR #45は未マージで取り下げた。既存Windows版はEnvironment.UserNameを使うmainの動作を維持し、将来のAPIではログイン結果から利用者を確定する。任意の利用者コード指定を本人確認の代わりにしない。
- **想定配置はサーバー上のDockerで動かすAPIと、サーバーの永続フォルダに置くSQLite。** 特定のメーカー・型番に依存しない構成として記述する。APIへ保存フォルダをマウントする。既存SQLiteを使う方向で検討し、具体的な配置・移行・バックアップと復旧手順は詳細設計で決める。Cloudflare Workers／D1は従来の比較候補として残すが、今回の採用構成ではない。
- **まず本人認証と利用者の紐付けを設計する。** LAN経由で使う想定。初期版のアカウント管理は管理者に限定し、家計データは登録利用者全員で全体を閲覧・編集する。家計簿分割・人物別の閲覧／編集範囲・参照専用権限は後続とする。ネットワークへの接続とアプリの本人確認は区別する。

開発先は同じリポジトリとし、APIの土台はDB・ログインなしで起動できる。Composeの既定ポート公開は`127.0.0.1:8080`で、同じ端末からの確認または将来のリバースプロキシ向けとする。LAN公開や業務データの取扱いは、HTTPSとログインの設計後に進める。

認証はパスキー中心とし、常設のパスワードは持たない。管理者のWeb画面から新しい人物の追加、アカウントと期限付き登録コードの発行を行い、本人がパスキーを登録する設計とする。人物だけを登録し、後から同じ人物にアカウントを発行することもできる。一般利用者の利用停止・紛失対応は管理者画面の同じ全失効操作にまとめ、再開時の登録コード発行は別操作とする。初期管理者の作成・管理者の復旧はサーバーの管理コマンドを使う。[43 認証設計](43-passkey-authentication-design.md)にIdentity・既存m_userとの対応・Cookieとセッション・失効の具体案をまとめる。ログインは実装済みであり、初期版は1家計簿を登録利用者全員で共有する方針が確定している。HTTPSの固定URL・証明書等の実環境の値は配備前に決める。保存済みtotalや過去の更新者を読込・移行だけで再計算・上書きしない。

関連: [ロードマップ](07-roadmap.md)、[構成](04-architecture.md)、[意思決定](13-glossary-decisions.md)、[計算契約](12-calculation-contract.md)、[振替入力](28-transfer-input-validation.md)。

認証の期限はログインから13日経過後、ログイン時の端末のタイムゾーンで次に迎える午前2時・自動延長なしとする。タイムゾーン未取得・不正時はサーバーの設定（DockerではTZで指定）を使い、端末やサーバーの地域変更でも既存セッションの期限は変えない。管理の更新操作・パスキー変更は直近5分以内の本人確認を求める。バックアップ復元後の認証情報全失効はシステム管理者の手動コマンドで行う（DEC-028、期限の後続変更はDEC-034）。URLと証明書の調達は運用側で扱い、具体的な方法を設計書へ記録しない。

今回の認証実装にDBファイル自体の暗号化を含めず、通常のSQLiteを継続する（DEC-030）。失効と認証完了の競合、人物・アカウント作成の応答喪失後の再送も検証し、無効な鍵による新規セッション発行と重複人物の作成を防止する。

初期管理者・コード再発行は[45](45-initial-admin-enrollment.md)、パスキー登録は[46](46-passkey-enrollment.md)、ログイン・セッション・本人情報・ログアウトは[47](47-passkey-login-sessions.md)、同じ本人・セッションのパスキー再確認と直近5分の判定は[48](48-passkey-reauthentication.md)まで実装した。全失効・管理コマンドによる復旧は[49](49-authentication-revocation-recovery.md)まで実装した。本人のパスキー一覧・追加／削除は[50](50-self-service-passkeys.md)、管理者向けの人物・アカウント一覧APIは[51](51-admin-account-list.md)、既存人物への一般アカウント初回発行APIは[54](54-admin-account-creation.md)まで実装した。一般・管理者アカウントのコード再発行APIは[55](55-admin-enrollment-code-reissue.md)まで実装した。Web管理画面・追加管理者の管理は後続とする。

別アプリのアカウントは独立させ、認証部分のコードを流用しやすい構成を目指す（DEC-036、[52](52-reusable-authentication-boundaries.md)）。共通アカウント・共通ログインは現時点では採用しない。人物必須の現行認証を維持した配置整理を先に行い、人物照合の窓口は[53](53-account-person-lookup.md)で分離した。人物コード・DBモデル・管理コマンドの依存は後続で整理する。Web版の業務入力は引き続きレシート→振替を優先する。
