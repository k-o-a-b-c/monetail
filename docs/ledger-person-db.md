# 人物・参加者のDB構成と更新版

[← 人物API・DBの入口](ledger-person-api.md)

## DBの構成（初回定義へ実装済み）

アカウントとの対応は参加者表に人物IDを持つ構成で利用者確認済み（DEC-059）。人物0人・人物未対応の参加者・アカウントに対応しない人物を認め、人物への対応から認証アカウントを自動作成しない。人物IDのUUID採用・日付の保存形式・更新版の保存単位も確認済み。以下は現在の実装内容。未実装の業務表や画面の設計とは区別する。

- `ledger_people`に人物名・有効開始日・有効終了日・共通順・人物の更新版を保存する。期間は時刻やタイムゾーンを持たない日付とし、SQLiteでは`YYYY-MM-DD`形式のTEXT、制限なしはNULLで保存する方針を確認済み（DEC-086）。APIでも同形式の文字列またはnullを使い、C#では`DateOnly?`で扱う。正しい日付を固定桁で保存し、両日がある場合の開始日≦終了日を検証する。DBのCHECKでも前後関係を検証する。
- 同一家計簿の人物名にUNIQUE制約を設け、同時登録でも同名を防ぐ。比較は前後空白除去後の完全一致とし、SQLiteのBINARY比較にそろえる。共通順は各人物行に保存し、並べた人物ID配列からサーバーが順序値を設定する（DEC-087）。
- 既存の`ledgers`行に、人物の並び順全体で共有する更新版`people_order_revision`を1つ追加する（DEC-087）。人物0人でも取得でき、名前・権限等の変更と並べ替えの競合を分けられる。人物の追加・削除・順序変更時に更新し、共通順を保存する要求で照合する。
- 人物の更新版は名前・有効期間が変わったときに更新する（DEC-087）。人物との対応は参加者の更新版で検証する。共通順だけの変更では人物の更新版を変更せず、人物情報・参加者情報・並べ替えの競合を区別する。
- 更新版の値は、現行の家計簿・参加者の実装と同様、APIが生成するUUID文字列へそろえる（DEC-087）。各対象に現在の値を1つ保持し、取得時に返した値を保存要求で照合して、新しい版への置換と業務変更を原子的に行う。値の大小で新旧を判定せず一致だけを見る。人物1人・参加者1人・家計簿ごとの人物順全体の3単位に分ける方針は確認済み。並び順の各人物行の更新と全体の更新版の置換は同じトランザクションで行う。

## アカウント対応の保存構成（API／DB実装済み）

`ledger_members`にNULL許容の`person_id`を設け、対応なしをNULLで表現する。`ledger_people`はアカウントIDを持たず、人物の名前・有効期間・表示順等を管理する。人物の登録とアカウントの参加は独立させ、対応専用表`ledger_member_people`は作らない。

- 参加者の主キー`(ledger_id, auth_user_id)`と人物IDの単一列で、1アカウントが同一家計簿で対応できる人物を最大1人とする。`(ledger_id, person_id)`へUNIQUE制約を置き、1人物へ複数アカウントが対応することも防ぐ。SQLiteではNULLを複数行に持てるため、人物未対応の参加者を複数登録できる。
- `(ledger_id, person_id)`から`ledger_people`の同じ組へRESTRICTの複合FKを設け、他家計簿の人物へ対応できないようにする。本人の人物IDは現在の参加者行から求める。参加者編集の人物候補は同じ家計簿の人物から取得する。
- 名前・期間は人物編集で人物行にまとめて保存し、対応は参加者編集で参加者行へ保存する。それぞれの画面の保存を1要求で完了し、操作の途中で失敗した場合はその保存全体を戻す。
- 対応変更は参加者の更新版で検証・更新する（DEC-087）。人物保存時の本人判定は、人物の更新版だけを根拠にせず、現在の参加者行と役割を要求ごとに確認する。参加者の役割変更等との競合の扱いはAPI設計で具体化する。
- 参加者の`person_id`が人物を参照している間は、RESTRICTの複合FKで人物削除を拒否する。人物削除APIは参加者の対応を変更しない。削除したい場合は、先に参加者編集で人物を「未設定」として保存し、参照がなくなってから削除する。アカウント本体・参加行・役割は保持する（DEC-060・061）。

保存構成とAPIを初回定義へ実装した。Windows／ブラウザーの管理画面は未実装。除外・再参加は上記の確認済み方針に従い、本人の退会は追加しない方針と、降格・除外は別の管理者が行う確定方針は上記を参照する。コードの責務と依存は[04](architecture-api.md#apiの責務と依存)を参照する。

## 人物IDの採番（API／DB実装済み）

DB自動採番の整数・家計簿内の整数・サーバー生成UUIDを比較し、人物IDはサーバー生成UUIDに決定した（DEC-062）。DB保存前にAPIで発行でき、既存の家計簿IDとC#の`Guid`による受け渡し・検証をそろえられる。単一SQLiteでは整数の自動採番も有効であり、UUIDの方が小さい・高速という理由ではない。

人物IDは表示順・人物名と分離し、同じ家計簿の人物へ複合FKで参照する。主キーは家計簿ID＋人物ID、人物IDはUUIDのN形式のTEXTとする。IDを知っていることは閲覧・更新権限の根拠にしない。UUIDだけで通信再送時の二重作成を防げるとは扱わず、再送管理は下記の確認対象とする。
