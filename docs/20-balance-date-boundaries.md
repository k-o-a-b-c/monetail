# 20 残高推算の日付境界の修正前の再現記録

更新: 2026-10-19 / CAL-005・LEG-025・LEG-029。PR #12時点の再現結果を履歴として保持する。この段階では製品コード・計算結果を変更しなかった。その後、利用者が登録残高を日末の値と確認し、境界を修正した。**現在の仕様と期待値は[21 日末残高](21-end-of-day-balance.md)を参照する。**

## 対象と確認方法

`Calculation.AutoBalance`と`DataAccess.GetAutoBalance`を、製品と同じSQLiteのFK ON/OFFで実行する。テスト用レシート・振替・残高は実際のDataAccessで保存し、端数付き時刻の読込も確認する。明示的な小数秒ゼロのTEXTは、保存表記の比較用にテストDBだけで設定する。

両経路をそれぞれ固定の期待値と比較し、期間読込の対象レシート・振替のIDも確認する。読込前後で全テーブルの値・格納型・更新版・スキーマを比較し、SQLite Updateイベントが0回、FKとuser_versionが不変であることを検証する。現在の構成・件数・CI結果は[tests/README.md](../tests/README.md)を参照する。

## PR #12時点の検索条件

- 起点は対象口座について`date < 対象日の00:00:00`を満たす最新残高。対象日の残高と未来の残高は起点にしない。別口座だけを含む残高も採用しない。
- 起点があれば、その保存日時に23時間59分59秒を足した日時を開始点とする。日付部分だけに切り詰めていない。
- 起点がなければ`DateTime.MinValue`から検索する。対象月以前の取引も反映する。
- 終点は対象日の23:59:59。呼出引数に含まれる時刻は使用しない。
- レシート・振替はTEXT列に対する`BETWEEN`で検索し、開始点・終点を含む。
- 起点も対象取引もなければ`Nothing`。0円の取引があれば0円を返す。負のレシート合計は残高を増やす。評価額は推算に使わない。

## 再現ケース

| ケース | 固定した現行結果 |
| --- | --- |
| 起点なし・別口座／翌日だけの取引 | 対象口座は`Nothing`。0円の対象レシートを追加すると0円。過去の支出7円・当日の収入25円・出金10円・入金5円では13円 |
| 最新残高の口座別選択・同日／未来の残高 | 10/17の推算では10/15の1000円を口座1、10/16の2000円を口座2の起点にする。同日残高は使わない。取引反映後は948円／2007円 |
| 開始点・終点の包含 | 10/15の1000円から、開始点10/15 23:59:59・10/16 00:00:00・終点10/16 23:59:59の取引を含め954円。開始点の直前と終点直後・翌日00:00:00は除外 |
| 小数秒とTEXT表記 | 23:59:59の翌1tick（100ns）・0.5秒後・当日最後のtickを除外。同じ日時に読める`23:59:59.0000000`も終点では除外するが、開始点では含む。テストの合計は928円 |
| 月末・年末・うるう日 | 2026/10/1、2027/1/1、2024/3/1、2025/3/1を対象に、前日の残高1000円から対象日の支出11円・入金7円・出金5円で991円。対象日の後の取引は除外 |
| 時刻付き残高 | 10/15 09:30の1000円を起点にすると、検索開始は10/16 09:29:59。当日早朝の取引を除外し、テストの合計は984円 |

## 当時の判断事項と、その後の決定

以下はPR #12時点の論点。現在は1〜3を日末残高の仕様として決定し、修正後の期待値へ更新した（[21 仕様](21-end-of-day-balance.md)）。その後、推算処理も共通化した。接続の選択と現在の回帰範囲は[21 仕様](21-end-of-day-balance.md)を参照する。

1. 登録残高がその日のどの時点を表すかを決める。日末残高なら、残高日の23:59:59を再集計する現行の包含条件は重複の原因になる。
2. 小数秒を含め対象日全体を集計する条件と、既存TEXT日時の表記差の扱いを決める。翌日00:00:00未満の半開区間だけに変更しても、保存表記の違いは別途考慮が必要。
3. 残高の保存日時に時刻が含まれる場合、日付へ正規化して扱うかを決める。
4. 仕様と期待値を確定してから境界の修正・重複計算の共通化を進める。

同一日時の複数残高の優先順位は未確定で、現在のSQLはseqによる順序を指定していない。今回のケースは異なる日時を使用する。タイムゾーン・夏時間、日付だけ／T区切り等の別のTEXT形式、実DBの整合性、利用者環境の画面E2Eは検証範囲に含めない。
