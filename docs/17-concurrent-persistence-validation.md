# 17 採番・更新競合の検証

更新: 2026-10-19 / LEG-003・LEG-016。[PR #9](https://github.com/k-o-a-b-c/monetail-legacy/pull/9)で製品コードを変更せず、実際の`DataAccess`の現在の動作を検証した。[CI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39182519779)で追加3チェックを含む全53件と既存Windowsビルドが成功。

## 対象と方法

同じ一時SQLiteファイルへ独立した2接続を開き、レシート・振替・残高をFK ON/OFFで検証する。接続やSQLのモックは使わない。

| 検証 | 確認する内容 |
| --- | --- |
| 登録の競合 | 最初の書込を完了前に止め、別接続のトランザクション開始を観測してから進める。採番の重複、親子の部分保存、対象外データの変更がないか確認する |
| 書込ロックと再試行 | 別接続で書込ロックを保持し、登録・更新がタイムアウトしたときの例外とDBの全行不変を確認する。ロック解放後、同じDataAccessで再試行する |
| 古い編集内容の更新 | 2接続で同じ伝票を読み、先の編集を保存してから古い内容を保存する。後の保存が先の内容を上書きするか、親子が混在するか、周囲のデータが保持されるかを確認する |

スレッドの進行はUpdate／Traceイベントで同期し、待機には上限を設ける。テスト用接続のタイムアウトは並行登録20秒・ロック失敗1秒。製品の接続設定・採番・保存・画面操作・DB定義は維持した。

実行時は.NET Framework 4.8、SQLite 3.32.1、`System.Data.SQLite.Core`パッケージ1.0.113.1（アセンブリ1.0.113.0）、`journal_mode=delete`。成功時は対象伝票の全業務列・子行と、対象外の監査列を含む全保存行を比較する。ロック失敗時は全表の全列とスキーマを比較する。成功した対象行の更新者・更新日時は比較対象外。列宣言による数値変換を避け、全表比較にはSQLiteの`typeof`／`quote`、小数率の業務値比較には`CAST(... AS REAL)`を使う。

## 結果と判断

| 結果 | 判断 |
| --- | --- |
| 登録6組合せすべてで`BEGIN IMMEDIATE`を観測。先行INSERTを保持した間は別接続が採番できず、解放後にseq=2／3で親子を完全保存 | 対象構成で採番重複は再現しなかった。現行のトランザクションが書込を直列化するため、採番方式は変更しない |
| 登録／更新のロック失敗12組合せすべてで`Busy`。保存内容・スキーマは不変で、ロック解放後に同じ接続・モデルで保存成功 | この経路で部分保存は再現しなかった。製品の待機時間・エラー表示・再試行操作は変更しない |
| 古い編集6組合せすべてで、後の保存が先のヘッダー・子データの業務値を上書き。対象外の全保存行は不変 | LEG-016を再現。上書き防止は未実装で、テスト成功を対策済みとは扱わない |

例えば、Aが金額や明細を更新した後、先に開いていたBがメモだけ変えて保存すると、Aの変更が古い内容へ戻る。保存1回のトランザクションは、画面を開いてから保存するまでの競合を検出しない。次の候補は、読込時の版を保存時に照合し、古い編集なら全体を保存しない方式。DB列・確認や再読込の案内は別途設計する。

対象はWindows CIのローカル一時ファイルと製品のSQLiteプロバイダーである。WAL、複数端末の共有フォルダー、同期ストレージ、実運用DBや複数プロセスの画面操作は検証対象に含めない。更新競合の対策は、結果を基に別の変更として提案する。
