# 52 共通アカウントと機能別の境界

**共通アカウントを使い、各機能のデータと利用権限を分ける方針を採用する（DEC-036）。** 家計簿以外の日用品在庫管理などを追加する場合も、まず同じAPI内で機能を分ける。認証サービスの別配備や別プロジェクト化は現段階では行わない。

## 責務

| 領域 | 扱うもの |
| --- | --- |
| 共通の認証 | 認証アカウント、パスキー、セッションとその失効。「誰がログインしたか」を扱う |
| Monetail | 家計簿の人物、レシート、振替、計算など。人物と共通アカウントの対応・人物とアカウントを組み合わせる管理もここに属する |
| 将来の別機能 | 在庫など、その機能のデータと利用権限。Monetailの人物マスタを利用者マスタとして流用する前提を置かない |

ログインの成功と、各機能・各家計簿の利用許可を区別する。現在のアカウント管理用`Admin`ロールから、将来の在庫管理権限や家計簿管理権限を自動的に与える仕様は設けない。各機能の参加・権限の保存方法は、その実装時に決める。

## 今回の整理

```text
src/Monetail.Api/
├─ Authentication/                  認証と既存の認証DB構成
├─ Features/
│  └─ Monetail/
│     └─ Accounts/                 人物とアカウントを組み合わせる管理
│        ├─ AdminAccountEndpoints.cs
│        └─ AdminAccountService.cs
└─ Program.cs                      認証と各機能の登録・起動
```

管理者一覧APIの2ファイルを`Features/Monetail/Accounts`へ移し、名前空間を`Monetail.Api.Features.Monetail.Accounts`に合わせる。サービスとURLの登録は`Program.cs`で行い、認証基盤の`PasskeyWeb`からMonetailの一覧APIを直接登録しない。[51 API契約](51-admin-account-list.md)のURL・JSON・管理者条件・エラー応答は維持する。

在庫管理を実装する場合は`Features/Inventory`などを設ける方針とし、今回は空の機能やテーブル・権限モデルを追加しない。API・プロジェクト・DBの名称や配置も変更しない。

## 現在残る依存と後続作業

現行の登録・ログイン・セッション検証・再確認等は、Monetailの人物と認証アカウントの対応を必須としている。`AuthDbContext`、`AuthUserLink`、`LegacyPerson`、人物指定の管理コマンドも現行構成を維持する。**今回のフォルダ整理だけで、人物未登録のアカウントによる別機能の利用が可能になったわけではない。**

別機能へ共通アカウントを提供する段階では、人物との対応確認をMonetailへのアクセス時に行う構成へ整理する。共通アカウントだけの発行・復旧、本人情報API、登録画面の表示名、各機能への参加条件などは、その実装時に確認する。現在の人物確認を単に削除してアクセスを許可する変更は行わない。

家計簿分割・同じアカウントの複数家計簿参加はDEC-035を引き継ぎ、家計簿のDB方式・人物やマスタの共有範囲は保留する。今回、EF移行・DB変更・新しい依存パッケージは不要で、Windows版・業務値・保存済み`receipt.total`・本番設定・実データを変更しない。

将来、別機能を別アプリ・別配備へ分離する際は、OpenID Connect等の標準方式による共通ログインを検討する。現時点で独自の認証プロトコルやCookie共有を追加するものではない。
