# レシートの子再読込に失敗したときのモデル保持

更新: 2026-10-21。編集画面の開始時に使う`DataAccess.LoadReceiptChildData`を対象とする（LEG-040）。

## 問題と変更

従来の内部処理は、渡されたReceiptのGroupsを空にしてから、読み終わったグループを順次追加していた。2つ目のグループの数値変換や対象者参照で例外になると、元のGroupsが1グループだけの途中状態になる。DBが変更されなくても、画面間で共有する元オブジェクトに影響する。

公開メソッドでは、Seqだけを指定した一時Receiptを子の読込先とする。全グループ・明細・対象者を読み終えた後に、元のGroupsをClear／AddRangeで更新する。元レシート全体のコピーやヘッダーの再読込は行わない。

- 失敗時は例外を従来どおり呼出元へ返し、元の子の値と各コレクション／要素の参照、ヘッダー・税設定・更新版・ポイントを保持する。
- 成功時は従来どおりDB上の子へ更新し、Groupsコレクションの参照を維持する。子のないSeqなら、成功後に元の子を空へ更新する。
- 子のSQL・順序・読込型・マスタ参照・NULLの扱いは変更しない。保存処理、DB構造、画面操作と例外の表示方法も維持する。

一時Receiptは子を組み立てるための領域で、元オブジェクトのヘッダーや子をコピーしない。[35](35-batch-receipt-reads.md)・[36](36-batch-payment-receipt-reads.md)の一覧／支払方法別の一括読込には変更を加えない。

## 検証

実SQLiteで、2番目のグループにINTEGER宣言の数量へREALの1.5を保存し、製品のGetInt32で途中失敗させる。FK ON/OFFで確認する。FK OFFでは、マスタにない対象者への割当でも途中失敗させる。従来の内部処理を直接呼ぶと2グループが1つになることを再現し、保護した公開メソッドでは全値と各参照が残ることを比較する。

連続失敗、数値／割当の修正後に同じDataAccessで再読込できること、以前保持した子が変化しないことを確認する。正常時の繰返し読込・空の読込、呼出元にある未保存のヘッダー・税設定・更新版・ポイントとGroups参照の保持も検証する。各読込は全保存値・SQLite型・版・スキーマ・PRAGMAの前後一致と書込0回を確認する。

障害はテスト用DBへ意図的に作るもので、利用者の実DBの不整合を確認した結果ではない。読込に失敗した画面の例外処理や再試行UIの追加は今回の対象に含めない。
