## 人物管理API・DB（実装済み）

人物情報の一括保存と更新後一覧の同一応答、参加者編集での対応保存、API側で生成するUUIDの人物IDは利用者確認済み（DEC-056・061・062）。下表の9操作のAPIパスとDB変更の構成は確認済み（DEC-089）。要求・応答と競合・再送のAPI契約は以下の実装内容に従い、参加者・招待の未実装画面と区別する。人物・参加者・招待の保存処理とAPI、未リリースAPIの初回定義へ実装した。Windowsの人物一覧と追加・編集・削除を接続済み。共通順の設定も接続済み。業務取引のモデル・実DBの移行は後続とする。

**APIのパス・通信単位（実装済み）**

以下のパスはすべて`/ledgers/{ledgerId}`からの相対パス。各要求で有効なログインと現在の参加を確認し、書込時は最新の役割・本人の対応もトランザクション内で検証する。

| メソッド・パス | 用途・権限 | 取得・保存の単位 |
| --- | --- | --- |
| `GET /people` | 全参加者が人物一覧を取得 | 全員を共通順で返し、ログイン中の本人の人物ID・現在の役割・並び順の更新版も返す。通常画面だけが表示時に本人を先頭へ移す |
| `POST /people` | 管理者が人物を追加 | 作成操作のrequestId・名前・有効開始日・有効終了日を送り、名前・期間をまとめて登録。新規人物は共通順の末尾へ追加する（DEC-085）。作成要求の再送は下記の共通記録表で識別する |
| `PATCH /people/{personId}` | 管理者、または自分の名前を変更する本人が保存 | 名前・有効期間を1要求・1トランザクションで保存し、更新後一覧を同じ応答で返す。アカウントとの対応は受け付けない。本人だけの権限では名前以外の変更を認めない。部分更新の省略・nullは下記のとおり |
| `DELETE /people/{personId}` | 管理者が削除 | 人物の更新版を照合して削除。参照があれば削除せず理由を返す |
| `PUT /people/order` | 管理者が共通順を保存 | 全人物のIDを設定順で並べた配列と並び順の更新版を送る。全体を同じトランザクションで保存し、［上へ］［下へ］の操作ごとの通信は行わない |
| `GET /members` | 管理者が参加者一覧を取得 | アカウントID・表示名・役割・対応人物・参加日時・参加者の更新版と、本人や人物順の表示に必要な情報をまとめて返す。IDは操作対象の特定用で、同名識別の画面表示には使わない |
| `GET /members/{accountId}/edit` | 管理者が参加者の対応を編集する情報を取得 | 現在の参加者情報と同じ家計簿の人物候補を1応答で返す（DEC-088）。他の参加者に対応済みの人物は選択できない状態で示す |
| `PATCH /members/{accountId}` | 管理者が参加者の役割と人物の対応を保存 | 役割と人物対応を1要求・同じトランザクションで保存することは確認済み。人物IDと参加者の更新版をJSON本文で送る。NULLなら対応解除、別の人物IDなら付け替え |
| `DELETE /members/{accountId}` | 管理者が別の参加者を除外 | 対象の参加者の更新版を照合して参加者行と人物対応だけを削除し、更新後参加者一覧を返す。自分自身は対象不可。更新版はJSON本文のrevisionで送る |

APIの具体的な項目名・型と更新版を送る場所は下記の形式で実装した。人物の新規作成では要求ID、更新・削除では対象の更新版、共通順保存では全人物のID配列と並び順全体の更新版を送る。作成・更新・削除・共通順保存の成功時は更新後一覧を含める。参加者の除外・役割変更は自分以外が対象だが、自分の人物対応だけの変更を禁止するものではない。

一覧の人物データは`personId`・`name`・`validFrom`・`validTo`・共通順・人物の`revision`を返す。人物とアカウントの全対応を全参加者に公開する必要はなく、通常表示で必要な本人の人物IDだけをログインアカウントから求める。

人物の作成・更新・削除・共通順保存では、更新後の人物一覧を同じ成功応答に含めることを確認済み（DEC-080）。参加者の更新・除外でも、操作者が管理者のままなら更新後の参加者一覧を同じ成功応答に含める。人物一覧に本人の人物ID・現在の役割・並び順の更新版も含める。一覧の再取得を別のHTTP要求にせず、画面は同じ形式の応答から一覧へ戻れる。更新後一覧の取得もサーバーの同じトランザクション内で行い、確定してから応答する。

人物編集では一覧応答の名前・期間・更新版から入力を始め、編集画面を開くためだけのGETを追加しない（DEC-088）。認証失効後の編集再開では、上記のとおり現在の参加・役割・本人対応を確認するために一覧を取得し、未保存入力と元の更新版を復元する。保存時に最新の参加・権限と更新版を検証する。参加者編集は現在の参加者情報と人物候補を1応答で取得する。この取得でも現在の管理者権限を検証する。

人物保存のPATCHでは項目の省略を「変更しない」、日付の明示的な`null`を「期間制限なし」と区別する。人物の更新版は必須とし、名前だけの更新で日付を意図せず解除しない。参加者保存のPATCHでは人物IDの明示的な`null`を「対応解除」とする。管理者以外の本人は人物の名前だけを送る。

**要求・応答の項目（実装済み）**

上記の9操作で、更新版はDELETEも含めJSON本文の`revision`へ統一し、省略・nullを区別し、エラー応答に種類と表示文を持たせる基本方針は確認済み（DEC-093）。以下の具体的なDTO項目は、既定の権限・通信単位・再送・競合の画面動作に従って整理する。

| 操作 | JSON本文の項目案 |
| --- | --- |
| 人物作成 | `requestId`、`name`、`validFrom`、`validTo`。要求IDと名前は必須。作成時の日付の省略またはnullは、その側の期間制限なし |
| 人物更新 | 必須の`revision`、変更する`name`・`validFrom`・`validTo`。管理者以外の本人は名前だけを送る |
| 人物削除 | 必須の`revision` |
| 共通順保存 | 必須の`revision`（順序全体の版）と`personIds`（現在の全人物IDを設定順で1回ずつ） |
| 参加者更新 | 必須の`revision`、変更する`role`・`personId` |
| 参加者除外 | 必須の`revision` |

更新で省略した項目は変更せず、日付のnullは期間制限の解除、人物IDのnullは対応解除とする（DEC-093）。人物名・役割にnullは認めない。画面の通常保存では編集可能な項目をまとめて送り、役割と人物対応は一括で確定する。省略の扱いを、項目ごとに別々の保存要求を送る意味にはしない。

人物一覧と人物の変更成功応答は、`people`配列・`myPersonId`・`currentRole`・`orderRevision`の共通形式を使う。各人物は`personId`・`name`・`validFrom`・`validTo`・`displayOrder`・`revision`を持つ。API内部とクライアントの操作対象の特定にはIDを使い、利用者への識別用表示には使わない。

参加者一覧と参加者の変更成功応答は`members`配列・`currentAccountId`・`currentRole`を返す。各参加者は`accountId`・`displayName`・`role`・`personId`・`personName`・`personDisplayOrder`・`joinedAtUtc`・`revision`を持つ。本人先頭や人物順・参加順を表示するための情報を同じ応答で返す。参加者編集の取得は`member`と`personCandidates`を返し、人物候補には`personId`・`name`・`isSelectable`を含める。他の参加者に設定済みの人物も選択不可で表示する既定方針に従う。

失敗応答は`code`（機械判定用）と`message`（表示用）を基本とし、必要に応じて該当欄や最新情報を含める方針は確認済み（DEC-093）。項目名は、入力欄を`field`、現在の権限で返せる競合の最新情報を`latest`とする。入力不備400・認証401・権限403・対象不在/未参加404・更新版や一意性等の競合409・既存の回数超過429・保存障害503とする。409の中でも更新版不一致と制約違反を`code`で区別し、既定の画面動作へ分岐する。共通の認証・CSRF・HTTP境界での拒否は既存の応答形式を維持し、各業務処理のエラーと区別する。既存の認証・家計簿APIの応答形式は一括変更していない。

**DBの構成（初回定義へ実装済み）**

アカウントとの対応は参加者表に人物IDを持つ構成で利用者確認済み（DEC-059）。人物0人・人物未対応の参加者・アカウントに対応しない人物を認め、人物への対応から認証アカウントを自動作成しない。人物IDのUUID採用・日付の保存形式・更新版の保存単位も確認済み。以下は現在の実装内容。未実装の業務表や画面の設計とは区別する。

- `ledger_people`に人物名・有効開始日・有効終了日・共通順・人物の更新版を保存する。期間は時刻やタイムゾーンを持たない日付とし、SQLiteでは`YYYY-MM-DD`形式のTEXT、制限なしはNULLで保存する方針を確認済み（DEC-086）。APIでも同形式の文字列またはnullを使い、C#では`DateOnly?`で扱う。正しい日付を固定桁で保存し、両日がある場合の開始日≦終了日を検証する。DBのCHECKでも前後関係を検証する。
- 同一家計簿の人物名にUNIQUE制約を設け、同時登録でも同名を防ぐ。比較は前後空白除去後の完全一致とし、SQLiteのBINARY比較にそろえる。共通順は各人物行に保存し、並べた人物ID配列からサーバーが順序値を設定する（DEC-087）。
- 既存の`ledgers`行に、人物の並び順全体で共有する更新版`people_order_revision`を1つ追加する（DEC-087）。人物0人でも取得でき、名前・権限等の変更と並べ替えの競合を分けられる。人物の追加・削除・順序変更時に更新し、共通順を保存する要求で照合する。
- 人物の更新版は名前・有効期間が変わったときに更新する（DEC-087）。人物との対応は参加者の更新版で検証する。共通順だけの変更では人物の更新版を変更せず、人物情報・参加者情報・並べ替えの競合を区別する。
- 更新版の値は、現行の家計簿・参加者の実装と同様、APIが生成するUUID文字列へそろえる（DEC-087）。各対象に現在の値を1つ保持し、取得時に返した値を保存要求で照合して、新しい版への置換と業務変更を原子的に行う。値の大小で新旧を判定せず一致だけを見る。人物1人・参加者1人・家計簿ごとの人物順全体の3単位に分ける方針は確認済み。並び順の各人物行の更新と全体の更新版の置換は同じトランザクションで行う。

**アカウント対応の保存構成（API／DB実装済み）**

`ledger_members`にNULL許容の`person_id`を設け、対応なしをNULLで表現する。`ledger_people`はアカウントIDを持たず、人物の名前・有効期間・表示順等を管理する。人物の登録とアカウントの参加は独立させ、対応専用表`ledger_member_people`は作らない。

- 参加者の主キー`(ledger_id, auth_user_id)`と人物IDの単一列で、1アカウントが同一家計簿で対応できる人物を最大1人とする。`(ledger_id, person_id)`へUNIQUE制約を置き、1人物へ複数アカウントが対応することも防ぐ。SQLiteではNULLを複数行に持てるため、人物未対応の参加者を複数登録できる。
- `(ledger_id, person_id)`から`ledger_people`の同じ組へRESTRICTの複合FKを設け、他家計簿の人物へ対応できないようにする。本人の人物IDは現在の参加者行から求める。参加者編集の人物候補は同じ家計簿の人物から取得する。
- 名前・期間は人物編集で人物行にまとめて保存し、対応は参加者編集で参加者行へ保存する。それぞれの画面の保存を1要求で完了し、操作の途中で失敗した場合はその保存全体を戻す。
- 対応変更は参加者の更新版で検証・更新する（DEC-087）。人物保存時の本人判定は、人物の更新版だけを根拠にせず、現在の参加者行と役割を要求ごとに確認する。参加者の役割変更等との競合の扱いはAPI設計で具体化する。
- 参加者の`person_id`が人物を参照している間は、RESTRICTの複合FKで人物削除を拒否する。人物削除APIは参加者の対応を変更しない。削除したい場合は、先に参加者編集で人物を「未設定」として保存し、参照がなくなってから削除する。アカウント本体・参加行・役割は保持する（DEC-060・061）。

保存構成とAPIを初回定義へ実装した。Windows／ブラウザーの管理画面は未実装。除外・再参加は上記の確認済み方針に従い、本人の退会は追加しない方針と、降格・除外は別の管理者が行う確定方針は上記を参照する。コードの責務と依存は[04](04-architecture.md#apiの責務と依存)を参照する。

**人物IDの採番（API／DB実装済み）**

DB自動採番の整数・家計簿内の整数・サーバー生成UUIDを比較し、人物IDはサーバー生成UUIDに決定した（DEC-062）。DB保存前にAPIで発行でき、既存の家計簿IDとC#の`Guid`による受け渡し・検証をそろえられる。単一SQLiteでは整数の自動採番も有効であり、UUIDの方が小さい・高速という理由ではない。

人物IDは表示順・人物名と分離し、同じ家計簿の人物へ複合FKで参照する。主キーは家計簿ID＋人物ID、人物IDはUUIDのN形式のTEXTとする。IDを知っていることは閲覧・更新権限の根拠にしない。UUIDだけで通信再送時の二重作成を防げるとは扱わず、再送管理は下記の確認対象とする。

**同時編集・失敗・再送（一部確認済み・未実装）**

- 古い更新版のまま上書き保存せず、競合応答の最新情報を画面内で確認して明示的に切り替える方式は確認済み（DEC-065）。更新・削除に人物の`revision`を必須とし、古い版なら409と最新情報を返す。共通順の保存も専用の更新版を必須とし、他の管理者の並べ替えや人物の追加・削除後に古い配列を上書きしない。
- 共通順のID配列には現在の全人物を1回ずつ含める。他家計簿のID・重複・欠落を受け付けない。同時変更は409、形式不備は400にする。
- 権限不足403、当該家計簿の不在・未参加や当該家計簿に存在しない人物404、入力不備400、同名・対応済みアカウント・既存記録を期間外にする変更・参照のある人物の削除409、保存障害503に理由を付ける。未認証・失効等の認証結果は既存契約に従う。DBの障害をすべて「参照あり」へ置き換えない。
- 人物編集では名前・期間のどこかが失敗した場合はその保存全体を戻す。参加者編集での対応の付け替えも、失敗時は元の対応を維持する。別の画面で既に保存した変更まで巻き戻す契約にはしない。期限の検証は今後実装する業務データの登録・更新側でも同じ書込トランザクション内で行う。未実装のレシート・振替・残高まで今回検証済みとは扱わない。
- 通信失敗時の再送では、作成の重複や、応答だけ失われた更新の再適用を防ぐ必要がある。更新等は古い版を受け付けず、再取得して結果を確認する案。作成は下記の共通要求記録表・基本6列・照合方法・自動削除しない保持方針を確認済み。人物が削除済みなら再作成せず、created_result_deletedで削除済みと応答する。

**作成結果が不明な場合の再送管理（API実装済み）**

入力不備等で保存前に拒否された場合と、タイムアウト等で保存結果が分からない場合を区別する。人物のUUIDはAPI側で発行する確定方針を維持し、作成操作ごとに要求IDで再送を識別する。機能ごとに再送管理表を増やさず、まず家計簿作成と人物作成で共通の要求記録表を使うことを確認済み（DEC-066）。

一覧で利用者が結果を確認する方式・人物行に要求IDを持つ方式・機能別の記録表と比較し、同じ仕組みを共有して表の増加を抑える構成を選んだ。基本6列と各列の役割、成功時だけ業務データと同時に確定する構成も実装済み（DEC-067）。既存の家計簿作成の再送契約を共通形式でも維持する。

同名禁止の制約は同じ名前の同時登録を防げるが、同じ作成操作かどうかを識別するものではない。元の作成が処理中なら、一覧に見えない時点でも保存失敗とは断定できない。再送管理を採用する場合も、要求IDだけで権限を与えず、対象家計簿の現在の参加・役割を確認する。

**共通の再送管理表（API／DB実装済み）**

共通の要求記録表`operation_requests`を使い、以下の6列を基本の保存項目とする方針は確認済み。SQLiteの具体的なDDLやシリアライズ等はこの方針に従って実装する。

| 列名 | 型 | 用途 |
| --- | --- | --- |
| `request_id` | TEXT（UUID・主キー） | クライアントが作成操作ごとに発行し、同じ操作の再送では同じ値を送る。人物そのもののUUIDとは別 |
| `operation_type` | TEXT | `ledger.create`・`person.create`等で処理の種類を区別する |
| `actor_auth_user_id` | TEXT | サーバーが検証済みログイン情報から設定し、誰の要求かを照合する |
| `request_hash` | TEXT | 正規化した要求内容から作るSHA-256の照合値。処理の対象範囲と、前後空白除去後の名前・期間等を含め、同じ要求IDで別内容が送られたことを識別する |
| `result_id` | TEXT | 作成済みの家計簿・人物のIDを保持し、各機能が現在の権限で結果を取得する |
| `created_at_utc` | TEXT（UTC日時） | 要求のUTC記録日時。自動削除の期限には使わない |

要求IDを主キーにして同じIDの別行を作らず、既存行の処理種類・操作者・要求内容も照合する。対象家計簿等の範囲は各機能が渡す正規化済み要求に含め、同じ内容を別家計簿へ送る要求を取り違えない。人物名や日付等を機能別の列として増やす代わりに照合値を使い、結果のHTTP本文全体を記録する前提にはしない。

成功した作成だけを業務データと同じトランザクションで記録し、独立した「処理中」「失敗」等の状態列は設けない。途中で失敗すれば業務データと要求記録の両方を戻す。同時再送はトランザクションと要求IDの主キーで整合させる。

家計簿専用だった`ledger_creation_requests`を共通形式へ置き換え、同じ要求の再送、異なる操作者・内容、失効・参加喪失時の既存契約を維持した。

要求の照合・記録は共通処理とし、人物や家計簿の作成・最新の参加や権限の確認・再送時に返せる結果の判断は各機能が担当する。業務データの保存と共通の要求記録を同じトランザクションで確定する構成とする。まずは作成操作を対象とし、更新・削除を含む全APIの履歴を一律に記録する前提にはしない。

作成結果のIDは処理履歴として保持し、対象の削除を止めるFKは設けない。人物削除後の古い要求を再作成と扱わないようにしつつ、参加者や支払方法等からの参照による削除制限は維持する。記録は作成操作ごとに増えるが、自動削除せず保持する（DEC-074）。既存の認証アカウント作成用`auth_account_creation_requests`まで統合するかは、その契約と認証側の責務を確認してから決める。共通化によって認証から家計簿への依存を作らない。

**再送記録の保持条件（API／DB実装済み）**

保持期限を定め、その期間内の再送だけを保証する方式がある。例えば[Stripe API v1](https://docs.stripe.com/api/idempotent_requests)は24時間以上経過したキーを削除可能とし、削除後に同じキーを使うと新しい要求として処理すると説明している。この期間を本アプリへ流用する決定ではない。

本アプリでは共通の再送記録を自動削除せず保持することを確認済み（DEC-074）。現在の対象は家計簿・人物の作成だけで、応答全体を保存せず6列の記録を残すため、期限切れ後の再送や定期削除の仕組みを追加せずに済む。人物が削除・改名された後も元の作成要求を識別できる。記録は増え続けるので、対象を大量の取引作成へ広げる場合等には再評価する。保持を有限にする場合は、保証期間を先に合意し、期限後の古い要求を新規作成に扱うか拒否できる仕組みを設けるかも合わせて決める。

**管理画面・後続業務で確認する残りの項目**

1. 人物・参加者のAPIは上記の要求・応答形式で実装済み。Windowsの各管理画面と、アカウント管理・パスキー管理の具体的な画面への入口・配置は後続で実装・確認する。
2. 共通の再送管理：共通化・基本6列・要求IDの主キー・内容照合・対象への削除制限FKなし・自動削除せず保持は確認済みなので再確認しない。人物削除後の古い再送では再作成せず「作成した人物は削除されています」と画面内に表示する方針も確認済み。応答項目は上記の実装形式を使う。既存の認証アカウント作成用表の統合はこの採用に含めず、了承前に範囲を追加しない。
3. 参加者一覧は家計簿管理者のみ、招待の入口はその一覧だけ、役割・人物対応は一括保存と確認済み。除外時は参加者行と対応だけを削除し、再参加は招待で閲覧者・人物未設定とすることも確認済み。同名アカウントを見分けるための内部IDは画面に表示しないと確認済み。権限喪失時は保存せず画面内に説明し、再取得・自動遷移をしないことも確認済み。その他の画面詳細は未確定。

**一覧の並び方（API実装／表示画面は未実装）**

- 新規人物は共通順の末尾へ追加する（DEC-085）。
- 参加者一覧は、利用者が提示した「本人を先頭、次に人物対応ありを人物の共通順、最後に人物未設定を参加順」でAPIから返す。参加者専用の並べ替え保存機能は追加していない。

**権限喪失・削除済み結果への再送（利用者確認済み・未実装）**

- 別の管理者による降格・除外等で必要な権限を失っていれば、登録・更新を拒否し、入力を残したまま画面内へ理由を表示する（DEC-081）。エラー後の再取得や自動遷移は行わない。
- 権限拒否等の403・404の応答に、操作者自身の現在の権限を`permissions`として含める（DEC-106）。`currentRole`と`myPersonId`を返し、未参加・存在しない家計簿では両方nullとする。参加中で人物だけが不在なら現在の役割を返す。画面は同じ失敗応答から閉じた後の操作可否を更新し、その確認のためのGETを追加しない。他の参加者や閲覧権限のない最新情報は返さない。共通認証・CSRF・回数制限等で受付前に拒否した応答は従来の形式を維持する。
- 画面を閉じた後、現在の権限では許可されない画面へ再入場させない。降格では管理画面等、除外では対象の家計簿へのアクセスを制限する。降格後も許可されている閲覧等まで一律に禁止しない。画面制御だけでなく各APIでも現在の参加・権限を検証する。
- 同じ人物を同時編集した更新版の競合はDEC-065の最新情報表示を維持する。権限喪失の応答には閲覧できない最新情報を含めず、追加取得もしない。
- 作成済み人物が削除された後の再送は再作成せず、「作成した人物は削除されています」と画面内に示す（DEC-081）。具体的なHTTP項目はAPI案で整理する。

人物・参加者を含む認証済み業務APIは、作成・更新・削除・順序保存等の書込を共有20回／分、参照・家計簿を開く操作を共有120回／分へ分ける方針を確認済み（DEC-069）。この2枠を原則とし、別枠が必要な操作を追加する場合は、理由と対象を示して確認する。
