更新: 2026-10-19 / 今後の再実装で誤解しやすい用語を、**現行ソースの意味**と**今後決めること**に分離。PR #1〜#3はmainへ反映済み。

## 1. 用語集（現行の意味）

| 用語 | 現行コード／DBでの意味 | 注意 |
| --- | --- | --- |
| レシート（`Receipt`） | 店・日時・支払方法と、費目グループ・購入明細・対象者を束ねる記録 | IDは`t_receipts.seq`。税込／税抜・税端数方式はレシート単位で保存 |
| レシートグループ（`ReceiptGroup`） | レシート内の費目分類と税率を持つ単位 | 明細の税率はグループから継承。`tax`は税率**コード** |
| 明細（`ReceiptDetail`） | 購入品目、単価・数量・値引・課税対象・備考 | 1明細に複数人を指定可能 |
| 人／利用者（`m_user`） | 家族など、支払方法の所有者・明細の対象者として扱う人 | `account_name`をWindowsログイン名に照合する。現在のログイン認証主体ではない |
| 対象者（`t_receipt_detail_users`） | 特定商品に関連する人。人数で按分して集計できる | **誰が支払ったか**とは別概念。対象者未設定の明細もDB表現可能 |
| 支払方法・口座（`m_payment_classification`） | レシート支払元、振替の移動元・先、残高記録の単位 | 有効期間列`valid_from/valid_to`はDBにあるが機能利用は未確認 |
| 分類（`m_group_classification`） | 費目分類。課税対象の初期値・軽減税率対象の初期値を持つ | グループ単位で分類と税率を指定 |
| 店／店舗（`m_shop`） | 店名と分類・ポイント等の初期候補を保持するマスタ | レシートと店舗は**コードFKではなく名前文字列で関連付け** |
| 税端数方式（`TaxRoundingMode`） | 各レシートの税率別合計へ適用する`floor`／`half_up` | 新規の初期選択は同じ店名・現在の利用者の直近レシートから取得。店舗マスタの端数列は使用しない |
| 合計プレビュー（`Receipt.GetTotal`） | 画面の未確定の税込／税抜・端数方式を引数で渡して合計を計算する | Receiptの両設定は変えず、すべての登録確認後に転記する。ディープコピーは採用していない |
| 消費税率（`m_tax_rate`） | `code`と`rate`を保持するマスタ | レシートグループは`code`を保存。物理FKはない |
| ポイント（`ReceiptPoint`／`t_receipt_points`） | ポイント種別・付与率・固定ポイント・合計ポイント | 物理表・クラス・一部UIは存在するが、DataAccessでの登録／再読込は未実装。採用範囲は未決定 |
| 振替（`Transfer`） | 口座間での金額移動 | 残高推算で出金側を減額、入金側を増額 |
| 残高（`Balance`／`BalanceGroup`） | 指定した日の日末における、支払方法ごとの残高 | 推算は残高日の翌日から対象日末まで。登録残高と任意の評価額を区別（[21 仕様](21-end-of-day-balance.md)） |
| 予測残高（`AutoBalance`） | 直近登録残高からレシートと振替を足し引きした推算 | 明細対象者による按分を残高に直接適用しない |
| 収入（`Incomes`） | 負のレシート明細を集計した額 | UIでは負号の表示などを確認 |
| 支出（`Expenses`） | 正のレシート明細を税率別に集計した額 | `Total`・`Incomes`と共通の端数処理。正負を分けるため`Total = Incomes + Expenses`とは限らない |
| 評価額（`valuation_amount`） | 口座の残高とは別に任意で記録する評価値 | 残高画面の評価額モードで利用 |
| オーケークラブ割引 | オーケーでは本体価格×3/103を商品1個ごとに切捨。Monetailでは**既存の`discount_fee`へ手入力**を継続 | 自動計算・専用入力欄は作らない。`discount_fee`は**単価あたり**なので数量に注意 |

## 2. 採用済みの仕様（2026-10-18時点）

- 消費税は**税率ごとに合算**し、**切り捨て／四捨五入を各レシートで指定・保存**。同じ店舗・現在の利用者の直近レシートを新規入力の初期選択に使い、店舗マスタの設定は使わない（DEC-001／DEC-005）。マスタを初期値にする旧案は置き換え済み。
- 入力画面では内税／外税と端数方式を独立したラジオボタンで選択し、登録確認までは画面だけで保持する。既存Receiptの両設定を編集時に書き換えたり、取消時に戻したりしない。流用は確認後の即時保存を維持し、追加操作はない。
- 個人配分は**目安**。新しい`half_up`の個人配分の最終端数は**四捨五入**し、既存`floor`の参考額は互換性を維持する。配分値の合計をレシート金額に強制一致させない（DEC-004）。
- 既存`floor`は負額・浮動小数点境界を含め旧`Double`式を保持する。新しい`half_up`の税額は`Decimal`・`MidpointRounding.AwayFromZero`を採用し、負の税額−0.5円は−1円とする。
- 既存DBの外部キー整合性は**保たれている前提**で作業を進める（実検査済みとの意味ではない）。
- レシート更新は対象者割当→明細→グループを削除して子を再登録し、削除操作では子削除後にレシート親を削除するよう修正済み。FK ON/OFFの自動テストで成功・失敗時のDB巻き戻しを検証したが、製品接続のFK設定は変更していない。
- 残高削除も`t_balance_groups`→`t_balances`の順とし、既存トランザクションを維持する。FK ON/OFFで削除成功（子0／2件）・親削除失敗時の復元と同じDataAccessでの再削除（子2件）、他の残高と無関係な全テーブルの保持を検証済み。DDL・製品のFK設定・画面操作は維持する（LEG-027）。
- レシートの所在地・タグ、グループと明細のタグはNULLを空文字として読み込む。DB内のNULLを読込・画面取消で更新しない（LEG-024、4列・6読込箇所）。
- 残高・支払方法別残高・振替の`tag`3列・6読込箇所もNULLだけを空文字として読み込む（LEG-028）。非NULL文字列・日時・金額・評価額・支払方法・保存済みNULLと既存の保存SQL・計算・画面操作を維持する。DB移行や全テーブルのNULL対応は行わない。
- 小数の割引率はモデルと同じ`Double`で読み込む。旧`GetInt32`によるREAL値の読込例外を修正し、INTEGER宣言・保存・値引計算・画面操作は維持する（LEG-005）。
- 支払メモの入力リスト全体を1つのトランザクションで保存する。全件成功時だけ確定し、失敗時は先行する追加・更新も戻して例外を再送出する。空リストでは保存せず、画面の確認操作と日付・タグの扱いは維持する（LEG-012）。
- オーケーは**今までどおり既存の明細「割引額」へ手入力**することに確定。**専用入力欄・3/103自動計算・DB拡張は不要**と判断。前回の別欄案は不採用。

詳細: [14 決定事項](14-decisions-2026-10-16.md)。

## 4. 仕様変更の原則（提案）

1. **事実**（実DDL／ソースの現在動作）と**要件**（次にしたいこと）を別ファイル・別表で管理する。
2. DBの変更は、**既存実データのバックアップ → 移行SQLのテスト → 旧アプリとの互換性試験 → 適用**の順とする。
3. 計算方式を変更するときは、旧方式・新方式の両方を表現可能にする。過去の合計が説明なく変わる状態を避ける。
4. 決定済みの条件には担当者・日付・判断理由・関連テストを記録する。未決定は「未決定」と明記する。
5. ポイントや有効期間等の**存在するDB列＝業務実装済み**とはみなさない。
6. 自動テスト・Windowsビルドの成功と、実ユーザーDBへの移行・手動画面確認を区別する。現在の構成・件数・最新CI結果は[tests/README.md](../tests/README.md)に集約する。実ユーザーDBへの適用は未確認。
