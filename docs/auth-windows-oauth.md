# Windows版OAuth・DPAPIと認証復元

[← 43 認証設計の入口](43-passkey-authentication-design.md)

## Windows版のOAuth認証（DEC-051）

OpenIddict 7.7.2のサーバー・検証機能を使い、外部ブラウザーでのパスキー認証後に認可コード＋PKCEでWindows版へAPI利用権限を渡す。新版のClientにはPKCE S256・ランダムstate・実行時ポートのループバック受付・コード交換を実装した。ID tokenやopenidスコープには依存しない。公開条件・証明書の準備は[42](42-api-foundation.md#windows版向けoauthの有効化)、実ブラウザーを含む検証範囲は[tests/README](../tests/README.md)を参照する。

| 経路 | 契約 |
| --- | --- |
| `GET /.well-known/openid-configuration` | 固定HTTPSオリジンに対応する標準メタデータを公開する |
| `GET /connect/authorize` | 登録済みWindowsクライアント・認可コード・PKCE S256を検証。未ログインなら既存のログイン画面を経由し、元の認可要求へ戻す |
| `POST /connect/token` | `application/x-www-form-urlencoded`で認可コード＋verifier、または更新トークンを交換する。Cookie・Origin・CSRFではなく標準のコード／トークン検証を使う |

Windowsの接続確認は上記メタデータの取得1回で行い、事前の`GET /health`は呼ばない。固定HTTPS接続先に対するissuer・認可／トークンエンドポイント・認可コード方式・PKCE S256対応の検証を維持する。接続確認の実施タイミングは変えず、本人情報の取得は別処理のままとする。APIの`/health`自体は運用の稼働確認として残す。

- 公式の公開クライアントIDは`monetail-windows`。利用者の認証IDとは別で、共有のクライアント秘密鍵をWindowsアプリへ埋め込まない。APIスコープは`monetail-api`、更新を利用する場合は`offline_access`も要求する。他のスコープを今回の受付から付与しない。
- 復帰先は`http://127.0.0.1/callback/`のループバック。応答はquery方式とする。標準ライブラリのNativeクライアント検証で実行時のポート変更を認め、それ以外のホスト・パスへの復帰を許可しない。サーバー側の認可・交換・API通信は引き続きHTTPSとする。
- 認可コードは1分・単回。アクセストークンは最大15分で、元のセッションの残り時間が短ければそれを上限にする。更新トークンも元の絶対期限までとし、更新で期限・直近本人確認時刻を延ばさない。
- 既にブラウザーでログイン済みなら再度のパスキー認証を要求しない。Windows用に独立した`auth_sessions`行を作り、ブラウザーのUTC期限と直近本人確認時刻を引き継ぐ。残り2日ならWindowsも残り2日。WindowsのログアウトはそのWindowsセッションだけを失効させ、ブラウザーはログアウトさせない。
- APIトークンは署名・暗号化した標準トークンを使い、検証後も毎回DBのセッション・利用可否・現在の全体ロールを確認する。期限切れ・失効・利用停止はアクセスと更新の両方を拒否する。保護APIは引き続き現在の家計簿参加・役割を確認し、トークンだけで家計簿権限を固定しない。
- CookieとBearerは認証時に分ける。Authorizationヘッダーがある場合はWindows用の標準検証を選び、不正なBearerから有効なCookieへ切り替えない。有効なBearerで認証できたAPI要求だけをCookie用のOrigin・CSRF検証から除外する。Cookie要求の検証は維持する。
- OAuthの認可・交換と既存パスキー操作は、検証途中の早期拒否を含め同じIP単位の1分20回を共有する。家計簿のアカウント別枠も、Cookie／Windowsセッションを問わず共有する。保存先の障害は503とし、HTTP経由でDBを自動作成・修復しない。
- `OpenIddictApplications`・`OpenIddictAuthorizations`・`OpenIddictScopes`・`OpenIddictTokens`は標準ライブラリの保存モデル。既存の初回EF定義に含め、Windowsクライアントの公開登録だけを初期データにする。アカウント・家計簿・人物は自動作成しない。
- 認可コード・更新／アクセストークンを通常ログへ残さない。OpenIddictの詳細ログを抑制し、ブラウザーの戻り先も同じオリジンの認可エンドポイントに限定する。

### Windows版の認証情報保存

Windows版のアクセス／更新トークンは、WindowsのDPAPI（`DataProtectionScope.CurrentUser`）で暗号化し、`%LOCALAPPDATA%\Monetail`内の専用ファイルへ保存する。接続先URLの`settings.json`とは分け、平文のトークンを設定ファイル・一時ファイル・通常ログへ残さない。暗号鍵の管理はWindowsに任せ、復号用パスワードの入力は追加しない。認証情報を別PC・別Windowsユーザーへ持ち運んで使う運用は前提にしない。

認証情報は取得元のAPI接続先と対応付け、接続先変更時は以前の認証情報を引き継がず、変更先でログインし直す。元のトークンを変更先へ送信しない。

専用ファイルは`authentication.dat`。形式の版・取得元の正規化したHTTPSオリジン・両トークン・アクセス期限をまとめて暗号化し、暗号化済みの一時ファイルだけを経由して置き換える。設定も`version`と`apiUrl`を原子的に保存する。接続先は固定HTTPSオリジンとし、パス・クエリー・フラグメント・ユーザー情報を受け付けない。

復元時は必要なトークン更新と`/auth/me`による確認を行う。アクセス期限の30秒前から更新を試み、有効期限内の401も一度だけ更新して再確認する。明確な失効（Bearerの401、更新時の`invalid_grant`）でのみ認証を破棄し、通信障害・503・保存先I/Oエラーでは保持する。更新済みトークンは以降の通信が失敗しても復元できるよう即保存する。元のログイン期限はサーバーが管理し、クライアントで延長・再計算しない。復号不能・破損なら認証だけを破棄する。接続先不一致は別ウィンドウの設定変更等として区別し、その認証を利用せず保持する。起動中に保存トークンの変更を検知した場合も、現在の画面の本人として操作を続けずログイン画面へ戻す。更新や失効確認の通信中に変更された認証を上書き・削除しないよう、保存・削除の前にも対応を再確認する。起動時の画面操作は[58](ledger-windows.md#windows版の起動表示接続失敗時の操作)を正本とする。
