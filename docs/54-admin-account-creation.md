# 54 既存人物への一般アカウント・初回登録コードの発行

**管理者が、アカウント未作成の既存人物へ一般アカウントと初回登録コードを発行するAPIを実装。** [43 認証設計](43-passkey-authentication-design.md)と[51 人物・アカウント一覧](51-admin-account-list.md)を引き継ぐ。Web管理画面、新規人物追加、停止のHTTP操作は後続とし、コード再発行は[55](55-admin-enrollment-code-reissue.md)で実装した。

## API契約

`POST /admin/accounts`へ、クライアントが発行操作ごとに作る空でないUUIDの`requestId`と、選んだ既存人物の`userCode`を送る。同じ操作の再送には同じ要求IDを使う。

```json
{ "requestId": "11111111-1111-4111-8111-111111111111", "userCode": 3 }
```

現在のAdminロール・有効なセッション・直近5分未満の本人確認・同一Origin・CSRFトークンを必須にする。既存の本文64 KiB上限、キャッシュ禁止、認証更新を合わせたIPごと1分20回の制限を使う。要求に名前・ロール・認証IDなどの未対応項目を追加した場合は400とする。

初回成功は201で、`authUserId`・`userCode`・`code`・`expiresAtUtc`を返す。コードは既存処理と同じ暗号学的乱数32バイト・有効期限10分で、DBへはSHA-256ハッシュだけを保存する。アカウントは無効・パスキー未登録・ロールなしで作り、[46 パスキー登録](46-passkey-enrollment.md)に成功するまで利用できない。管理者や対象者のログインセッションを発行・更新せず、既存の人物・Windows用`account_name`・業務データを変更しない。

| 結果 | HTTP応答 |
| --- | --- |
| 同じ管理者・要求ID・人物の再送 | 200。同じアカウントID・人物コードを返し、`code`と`expiresAtUtc`はnull。コードの再表示・再発行やアカウントの再有効化を行わない |
| 人物がない | 404 |
| 別の要求ですでにアカウントが作成済み | 409。登録待ち・利用中・停止中・管理者も含め、既存アカウントを変更しない |
| 同じ要求IDを別の人物・別の管理者が使用 | 409。元のコードやアカウント情報は返さない |
| 入力形式・必須項目・未対応項目・CSRFが不正 | 400 |
| 未認証・期限切れ・失効・利用停止 | 401 |
| 管理権限不足・本人対応不備・本人確認期限切れ・処理中の認証変更 | 403 |
| 回数超過／DB障害・移行未適用 | 429／内部情報を含めない503 |

応答を受け取れなかった場合も再送で作成結果を確認できる。生コードは再取得できないため、必要なら[55 再発行API](55-admin-enrollment-code-reissue.md)から明示的に新しいコードを発行する。[45 管理コマンド](45-initial-admin-enrollment.md)でも再発行できる。

## 保存と追加移行

EF移行`20261026064157_AddAccountCreationRequests`は`auth_account_creation_requests`と索引だけを追加する。

| 列 | 用途 |
| --- | --- |
| RequestId | UUIDをN形式の文字列で保存する主キー |
| CreatedByAuthUserId | 発行した管理者の認証ID |
| AuthUserId | 作成した一般アカウントの認証ID。UNIQUE |
| UserCode | 作成時に選んだ人物コード |
| CreatedAtUtc | 発行日時（UTC） |

全列NOT NULL。管理者・作成先アカウントからIdentityアカウント、人物コードから`m_user(code)`へRESTRICTの外部キーを設ける。生コード・コードハッシュ・Cookie・セッションの秘密は要求記録へ保存しない。要求記録を自動削除する処理も追加しない。

既存の認証・業務テーブルは再作成・再計算しない。[44](44-auth-database-foundation.md)の`migrate-auth-db`で検証用コピーへ明示的に追加移行する。API起動や発行要求から自動移行しない。

SQLiteの書込トランザクション内で、現在の管理者のロール・有効性・人物対応・セッション・直近本人確認を確認し、要求IDと人物の状態を照合する。一般アカウント・人物対応・登録コード・要求記録を同時に保存し、管理者を保存後にも再確認してから確定する。途中失敗や確認条件の変化では全変更を戻す。同じ要求の同時送信では201と200の一組だけが成功し、異なる要求から同じ人物を作る場合は一方を409とする。

本番設定・実データは変更していない。検証結果・件数・CIは[tests/README.md](../tests/README.md)を参照する。
