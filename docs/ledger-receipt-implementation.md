### 税率履歴：全件GETと全履歴同期CLI（仕様確定）

税率履歴は全家計簿共通。**全件GET・応答JSON・接続先/ログインアカウント単位のメモリキャッシュ・全履歴同期CLIの方式は利用者承認済み**。`Program.cs`の税率管理CLIとAPI税率履歴GETは未実装。取引日指定GETへ戻さず、固定税率・施行日を自動投入しない。CLIの実データファイルは運営者が作成する。

#### 1. 全件GETの応答JSON（確定・未実装）

`GET /ledgers/{ledgerId}/tax-rates`。既存の認証・家計簿参加検証と読取制限を適用し、日付クエリなしで全区分・全期間の履歴を返す。

```json
{
  "rates": [
    { "taxCategoryCode": "Standard", "validFrom": "0001-01-01", "validTo": "1989-03-31", "rate": null },
    { "taxCategoryCode": "Standard", "validFrom": "1989-04-01", "validTo": "1997-03-31", "rate": "3" },
    { "taxCategoryCode": "Exempt", "validFrom": "0001-01-01", "validTo": null, "rate": null }
  ]
}
```

**上記は境界日・NULL表現の説明用の抜粋で、運用DBに投入する全履歴データではない。** CLI全履歴同期では、1997年以降の標準税率の改定・食品/新聞区分の必要期間を含めた完全なファイルを用意する。`initialize-db`による自動投入は行わない。**成功200のトップレベルは`rates`配列のみ**。0件なら`{"rates":[]}`。各行は`taxCategoryCode`（既存4コード）、`validFrom`（実在`YYYY-MM-DD`）、`validTo`（同形式またはnull）、`rate`（InvariantCultureのDecimal文字列または税なしのnull）の**4フィールドのみ**。**`Exempt`は常にnull、`Standard`等の課税区分でもnullを許可**し、課税`0%`の`"0"`と区別。`Standard`の履歴行あり・率nullは「税なし」の選択、履歴行なしは「初期未選択」であり、同じ扱いにしない。履歴ID/行更新版/名前/家計簿IDは返さない。

APIは同率の複数区分、同区分の複数期間を**統合・除去しない**。同一区分の期間非重複は既存DB制約に従う。**レスポンス配列順は契約に含めない**。候補の昇順・同率統合はWindows側で行う。非課税は履歴がなくても選択肢に常設し、`Exempt`科目なら初期選択する。保存APIでの全明細の最新履歴照合は省略しない。

#### 2. 管理CLI：将来の改定まで扱う全履歴同期（確定・未実装）

初回の**追加入力だけ**の`import-tax-rates`案には欠点がある。たとえば`validTo=null`の履歴があるまま将来の税率を追加すると期間重複になる。既存行の終了日変更と新履歴追加を**同一トランザクション**で行える方式が必要。

**採用方式**：`sync-tax-rates --file /path/tax-history.json --dry-run`で差分の確認、`sync-tax-rates --file /path/tax-history.json --apply`で明示確定。`--allow-delete`は`--apply`との併用時だけ意味を持ち、単独では削除を許可しない。入力ファイルはDB内の**全区分・全期間の希望状態**を列挙する（部分更新とはみなさない）。JSONは`{"rates":[...]}`の形で、GETと同じ4項目に限定する。**`rate:null`は`Standard`等でも許可、`Exempt`はnull必須**。UUID/更新版はサーバー側で管理。

- JSONの実在日付、区分4コード、Decimal文字列/NULL、終了日、同区分の期間非重複を投入前に全件検証し、入力ファイル内部と既存DBの整合性も確認。
- 既存行を`(taxCategoryCode,validFrom)`で照合し、変わらない行のID/更新版は保持、終了日・率の変更は既存行を更新、新規期間は追加する。開始日を変更するときは旧行の削除と新規行の追加として扱う。
- ファイルから消えた履歴は**意図しない消去と区別**し、通常の`--apply`では削除を拒否。削除が必要な場合のみ`--apply --allow-delete`を明示する。**`rate:null`は正当な値であり、当該履歴行を削除する指示ではない**。**`--apply`実行時もDBの最新状態を同一SQLite書込トランザクション内で再読込・検証**し、差分を確定する。成功した全変更だけを同一トランザクションで反映。途中失敗は全件ロールバックする。重複トリガーを一時停止せず、既存区間の終了日の更新と新規区間の追加が両立する書込み順を採用する。
- `--dry-run`では追加・変更・削除予定を出力しDBを変更しない。実行時は事前にAPIを停止し、バックアップを取得。通常のWebログインは不要だが、サーバー/DBの運営者のみが実行できるようにし、HTTPの税率変更APIは設けない。
- 新規DBの`initialize-db`は履歴0件のままとし、CLI実行でDBや認証情報を作り直さない。履歴変更で過去レシートが現在のマスタ検証に不適合となり得ることは、差分確認時に注意喚起する。DB側の期間重複トリガーと**`Exempt`のNULL必須制約**を維持する。課税区分のNULLを拒否する**現行CHECK制約は変更が必要**。

**残る別判断**：実際に投入する全税区分・全期間の税率と施行日を含むファイルの内容。**CLI/APIの構造・引数・基本振る舞いは確定**。税率・日付はこの文書例から自動作成しない。実装方式固有の例外処理は既存管理CLIの終了コード0/1・ログ出力に揃える。

#### 3. Clientキャッシュ・受入条件（仕様確定）

- 初回に必要となった時だけ全件取得。同じ接続先/アカウントなら家計簿切替・日付変更・科目変更で再取得しない。全件取得スロットは既存の家計簿別`LedgerMasterCache`とは分離し、`ClientConnection`の接続先/認証コンテキストに結び付ける。
- 接続先変更・ログアウト・別アカウント切替で破棄、再ログインでは再取得。破棄前の通信応答は採用しない。ディスク保存・TTL・定期確認は行わない。
- 各行の`validFrom <= 取引日 <= validTo`（終了nullは無期限）で絞る。数値同率は候補表示だけで重複除去し、科目初期選択は初期税区分コードから求める。保存済みの実税率や下書きは自動変更しない。
- 保存APIで税率履歴の変化が原因の拒否を受けたら、全件を強制再取得し、入力を保持して利用者に再選択を求める。
- **NULLの起源は明細に保存しない**：履歴`Standard/rate:null`から選んだ明細と、`Exempt`科目で選んだ明細はどちらも`taxRate:null`で保存する。保存済み明細を参照しても区分の起源は特定できない。必要なら将来の別設計とし、ここで明細の税区分列を追加しない。
- **既存実装との差分**：`src/Monetail.Api/Features/Monetail/Taxes/TaxModel.cs`の`CK_tax_rate_history_rate`は課税区分に`rate IS NOT NULL`を要求するため、`Exempt`以外もNULL可へ緩和する。`CategoryTaxSchemaTests.TaxableZeroIsStoredButTaxableNullIsRejected`等の固定期待値を改め、NULL履歴行/履歴不在/数値0の区別を追加。レシート計算器・保存APIは既に明細`taxRate:null`を税なしとして扱うので、初期税率判定の非選択との混同に注意する。既存データの自動変換や正式リリース前のMigrationは実装しない。
- 回帰：0件/複数期間/境界日（例：1989-03-31の`Standard/null`と1989-04-01の`Standard/3`）/期間間隙/同率異区分/税なしNULL・課税0%/再ログイン/家計簿切替/更新後の旧応答/履歴変更による保存拒否。CLIではdry-run非変更・再適用同値・重複期間・原子的失敗・削除ガード・将来改定時の終了日変更を検証する。**実例の日付・率は検証データであり、履歴の初期自動投入を承認するものではない。**

## DB実装の判断境界

**初回DB実装PRに着手する際は、既存文書の「提案」をユーザー承認済みと推定しない。** [DB4表の物理設計](ledger-receipt-schema.md)に含まれる規則を次のように分ける。

| 区分 | 例と対応 |
| --- | --- |
| **確定済み・必須** | 家計簿単位の複合PK/FK・家計簿間参照禁止、子ID維持、同一レシート内の同一科目1グループ、監査アカウントRESTRICT FK、周期・金額・列挙値の検証、明細ごとの実税率、**初期DB作成は最新モデルで行いMigrationを使わない**。既存の決定と文書の要件として実装 |
| **物理設計案・承認確認** | DB文書で確定と明示されていない**列・列型・CHECK/FKの物理詳細**。業務挙動に影響する変更・新制限は独断で追加しない。必要ならDB実装前に採用可否を確認 |
| **性能・内部実装の選択** | キーセット一覧の`(ledger_id,transaction_at,receipt_id)`索引はDEC-231との整合を必須とする。支払方法条件に対する追加複合索引は**候補**であり、正しさの仕様とは別。実行計画・回帰テストで必要性を示し、追加する場合はPRに理由を記載。独自のユーザー向け制限やDB列は増やさない |
