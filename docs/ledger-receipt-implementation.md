### 税率履歴：GETの基本方針確定、CLIと応答詳細は提案

現状は`Program.cs`の管理コマンドに税率操作がなく、税率のGET APIもない。**GETのパス・認証と家計簿参加確認・指定日有効な履歴だけ返す方針は確定済み**。税率履歴は全家計簿共通（DEC-138）。下記のCLI引数・一括投入方式、GET応答DTO・キャッシュ方式は**未承認の提案**であり、実装時に独断で確定しない。

- **投入CLI案**：`import-tax-rates --file /path/tax-history.json --dry-run`で事前検証し、`import-tax-rates --file /path/tax-history.json`で登録。既存`initialize-db`とは分離。API停止・DBバックアップ後、サーバーの既存DB接続設定を使って実行し、WebログインやHTTPでの税率変更口は設けない。
- **JSONの1履歴行の案**：`taxCategoryCode`（既存4区分のコード）、`validFrom`（`YYYY-MM-DD`）、`validTo`（同日付またはnull）、`rate`（正確なDecimal文字列、非課税だけnull）。履歴ID・更新版はサーバー側が生成。個々の区分の期間・率は**運営者が明示する**。施行日や8%/10%/1%などを推測・自動投入しない。
- **安全条件案**：全行を先に検査し、同区分の期間重複・無効日付・区分/NULL不一致を拒否。全行を1トランザクションで確定し、途中失敗は全件ロールバック。同一内容の再投入は無変更とし、既存期間との矛盾や変更は自動上書きせず中止。履歴の修正・削除は別途明示的な管理操作を設計し、初期投入コマンドへ「全件置換」を混ぜない。既存DBの自動作成・Migrationは行わない。
- **GETの確定骨格＋応答形の提案**：`GET /ledgers/{ledgerId}/tax-rates?date=YYYY-MM-DD`は既存の家計簿参加/認証境界と読取回数制限を適用し、取引日に有効な履歴を返す。**レスポンスの具体的なフィールド・型は未承認**で、後続の合意までは実装しない。

  ```json
  {
    "date": "2026-11-12",
    "rates": [
      { "taxCategoryCode": "Standard", "rate": "10" },
      { "taxCategoryCode": "ReducedFood", "rate": "8" },
      { "taxCategoryCode": "ReducedNewspaper", "rate": "8" },
      { "taxCategoryCode": "Exempt", "rate": null }
    ]
  }
  ```

  上記の率・日付は**例示であって実際の税率データではない**。案の詳細：
  - 必須のルート項目は`date`（検索対象のローカル取引日`YYYY-MM-DD`）と`rates`（配列）の2つ。各行は`taxCategoryCode`（4区分コード）と`rate`（課税ならInvariantCultureのDecimal文字列、非課税ならJSON null）の2つ。
  - 指定日に有効な**実在する履歴行だけ**を税区分単位で返す。履歴0件なら`"rates":[]`、履歴がない区分の仮値は返さない。非課税履歴があれば`Exempt/null`行も返すが、なくてもクライアントでは非課税を常設する。課税`0%`は`"0"`であり非課税`null`とは区別する。
  - 同じ数値の課税税率が複数区分にある場合は**区分ごとの行を保持**する。画面で選択肢を作る際だけ数値で重複除去。科目の初期値は科目マスタの`taxCategoryCode`で対応させ、別区分の率では代用しない。
  - 履歴ID、revision、開始日、終了日、家計簿情報は含めず、計算用の参考額・保存可否も返さない。並び順のAPI契約は設けず、UI側で数値順・非課税の位置を決める案。
  - `date`は必須、形式`YYYY-MM-DD`かつ実在日付に限定。欠落・不正書式・非実在日は既存`invalid_input`形式の400（`field=date`）とする案。未認証401、家計簿未参加/存在なし404、既存の読取回数超過429・DB障害503の境界を引き継ぐ。成功は200。取得日変更・古い応答破棄は下記の再読込案を参照。
  - 取得APIは表示候補のための読み取り専用。**保存時の全明細の税率再照合はAPI側の既存処理を維持する**。
- **取得/再読込案**：レシート入力を開いた時と取引日変更時に取得し、別日付の古い応答・別家計簿/別ログインの応答は適用しない。保存時に税率履歴の変更が判明した場合は明細を自動書換えせず、候補を再取得して手動再選択を求める。永続キャッシュや固定の更新間隔は設けない。
- **確定済みの非課税初期選択**：初期税区分が`Exempt`の科目では税率履歴が0件でも非課税（保存値NULL）を初期選択する。非課税は税率候補として常時表示し、保存時も既存`ReceiptValidation`どおり履歴を必要としない。課税区分の科目だけ、該当日付の区分別履歴がなければ未選択とする。**GET案**は当日有効な履歴行だけを返す想定のため、非課税の常設候補・初期選択はクライアント側の確定規則として補う（GETパス・認証／参加確認・指定日適用は確定、JSONの細部は未承認）。

## DB実装の判断境界

**初回DB実装PRに着手する際は、既存文書の「提案」をユーザー承認済みと推定しない。** [DB4表の物理設計](ledger-receipt-schema.md)に含まれる規則を次のように分ける。

| 区分 | 例と対応 |
| --- | --- |
| **確定済み・必須** | 家計簿単位の複合PK/FK・家計簿間参照禁止、子ID維持、同一レシート内の同一科目1グループ、監査アカウントRESTRICT FK、周期・金額・列挙値の検証、明細ごとの実税率、**初期DB作成は最新モデルで行いMigrationを使わない**。既存の決定と文書の要件として実装 |
| **物理設計案・承認確認** | DB文書で確定と明示されていない**列・列型・CHECK/FKの物理詳細**。業務挙動に影響する変更・新制限は独断で追加しない。必要ならDB実装前に採用可否を確認 |
| **性能・内部実装の選択** | キーセット一覧の`(ledger_id,transaction_at,receipt_id)`索引はDEC-231との整合を必須とする。支払方法条件に対する追加複合索引は**候補**であり、正しさの仕様とは別。実行計画・回帰テストで必要性を示し、追加する場合はPRに理由を記載。独自のユーザー向け制限やDB列は増やさない |

| 有効期間変更後の再編集 | **保存API（PR3）**：変更対象に関係なく全明細の税率を現行の取引日履歴へ照合し、保存済み税率は自動変更しない。科目・支払方法・人物の有効期間が後から変更された場合の細則は、実装時に既存のマスタ有効期間契約と照合 |
| レシート一覧・詳細・保存API | **API（PR3・4）**：[API契約](ledger-receipt-api.md)のPOST/PUT/DELETE、詳細・一覧GET、版・再送・競合・カーソル等を検証。HTTP/JSONは確定済みで、未承認の追加エラーやパラメータを作らない |
| 旧Windows版データの引継ぎ | **別工程**：実データ検査まで保留。旧グループ税率・課税対象フラグを新明細の税率へ対応付け、同じ科目のグループを統合する必要がある。現行のDB初期化へ混ぜない |
| 候補`AutoSuggestBox`の矢印・Tab・Esc・Enter | **WinUI（PR6）**：プレビューと業務値確定の分離、自由入力復元、次欄移動、IME確定、二重イベントを実画面で検証。[レシート候補](ledger-receipt-suggestions.md)と[Microsoft仕様](https://learn.microsoft.com/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.autosuggestbox)を参照 |
| Enterのコントロール別扱い | **WinUI（PR6）**：共通入力契約59の`ComboBox`は候補確定時に移動しないが、レシートの`AutoSuggestBox`はDEC-196で確定後次欄へ移動。コントロールを混同せず、IME確定・入力確定の順序を検証 |
| 履歴候補検索・負荷 | **候補API（PR5）**：全対象検索→正規化付き部分一致→**元文字列**で重複排除→更新UTC降順→最大100件（店名／所在地／科目の条件別スコープ）。権限・キャンセル・古い応答の破棄、検索計画・索引・負荷試験を確認。APIの経路や基本エラーは[候補契約](ledger-receipt-suggestions.md)に確定済み |

**今回の対象外（将来の別判断）**：必須の店舗マスタ、明細の税区分コード・別の課税対象フラグ、グループ専用表示順、明細の周期列、旧ポイント明細（`t_receipt_points`）、週/月/年から次回入力候補を計算する月末・曜日・営業日ルール。現時点では周期を保存するだけ。これらの機能を先取りしてDBに追加しない。

## 未決定・後続検証（独断で確定しない）

- 物理設計で未承認の列・制約の採用可否は、上記**DB実装の判断境界**に従う。性能索引はユーザー向け仕様と区別し、必要性を計測してPRで説明する。
- 人物別の参考額の細かな端数期待値、人物別レシート／期間合計の集計境界。

- 旧Windows版DBの実データ移行（`total=NULL`等）。**新API DBの現行モデル初期化**と**旧Windows版からの業務データ移行**は別工程。
- リリース後のMigrationの初回導入・アップグレード／ロールバック方針はリリース準備時に設計し、正式リリース前の実装PRへ先取りしない。
