## レシート401認証復帰の実装境界

PR #189の遷移構造を利用し、[DEC-268・269・267](ledger-receipt-ui.md#401再認証と元の画面復元dec-268)の認証退避・同じ本人/家計簿/接続先への復帰・マスタ/税率再取得・読み取り専用/手動再試行を接続済み。PR3の入力Page化では、同じReceiptEditorPage/既存VM/実コントロールをNavigateせず保持する。通常離脱ではPageを解放し、詳細GET・自動保存・自動再送は行わない。構成は[WinUI正本](architecture-winui.md#pr3入力pageへの移管)を参照。異なる本人/接続先・終了時は破棄する。保存APIは未接続のため、**保存操作起因の401、未完了の書込要求保持、保存結果不明・409 UIは後続で検証/実装する**。通常の離脱確認と明細下書きの3択は維持する。

## 工程6-D4の実装前整理（調査済み事実と分割案）

**D4-0・D4-A・D4-CLI・D4-B・D4-Cは実装済み。** 税率履歴APIの正本は[共通税区分・税率履歴API](specs/api/features/tax-rates.md)、DB・CLI・キャッシュは[共通税率履歴](ledger-core-schema.md#shared-tax-history)、計算は[計算契約](12-calculation-contract.md)、画面は[レシートUI](ledger-receipt-ui.md)を参照する。登録用の全期間JSONは[`config/tax-history.json`](../config/tax-history.json)にあるが、初期DBへ自動投入しない。

### 現状確認（工程6-D4-Cまで）

- **D4-0**：課税区分の履歴`rate:null`を許可し、`Exempt`はNULL必須。期間重複禁止と最新スキーマでの新規DB初期化を維持。
- **D4-A・D4-CLI**：税率履歴の全件GET、Clientの接続先/アカウント別キャッシュ、全履歴同期CLIを実装済み。CLIはdry-run/明示apply、削除ガード、トランザクションを備える。
- **D4-B・D4-C**：API/Clientの共通`Monetail.Calculations`による正式計算と、WinUIの候補・初期選択・参考額/合計表示を実装済み。計算不能時は未計算とし、入力を変更しない。
- **未接続**：レシート全体保存と履歴候補UI。保存ボタンは接続まで無効。人物按分の最終端数・人物別期間合計は未決定。

### 推奨する小PRの境界（D4-0・D4-A・D4-CLI・D4-B・D4-C実装済み）

完了済み工程のPR分割表・計測・テスト結果はGit履歴と[テスト記録](../tests/README.md)を参照する。今後の実装では以下を回帰条件とする：履歴0件の`Exempt`初期非課税、課税履歴`rate:null`の非課税選択と履歴行欠落時の未選択の区別、課税0%との区別、境界日・期間間隙・同率異区分、保存済み税率と下書き保持、CLIのdry-run/削除ガード/同値再適用/全件ロールバック。API保存は画面接続まで実行しない。

### D4着手前の実装境界（確認済み/後続）

当初の日付指定GETと追加入力だけのCLI案は採用しない。現在は**全件GETと全履歴同期CLI**を使用し、取引日の候補解決はClientキャッシュで行う。正式計算はAPIとClientの同一実装を使用する。確定したデータ契約や制限は以下の正本へ一本化する。

### 税率履歴：全件GETと全履歴同期CLI（仕様確定）

#### 1. 全件GETの応答JSON（D4-A実装済み）

[共通税区分・税率履歴API](specs/api/features/tax-rates.md)を正本とする。履歴の例示値は運用DBへの自動投入を意味しない。

#### 2. 管理CLI：将来の改定まで扱う全履歴同期（D4-CLI実装済み）

`sync-tax-rates`は入力JSONを部分追加ではなく**全区分・全期間の希望状態**として扱う。dry-run、明示apply、削除の`--allow-delete`、同値再適用時のID/revision保持、最新DBとのトランザクション内再照合・原子的反映を含む契約は[税率履歴同期CLI](ledger-core-schema.md#税率履歴の全履歴同期clid4-cli実装済み)を正本とする。運用は[DB初期化・管理コマンド](42-api-foundation.md#db初期化登録復旧コマンド)を参照し、API停止・バックアップ後に明示実行する。

#### 3. Clientキャッシュ・受入条件（仕様確定）

キャッシュの取得・保持・破棄・再取得は[Clientキャッシュ契約](ledger-core-schema.md#共通税率履歴の全件getメモリキャッシュ)、税率候補・入力保持は[レシート画面](ledger-receipt-ui.md#税率候補正式計算の画面接続工程6-d4-c実装済み)を参照する。履歴NULLの起源は明細`taxRate:null`に保存しない。

## DB実装の判断境界

**初回DB実装PRに着手する際は、既存文書の「提案」をユーザー承認済みと推定しない。** [DB4表の物理設計](ledger-receipt-schema.md)に含まれる規則を次のように分ける。

| 区分 | 例と対応 |
| --- | --- |
| **確定済み・必須** | 家計簿単位の複合PK/FK・家計簿間参照禁止、子ID維持、同一レシート内の同一科目1グループ、監査アカウントRESTRICT FK、周期・金額・列挙値の検証、明細ごとの実税率、**初期DB作成は最新モデルで行いMigrationを使わない**。既存の決定と文書の要件として実装 |
| **物理設計案・承認確認** | DB文書で確定と明示されていない**列・列型・CHECK/FKの物理詳細**。業務挙動に影響する変更・新制限は独断で追加しない。必要ならDB実装前に採用可否を確認 |
| **性能・内部実装の選択** | キーセット一覧の`(ledger_id,transaction_at,receipt_id)`索引はDEC-231との整合を必須とする。支払方法条件に対する追加複合索引は**候補**であり、正しさの仕様とは別。実行計画・回帰テストで必要性を示し、追加する場合はPRに理由を記載。独自のユーザー向け制限やDB列は増やさない |

## PR工程別・実装前確認と受入検証

PR #135の「実装前に残る確認事項」を工程別に整理した一覧。**確定規則の正本をここへ複製するものではない**。右列の未決定・保留条件を確認済みと誤認しない。

| 元の論点 | 実装時期と必要な確認 |
| --- | --- |
| 取引日時の詳細書式 | **DB・詳細/一覧API（PR1・3・4）**：DEC-253のローカル日時`yyyy-MM-ddTHH:mm:ss`をDB/API全体で統一。監査日時UTCと区別。旧データの秒未満精度は移行時に検証 |
| 旧版`total`がNULLのデータ | **旧DB引継ぎ時**：新DBの`total_amount INTEGER NOT NULL`は確定。旧実データのNULLを**自動0変換しない**。個別対応を要する |
| 主キーとID一意性 | **DB（PR1）**：全4表が`ledger_id`を含む複合PK。レシート・グループ・明細のID単独UNIQUEは設けず、複合FKによる家計簿分離をテスト |
| 監査アカウント参照と削除 | **DB（PR1）**：作成者・更新者を認証アカウントへRESTRICT FK。将来のアカウント物理削除/退会の業務設計は対象外 |
| 複数税率グループの参考額・人物按分 | **計算（PR2）**：DEC-156・157の集計境界。0～3人、正負、税率混在、税込/税抜、切り捨て/四捨五入を固定例でテスト。**人物按分後の最終端数は未確定**であり、必要な段階で期待値を確認 |
| 人物別レシート・期間合計 | **集計機能の実装時**：全体・期間合計の集計境界は未確定。グループ参考額の単純合算を会計上の正本としない |
| 有効期間変更後の再編集 | **保存API（PR3）**：変更対象に関係なく全明細の税率を現行の取引日履歴へ照合し、保存済み税率は自動変更しない。科目・支払方法・人物の有効期間が後から変更された場合の細則は、実装時に既存のマスタ有効期間契約と照合 |
| レシート一覧・詳細・保存API | **API（PR3・4）**：[API契約](ledger-receipt-api.md)のPOST/PUT/DELETE、詳細・一覧GET、版・再送・競合・カーソル等を検証。HTTP/JSONは確定済みで、未承認の追加エラーやパラメータを作らない |
| 旧Windows版データの引継ぎ | **別工程**：実データ検査まで保留。旧グループ税率・課税対象フラグを新明細の税率へ対応付け、同じ科目のグループを統合する必要がある。現行のDB初期化へ混ぜない |
| 候補`AutoSuggestBox`の矢印・Tab・Esc・Enter | **WinUI（PR6）**：プレビューと業務値確定の分離、自由入力復元、次欄移動、IME確定、二重イベントを実画面で検証。[レシート候補](ledger-receipt-suggestions.md)と[Microsoft仕様](https://learn.microsoft.com/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.controls.autosuggestbox)を参照 |
| Enterのコントロール別扱い | **WinUI（PR6）**：共通入力契約59の`ComboBox`は候補確定時に移動しないが、レシートの`AutoSuggestBox`はDEC-196で確定後次欄へ移動。コントロールを混同せず、IME確定・入力確定の順序を検証 |
| 履歴候補検索・負荷 | **候補API（PR5）**：全対象検索→正規化付き部分一致→**元文字列**で重複排除→更新UTC降順→最大100件（店名／所在地／科目の条件別スコープ）。権限・キャンセル・古い応答の破棄、検索計画・索引・負荷試験を確認。APIの経路や基本エラーは[履歴API](specs/api/features/receipt-history.md)に従う |

**今回の対象外（将来の別判断）**：必須の店舗マスタ、明細の税区分コード・別の課税対象フラグ、グループ専用表示順、明細の周期列、旧ポイント明細（`t_receipt_points`）、週/月/年から次回入力候補を計算する月末・曜日・営業日ルール。現時点では周期を保存するだけ。これらの機能を先取りしてDBに追加しない。

## 未決定・後続検証（独断で確定しない）

- 物理設計で未承認の列・制約の採用可否は、上記**DB実装の判断境界**に従う。性能索引はユーザー向け仕様と区別し、必要性を計測してPRで説明する。
- 人物別の参考額の細かな端数期待値、人物別レシート／期間合計の集計境界。
- 履歴検索のSQL性能・索引要否とURLバイト長上限。画面上の標準コントロール差異やIME／フォーカスの実機挙動。
- 旧Windows版DBの実データ移行（`total=NULL`等）。**新API DBの現行モデル初期化**と**旧Windows版からの業務データ移行**は別工程。
- リリース後のMigrationの初回導入・アップグレード／ロールバック方針はリリース準備時に設計し、正式リリース前の実装PRへ先取りしない。
