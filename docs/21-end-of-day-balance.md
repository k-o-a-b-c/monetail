# 21 日末残高に基づく推算期間

更新: 2026-10-19 / LEG-029・CAL-005。利用者が「登録残高は、その日の終了時点の金額」と確認した仕様を実装した。[PR #12の修正前の再現記録](20-balance-date-boundaries.md)を基に期待値を更新する。

## 確定した仕様

- 起点は、対象日の00:00:00より前の、対象口座の最新残高。同日・未来・別口座の残高を起点にしない。
- 登録残高は日末の値なので、起点の日の取引は再集計しない。保存日時の**日付部分の翌日00:00:00以上**を集計する。保存日時に時刻があっても、保存値を変更せず日付として扱う。
- **対象日の翌日00:00:00未満**までを集計する。対象日の23:59:59以降の小数秒と、その日の最後の1tick（100ns）も含め、翌日00:00:00は含めない。
- 起点がなければ`DateTime.MinValue`から開始する。対象月より前の取引も反映する。
- 起点も対象取引もなければ`Nothing`。取引があれば0円も既知の値として返す。収入の符号・評価額を推算に使わないこと・引数時刻を切り詰めることは維持する。

通常の集計区間は`[残高日の翌日00:00:00, 対象日の翌日00:00:00)`となる。DateTimeの最終日9999/12/31は翌日を表せないため、`DateTime.MaxValue`を含む上限とする。最小日・最終日ともオーバーフローせず、その日の最後のtickまで計算する。

## 実装と保存値

両AutoBalanceで同じ期間を求め、`GetPaymentReceipts`と`GetPaymentTransfers`の追加引数`endExclusive=True`を使う。この場合のSQL条件は`date >= :date_from AND date < :date_to`。一般の3引数呼出は従来どおり両端を含む`BETWEEN`を使う。最終日は上限を含むモードでMaxValueまでを集計する。

アプリが保存するスペース区切りの日時と小数秒・明示的な`.0000000`を、日付の両側の0時で区切って扱う。日時列・レシート合計・税端数方式・更新版などの保存値を正規化・再保存しない。DB定義・移行SQL・登録操作も追加しない。修正した推算値は再読込時に表示へ反映される。

## 回帰テスト

両経路を実DataAccess・製品SQLiteのFK ON/OFFで固定の期待値と比較する。読込前後の全表の値・型・版・スキーマ、FK・user_versionを比較し、SQLite Updateイベント0回も確認する。一般の期間読込の包含条件も維持する。

| ケース | 修正後の期待値・確認内容 |
| --- | --- |
| 残高日の翌日から対象日末まで | PR #12と同じデータで954円から752円へ変わる。残高日末の取引を除外し、対象日末の小数秒を含める |
| 小数秒とTEXT表記 | 小数秒・明示的なゼロを対象日に含め、両側0時のゼロ表記も確認。PR #12のデータへ0時の取引を追加し、期待値は871円 |
| 時刻付き残高 | 同じ10/15 09:30の残高を10/15の日末として扱い、10/16の早朝取引も含める。984円から774円へ変わる。保存日時は9:30を保持 |
| 起点なし・同日／別口座・月末／年末／うるう日 | 既存の期待値を維持する |
| DateTimeの最小日・最終日 | 最小日の推算−22円、最終日の推算978円。各日の最後のtickを含める |

構成・件数・最新CI結果は[tests/README.md](../tests/README.md)を参照する。レシートの会計合計・税計算・オーケー割引は変更しない。

## 残る範囲

推算処理の共通化（LEG-025）は後続の作業。同一日時の複数残高の優先順位も未確定で、現在のSQLにseqの順序指定はない。日付だけ／T区切り／タイムゾーン付きなど別のTEXT形式、夏時間、実データの整合性、利用者環境の手動E2Eは今回の検証範囲に含めない。
