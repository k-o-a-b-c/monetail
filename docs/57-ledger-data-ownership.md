# 57 アカウント・家計簿・人物とマスタの所属

更新: 2026-10-26。**所属の区分、単一SQLite・家計簿IDによる区分、アカウントと人物を直接紐付けない方針を利用者が決定。スキーマ・詳細な操作は未設計で、コードとDBは未変更。** [56 新規導入](56-new-user-onboarding-policy.md)を具体化する方針とする（DEC-040〜042）。

## 決定した所属

| 管理するもの | 所属・範囲 |
| --- | --- |
| 認証アカウント | Monetail全体。ログインと全体管理者の権限を扱い、家計簿への参加とは分ける |
| 家計簿 | 参加するアカウントと、その家計簿内での権限を管理する |
| 人物 | 家計簿ごと。明細対象者などの人物を管理し、ログインしない人も登録できる |
| 支払方法・分類などの業務マスタ | 家計簿ごと。家計簿内の入力・計算・管理に使うデータとして扱う |

同じアカウントが複数の家計簿へ参加できる。それぞれの家計簿で参加と権限を管理し、全体管理者の`Admin`ロールと家計簿の管理権限を同一視しない。これはMonetail内の区分であり、別アプリとの共通アカウントやSSOを導入するものではない。

家計簿ごとの人物・業務マスタは独立したデータとする。一方の家計簿で人物名や支払方法・分類の設定を変更しても、他の家計簿のデータへ変更を波及させない。同じ名前があっても、人物・マスタを名前一致で統合したり自動的に共有したりしない。

アカウントと人物は別の概念・管理対象とし、初期の新規設計では直接紐付けない（DEC-042）。家計簿未参加のアカウントと、ログインしない名前だけの人物を区別する。

## アカウントと人物を直接紐付けない

| 対象 | 役割と名前の管理 |
| --- | --- |
| アカウント | ログイン・新しいデータの入力者／更新者の記録。Monetail全体のアカウント自身の表示名を持つ |
| 人物 | 家計簿内の明細対象者や支払方法の所有者など。家計簿ごとの人物名を持つ |

アカウント登録で人物の作成・選択を必須にしない。人物や家計簿が未登録・未作成の段階でも、招待を受けてアカウント登録・明示ログインできるようにする。人物の登録からアカウントや参加権限を自動作成することもしない。

アカウントの表示名と人物名は別々に管理し、名前一致で紐付け・統合しない。一方の名前を変更しても他方へ自動反映しない。初期設計にはアカウントと人物を直接対応付ける操作・関係を設けない。

新規Web/APIから保存するデータの入力者・更新者は、サーバーがログイン中のアカウントの識別子から決める。明細対象者などの人物とは分け、表示名を本人確認のキーにしない。保存項目・名前変更時の表示・履歴の扱いはスキーマとAPIの詳細設計で決める。既存の`update_user`等の保存値を一括変換・補完せず、過去の更新者は保持する。

家計簿への参加と操作権限はアカウントを基準に確認し、人物の作成・変更・削除をアカウントの本人確認の根拠にはしない。ログイン可否・セッション失効・パスキー検証等の認証条件は、人物との紐付けに依存しない形へ設計し直す。

## SQLite 1ファイルと家計簿IDによる区分

- MonetailのDBはSQLiteの1ファイルとし、認証アカウントと家計簿のデータを同じDBで保存する。家計簿ごとにDBファイルを作る方式は採用しない。
- アカウントはMonetail全体で管理し、家計簿への参加と権限を別に保持する。
- 家計簿ごとの人物・業務マスタ・取引の所属は家計簿IDで区別する。各表で直接IDを持つか、親への参照から所属を確認するか、具体的な列・キー・外部キーは後続のスキーマ設計で決める。
- 家計簿データを扱うAPIはログイン中のアカウントについて、対象家計簿への参加と操作権限を確認してから読み書きする。画面の選択やクライアントが送った家計簿IDだけでアクセスを許可しない。
- 読込の対象と、保存する人物・マスタ・親子データの関連について、対象家計簿の所属を照合する設計にする。詳細な制約と検証方法はスキーマ・API設計で具体化する。

初期設定・バックアップ・DBスキーマ更新をDB全体で管理しやすい構成とする。所属の分離はAPIと保存時の照合・制約で行い、SQLiteファイルが家計簿単位のアクセス権を提供するものとは扱わない。

## 新規導入・招待との関係

- アカウントはMonetail全体で管理するため、家計簿をまだ作成・参加していない段階の登録・ログインを扱う。
- 全体のアカウント一覧と新規登録招待は、全体管理者だけが利用する。通常の登録招待は一般アカウントを作り、家計簿への参加を自動的に確定しない。
- ログイン可能な登録利用者全員が家計簿を作成できる。作成時の最初の家計簿管理者の割当方法は後続設計とする。
- 家計簿管理者は、相手のアカウント一覧・検索・存在照会を使わずに参加を招待する。受け取った人がログインして参加を確定する。未登録なら先に全体管理者の登録招待が必要となる。
- 名前だけの人物を登録しても、認証アカウント・家計簿への参加・アクセス権は自動作成しない。

家計簿の読込・更新では、API側で対象家計簿への参加と操作権限を確認する設計にする。画面の切替や人物の指定だけをアクセス許可の根拠にしない。権限の種類や人物別の閲覧・編集範囲は未確定のままとする。

## 現在の実装との違い

現行の認証は、`auth_user_links`によるアカウントと既存`m_user`の1対1対応を必須としている。現在の一覧APIも人物を起点に対応アカウントを添えるもので、家計簿の所属・参加を保存する実装はない。

新規導入ではアカウントと人物を直接紐付けないため、この依存を見直す。現行の照合を単純に削除する実装には進まず、アカウント自身の表示名、入力者・更新者、セッションや管理者保護・復旧処理等も含めて設計・検証する。現在の照合窓口・DB対応表・人物指定のコマンドは、今回の文書更新では変更しない。

## 次に決めること

| 対象 | 未決定の内容 |
| --- | --- |
| スキーマ詳細 | SQLiteは1ファイルとし、家計簿IDで所属を区別。物理テーブル・列・主キー・外部キー・索引、親子データの所属確認方法を決める |
| 表示名と入力者・更新者 | アカウント自身の表示名と人物名の保存項目、変更時の表示、履歴・入力者／更新者の保存方法 |
| 家計簿作成 | 作成時の最初の管理者割当、必要な入力、途中失敗と再試行 |
| 初期データ | 各業務マスタの初期値・テンプレート・設定操作、入力開始に必要な項目 |
| 招待とアクセス | 招待の期限・対象との結び付け・取消と再発行・操作再開、家計簿内の具体的な権限 |
| 既存DBの引継ぎ | 新構成の確定後に、一度きりの移行に必要な最小限の対応を設計 |

家計簿ごとの所属、SQLite 1ファイル・家計簿IDによる区分、アカウントと人物の直接紐付けなしは確定した。具体的なスキーマ・認証の改修手順・表示名と入力者／更新者の保存項目等は後続設計。新しいテーブル・列・EF移行やマスタ画面は今回追加しない。既存人物・業務値・保存済み`receipt.total`を再計算・変更しない。
