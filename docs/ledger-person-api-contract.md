# 人物・参加者APIの操作とJSON契約

[← 人物API・DBの入口](ledger-person-api.md)

## 人物管理API・DB（実装済み）

人物情報の一括保存と更新後一覧の同一応答、参加者編集での対応保存、API側で生成するUUIDの人物IDは利用者確認済み（DEC-056・061・062）。下表の9操作のAPIパスとDB変更の構成は確認済み（DEC-089）。要求・応答と競合・再送のAPI契約は以下の実装内容に従い、業務取引の未実装部分と区別する。人物・参加者・招待の保存処理とAPI、未リリースAPIの初回定義へ実装した。Windowsの人物一覧と追加・編集・削除を接続済み。共通順の設定と、参加者一覧・編集／除外、招待発行・一覧・コピー・取消のWinUI 3画面も既存APIへ接続済み。ブラウザーの招待受領画面は未実装。業務取引のモデル・実DBの移行は後続とする。

**APIのパス・通信単位（実装済み）**

以下のパスはすべて`/ledgers/{ledgerId}`からの相対パス。各要求で有効なログインと現在の参加を確認し、書込時は最新の役割・本人の対応もトランザクション内で検証する。

| メソッド・パス | 用途・権限 | 取得・保存の単位 |
| --- | --- | --- |
| `GET /people` | 全参加者が人物一覧を取得 | 全員を共通順で返し、ログイン中の本人の人物ID・現在の役割・並び順の更新版も返す。通常画面だけが表示時に本人を先頭へ移す |
| `POST /people` | 管理者が人物を追加 | 作成操作のrequestId・名前・有効開始日・有効終了日を送り、名前・期間をまとめて登録。新規人物は共通順の末尾へ追加する（DEC-085）。作成要求の再送は下記の共通記録表で識別する |
| `PATCH /people/{personId}` | 管理者、または自分の名前を変更する本人が保存 | 名前・有効期間を1要求・1トランザクションで保存し、更新後一覧を同じ応答で返す。アカウントとの対応は受け付けない。本人だけの権限では名前以外の変更を認めない。部分更新の省略・nullは下記のとおり |
| `DELETE /people/{personId}` | 管理者が削除 | 人物の更新版を照合して削除。参照があれば削除せず理由を返す |
| `PUT /people/order` | 管理者が共通順を保存 | 全人物のIDを設定順で並べた配列と並び順の更新版を送る。全体を同じトランザクションで保存し、［上へ］［下へ］の操作ごとの通信は行わない |
| `GET /members` | 管理者が参加者一覧を取得 | アカウントID・表示名・役割・対応人物・参加日時・参加者の更新版と、本人や人物順の表示に必要な情報をまとめて返す。IDは操作対象の特定用で、同名識別の画面表示には使わない |
| `GET /members/{accountId}/edit` | 管理者が参加者の対応を編集する情報を取得 | 現在の参加者情報と同じ家計簿の人物候補を1応答で返す（DEC-088）。他の参加者に対応済みの人物は選択できない状態で示す |
| `PATCH /members/{accountId}` | 管理者が参加者の役割と人物の対応を保存 | 役割と人物対応を1要求・同じトランザクションで保存することは確認済み。人物IDと参加者の更新版をJSON本文で送る。NULLなら対応解除、別の人物IDなら付け替え |
| `DELETE /members/{accountId}` | 管理者が別の参加者を除外 | 対象の参加者の更新版を照合して参加者行と人物対応だけを削除し、更新後参加者一覧を返す。自分自身は対象不可。更新版はJSON本文のrevisionで送る |

APIの具体的な項目名・型と更新版を送る場所は下記の形式で実装した。人物の新規作成では要求ID、更新・削除では対象の更新版、共通順保存では全人物のID配列と並び順全体の更新版を送る。作成・更新・削除・共通順保存の成功時は更新後一覧を含める。参加者の除外・役割変更は自分以外が対象だが、自分の人物対応だけの変更を禁止するものではない。

一覧の人物データは`personId`・`name`・`validFrom`・`validTo`・共通順・人物の`revision`を返す。人物とアカウントの全対応を全参加者に公開する必要はなく、通常表示で必要な本人の人物IDだけをログインアカウントから求める。

人物の作成・更新・削除・共通順保存では、更新後の人物一覧を同じ成功応答に含めることを確認済み（DEC-080）。参加者の更新・除外でも、操作者が管理者のままなら更新後の参加者一覧を同じ成功応答に含める。人物一覧に本人の人物ID・現在の役割・並び順の更新版も含める。一覧の再取得を別のHTTP要求にせず、画面は同じ形式の応答から一覧へ戻れる。更新後一覧の取得もサーバーの同じトランザクション内で行い、確定してから応答する。

人物編集では一覧応答の名前・期間・更新版から入力を始め、編集画面を開くためだけのGETを追加しない（DEC-088）。認証失効後の編集再開では、上記のとおり現在の参加・役割・本人対応を確認するために一覧を取得し、未保存入力と元の更新版を復元する。保存時に最新の参加・権限と更新版を検証する。参加者編集は現在の参加者情報と人物候補を1応答で取得する。この取得でも現在の管理者権限を検証する。

人物保存のPATCHでは項目の省略を「変更しない」、日付の明示的な`null`を「期間制限なし」と区別する。人物の更新版は必須とし、名前だけの更新で日付を意図せず解除しない。参加者保存のPATCHでは人物IDの明示的な`null`を「対応解除」とする。管理者以外の本人は人物の名前だけを送る。

**要求・応答の項目（実装済み）**

上記の9操作で、更新版はDELETEも含めJSON本文の`revision`へ統一し、省略・nullを区別し、エラー応答に種類と表示文を持たせる基本方針は確認済み（DEC-093）。以下の具体的なDTO項目は、既定の権限・通信単位・再送・競合の画面動作に従って整理する。

| 操作 | JSON本文の項目案 |
| --- | --- |
| 人物作成 | `requestId`、`name`、`validFrom`、`validTo`。要求IDと名前は必須。作成時の日付の省略またはnullは、その側の期間制限なし |
| 人物更新 | 必須の`revision`、変更する`name`・`validFrom`・`validTo`。管理者以外の本人は名前だけを送る |
| 人物削除 | 必須の`revision` |
| 共通順保存 | 必須の`revision`（順序全体の版）と`personIds`（現在の全人物IDを設定順で1回ずつ） |
| 参加者更新 | 必須の`revision`、変更する`role`・`personId` |
| 参加者除外 | 必須の`revision` |

更新で省略した項目は変更せず、日付のnullは期間制限の解除、人物IDのnullは対応解除とする（DEC-093）。人物名・役割にnullは認めない。画面の通常保存では編集可能な項目をまとめて送り、役割と人物対応は一括で確定する。省略の扱いを、項目ごとに別々の保存要求を送る意味にはしない。

人物一覧と人物の変更成功応答は、`people`配列・`myPersonId`・`currentRole`・`orderRevision`の共通形式を使う。各人物は`personId`・`name`・`validFrom`・`validTo`・`displayOrder`・`revision`を持つ。API内部とクライアントの操作対象の特定にはIDを使い、利用者への識別用表示には使わない。

参加者一覧と参加者の変更成功応答は`members`配列・`currentAccountId`・`currentRole`を返す。各参加者は`accountId`・`displayName`・`role`・`personId`・`personName`・`personDisplayOrder`・`joinedAtUtc`・`revision`を持つ。本人先頭や人物順・参加順を表示するための情報を同じ応答で返す。参加者編集の取得は`member`と`personCandidates`を返し、人物候補には`personId`・`name`・`isSelectable`を含める。他の参加者に設定済みの人物も選択不可で表示する既定方針に従う。

失敗応答は`code`（機械判定用）と`message`（表示用）を基本とし、必要に応じて該当欄や最新情報を含める方針は確認済み（DEC-093）。項目名は、入力欄を`field`、現在の権限で返せる競合の最新情報を`latest`とする。入力不備400・認証401・権限403・対象不在/未参加404・更新版や一意性等の競合409・既存の回数超過429・保存障害503とする。409の中でも更新版不一致と制約違反を`code`で区別し、既定の画面動作へ分岐する。共通の認証・CSRF・HTTP境界での拒否は既存の応答形式を維持し、各業務処理のエラーと区別する。既存の認証・家計簿APIの応答形式は一括変更していない。
