# 56 新規利用を基本とする導入設計

具体化の案は[58 家計簿のDB・API基盤](58-ledger-foundation-design.md)を参照する。作成時の動作と任意の1対1対応はDEC-046で確定。その他の技術案はレビュー対象であり、機能は未実装。

更新: 2026-10-27。**設計方針を利用者が決定。新規利用の初期化・画面遷移は未実装で、詳細は未確定。** 既存Windows版DBの有無に依存せず、新しく利用を始める場合を基本に設計する。

## 決定した方針

- 通常の利用開始は、新しいアカウント・家計簿を用意し、入力に必要な初期設定を済ませてレシート入力へ進めることを目標にする。次に振替入力を扱う。
- 新規アカウントの登録は、Monetail全体のアカウント管理者（`Admin`ロール）からの招待を必須にする。家計簿の管理者であることだけでは、新規アカウントの登録を招待できない（DEC-038）。
- 家計簿から独立したアカウント一覧は全体管理者だけが参照し、そこから新規登録の招待を発行する。家計簿は、ログイン可能な登録利用者全員が作成できる（DEC-039）。
- 家計簿への参加は、その家計簿の管理者による招待から行う。家計簿の管理権限では相手のアカウントを一覧・検索・存在照会する機能を提供せず、招待を受け取った本人がログインして参加を確定する（DEC-039）。
- アカウントと人物は別の概念・管理対象とする。認証・家計簿への参加と、明細対象者等の人物を同一視しない。アカウントはMonetail全体、参加と権限・人物・業務マスタは家計簿ごとに管理する（DEC-040、[57 所属の区分](57-ledger-data-ownership.md)）。アカウントと人物は家計簿ごとに任意で対応付け、人物の登録・選択をアカウント登録・ログイン・家計簿作成の前提にしない。表示名は別管理とし、入力・更新者はログインアカウントで記録する（DEC-044）。
- DBはSQLite 1ファイルとし、家計簿ごとの人物・業務マスタ・取引の所属を家計簿IDで区別する。家計簿データを扱うAPIで参加と操作権限を確認して読み書きする（DEC-041）。
- 既存DBからの移行は、今回の利用者に対する一度きりの運用作業とする。必要最小限の手順・専用スクリプトで対応し、汎用のインポート画面・常設APIを製品要件にしない。新規利用の設計を移行の都合に合わせない。
- 移行後の通常運用には移行専用の入口を残さない。既存DBをそのまま引き継げるか、差分の適用が必要かは新構成を決めてから判断する。
- 今後のバージョン更新に必要なDBスキーマ更新は維持する。一度きりのデータ移行、バックアップ、復元後の認証リセットとは別の処理として扱う。
- 移行時も既存の人物・取引・対象者の関係と保存値を保持し、保存済み`receipt.total`を再計算・補完しない。

## 現在の実装との差

| 対象 | 現在の実装 | 新規利用に向けた設計課題 |
| --- | --- | --- |
| Docker Compose | 既定は`/health`だけを提供し、DBの作成・移行を自動実行しない | 初期準備と利用開始の手順を定義する |
| DB | `migrate-auth-db`は既存DBへの認証テーブル追加用で、未存在ファイル・空DBを拒否する | 初期設定コマンドで新規DBの準備と最初の管理者用コード発行をまとめる。スキーマ等の詳細は後続 |
| 最初の管理者 | `initialize-admin`で人物を指定せず新規管理者とコードを発行する | 新規利用用の初期設定コマンドと、共通の招待登録画面を接続する |
| 認証・人物 | 初回表示名・パスキー登録・明示ログインを人物なしで実装 | 入力者／更新者の業務保存と家計簿ごとの任意人物対応を設計する |
| アカウント一覧 | アカウント起点の全体管理者専用一覧と、人物不要の登録コード発行APIを実装 | 家計簿から独立した全体管理者専用のアカウント一覧と登録招待の画面を設計する |
| 家計簿・初期設定 | 家計簿作成・参加先選択・Webマスタ設定・業務入力は未実装 | 全利用者による作成、家計簿管理者による参加招待と入力開始までの遷移を具体化する |

人物に依存しない認証・表示名・一覧・発行は[43](43-passkey-authentication-design.md)まで実装した。空DBの初期化や家計簿作成まで実装済みとは扱わない。新規DBは明示的な初期設定コマンドで準備し、Dockerの通常起動だけで初期化・移行する仕様にはしない。招待なしの公開アカウント登録は採用しない。

## アカウント一覧と家計簿の管理

| 操作 | 担当・対象 |
| --- | --- |
| 全体のアカウント一覧を参照 | システム全体のアカウント管理者だけ。家計簿未参加のアカウントも対象 |
| 新規アカウントの登録を招待 | 全体管理者がアカウント一覧から行う。家計簿の参加者画面には新規アカウント登録の招待入口を置かない |
| 家計簿を作成 | ログイン可能な登録利用者全員 |
| 家計簿への参加を招待 | その家計簿の管理者。全体のアカウント一覧・検索・存在照会による相手の選択や直接追加は行わない |

家計簿は閲覧者・編集者・家計簿管理者の3権限とする。招待された人は閲覧者として参加し、入力・編集を自動的に許可しない。家計簿管理者が編集権限を付与し、参加者の招待・除外・権限変更を行う。支払方法の編集は、管理者は他人のものも可能、編集者は自分のものだけとする。振替は移動元・移動先の両側の編集権限を確認する。「自分」は家計簿ごとの任意のアカウント→人物→支払方法の対応で判定し、対応は家計簿管理者が設定する（DEC-043・044、[57 操作権限](57-ledger-data-ownership.md)）。

アカウント一覧は家計簿の参加者一覧や人物一覧とは別に扱う。現在の[51 一覧API](51-admin-account-list.md)はアカウント起点。Web管理画面は後続とする。

家計簿に参加していないアカウントと、ログインしない名前だけの人物を別々に扱う。アカウントと人物を表示名で照合して自動的に同一人物とみなさない。人物・支払方法・分類などの業務マスタは家計簿ごとに管理し、別の家計簿の同名データを自動的に共有しない。アカウントと人物の対応は家計簿ごとの任意設定とし、表示名は独立して管理する（DEC-044）。人物に依存しない認証と初回表示名入力は実装した（DEC-045）。家計簿側の任意対応は未実装。

表示名は初回登録で前後の空白を除き、空白のみ不可・100文字以内・同名可。復旧では保存済み名を維持する。アカウントは独立して新規作成し、既存人物名のコピーや名前一致による対応は行わない（DEC-045）。

家計簿作成は名前だけを入力し、作成者を家計簿管理者にする。人物・支払方法は自動作成しない。人物対応は家計簿内で双方0〜1の任意の1対1とし、親の管理者アカウントと子供だけの人物登録も可能とする（DEC-046）。

## 管理者の招待によるアカウント登録

最初の全体管理者はサーバー側の初期設定コマンドと招待登録画面で用意する。以降の利用者は、全体管理者がアカウント一覧から発行した招待を受けて登録する。招待されたことだけを理由に`Admin`ロールを付与せず、通常の招待登録は一般アカウントとする。家計簿の管理権限は別に扱う。

ログイン画面には「パスキーでログイン」と「招待コードで登録」の入口を用意する。未登録の人は「招待コード入力 → 名前・パスキー登録 → 明示ログイン」と進む。コード入力だけで登録や家計簿への参加を確定せず、本人の登録成功後に利用可能とする。表示名から既存アカウントの有無を判断したり、同じ名前の人物へ自動で紐付けたりしない。

画面の表示制御だけでなく、登録APIでも有効な招待コードを要求する。コードは期限付き・1回限りとし、具体的な有効期間と失効・再発行の扱いは後続設計で決める。現在の登録コードは[45](45-initial-admin-enrollment.md)の10分・1回限りの実装であり、新しい招待の有効期間を同じと決めたものではない。

| 招待の目的 | 権限と扱い |
| --- | --- |
| 新規アカウントの登録 | システム全体のアカウント管理者が発行する。登録の完了は家計簿への参加を意味しない |
| 家計簿への参加 | その家計簿の管理者が招待する。招待発行時に相手のアカウントの有無を照会しない。アカウント登録の招待とは分ける |

既存アカウントの利用者はログインして家計簿への参加を確認する。未登録者を家計簿へ参加させる場合は、先に全体管理者の登録招待を受けてアカウント登録・ログインを済ませ、その後に参加を確定する。家計簿への参加招待だけで、新規アカウントの登録を許可しない。

家計簿管理者はアカウントの有無を調べずに参加招待を渡せるようにする。招待の渡し方・対象との結び付け・期限・取消と再発行・登録やログインを挟んだ参加操作の再開方法は後続設計とし、招待を所持するだけで参加済みにしない。

現在の[54 一般アカウント発行](54-admin-account-creation.md)は、管理者が先に人物と独立した無効アカウントとコードを作る。本人の表示名・パスキー登録成功まで利用可能にしない（DEC-045）。必要な家計簿での任意の人物対応は後続機能とする（DEC-044）。

## 初回のDB準備と最初の全体管理者

次の基本導線は利用者確認済み（DEC-039）。Docker起動後、初期設定コマンドでDB準備と最初の管理者用コード発行をまとめて行う。既存Windows版DBの用意を前提にしない。

1. サーバー側で初期設定コマンドを実行し、必要なDBを用意する。
2. 最初の全体管理者を登録する専用コードを表示する。通常の一般アカウント用招待とは用途を区別する。
3. 本人が、2人目以降と共通の「招待コードで登録」画面でコード・名前を入力し、パスキーを登録する。
4. 登録完了後に明示的にログインし、家計簿の用意・初期設定へ進む。

再実行時は初期設定済みの管理者を上書きせず終了し、登録前の期限切れコードはサーバー側から同じ初期登録対象へ再発行する案を維持する。具体的な再実行・再発行と失敗からの再開方法は後続設計とする。登録済みの管理者やパスキーを、初期設定の再実行で作り直したり失効させたりしない。

現在の`initialize-admin`も人物を指定せず新規アカウントとコードを発行し、初回登録で本人が表示名を入力する（DEC-045）。新規空DBの準備までまとめる動作は未実装。初期DBのスキーマ・初期設定コマンドの具体形と失敗時の再開は後続設計とする。

## 次に詰める画面と状態

基本の流れは「Docker起動 → 初期設定コマンドでDB準備・最初の管理者用コード発行 → 共通画面で登録 → 明示ログイン → 家計簿作成または全体管理者としてアカウント招待」とする。家計簿の入力開始は「家計簿の用意 → 入力に必要な初期設定 → 家計簿ホーム → レシート入力」とし、以降の利用者は全体管理者の登録招待と家計簿管理者の参加招待を使う。画面のURL・自動遷移等の詳細は未確定。

| 設計対象 | 確認すること |
| --- | --- |
| 新規導入 | 初期設定コマンド名、空DBのスキーマ、アカウント等の作成順と失敗時の再開 |
| 家計簿の用意 | 全利用者が作成可能。未参加・1件参加・複数参加の場合の遷移。名前のみの作成と作成者の管理者参加はDEC-046で確定 |
| 人物・利用者追加 | 家計簿ごとの任意の人物対応と設定手順、各表示名と入力者／更新者の保存項目、家計簿招待の受取・参加操作 |
| 初期設定 | 入力開始に必須のマスタ、初期データの有無、設定途中の再開方法。店舗マスタ未登録での入力は維持する |
| 通常利用 | ログイン後の行き先、家計簿の切替、設定から入力画面へ戻る経路 |

同じアカウントの複数家計簿への参加と、家計簿ごとの管理者を認める既存方針は維持する。人物・業務マスタは家計簿ごとの所属とする（DEC-040）。保存はSQLite 1ファイル・家計簿IDによる区分とする（DEC-041）。アカウントと人物の対応は家計簿ごとの任意設定とする方針が確定した（DEC-044）。具体的なスキーマ・認証等の改修手順・表示名と入力者／更新者の保存項目・初版で提供する家計簿分割の範囲は後続設計とする。アカウント管理の`Admin`ロールを家計簿の管理権限へ自動的に読み替えない。仕様の推測が必要な部分は、確認を得るまで実装しない。
