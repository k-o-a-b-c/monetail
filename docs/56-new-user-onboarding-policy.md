# 56 新規利用を基本とする導入設計

更新: 2026-10-26。**設計方針を利用者が決定。新規利用の初期化・画面遷移は未実装で、詳細は未確定。** 既存Windows版DBの有無に依存せず、新しく利用を始める場合を基本に設計する。

## 決定した方針

- 通常の利用開始は、新しいアカウント・家計簿を用意し、入力に必要な初期設定を済ませてレシート入力へ進めることを目標にする。次に振替入力を扱う。
- 新規アカウントの登録は、Monetail全体のアカウント管理者（`Admin`ロール）からの招待を必須にする。家計簿の管理者であることだけでは、新規アカウントの登録を招待できない（DEC-038）。
- 既存DBからの移行は、今回の利用者に対する一度きりの運用作業とする。必要最小限の手順・専用スクリプトで対応し、汎用のインポート画面・常設APIを製品要件にしない。新規利用の設計を移行の都合に合わせない。
- 移行後の通常運用には移行専用の入口を残さない。既存DBをそのまま引き継げるか、差分の適用が必要かは新構成を決めてから判断する。
- 今後のバージョン更新に必要なDBスキーマ更新は維持する。一度きりのデータ移行、バックアップ、復元後の認証リセットとは別の処理として扱う。
- 移行時も既存の人物・取引・対象者の関係と保存値を保持し、保存済み`receipt.total`を再計算・補完しない。

## 現在の実装との差

| 対象 | 現在の実装 | 新規利用に向けた設計課題 |
| --- | --- | --- |
| Docker Compose | 既定は`/health`だけを提供し、DBの作成・移行を自動実行しない | 初期準備と利用開始の手順を定義する |
| DB | `migrate-auth-db`は既存DBへの認証テーブル追加用で、未存在ファイル・空DBを拒否する | 空の状態から業務・認証の保存先を用意する方法を決める |
| 最初の管理者 | `initialize-admin`で既存人物を明示し、登録コードを発行する | 既存人物のいない状態で、最初の人物・アカウントを用意する方法を決める |
| 認証 | コード入力・パスキー登録・明示ログインを実装し、人物との対応を必須にする | 家計簿を作る前後の人物・アカウントの作成順を決める |
| 家計簿・初期設定 | 家計簿作成・参加先選択・Webマスタ設定・業務入力は未実装 | 利用者の状態ごとの画面と必要な操作を定義する |

この方針記録だけでは現在のコマンド・DB制約・認証条件・Compose設定を変更しない。自動DB作成・自動移行の採否は未確定。招待なしの公開アカウント登録は採用しない。

## 管理者の招待によるアカウント登録

最初の全体管理者はサーバー側で用意する。人物のいない状態から初期管理者を作成する方法は、引き続き設計対象とする。以降の利用者は、全体管理者が発行した招待を受けて登録する。招待されたことだけを理由に`Admin`ロールを付与せず、通常の招待登録は一般アカウントとする。家計簿の管理権限は別に扱う。

ログイン画面には「パスキーでログイン」と「招待コードで登録」の入口を用意する。未登録の人は「招待コード入力 → 名前・パスキー登録 → 明示ログイン」と進む。コード入力だけで登録や家計簿への参加を確定せず、本人の登録成功後に利用可能とする。表示名から既存アカウントの有無を判断したり、同じ名前の人物へ自動で紐付けたりしない。

画面の表示制御だけでなく、登録APIでも有効な招待コードを要求する。コードは期限付き・1回限りとし、具体的な有効期間と失効・再発行の扱いは後続設計で決める。現在の登録コードは[45](45-initial-admin-enrollment.md)の10分・1回限りの実装であり、新しい招待の有効期間を同じと決めたものではない。

| 招待の目的 | 権限と扱い |
| --- | --- |
| 新規アカウントの登録 | システム全体のアカウント管理者が発行する。登録の完了は家計簿への参加を意味しない |
| 家計簿への参加 | 家計簿側の管理権限で扱い、アカウント登録の招待とは分ける。参加条件と具体的な操作は後続設計で決める |

既存アカウントの利用者はログインして家計簿への参加を確認する。未登録者を家計簿へ参加させる場合は、先に全体管理者の登録招待を受けてアカウント登録・ログインを済ませ、その後に参加を確定する。家計簿への参加招待だけで、新規アカウントの登録を許可しない。

現在の[54 一般アカウント発行](54-admin-account-creation.md)は、管理者が先に無効アカウントと人物対応を作る実装である。新しい招待登録でのDB行の作成時点と人物との対応方法は未確定で、画面上の登録完了とDB行の先行作成を混同しない。

## 次に詰める画面と状態

検討する流れは「サーバーの初期準備 → 最初の利用者の登録・ログイン → 家計簿の用意 → 入力に必要な初期設定 → 家計簿ホーム → レシート入力」とする。以降の利用者は、全体管理者の招待を受けて登録する。画面のURL・自動遷移・家計簿の作成権限は未確定で、この並びをそのまま実装仕様にはしない。

| 設計対象 | 確認すること |
| --- | --- |
| 新規導入 | 空DBの初期化、最初の人物と管理者の作成順、既存のコード発行・パスキー登録の接続 |
| 家計簿の用意 | 作成できる人、未参加・1件参加・複数参加の場合の遷移、家計簿作成者と管理者の関係 |
| 人物・利用者追加 | アカウント登録の招待は全体管理者に限定。名前だけの人物との対応、家計簿の参加先・権限を設定する具体的な操作 |
| 初期設定 | 入力開始に必須のマスタ、初期データの有無、設定途中の再開方法。店舗マスタ未登録での入力は維持する |
| 通常利用 | ログイン後の行き先、家計簿の切替、設定から入力画面へ戻る経路 |

同じアカウントの複数家計簿への参加と、家計簿ごとの管理者を認める既存方針は維持する。DB方式・人物やマスタの共有範囲・初版で提供する家計簿分割の範囲は今回確定しない。アカウント管理の`Admin`ロールを家計簿の管理権限へ自動的に読み替えない。仕様の推測が必要な部分は、確認を得るまで実装しない。
