# APIの配備・運用（共通要件）

monetail APIは特定のVPN、DNSサービス、サーバー製品、コンテナ構成に依存しない。接続手段は運用環境で選択する。APIの起動設定と管理コマンドの正本は[42 APIの起動・設定・運用](42-api-foundation.md)、認証仕様は[認証・パスキー](auth-passkeys.md)および[Windows OAuth](auth-windows-oauth.md)を参照する。

## 通信・認証

```text
Windows / ブラウザー / 将来のスマートフォン
           │ HTTPS（固定オリジン）
           ▼
    HTTPS終端（リバースプロキシ等）
           │ HTTP（アクセス制限された経路）
           ▼
       monetail API
           │
           ▼
       永続データベース
```

これは構成の一例であり、API自身にHTTPSを終端させる構成も妨げない。**クライアントとの認証通信はHTTPS**とし、公開するURLを`Passkeys:Origin`に固定、`Passkeys:RpId`にはそのDNSホスト名を指定する。WinUIの接続先も同じHTTPSオリジンにする。

- リバースプロキシを使う場合、`Passkeys:TrustedProxies`には**実際の直前のプロキシIPだけ**を指定する。未知の転送元からの`X-Forwarded-*`ヘッダーを信用しない。HTTPS終端で必要なホスト・プロトコル情報が正しくAPIへ渡ることを確認する。
- HTTPで待ち受けるAPIポートは、信頼するプロキシだけが到達できるようにする。同一ホストの場合は`127.0.0.1`へのバインドやループバック限定のポート公開を利用できる。他ホスト・別Dockerネットワークの場合は接続元と公開範囲を個別に設計する。`0.0.0.0`への無条件公開はしない。
- TLS証明書の発行・更新、DNS、VPNやファイアウォールは配備環境側で管理する。特定のVPN製品やクラウドサービスはアプリの必須条件ではない。
- 認証・アカウント権限はネットワークアクセス制御とは別に必須。匿名登録の公開可否や運用条件は認証仕様に従う。

## 永続化・初期化・更新

- SQLiteのDB、Data Protectionキー、OAuthの署名・暗号化PFXと読込設定をコンテナ外に永続化し、秘密値をリポジトリや通常ログへ入れない。SQLiteファイルにはロック可能なローカルストレージを使う。
- `initialize-db`は**初回と既知のDB追加移行時に明示実行**する。通常のAPI起動でDBを自動作成・変更しない。`initialize-admin`は初回管理者の作成時だけ実行する。
- 更新前はAPIを停止してDB・キー・PFXを一貫してバックアップする。DB移行が必要ならリリース手順に従う。新イメージへの交換とDB移行は別操作であり、古いAPIへの単純なロールバックは保証されない。
- `GET /health`の`200 Healthy`はHTTP応答の確認にとどまる。HTTPSの認証メタデータ、パスキー登録・ログイン、WinUIのOAuth接続、データ保持は別途検証する。

## 配備例

- [Dockerサーバー + 別管理のTailscale Serve](deployment-examples/docker-tailscale.md)：既存の同一サーバー上のHTTPS転送を使い、GHCRのAPIイメージを配備する**具体例**。Tailscaleはmonetailの必須要件ではなく、別のHTTPS終端を採用してもよい。

配備例の`127.0.0.1:8080`、Docker hostネットワーク、固定ディレクトリは**その環境に固有の値**。別のネットワーク構成へ流用するときは、転送元IP・待受アドレス・秘密ファイル権限を再評価する。
