# 明細単位の税率・対象外と分類グループの統一設計

状態: **利用者方針を反映した設計案・製品とDBへの実装は未着手**。2026-10-21。LEG-042／DEC-025。

既存・新規の全レシートを同じモデルと計算経路に移す。参考集計の端数差は許容し、旧データ専用モードは設けない。[39](39-classification-tax-groups.md)の同分類・複数税率グループは現行実装の記録として残し、本設計の実装後は分類だけで1グループに統合する。

## 1. 方針と未決定点

- 税率の正本は各明細の確定した税率コード。グループは分類とメモを持つ。
- 「対象外」を税率と同じ選択欄へ統合する。0%課税と対象外はマスタの属性で区別する。
- 同じレシート・分類は既存分も含め1グループ。税率の違いではグループを分けない。
- 分類・個人・グループ・明細の参考集計は、過去分も新しい粒度で再計算する。旧参考額との一致は受入条件にしない。
- 会計は明細を税率値ごとに合算してから各レシートの端数方式を適用する。分類によって分割しない。
- 複数の税率区分と適用履歴は初期選択に使う。保存済みの明細へ適用履歴を遡及適用しない。

**支払合計の互換性は未解決**。対象外の独立集計と従来Double式の組合せでは、会計合計にも1円差が出る反例がある（第4節）。参考額の差を許容する決定を、会計差も許容する決定と解釈しない。新旧で処理を分けずにどの会計ルールへ統一するかは、この差の扱いを決めてから確定する。

## 2. 保存モデル案

| 対象 | 移行後の役割・制約 |
| --- | --- |
| `m_tax_rate` | 既存`code`・`rate`を維持し、`tax_treatment`を追加。`taxable`／`out_of_scope`を区別。対象外行の`rate`は0、0%課税は`taxable`の別コード。既存コードの税率値を書き換えない |
| `t_receipt_details` | 必須`tax_code`から`m_tax_rate.code`を参照。旧`tax_target`を置き換える。単価・数量・値引・名称・メモ・対象者は維持 |
| `t_receipt_groups` | 分類・メモを保持し、`UNIQUE(receipt_seq, group_classification_code)`を設ける。旧`tax`は廃止 |
| `m_tax_category` | 追加可能な税率区分のコード・名称。通常・食品・その他軽減・対象外など。区分数やコードを計算へ固定しない |
| `m_group_classification` | `default_tax_category_code`で初期値用の区分を参照。旧`default_tax_target`・`reduced_tax_target`を置き換える |
| `m_tax_rate_rule` | `(tax_category_code, start_date)`を主キーとし、適用する`tax_code`を参照。同一区分で開始日が重複しない。日付はISO形式の年月日に正規化 |

`tax_treatment`は計算上の扱い、`tax_category`は初期値選択の分類であり、役割が異なる。将来の法制度を確定したものではなく、食品1%・その他8%・通常10%は設定可能性を示す例である。

適用日の正本は`m_tax_rate_rule.start_date`とする。既存`m_tax_rate.start_date`は移行資料・既存値保持のため当面残し、初期選択には使わない。税率候補の`code >= 4`という固定フィルタは廃止し、参照コードを欠落させない。

## 3. データ移行案

1. 元DBを閉じた状態のコピーで検証する。元の接続FK設定・スキーマ・版・全行と、現行コードによる会計・収支・参考額を記録する。保存済み`t_receipts.total`と現在の再計算値の既存不一致も分けて報告する。
2. 対象外用コードは固定の空き番号を仮定せず、既存マスタを確認して採番する。旧税率行は`taxable`として値を維持し、旧`rate=0`を対象外へ読み替えない。課税明細の親税率コードが不明なら移行を中止し、率から推測しない。
3. 課税明細には旧親グループの税率コードをコピーする。非課税明細には対象外コードを設定する。税率区分や移行時の日付から既存明細の率を再選択しない。
4. `(receipt_seq, group_classification_code)`ごとにグループを統合する。統合先の`seq`は元の最小値とし、空グループも同分類があれば統合する。分類そのものを税率から変更しない。
5. 明細は元の`group_seq, seq`順に全件保持して統合先で1から採番する。旧→新の複合キー対応表を作り、`t_receipt_detail_users`の全割当を同じ対応で移す。異なる元明細の同じ番号・名称・対象者を重複として削除しない。
6. グループが1つならメモのNULL・空文字を含む元値を保持する。複数グループなら、空でない各メモを元seq順に1からの連番で`【統合元 <番号>】`と改行を付けて連結し、内容・空白・重複文を保持する。全てNULLならNULL、それ以外に有効なメモがなければ空文字とする。明細・ヘッダーのメモは変更しない。
7. 初期値用の区分は、旧課税対象初期値が偽なら対象外、真なら旧軽減フラグに応じた通常／既存軽減へ対応付ける。「食品」等への細分は名称から推測せず、分類ごとの対応を確認する。実際の適用開始日は実マスタと運用確認から決め、未確定の1%期間等を登録しない。
8. SQLite 3.32で動作するテーブル再構築を設計する。FK設定を記録し、接続でFKを一時無効化してから`BEGIN IMMEDIATE`。中間表と対応表へ全件生成し、子から旧表を置換、最終名への参照を持つ新表へ切り替える。件数・制約・`foreign_key_check`・検証値を確認してCommitする。失敗はDDLを含めRollbackし、トランザクション外で元のFK設定を必ず復元する。`DROP COLUMN`が使える版を前提にしない。
9. レシートID・日時・店舗・支払方法・内税／外税・端数方式・更新版、振替・残高・支払メモ・ポイントを保持する。グループ／明細と対象者割当のキーだけを対応表に従って変更する。移行状態を記録して再適用を拒否する。

旧列を使うアプリと移行後アプリを同時運用しない。旧列は検証中の作業領域に保持し、完了スキーマから整理する。実行時に旧列へフォールバックする経路やレシートごとの旧方式フラグは追加しない。

## 4. 会計と参考集計

明細の値引計算`(fee - discount_fee) × quantity - Ceiling(基礎金額 × discount_rate / 100)`、収支の符号判定、内税／外税とレシートごとの端数方式は引き継ぐ。

統一計算の候補は、課税明細を税率値で合算して現行の`TaxRateSubtotal(T, 0, rate, ...)`を適用し、対象外明細の金額を別に加える方式。同率の別コードは合算し、0%課税と対象外はモデル上区別する。

ただし現行floorは`Floor(Double(T × (1 + rate / 100) + N))`であり、対象外金額`N`も丸め前に含む。**10%課税−100円＋対象外1,000円**の例では次の差になる。

| 計算 | 会計合計 |
| --- | ---: |
| 現行：`Floor(-100 × 1.1 + 1000)` | 890円 |
| 候補：`Floor(-100 × 1.1) + 1000` | 889円 |

Doubleの−100×1.1は−110をわずかに下回る一方、1,000加算後は890に表現されるためである。現行の890円、収入−111円・支出1,000円を製品コードの既存`LegacyFloorSnapshots`チェックへ固定例として追加する。候補の889円を採用済みの期待値とはしない。

Decimalへ全体を変更するだけでも解決しない。課税−100円のみの現行floorは−111円で、Decimalの税額切捨では−110円になる。**会計端数差も許容して統一するか、支払額の保存・計算の役割を見直して保持するか**を利用者と確認する。比較差を自動補正する隠し明細や、旧レシートだけの特例は設けない。

参考集計は、対象の明細を従来の人選択・一致条件・人数按分で抽出してから、分類内の税率値ごとに合算・丸める。対象外は対象外として加算する。明細単位の参考額も同じ明細税設定から計算する。同分類グループ統合による40円→41円等の差は許容する。按分条件や金額範囲超過の扱いを無断で別仕様に変えない。

## 5. 初期選択と画面

- 区分内で`start_date <= レシート日.Date`の最新行を選び、その税率コードを新規明細の初期値とする。終了日は次行の開始日で決まり、開始日当日を含む。適用行なしは未選択として追加を止める。
- A=8%→B=1%→C=8%ではCから既存8%コードを再利用できる。区分ごとに開始日を持ち、食品だけの期間変更も設定できる。
- 分類の区分は初期値用であり、別税率の手動選択を禁止しない。保存済み明細の表示・分類変更・日付変更だけで確定税率を上書きしない。未反映入力と明示選択も保持する。
- グループ側の税率欄を明細側へ移し、課税チェックを同じ選択欄へ統合する。選択肢は10%・8%・対象外など。新たなマスタメンテナンス画面は作らない。
- グループ一覧は分類名のみ。明細一覧では分類・日付から初期選択される税設定を標準とし、異なる場合だけ税率／対象外を付記する。同率コードは同じ表示、0%課税と対象外は別表示とする。
- 分類だけで重複追加を防ぎ、別の既存分類へ変更すると統合する。その際も各明細の税率を保持し、メモは同じ引継ぎ方針で扱う。
- 確認後すぐ保存する流用、レシートの税設定を確認後に反映する方式、オーケーの手入力値引は維持する。全Receiptのディープコピーは導入しない。

## 6. 実装順と受入確認

1. 会計差の許容範囲を決め、[比較ケース](tests/detail-tax-migration-cases.json)と現行の製品計算による期待値を確定する。
2. コピーDBの移行を実装し、FK ON/OFF、対象者複合キー、同分類統合、NULL／メモ、空グループ、採番衝突、途中失敗・再適用・同じ接続での復帰を検証する。
3. モデル・全読込／保存・会計／参考集計・残高推算・一覧／詳細／登録画面をまとめて明細税率へ切り替える。一覧・支払方法別の1 SELECTを維持する。起動時は移行済み構造を必須とする。
4. 初期値用の区分・適用履歴と明細の標準表示を実装する。DB移行とアプリ切替の完了時点では旧列依存を残さない。

実装作業を分割しても、利用開始時は過去・新規とも同じ完了仕様とする。内部の作業順は運用時の新旧併用を意味しない。

比較では移行直前の製品再計算値と移行後の値を照合し、保存済みtotalとも別途照合する。会計・収支の差は未決定のまま通さず、参考額の旧値との差は許容する。明細金額・対象者の集合、メモ内容と順序、他機能の全行保持を確認する。期間データの未確定と会計差の判断が残るため、本設計だけで実DB移行を開始しない。
