# 明細単位の税率・対象外と分類グループの統一設計

状態: **コピーDB移行とWindowsアプリ切替を実装、Windows自動検証済み、手動確認と実期間確認は未完了**。2026-10-22。LEG-042／DEC-025／DEC-026。[41 実装と実行方法](41-detail-tax-copy-migration.md)。

既存・新規の全レシートを同じモデルと計算経路に移す。参考集計の端数差は許容し、旧データ専用モードは設けない。[39](39-classification-tax-groups.md)の同分類・複数税率グループは現行実装の記録として残し、本設計の実装後は分類だけで1グループに統合する。

## 1. 採用方針

- 税率の正本は各明細の確定した税率コード。グループは分類とメモを持つ。
- 「対象外」を税率と同じ選択欄へ統合する。0%課税と対象外はマスタの属性で区別する。
- 同じレシート・分類は既存分も含め1グループ。税率の違いではグループを分けない。
- 分類・個人・グループ・明細の参考集計は、過去分も新しい粒度で再計算する。旧参考額との一致は受入条件にしない。
- 会計は明細を税率値ごとに合算してから各レシートの端数方式を適用する。分類によって分割しない。
- 複数の税率区分と適用履歴は初期選択に使う。保存済みの明細へ適用履歴を遡及適用しない。

**Decimalによる統一計算を採用する方針が利用者により確定した**。10%課税−100円＋対象外1,000円は890円を保ち、Doubleの二進誤差は引き継がない。過去分も新しい十進計算へ移し、旧Doubleの誤差で−111円になっていた課税−100円単独は−110円へ修正する。旧値の無条件一致ではなく、移行前の明細から独立に求めた新Decimal期待値との一致を受入条件にする。差は全件報告し、隠し補正や旧データ専用モードを設けない。

## 2. 保存モデル案

| 対象 | 移行後の役割・制約 |
| --- | --- |
| `m_tax_rate` | 既存`code`・`rate`を維持し、`tax_treatment`を追加。`taxable`／`out_of_scope`を区別。対象外行の`rate`は0、0%課税は`taxable`の別コード。既存コードの税率値を書き換えない |
| `t_receipt_details` | 必須`tax_code`から`m_tax_rate.code`を参照。旧`tax_target`を置き換える。単価・数量・金額値引・名称・メモ・対象者は維持。割引率はDecimal値をInvariantCultureの文字列にしてSQLiteのTEXTで正確に保持 |
| `t_receipt_groups` | 分類・メモを保持し、`UNIQUE(receipt_seq, group_classification_code)`を設ける。旧`tax`は廃止 |
| `m_tax_category` | 追加可能な税率区分のコード・名称。通常・食品・その他軽減・対象外など。区分数やコードを計算へ固定しない |
| `m_group_classification` | `default_tax_category_code`で初期値用の区分を参照。旧`default_tax_target`・`reduced_tax_target`を置き換える |
| `m_tax_rate_rule` | `(tax_category_code, start_date)`を主キーとし、適用する`tax_code`を参照。同一区分で開始日が重複しない。日付はISO形式の年月日に正規化 |

`tax_treatment`は計算上の扱い、`tax_category`は初期値選択の分類であり、役割が異なる。将来の法制度を確定したものではなく、食品1%・その他8%・通常10%は設定可能性を示す例である。

適用日の正本は`m_tax_rate_rule.start_date`とする。既存`m_tax_rate.start_date`は移行資料・既存値保持のため当面残し、初期選択には使わない。税率候補の`code >= 4`という固定フィルタは廃止し、参照コードを欠落させない。

## 3. データ移行案

1. 元DBを閉じた状態のコピーで検証する。元の接続FK設定・スキーマ・版・全行と、現行コードによる会計・収支・参考額を記録する。保存済み`t_receipts.total`と現在の再計算値の既存不一致も分けて報告する。さらに元明細から新Decimal計算の期待値を求め、旧値との差と修正理由を記録する。
2. 対象外用コードは固定の空き番号を仮定せず、既存マスタを確認して採番する。旧税率行は`taxable`として値を維持し、旧`rate=0`を対象外へ読み替えない。課税明細の親税率コードが不明なら移行を中止し、率から推測しない。
3. 割引率の旧INTEGER値は正確に変換し、REAL値は往復可能なInvariantCulture文字列を経由してDecimalへ変換する。例えば0.14%は文字列`0.14`として保持し、DB側でREALへ戻らないTEXT列を使う。Decimalで正確に表せない桁数・範囲、非有限値などは事前診断し、0や丸めた値に黙って変換しない。元の入力文字列が残っていない値を推測で修正しない。
4. 課税明細には旧親グループの税率コードをコピーする。非課税明細には対象外コードを設定する。税率区分や移行時の日付から既存明細の率を再選択しない。
5. `(receipt_seq, group_classification_code)`ごとにグループを統合する。統合先の`seq`は元の最小値とし、空グループも同分類があれば統合する。分類そのものを税率から変更しない。
6. 明細は元の`group_seq, seq`順に全件保持して統合先で1から採番する。旧→新の複合キー対応表を作り、`t_receipt_detail_users`の全割当を同じ対応で移す。異なる元明細の同じ番号・名称・対象者を重複として削除しない。
7. グループが1つならメモのNULL・空文字を含む元値を保持する。複数グループなら、空でない各メモを元seq順に1からの連番で`【統合元 <番号>】`と改行を付けて連結し、内容・空白・重複文を保持する。全てNULLならNULL、それ以外に有効なメモがなければ空文字とする。明細・ヘッダーのメモは変更しない。
8. 初期値用の区分は、旧課税対象初期値が偽なら対象外、真なら旧軽減フラグに応じた通常／既存軽減へ対応付ける。「食品」等への細分は名称から推測せず、分類ごとの対応を確認する。実際の適用開始日は実マスタと運用確認から決め、未確定の1%期間等を登録しない。
9. SQLite 3.32で動作するテーブル再構築を設計する。FK設定を記録し、接続でFKを一時無効化してから`BEGIN IMMEDIATE`。中間表と対応表へ全件生成し、子から旧表を置換、最終名への参照を持つ新表へ切り替える。件数・制約・`foreign_key_check`と独立した新Decimal期待値との一致を確認してCommitする。失敗はDDLを含めRollbackし、トランザクション外で元のFK設定を必ず復元する。`DROP COLUMN`が使える版を前提にしない。
10. レシートID・日時・店舗・支払方法・内税／外税・端数方式・入力メモと元の更新者／更新日時、振替・残高・支払メモ・ポイントを保持する。`t_receipts.total`は新Decimal計算値へ更新する。グループ／明細と対象者割当のキーを対応表で移し、変更対象レシートの更新版を更新して旧スナップショットを失効させる。監査用の旧→新対応・旧保存total／旧再計算／新計算と差分を記録し、移行状態により再適用を拒否する。

旧列を使うアプリと移行後アプリを同時運用しない。旧列は検証中の作業領域に保持し、完了スキーマから整理する。実行時に旧列へフォールバックする経路やレシートごとの旧方式フラグは追加しない。

## 4. 会計と参考集計：Decimalで統一

### 数値と保存

レシートの金額・税額・値引率・按分はDecimalで扱い、演算前に整数からDecimalへ変換する。金額計算中にDouble／Single、SQLのREAL演算、暗黙の二進浮動小数変換を挟まない。グラフ表示等のための変換を会計計算へ戻さない。

SQLiteの割引率はTEXTに十進値をInvariantCultureで保存し、Decimalとして読み込む。`INTEGER`／`NUMERIC`宣言に小数文字列を入れるだけではREALへ自動変換されるため不十分。論理型はDecimalとし、別DBでは同等の正確な十進型へ対応できるようにする。税率マスタの整数％、単価・数量・金額値引の整数保存は維持する。

Decimalにも有限精度と範囲がある。入力・移行時に表現可能な桁数と範囲を検証し、収まらない値は診断する。乗除算の途中で暗黙に精度を落とさないことも検証し、必要な端数判定には整数の商・余りによる方法も用いる。受理した値を正確に処理できない場合は診断し、暗黙の丸めで通さない。3人按分のような割り切れない値には、精度と業務上の丸め位置を明示した受入ケースを設ける。意図した端数処理と二進誤差を混同せず、0補正やDoubleへのフォールバックで隠さない。

### 会計の式

1. `B = (Decimal(fee) - discount_fee) × quantity`、`net = B - Ceiling(B × discount_rate / 100D)`で明細金額を求める。割引率のCeilingという業務ルールは維持する。`D`はVBのDecimalリテラルを表す。
2. 課税明細はレシート全体で税率値ごとに`net`を合算する。同率の別コードも合算する。対象外明細は別に合算し、0%課税とはモデル上区別する。
3. 外税・切り捨ては`tax = Floor(T × Decimal(rate) / 100D)`、四捨五入は同じ税額を`Round(..., 0, AwayFromZero)`で丸める。税率ごとの税込額は`T + tax`とする。対象外額を税率の丸め前へ混ぜない。内税では元の`net`合計を使用する。
4. 全税率の税込額と対象外額を加える。収入／支出は従来どおり`net`の符号で抽出して同じ式を使う。Int32への最終変換と範囲超過時の警告・入力保持を維持し、暗黙の銀行丸めに任せない。

負の税額のfloorは数学上の負方向への切り捨てとする。−0.5円はfloorでもhalf_upでも−1円、−10円は−10円のままである。

| 例 | 現行Double | 採用するDecimal |
| --- | ---: | ---: |
| 10%課税−100円＋対象外1,000円、外税floor | 会計890円、収入−111円、支出1,000円 | 会計890円、収入−110円、支出1,000円 |
| 10%課税−100円のみ、外税floor | −111円 | −110円 |
| 10,000円に0.14%値引、対象外 | 値引15円・差引9,985円 | 値引14円・差引9,986円 |

889円は旧Doubleの`Floor(-100 × 1.1) + 1000`による不採用案として履歴に残す。採用式は`-100D + Floor(-100D × 10D / 100D) + 1000D = 890D`。既存の`LegacyFloorSnapshots`等は移行前の事実確認用であり、誤差を将来も維持する契約ではない。比較JSONには採用する十進期待値と旧値を別々に記録する。

### 参考集計

対象の明細を従来の人選択・一致条件・人数按分で抽出してから、分類内の税率値ごとにDecimalで合算・税額を丸める。対象外は対象外として加算する。明細単位の参考額も同じ明細税設定から計算する。最終の参考円額も明示的に丸める。同分類グループ統合による40円→41円等の差は許容し、按分条件そのものは変更しない。過去分もこの新方式で計算する。

## 5. 初期選択と画面

- 区分内で`start_date <= レシート日.Date`の最新行を選び、その税率コードを新規明細の初期値とする。終了日は次行の開始日で決まり、開始日当日を含む。適用行なしは未選択として追加を止める。
- A=8%→B=1%→C=8%ではCから既存8%コードを再利用できる。区分ごとに開始日を持ち、食品だけの期間変更も設定できる。
- 分類の区分は初期値用であり、別税率の手動選択を禁止しない。保存済み明細の表示・分類変更・日付変更だけで確定税率を上書きしない。未反映入力と明示選択も保持する。
- グループ側の税率欄を明細側へ移し、課税チェックを同じ選択欄へ統合する。選択肢は10%・8%・対象外など。新たなマスタメンテナンス画面は作らない。
- グループ一覧は分類名のみ。明細一覧では分類・日付から初期選択される税設定を標準とし、異なる場合だけ税率／対象外を付記する。同率コードは同じ表示、0%課税と対象外は別表示とする。
- 分類だけで重複追加を防ぎ、別の既存分類へ変更すると統合する。その際も各明細の税率を保持し、メモは同じ引継ぎ方針で扱う。
- 確認後すぐ保存する流用、レシートの税設定を確認後に反映する方式、オーケーの手入力値引は維持する。全Receiptのディープコピーは導入しない。

## 6. 実装順と受入確認

1. 採用したDecimal仕様の[比較ケース](tests/detail-tax-migration-cases.json)を正確な十進演算で検証し、旧製品の実値との差を固定する。
2. コピーDBの移行を実装し、FK ON/OFF、対象者複合キー、同分類統合、NULL／メモ、空グループ、採番衝突、途中失敗・再適用・同じ接続での復帰を検証する。
3. モデル・全読込／保存・会計／参考集計・残高推算・一覧／詳細／登録画面をまとめて明細税率へ切り替える。一覧・支払方法別の1 SELECTを維持する。起動時は移行済み構造を必須とする。
4. 初期値用の区分・適用履歴と明細の標準表示を実装する。DB移行とアプリ切替の完了時点では旧列依存を残さない。

実装作業を分割しても、利用開始時は過去・新規とも同じ完了仕様とする。内部の作業順は運用時の新旧併用を意味しない。

比較では移行直前の明細から求めた新Decimal期待値と移行後の値を照合し、旧製品の再計算値・保存済みtotalとの差も全件報告する。旧Double由来の会計差と、グループ統合による参考差は採用仕様に従って説明し、明細欠落等の予期しない差を許容しない。金額入力・対象者の集合、メモ内容と順序、他機能の全行保持を確認する。コピー移行の検証結果は41とtests/READMEを参照。実際の期間データの確認とWindowsの手動確認が残るため、実運用DBの置換は行わない。
