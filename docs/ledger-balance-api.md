# 残高・推算残高API設計

更新: 2026-11-16。**API未実装**。推算残高の一括取得について、確定したGET・成功応答・参照権限と、未決定のエラー詳細・障害復帰などを区別する。

## 1. 確定済みの契約（DEC-331〜347）

- 残高登録・編集画面を開いたとき、または共通登録日を確定変更したときに、1回のAPI要求で**対象日に有効な、同一家計簿内の全支払方法**の推算結果を取得する（DEC-331・340）。今日現在の有効状態ではなく対象日の有効期間で判定。両端包含・NULL端点は無制限。支払方法の所有者で絞らず、本人以外の所有分も含める（DEC-120）。対象0件では空集合。
- 日付変更前の遅い応答を現在の表示に反映しない。画面内での手動再計算・他画面／別端末の取引変更による自動更新はしない（DEC-331〜333）。
- 推算の起点は対象日より前の最新の非NULL登録残高（0円含む）。評価額だけの登録は起点に使わず、評価額を代用しない（DEC-334）。
- レシート・振替は既存Int32金額のまま、推算の累積・結果はInt64。途中の範囲超過は`overflow`とし、他支払方法の結果を欠落させない（DEC-335・336・339）。
- 1支払方法につき**`calculated`・`no_data`・`overflow`の3状態のうち1つ**。成功金額は**正規10進整数のJSON文字列**（`"0"`も可）、ほかの状態の金額はJSON `null`。金額表記・値域はDEC-337・338。
- 推算取得は参照のみ。表示と［反映］の分離、未保存入力保持はDEC-324・325に従う。認証・DB・通信などの全体障害は行状態と区別する（DEC-339）。
- **参照権限はDEC-342で確定**。現在の認証済み家計簿参加者のAdmin・Editor・Viewer全員が取得可能。参照対象は同一家計簿内の対象日有効な全支払方法で、所有人物・本人対応人物で絞らない。閲覧許可は書込権限を付与せず、別家計簿・未参加者には情報を返さない。
- レシート・振替の既存API契約は変更しない。

## 2. 一括GETと応答フィールド（DEC-341・確定／未実装）

**確定APIパス**：`GET /ledgers/{ledgerId}/balance-estimates?date=YYYY-MM-DD`。`date`は必須の正しい暦日を示す`YYYY-MM-DD`で、時刻・UTCオフセットは送らない。

**200 OKの確定応答**：トップレベルは`date`と`estimates`の2フィールドのみ、配列内は`paymentMethodId`・`status`・`amount`の3フィールドのみとする。5項目は必須で省略しない。状態と金額の組合せはDEC-339に従う。

```json
{
  "date": "2026-11-16",
  "estimates": [
    {
      "paymentMethodId": "11111111-1111-4111-8111-111111111111",
      "status": "calculated",
      "amount": "125000"
    },
    {
      "paymentMethodId": "22222222-2222-4222-8222-222222222222",
      "status": "no_data",
      "amount": null
    },
    {
      "paymentMethodId": "33333333-3333-4333-8333-333333333333",
      "status": "overflow",
      "amount": null
    }
  ]
}
```

サンプルのUUIDと金額は説明用の架空値。

| キー | JSON型 | 規則 |
| --- | --- | --- |
| `date` | 文字列（必須） | 要求した対象日を`YYYY-MM-DD`でエコーする。日付変更の古い応答を識別するために利用 |
| `estimates` | 配列（必須） | 対象日に有効な全支払方法を含む。0件なら`[]`、ページングなし |
| `paymentMethodId` | UUID D形式の文字列（必須） | 配列内の支払方法を一意に識別。1IDにつき1件 |
| `status` | 文字列（必須） | `calculated`・`no_data`・`overflow`のみ |
| `amount` | 文字列または`null`（必須） | `calculated`なら正規のInt64金額文字列。`no_data`・`overflow`なら`null` |

- **APIの`estimates`配列順序は保証しない**（DEC-345）。WinUIは配列順に依存せず、`paymentMethodId`で対象行へ結果を対応付け、既存の支払方法・人物マスタキャッシュから名称・所有者・表示順を解決する。表示は本人の所有分を優先し、その後は人物マスタの共通順、各人物の支払方法は`display_order ASC, payment_method_id ASC`（DEC-118・132）。
- 明細、レシート、振替、登録済み残高や評価額、計算根拠、支払方法名・人物名はこの推算レスポンスに**含めない**。対象日・ID・状態・金額だけを返し、ページングや次ページカーソルは設けない。
- **未決定**：確定したHTTPステータス以外のエラー応答詳細、障害復帰。**GETパス・必須`date`・成功200の5項目はDEC-341、参照権限はDEC-342、401／404／400の基本エラーはDEC-343、全行同一DBスナップショットはDEC-344、配列順序の非保証とWinUI表示順はDEC-345で確定済み**。

## 3. 参照権限（DEC-342・確定／未実装）

- **現在の認証済み家計簿参加者であるAdmin・Editor・Viewer全員が利用可能**。Viewerも参照できるが、残高登録・編集・削除の権限は一切追加しない。
- **本人に対応する人物の有無、支払方法の所有人物、レシート・振替の作成者による結果の絞り込みはしない**。参照できるのはあくまで要求した家計簿内の、推算対象日に有効な全支払方法の結果（DEC-340）。
- **API要求のたびに認証と当該家計簿への現在の参加資格を確認**する。確認時期は[共通HTTP境界・認可](ledger-core-api.md#共通http境界認可)に従う。未参加者・参加失効者は参照できず、全体管理者であっても家計簿への参加を迂回できない。家計簿IDを検索・結合・キャッシュの境界にし、他家計簿の情報を混ぜない。
- 認証なし・失効時は**HTTP 401**、対象家計簿が存在しない・未参加・参加失効時は**HTTP 404**（DEC-343）。共通エラー本文の詳細は既存認証・非公開規則に従い、残高専用の認証エラー表現を追加しない。行ごとの`no_data`・`overflow`に変換しない。

## 4. HTTPエラー（DEC-343・確定／未実装）

| 条件 | HTTP | エラー |
| --- | --- | --- |
| 未認証・認証期限切れ | **401 Unauthorized** | 既存の認証エラー形式を維持 |
| 家計簿が存在しない・未参加・参加失効 | **404 Not Found** | 家計簿の存在・他参加者の情報を公開しない既存の非公開エラー |
| 必須の`date`欠落、`YYYY-MM-DD`以外の書式、実在しない暦日、時刻やUTCオフセット付きの値 | **400 Bad Request** | **`invalid_input`**（既存の共通エラー形式） |

- エラー時は**200相当の`estimates`配列を返さず**、認証・入力・家計簿参照のエラーを`no_data`や`overflow`の行状態へ変換しない。
- **家計簿参加の現在状態を毎回確認**し、Admin・Editor・Viewerのロール差では403を返さない（DEC-342）。対象日の有効な支払方法が0件であることはエラーではなく200と空配列（DEC-340・341）。
- `400 invalid_input`は共通エラーの`code`に格納する。該当フィールド名を返せる場合は`field: "date"`を用いる方向とするが、**共通本文の必須キー・ほかのエラーコード・503・通信失敗・サーバー内部障害等の詳細は後続設計**。

## 5. 一括推算時のDB読み取り一貫性（DEC-344・確定／未実装）

- **1回の推算GET内では対象となる全支払方法の結果を、同一のDB読み取りスナップショットに基づいて計算する**。対象日時点の支払方法・有効期間、推算の起点となる登録済み残高、期間中のレシート合計、振替金額（手数料等の計算対象を含む）は**同じ読取状態**に揃える。
- 対象の支払方法一覧を先に取得し、方法ごとのレシートや振替を別々の独立した読み取りで更新後の値と混在させない。実装では**一つの読み取りトランザクション／同等の一貫したスナップショット**で必要データを取得し、そのスナップショットから全件を計算する。SQLite／EF Coreの具体的なトランザクション・ロック方式は実装検証で選定し、書込ロックを長時間保持する設計は避ける。
- **取得中の他端末・他画面による保存は、その一括レスポンスに一部だけ混入させない**。スナップショット取得後の変更をこの応答に逐次反映する必要はなく、表示中の自動再取得は行わない（DEC-333）。これは後続の保存時に競合が起きないという保証ではない。
- `no_data`・`overflow`は支払方法ごとの有効な計算結果（DEC-339）として継続返却する。一方、**スナップショットを安全に取得できない・DB読取中に全体障害が発生した場合は、部分的な200応答や偽の`no_data`を返さずリクエスト全体をエラー**とする。具体的なHTTPコードと再試行は後続で定義する。
- **検証**：レシート・振替・基準残高・支払方法有効期間を並行更新しても、同じ200応答内で更新前後の値が混在しないこと、計算結果の範囲超過は他行を失わせないこと、DBエラーでは部分結果を返さないことをテストする。

## 6. 推算結果の配列順序と画面表示順（DEC-345・確定／未実装）

- **APIの`estimates`配列の順序は契約として保証しない**。APIは表示用に並び替える必要がなく、結果の対応関係は`paymentMethodId`で確定する。順序が変わっても推算金額や結果状態には影響させない。
- **WinUIは既存の支払方法・人物マスタキャッシュに従って行を配置**し、推算APIの各結果をIDで対応付ける。通常の表示順は**本人の所有分を優先**、その後は人物マスタの共通順、各所有人物内は`display_order ASC, payment_method_id ASC`（DEC-118・132）。推算結果を並び替えキーには使用しない。
- **キャッシュに不足・不整合がある場合は、不明な支払方法を適当に別行へ割り当てたり推算配列の順序を代用したりしない**。必要なマスタを取得し直してID照合する。具体的なマスタ更新時の画面挙動・失敗時の通知は後続設計。

## 7. 推算一括GETの取得失敗時のWinUI表示（DEC-346・確定／未実装）

- 1回の推算GETが**通信エラー・HTTPエラー・データ読取障害・応答形式不正等で全体失敗**した場合、**その要求日で表示中の対象支払方法の推算残高セルに「取得失敗」**と表示する。一括応答を成功扱いせず、前回の成功値・別日付の推算値を現在の結果として流用しない。
- **全行の［反映］を無効**にし、取得失敗を`no_data`（画面「—」）・`overflow`（画面「範囲超過」）と区別する（DEC-325・335・339）。「取得失敗」は**クライアント側の一括要求状態**であって、APIの`status`に第4の値を追加しない。成功200内の行単位`no_data`・`overflow`とは別扱い。
- **残高・評価額・メモの編集中の値および未保存状態を保持**し、取得失敗だけを理由に入力欄を空欄化・書き換え・保存・破棄しない。残高の手入力は継続可能とする。ただし401認証失効・404家計簿非参加等に起因して**そもそも保存権限がない場合は既存の認証・権限失効処理を優先**し、手入力可能をもって保存成功を保証しない。
- **WinUI 3では推算セルのテキストと画面上の`InfoBar`等で取得失敗を通知**し、色だけに依存しない。各セルと［反映］の無効理由をキーボード・スクリーンリーダーにも認識できるようにする。**確認用`ContentDialog`は開かない**。通知の具体的な配置と文面は実装時に画面全体と調整する。
- 対象日変更後の古い要求の失敗・成功を現在の日付へ反映しない（DEC-331）。自動ポーリング・定期再取得・通常時の手動再計算ボタンは追加しない（DEC-332・333）。**取得失敗時だけInfoBarに［再試行］を表示する（DEC-347）**。401認証復旧・404権限喪失後の具体的な遷移は既存の認証・権限制御を優先する。
- **検証**：成功後に別日付のGETが失敗した際の古い推算値不使用、全行の［反映］無効化、残高／評価額／メモの維持、アクセシビリティ説明、古い非同期応答の破棄を確認する。

## 8. 取得失敗時だけの手動再試行（DEC-347・確定／未実装）

- **推算一括GETが失敗した場合だけ**、非モーダルのWinUI 3標準`InfoBar`に［再試行］を表示する。成功時・通常表示時には手動［再計算］／［再試行］ボタンを設けない（DEC-332）。取得失敗時の「取得失敗」表示と全［反映］無効化はDEC-346を維持する。
- ［再試行］の明示操作時のみ、**現在画面で確定している対象日・家計簿の推算一括GET**を再実行する。要求実行中は二重押下・同一条件の重複送信を防ぎ、日付や家計簿が変わった後に届いた古い結果を採用しない（DEC-331）。
- **残高・評価額・メモの未保存入力、選択や編集状態を維持**し、取得成功後は各行の`calculated`／`no_data`／`overflow`表示と［反映］の可否だけを更新する。取得失敗なら「取得失敗」表示を継続し、勝手に繰り返し要求しない。
- **401認証失効・404家計簿への参加喪失では既存の認証復帰・権限制御が優先**し、単に再試行して権限を回避したり保存可能と誤案内したりしない。詳細なメッセージ／認証復旧の動線は既存画面と照合して実装時に決める。
- これは**利用者が明示操作する失敗復旧**であり、定期ポーリング・常時再計算・他端末更新の自動検知ではない。WinUIの動作とテストに限り、APIのレスポンス構造や結果`status`3値は変更しない。
