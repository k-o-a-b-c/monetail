# 残高・推算残高API設計

更新: 2026-11-16。**API未実装**。推算残高の一括取得について、確定したGET・成功応答と、未決定の認可・障害処理などを区別する。

## 1. 確定済みの契約（DEC-331〜343）

- 残高登録・編集画面を開いたとき、または共通登録日を確定変更したときに、1回のAPI要求で**対象日に有効な、同一家計簿内の全支払方法**の推算結果を取得する（DEC-331・340）。今日現在の有効状態ではなく対象日の有効期間で判定。両端包含・NULL端点は無制限。支払方法の所有者で絞らず、本人以外の所有分も含める（DEC-120）。対象0件では空集合。
- 日付変更前の遅い応答を現在の表示に反映しない。画面内での手動再計算・他画面／別端末の取引変更による自動更新はしない（DEC-331〜333）。
- 推算の起点は対象日より前の最新の非NULL登録残高（0円含む）。評価額だけの登録は起点に使わず、評価額を代用しない（DEC-334）。
- レシート・振替は既存Int32金額のまま、推算の累積・結果はInt64。途中の範囲超過は`overflow`とし、他支払方法の結果を欠落させない（DEC-335・336・339）。
- 1支払方法につき**`calculated`・`no_data`・`overflow`の3状態のうち1つ**。成功金額は**正規10進整数のJSON文字列**（`"0"`も可）、ほかの状態の金額はJSON `null`。金額表記・値域はDEC-337・338。
- 推算取得は参照のみ。表示と［反映］の分離、未保存入力保持はDEC-324・325に従う。認証・DB・通信などの全体障害は行状態と区別する（DEC-339）。
- **参照権限はDEC-342で確定**。現在の認証済み家計簿参加者のAdmin・Editor・Viewer全員が取得可能。参照対象は同一家計簿内の対象日有効な全支払方法で、所有人物・本人対応人物で絞らない。閲覧許可は書込権限を付与せず、別家計簿・未参加者には情報を返さない。
- レシート・振替の既存API契約は変更しない。

## 2. 一括GETと応答フィールド（DEC-341・確定／未実装）

**確定APIパス**：`GET /ledgers/{ledgerId}/balance-estimates?date=YYYY-MM-DD`。`date`は必須の正しい暦日を示す`YYYY-MM-DD`で、時刻・UTCオフセットは送らない。

**200 OKの確定応答**：トップレベルは`date`と`estimates`の2フィールドのみ、配列内は`paymentMethodId`・`status`・`amount`の3フィールドのみとする。5項目は必須で省略しない。状態と金額の組合せはDEC-339に従う。

```json
{
  "date": "2026-11-16",
  "estimates": [
    {
      "paymentMethodId": "11111111-1111-4111-8111-111111111111",
      "status": "calculated",
      "amount": "125000"
    },
    {
      "paymentMethodId": "22222222-2222-4222-8222-222222222222",
      "status": "no_data",
      "amount": null
    },
    {
      "paymentMethodId": "33333333-3333-4333-8333-333333333333",
      "status": "overflow",
      "amount": null
    }
  ]
}
```

サンプルのUUIDと金額は説明用の架空値。

| キー | JSON型 | 規則 |
| --- | --- | --- |
| `date` | 文字列（必須） | 要求した対象日を`YYYY-MM-DD`でエコーする。日付変更の古い応答を識別するために利用 |
| `estimates` | 配列（必須） | 対象日に有効な全支払方法を含む。0件なら`[]`、ページングなし |
| `paymentMethodId` | UUID D形式の文字列（必須） | 配列内の支払方法を一意に識別。1IDにつき1件 |
| `status` | 文字列（必須） | `calculated`・`no_data`・`overflow`のみ |
| `amount` | 文字列または`null`（必須） | `calculated`なら正規のInt64金額文字列。`no_data`・`overflow`なら`null` |

- 配列の並び順の保証は**未決定**。WinUIは応答順に表示順を依存させず、支払方法IDで画面の行へ突き合わせる。名称・所有人物名・表示順は既存マスタキャッシュから解決する。
- 明細、レシート、振替、登録済み残高や評価額、計算根拠、支払方法名・人物名はこの推算レスポンスに**含めない**。対象日・ID・状態・金額だけを返し、ページングや次ページカーソルは設けない。
- **未決定**：配列の並び順の保証、確定したHTTPステータス以外のエラー応答詳細、データ取得中の一貫性、障害復帰。**GETパス・必須`date`・成功200の5項目はDEC-341、参照権限はDEC-342、401／404／400の基本エラーはDEC-343で確定済み**。

## 3. 参照権限（DEC-342・確定／未実装）

- **現在の認証済み家計簿参加者であるAdmin・Editor・Viewer全員が利用可能**。Viewerも参照できるが、残高登録・編集・削除の権限は一切追加しない。
- **本人に対応する人物の有無、支払方法の所有人物、レシート・振替の作成者による結果の絞り込みはしない**。参照できるのはあくまで要求した家計簿内の、推算対象日に有効な全支払方法の結果（DEC-340）。
- **API要求のたびに認証と当該家計簿への現在の参加資格を確認**する。未参加者・参加失効者は参照できず、全体管理者であっても家計簿への参加を迂回できない。家計簿IDを検索・結合・キャッシュの境界にし、他家計簿の情報を混ぜない。
- 認証なし・失効時は**HTTP 401**、対象家計簿が存在しない・未参加・参加失効時は**HTTP 404**（DEC-343）。共通エラー本文の詳細は既存認証・非公開規則に従い、残高専用の認証エラー表現を追加しない。行ごとの`no_data`・`overflow`に変換しない。

## 4. HTTPエラー（DEC-343・確定／未実装）

| 条件 | HTTP | エラー |
| --- | --- | --- |
| 未認証・認証期限切れ | **401 Unauthorized** | 既存の認証エラー形式を維持 |
| 家計簿が存在しない・未参加・参加失効 | **404 Not Found** | 家計簿の存在・他参加者の情報を公開しない既存の非公開エラー |
| 必須の`date`欠落、`YYYY-MM-DD`以外の書式、実在しない暦日、時刻やUTCオフセット付きの値 | **400 Bad Request** | **`invalid_input`**（既存の共通エラー形式） |

- エラー時は**200相当の`estimates`配列を返さず**、認証・入力・家計簿参照のエラーを`no_data`や`overflow`の行状態へ変換しない。
- **家計簿参加の現在状態を毎回確認**し、Admin・Editor・Viewerのロール差では403を返さない（DEC-342）。対象日の有効な支払方法が0件であることはエラーではなく200と空配列（DEC-340・341）。
- `400 invalid_input`は共通エラーの`code`に格納する。該当フィールド名を返せる場合は`field: "date"`を用いる方向とするが、**共通本文の必須キー・ほかのエラーコード・503・通信失敗・サーバー内部障害等の詳細は後続設計**。
