## アカウントと人物

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装せず、常設パスワードを持たない（DEC-026）。
- アカウントはMonetail全体で独立して新規作成する。人物の存在・選択・紐付けを登録・ログイン・セッション検証・復旧の条件にしない。人物名やWindows用`account_name`からアカウントを自動作成・統合しない（DEC-044・045）。
- アカウント自身の`DisplayName`は、初回パスキー登録時に本人が入力する。前後の空白を除き、空白のみ不可・100文字以内・同名可とする。上限は.NETの`string.Length`とHTMLの`maxlength`で扱う。復旧再登録では保存済み表示名を維持し、別の名前を送っても変更しない。アカウント自身の表示名を変更するAPIは追加しない。パスキーの名前とは別に扱う。
- 既存の人物名を表示名へコピーしたり、認証IDを仮の表示名として補完したりしない。既存認証行も削除・再作成しない。表示名未設定の旧アカウントは`null`のまま保持する。既存人物への対応は家計簿側で任意に設定する後続機能とする。
- 表示名は本人識別・ロール・家計簿権限の根拠にしない。認証ID、セッション、鍵の所有者で本人を確認する。人物の作成・名前変更・対応変更・削除はログイン可否へ影響しない。
- 家計簿内の任意のアカウント→人物→支払方法の対応は、その家計簿の管理者が設定する方針（DEC-044）。認証アカウントの登録・ログインの必須条件にはしない。

## 認証コードの境界

別アプリのアカウントは独立させ、認証コードを流用しやすい構成を目指す（DEC-036、[構成](04-architecture.md)）。共通アカウント・共通ログインは採用しない。`CurrentSession`とチャレンジはアカウントの識別情報を扱う。

全体のアカウント管理APIは`Features/Accounts`、発行要求の保存モデルは`Authentication`に配置し、認証基盤から家計簿機能への参照を持たせない。APIのURL・入出力・認証条件は維持する。

APIは未リリースであり、過去の開発案との互換モデル・旧コマンド専用の処理は持たせない。空DBの初期定義はEFで管理し、家計簿データのスキーマは後続設計とする。

## 普段のログイン

1. 固定HTTPSのログイン画面で「ログイン」を選ぶ。画面自体は未実装で、表示・遷移は[58](ledger-onboarding.md#登録ログインの3画面dec-050未実装)を正本とする。
2. APIがチャレンジを発行し、ブラウザーでパスキー選択・端末の本人確認を行う。利用者コードやWindowsログイン名は入力しない。
3. Identityが署名・Origin・RP ID・チャレンジ・UV・鍵の所有者等を検証し、有効なアカウントを確認する。
4. SQLiteの同じ書込トランザクションで鍵状態と新しいセッションを保存し、Cookieを発行する。途中失敗は両方を戻す。失効・削除済みの鍵からセッションを作らない。

discoverable credential（ResidentKey=Required）とUserVerification=Requiredを必須にする。未対応端末へパスワード等で自動的に切り替えない。端末の生体情報・PIN・秘密鍵をAPIへ保存せず、公開鍵等はIdentity標準ストアで管理する。1アカウントに複数パスキーを登録できる。端末提供側の同期をアプリ側の保証とは扱わない。

## パスキーの表示名（DEC-143・実装済み）

初回登録・一般公開の自己登録・追加登録・CLI復旧後の登録は、**Identityの登録検証成功後だけ**共通の`PasskeyNames.ForVerifiedRegistration`で初期名を決め、`UserPasskeyInfo.Name`へ保存する。登録時のパスキー名入力欄は設けず、従来のアカウント本人表示名の入力とは区別する。既存の鍵を起動・参照・ログイン時に自動改名しない。

- 現行.NET 10の`UserPasskeyInfo`に`Aaguid`はないため、承認済みの代替方式として保存対象の`AttestationObject`から取得する。既存ASP.NET Core共有フレームワークの`System.Formats.Cbor.CborReader`でルートのCBORマップを構造的に読み、`authData`内のATフラグ・最小長を確認してネットワーク順の16バイトをUUIDへ変換する。独自CBORパーサー・反射による内部API利用・追加ライブラリは使わない。資格情報の検証はIdentityへ委ねる。
- 主要対応はGoogle パスワード マネージャー・1Password・Windows Hello・Bitwarden・Dashlane・Apple パスワード・iCloud キーチェーン（管理対象）の9 AAGUID。[実装内の対応表](../src/Monetail.Api/Authentication/PasskeyNames.cs)を使用し、未取得・未知・ゼロ・解析失敗は「パスキー」にする。任意の命名解析が失敗しても正常な登録を失敗させない。
- AAGUIDは**編集可能な表示名だけ**に使い、プロバイダー・同期先・機種・所有者・真正性や安全性を保証しない。匿名化されたゼロ値、未収録や将来のAAGUIDからは判別できない。認証・認可・署名/Origin/UV等の判定へ流用しない。
- 対応表はMITの[`passwordless-id/webauthn`内蔵メタデータ](https://github.com/passwordless-id/webauthn/blob/41842c401f8dd8cb40b53be6eef4bb9ee30913ee/src/authenticatorMetadata.ts)の主要項目を抽出し、日本語表示名を付けた。出典コミットと全文ライセンスは[同梱NOTICE](../src/Monetail.Api/Authentication/PasskeyNames.NOTICE)に記載し、publish/コンテナにも含める。元データはFIDO MDS・コミュニティ表を参照した表示用メタデータであり、信頼判定用の署名検証等を実装した意味ではない。
- 更新は保守時に出典コミット・ライセンスとベンダー情報を確認し、UUID/名称の選択項目と既知・未知・バイト順のテストを同時に変更する。上流コミュニティ表は廃止予定を告知しているため、空の表を自動取込しない。実行時の外部API照会・ネットワーク更新は行わない。

登録後は`/auth/login`の登録済みパスキー一覧で［名前変更］を選ぶ。標準Webダイアログに現在名を表示し、Trim後1〜100 UTF-16コード単位を許可する。同名可、最後の鍵も改名可能。入力不正・通信/HTTPエラー時は入力を保持する。同じダイアログで既存のパスキー本人再確認を実行でき、再確認後は利用者が明示的に保存する。保存先側（Windows/iCloud等）の名前は変更しない。

名前変更はログイン中の本人の鍵だけに許可し、直近5分未満の本人確認・既存のHTTPS/Origin/CSRF/認証共通枠を要求する。保存前・確定前に現在のセッションと有効アカウントをDBで再確認し、SQLite書込トランザクション内で現在の鍵を読んで名前だけを更新する。`IUserPasskeyStore<AuthUser>`の既存EFストアを使用し、アカウント全体を保存する`UserManager.AddOrUpdatePasskeyAsync`による状態の上書きを避ける。認証ID・公開鍵・署名カウンター・他の鍵メタデータ・アカウント行・セッション・ログイン状態は変更しない。同名の再保存は書込不要とし、失敗は全体ロールバックする。DBモデル・初期化・Migrationの追加は不要。APIの要求/応答は[契約](auth-api-contract.md#パスキー名変更api)を正本とする。

## 登録リンクと全失効

| 操作 | 処理 |
| --- | --- |
| 新規発行 | 全体Adminが新規一般アカウントと7日間の招待を発行する。要求IDは発行者・作成先を固定し、再送で二重作成しない |
| 登録 | トークンと表示名をPOSTし、標準WebAuthn検証成功時だけ表示名・鍵・有効化・招待消費を同時確定する。自動ログインしない |
| Webの再発行・取消 | Admin＋直近5分の本人確認＋CSRF。再発行は無効・鍵なし・未登録の対象だけ。同じ認証IDを維持して旧リンクを失効し、新リンクは発行時だけ返す。取消は通常・初期管理者招待だけを対象とし、CLI復旧リンクは変更しない |
| CLI緊急復旧 | サーバー運営者が登録済みかつ停止・鍵なしの対象へ`issue-recovery-link`を明示し、暫定10分のHTTPSリンクを発行する。認証ID・既存表示名（NULLを含む）・ロールを維持する |
| 鍵の追加・削除 | 本人と同じセッション・直近5分の確認を要求。最後の鍵の削除は拒否し、削除成功で全セッションを失効する |
| 全失効 | アカウントを無効化し、鍵・セッション・未使用リンクを失効させる。リンクは自動発行せず、人物・業務値・認証ID・表示名・ロールは保持する |

状態は「アカウント未作成 → 登録待ち → 利用中 → 停止中 → 登録待ち → 利用中」。停止と再発行は別操作。初期管理者の初回招待と未登録時の再発行は30分、一般の未登録アカウントは7日。**登録済みの停止アカウントをWebで再招待することは禁止し、明示的なCLI緊急復旧へ分離する**。未登録判定では表示名・登録消費・セッションの履歴を照合する。

全体管理者の招待・メモ管理Web画面は[DEC-115](ledger-onboarding.md#全体アカウント管理画面dec-115利用者確認済み未実装)で実装済み。HTTP全失効・追加Adminの権限変更は後続。最後のログイン可能なAdminの通常停止は拒否し、必要な場合だけCLIで`revoke-account --account-id ID --emergency-recovery`を明示する。バックアップ復元後は全体リセット後に各対象へCLI復旧リンクを発行する。これは信頼するサーバー運営者の緊急手段であり、不特定多数向けの本人確認・自己復旧を実装したものではない。

### アカウント登録の招待リンク（DEC-050・実装済み）

**招待制では**全体管理者がアカウント一覧から招待リンクを発行し、本人へ個別に渡す方式を採用する。リンクを開いた利用者は表示名だけ入力し、登録ボタンからパスキーを作成する。初期管理者もコマンドが出力する招待リンクから登録する。画面仕様は[58](ledger-onboarding.md#登録ログインの3画面dec-050未実装)を参照する。

招待リンクの形式・期限・取消・画面の受け渡しをDEC-113で実装した。通常招待は7日、初期管理者は30分。32バイト乱数・単回使用・SHA-256のみ保存とし、コード入力や旧公開DTO・CLIの互換は残さない。運営者の明示的なCLI復旧は別用途として既存の10分を暫定維持する（今回の利用者確認による補足）。

<a id="招待リンクの詳細契約dec-113利用者確認済み未実装"></a>

### 招待リンクの詳細契約（DEC-113・実装済み）

| 項目 | 決定した実装仕様 |
| --- | --- |
| 通常の新規アカウント招待 | **発行から7日間**、1回のみ。全体Adminが発行し、登録待ちアカウントに固定 |
| 初期管理者招待 | **`initialize-admin`から30分間**、1回のみ。初期管理者作成・既存Admin判定の保護は維持 |
| URL | 固定の`Passkeys:Origin` + `/auth/enroll#token=<43文字のbase64urlトークン>`。招待先の情報や認証IDはURLに追加しない |
| 生トークン | 発行時だけURLに組み込み返却。DBにはSHA-256のみ。通常ログ・監査ログ・エラー文・アクセスログには含めない |
| 発行結果 | 管理者の新規発行・再発行APIは`enrollmentUrl`を返し、旧`code`項目は返さない。再送時は新トークンもURLも再表示しない |
| CLI | `initialize-admin`・`issue-enrollment-invitation`・`issue-recovery-link`の標準出力は、発行成功時のURLのみ。`Passkeys:Origin`だけを発行に必須とし、不備なら失敗する。診断・監査は標準エラーへ出し、URLや生トークンを含めない |
| 取消・再発行 | Admin＋直近本人確認＋CSRFを条件に通常・初期管理者の未使用招待だけを明示的に取消可能。CLI復旧リンクは取消対象外。再発行で以前の未使用リンクを失効させ、同じリンクを再表示しない |
| 既存コード方式 | **互換性不要**。旧コード手入力欄・`code`の公開DTO／CLI出力を廃止。検証APIは`token`と`displayName`をPOST本文で受け取る |
| 発行対象 | 既存の全体管理者によるアカウント作成／未利用・パスキーなしアカウントの発行制限を維持。全体Admin権限を匿名招待へ付与しない |

**ブラウザーの安全な受け渡し**：`/auth/enroll`はページ表示直後にURLのフラグメントを検証・抽出し、`history.replaceState`でアドレスバー／現在の履歴項目から**トークン付きURLを直ちに除去**する。トークンはタブ内のJavaScriptメモリだけに保持し、`localStorage`・`sessionStorage`・Cookie・クエリ文字列へ保存しない。URLフラグメントはHTTPリクエスト・通常のRefererに送られない。ただし共有リンク自体が第三者に渡れば登録され得るため、送付先を限定する。画面更新・タブ閉鎖時はメモリのトークンを失い、元の招待リンクから開き直す。開封・options発行では招待を消費せず、標準WebAuthnの検証・アカウント有効化と同じDBトランザクションで**登録成功時だけ消費**する。

**利用者の画面**：招待制ではログイン画面へ「新規登録」のリンクを表示しない。招待リンクを開くとコード入力なしの表示名＋「登録」画面を表示する。登録成功画面の「ログイン」は同じ画面で既存パスキー認証を開始し、自動ログイン／自動家計簿参加はしない。`Public`ではログイン画面へ「新規登録」を表示し、`/auth/register`から既存のDEC-112自己登録APIを呼び出す。一般公開モードでも管理者の招待リンク経路は残す。`InvitationOnly`で一般公開の画面・APIを使わせない。入力エラー・キャンセルは画面内で表示し、表示名を保持する。

**無効リンク・失効と再送**：リンクの不正・期限切れ・使用済み・取消済み・登録対象不一致は情報を明かさない共通案内とし、通常の登録を確定させない。発行済みトークンは登録完了後に再利用できず、複数タブ・同時登録で成功は1回のみ。通信失敗やチャレンジ期限切れ時は保存済みか不明な場合があるため、登録できたパスキーでログインを試せる導線を用意する。管理APIの既存要求IDによる再送は二重発行を防止するが、生トークンの復元はしない。

**実装時の補足**：固定OriginがCLI操作で未設定の場合のエラーと、通常の認証設定を必要としない管理コマンドの性質を両立させる。`/auth/enroll`のブラウザースクリプトへURL生トークンをサーバー側テンプレートから埋め込まず、クライアントでフラグメントから取得する。発行のAPI・CLI、登録API、画面、検証テストを同じ実装PRで整合させる。URL発行時の秘密トークンのログ・履歴漏洩、Origin不一致、同時消費、初期管理者期限、管理者の取消・再発行、旧入力DTOの不受理を検証する。

実装は既存の`auth_enrollment_codes`保存領域（ハッシュ列等の内部名は維持）を再利用し、用途を通常招待・初期管理者・CLI復旧へ分離する。追加移行`RetireEnrollmentCodes`は旧用途の未使用トークンを失効し、消費履歴・アカウント・鍵・ロールを保持する。旧用途の受付や互換分岐は設けない。CLI復旧と移行手順は[42](42-api-foundation.md#db移行登録復旧コマンド)を参照する。

## 登録方式の段階的拡張（DEC-110・API実装／画面等未実装）

将来の不特定多数への提供に備え、**アカウントの登録方式を設定で「招待制／一般公開」に切り替えられる構造**とする。当面は招待制で運用する。登録設定はDEC-111、匿名自己登録API・DB保存・濫用防止はDEC-112で実装した。登録画面は実装済み。CAPTCHA・退会・全パスキー喪失時の自己復旧は未実装であり、不特定多数への本番公開は開始しない。

| 項目 | 招待制（当面の運用） | 一般公開（将来の方式） |
| --- | --- | --- |
| 新規アカウント | 全体管理者が発行する登録招待から本人が登録 | 未ログインの本人が招待なしで登録 |
| 認証と登録後 | パスキー必須。登録後に明示ログイン | 同じくパスキー必須。登録後に明示ログイン |
| 初期権限 | 全体Adminを自動付与しない | 全体Adminを自動付与しない |
| 家計簿 | ログイン済みなら誰でも作成可。参加は家計簿招待 | 同左。アカウントの自由登録だけで他人の家計簿を閲覧できない |
| 運営管理 | 初期管理者コマンド・管理者による発行／復旧経路を保持 | 一般利用者の画面から独立した運営用権限を保持 |

アカウント、家計簿、家計簿内の人物を独立させる現行モデルは維持する。家計簿管理者権限と全体Admin権限は相互に付与されず、アカウント自己登録時に家計簿や人物を自動作成しない。一般利用者向けの全アカウント一覧・他人のアカウント編集は追加しない。全体管理者向け現行APIと管理コマンドはこの段階では削除しない。

### 自己登録の保存と認証（DEC-112・API実装済み）

- **一般公開のときだけ**未認証の自己登録開始・完了を許可する。招待制では同じ要求を拒否し、アカウント行や鍵を作らない。方式変更をまたいだ未完了チャレンジも、完了時に現在の方式を再確認する。
- 表示名は既存の初回登録条件を共用する。パスキーはIdentityの標準WebAuthn検証を使い、既存のOrigin・RP ID・本人確認・チャレンジの保護を弱めない。自己登録のためにパスワードやメール認証を追加しない。
- 未検証の登録開始だけでアカウントを永続化しない。**パスキー検証成功後に、一般アカウント・鍵・有効化・成功日時を同じDBトランザクションで確定する**。途中失敗や同時完了による孤立アカウント・二重確定を防ぐ。
- 登録成功では自動ログインせず、既存のログインへ進む。新規一般アカウントは全体Adminのロールを持たず、家計簿の参加者にもならない。家計簿作成・招待受領の既存APIによってのみ所属を作る。
- 管理者が先に作成した登録待ちアカウントの招待登録・再発行と、初期管理者のCLI登録経路は**別経路として維持**する。一般公開の自己登録を、停止アカウントの本人確認やパスキー喪失からの復旧経路として流用しない。

### 登録モードの設定（DEC-111・設定読込と検証は実装）

**API起動時に設定を読み取り、既定は招待制**とする。環境変数では階層区切りの`:`を`__`へ置き換えるため、Docker Composeでは`Registration__Mode`を指定する。

| 設定 | 設定としての動作 | 状態 |
| --- | --- | --- |
| `Registration:Mode` 未指定 | `InvitationOnly`を選択 | 実装 |
| `Registration:Mode=InvitationOnly` | 招待制を選択 | 実装 |
| `Registration:Mode=Public` | 匿名自己登録APIを利用可能にする | **API・DB・濫用防止・登録画面は実装。自己復旧等は未実装** |
| 空文字・未知の値 | 通常APIの起動を拒否 | 実装 |

- 通常起動時に設定を一度だけ読み込み、DIに固定する。変更はAPIコンテナの再作成／API再起動で反映する。起動中のホットリロードや登録方式変更APIは設けない。
- 管理コマンド`initialize-db`・`initialize-admin`・`issue-enrollment-invitation`・`issue-recovery-link`等はこの設定の検証を要求しない。管理者発行の招待リンクによる登録・ログイン・家計簿操作はどちらの値でも変更しない。
- **`Public`への変更と再起動で、匿名自己登録APIが直ちに有効になる。** 既存Composeの`InvitationOnly`は維持する。設定ファイル・配備環境を変更できる運営者だけが切り替え、自己復旧・退会等が整うまでは本番一般公開しない。停止時は`InvitationOnly`へ戻して再起動し、未完了チャレンジも破棄する。

### 自己登録の一括保存フロー（DEC-112・実装済み）

1. `options`で公開モード・表示名・HTTPS・Origin・CSRF・回数制限を確認。既存の表示名の規則（前後空白を除く・100文字以内・空白のみ拒否・同名可）を共用する。
2. サーバーで候補の認証IDを生成し、WebAuthn作成オプションとチャレンジへ結びつける。**この時点ではアカウント・パスキー・セッションをDBに作らない。**
3. `verify`で同一ブラウザー・用途・候補ID・期限・未使用のチャレンジを検査し、現在もPublicか再確認する。Identity標準のWebAuthn検証を使用し、独自暗号検証は行わない。
4. 検証が成功した場合だけ、SQLiteの一つの書込トランザクションで件数を判定し、アカウント（一般）、表示名、パスキー、有効化と成功日時を確定する。全体Adminロール、家計簿参加、セッション、管理者用発行記録は作らない。
5. 途中のDB例外・同時確定・証明書検証失敗等では全体をロールバックする。成功後も自動ログインせず既存ログインへ誘導する。

既存の招待制登録チャレンジは5分・1回限り・ブラウザー固定・最大1024件・プロセス内保存を維持する。DEC-112の自己登録は用途別のCookie・格納領域で分離し、**同時最大128件・5分・1回限り**とする。用途の取り違え・再利用を防ぎ、再起動後の未完了分は無効とする。多重プロセス運用は別途設計する。

保存完了の応答が失われた場合、再度のアカウント作成を無条件に行わず、作成済みパスキーで通常ログインを試せる案内を検討する。既存の管理者招待・紛失復旧・家計簿参加の契約は変更しない。具体的な回数・保存・HTTP条件は次節を正本とする。

### 自己登録API・濫用防止の確定仕様（DEC-112・実装済み）

DEC-110の自己登録方式とDEC-111の設定を前提に、以下をAPIとDBマイグレーションへ実装した。登録画面はDEC-050・113で実装した。CAPTCHA、退会、パスキー全喪失時の自己復旧は別工程であり、実装していない。

| 要素 | 確定仕様 |
| --- | --- |
| 利用モード | `Registration:Mode=Public`でだけ匿名の自己登録を開始・確定。招待制では両POSTを403で拒否し、状態を変更しない |
| API | `POST /auth/self-registration/options`、`POST /auth/self-registration/verify` |
| 入力 | optionsは`displayName`のみ。verifyは既存enrollmentと同形の`credential`オブジェクト。メール・電話・パスワードは使わない |
| 表示名 | 前後空白を除去、空欄・空白のみ・100文字超を拒否。同名を許可。認証IDには使わない |
| 登録成功 | 既存Identity標準WebAuthn検証成功後に、一般アカウント・表示名・パスキー・有効化を単一SQLiteトランザクションで確定 |
| 初期状態 | 全体Adminロールなし、家計簿・家計簿参加者・人物なし。Cookie／Bearerトークンを発行せず、明示ログインへ進む |
| 失敗時 | 検証・保存・回数制限失敗では利用可能なアカウント／鍵／セッションを作らない。保存失敗は必ず全体ロールバック |

**IP・チャレンジ・成功件数の制限**

| 制限 | 値と適用条件 |
| --- | --- |
| 既存認証API共通 | **20要求／1分／IP**を維持。新しい自己登録のoptions／verifyも同じ枠を消費 |
| 自己登録の開始 | **5要求／直近10分／IP**。`options`だけを追加で数え、6件目は429。入力不正も試行として数え、`verify`はここでは数えない |
| 自己登録成功数 | **サーバー全体で直近24時間に100件**。100件到達後の`verify`は429。成功した匿名自己登録だけ数える（管理者登録・パスキー追加は対象外） |
| 自己登録チャレンジ | **同時最大128件・5分・1回限り**。別用途Cookieと格納領域で招待制の登録チャレンジ（既存最大1024件）と分離。満杯は429、期限切れ・不一致・再利用は400 |
| 上限超過 | **HTTP 429**。待ち行列・自動再試行を設けず、拒否された操作でDBにアカウント・鍵を作らない |

自己登録の開始IP判定は`RemoteIpAddress`と既存の**信頼済みプロキシのみ**の転送ヘッダー処理を使用し、任意の`X-Forwarded-For`を信用しない。自己登録用のIP別状態はプロセス内で管理してよいが、**10分を過ぎた状態を掃除し、最大4096 IPキー**を保持する。有効キーで満杯なら新規IPは429で拒否し、無制限にメモリを消費しない。再起動時はIP別の回数枠がリセットされてもよいが、下記の成功件数はリセットされない。IPを成功件数のDBへ保存しない。

成功数の厳密な24時間は**UTCの直近24時間の移動窓（日時境界でのリセットなし）**とする。DBに自己登録成功の日時を保持する独立した記録（例：`auth_self_registration_completions`）を設け、管理者発行・復旧と分ける。記録はアカウントの将来の退会に伴って削除しない設計とし、IP・鍵・表示名は記録しない。48時間より古い成功件数記録はトランザクション内で削除可能とする。**24時間内件数の照合、100件未満の判定、アカウント／鍵／成功記録の追加を1つの排他的なSQLite書込トランザクション内**で実行し、同時要求でも100件を超えない。SQLiteのロック競合・DB障害では安全側に失敗させ、制限を迂回しない。開始側での残枠照合は任意の早期拒否にとどめ、必ず完了側で判定する。

実装は`Authentication/SelfRegistration*`に分離し、Identity標準の作成オプション・検証を再利用する。完了側は本文解析前にチャレンジを消費し、WebAuthn検証後に`BEGIN IMMEDIATE`の書込権を取得する。件数照合に加え、同じ鍵が先に登録されていないかもトランザクション内で再確認する。成功記録は自動採番IDとUTC成功日時だけを持ち、アカウントへのFKは持たない。48時間より古い記録の削除も成功保存と同じトランザクションに含める。移行・停止・バックアップは[42](42-api-foundation.md#db移行登録復旧コマンド)を参照する。

**チャレンジとセキュリティ境界**

- `options`では暗号学的乱数の候補認証IDだけ生成し、DBにアカウントを作らない。候補ID・表示名・標準WebAuthnの検証状態を、同一ブラウザー・自己登録用途・5分有効・単回使用のサーバーチャレンジへ固定する。
- `verify`は同じ用途のCookie・候補IDを照合し、チャレンジを原子的に消費する。失敗や同時送信でも使い回せない。固定RP ID・Origin・UV等のIdentity標準WebAuthn検証、CSRF、固定HTTPS・本文64 KiBを既存より弱めない。
- `InvitationOnly`で両POSTを403。登録モードは起動時固定で、設定変更時はAPI再起動で未完了チャレンジが消える。再起動前に開始された匿名登録を招待制になった後で確定させない。
- 完了のHTTP応答が失われた場合、無条件で再登録しない。利用者には通常ログインを試す案内を検討する（画面は別工程）。登録コード方式、管理CLI、ログイン、Windows OAuth、家計簿操作は変更しない。
- 最初のAPI実装・運用は**単一APIプロセス**を前提とする。複数プロセス・複数ホスト配備ではメモリ内IP制限とチャレンジの共有／集中制御を設計し直す。DB側100件制限は再起動後も維持する。

**一般公開前の残作業**：パスキーを全て失った一般利用者の本人確認・自己復旧と、退会／共有家計簿の取り扱いはまだ未実装。この状態で不特定多数への本番一般公開を開始しない。実装PRでは匿名APIの有効化が`Public`によって直ちに可能になる旨を運用文書へ明記し、既存Composeの`InvitationOnly`を変更しない。

### 一般公開前に確定する事項（未決定）

- 登録モード・再起動による未完了操作の破棄・有効化と停止は実装・テスト済み。実配備の設定変更権限と、運営者以外が切り替えられないことは運用環境で確認する。
- 自己登録API向け回数・件数・容量制限の数値はDEC-112で確定。ただし分散IP・BOT対策の運用評価と、多重プロセス環境への拡張は一般公開前に別途検証する。
- 自己登録APIのパス・基本DTO・エラー区分とチャレンジ・一括保存の主要条件はDEC-112で確定。応答文面・内部構造・HTTP失敗時の利用者向け復帰表示は実装・画面工程で詳細化する。
- パスキーを全て失った一般利用者の本人確認・復旧。現行の全体管理者による再発行を、不特定多数の通常サポートの唯一の前提にはしない。
- アカウント本人による退会、共有家計簿の履歴の保持・管理者引継ぎ・業務上の参照、運営による利用停止と復旧条件。退会API・画面はこの設計段階では追加しない。
