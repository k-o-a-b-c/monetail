## アカウントと人物

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装せず、常設パスワードを持たない（DEC-026）。
- アカウントはMonetail全体で独立して新規作成する。人物の存在・選択・紐付けを登録・ログイン・セッション検証・復旧の条件にしない。人物名やWindows用`account_name`からアカウントを自動作成・統合しない（DEC-044・045）。
- アカウント自身の`DisplayName`は、初回パスキー登録時に本人が入力する。前後の空白を除き、空白のみ不可・100文字以内・同名可とする。上限は.NETの`string.Length`とHTMLの`maxlength`で扱う。復旧再登録では保存済み表示名を維持し、別の名前を送っても変更しない。名前変更APIは今回追加しない。
- 既存の人物名を表示名へコピーしたり、認証IDを仮の表示名として補完したりしない。既存認証行も削除・再作成しない。表示名未設定の旧アカウントは`null`のまま保持する。既存人物への対応は家計簿側で任意に設定する後続機能とする。
- 表示名は本人識別・ロール・家計簿権限の根拠にしない。認証ID、セッション、鍵の所有者で本人を確認する。人物の作成・名前変更・対応変更・削除はログイン可否へ影響しない。
- 家計簿内の任意のアカウント→人物→支払方法の対応は、その家計簿の管理者が設定する方針（DEC-044）。認証アカウントの登録・ログインの必須条件にはしない。

## 認証コードの境界

別アプリのアカウントは独立させ、認証コードを流用しやすい構成を目指す（DEC-036、[構成](04-architecture.md)）。共通アカウント・共通ログインは採用しない。`CurrentSession`とチャレンジはアカウントの識別情報を扱う。

全体のアカウント管理APIは`Features/Accounts`、発行要求の保存モデルは`Authentication`に配置し、認証基盤から家計簿機能への参照を持たせない。APIのURL・入出力・認証条件は維持する。

APIは未リリースであり、過去の開発案との互換モデル・旧コマンド専用の処理は持たせない。空DBの初期定義はEFで管理し、家計簿データのスキーマは後続設計とする。

## 普段のログイン

1. 固定HTTPSのログイン画面で「ログイン」を選ぶ。画面自体は未実装で、表示・遷移は[58](ledger-onboarding.md#登録ログインの3画面dec-050未実装)を正本とする。
2. APIがチャレンジを発行し、ブラウザーでパスキー選択・端末の本人確認を行う。利用者コードやWindowsログイン名は入力しない。
3. Identityが署名・Origin・RP ID・チャレンジ・UV・鍵の所有者等を検証し、有効なアカウントを確認する。
4. SQLiteの同じ書込トランザクションで鍵状態と新しいセッションを保存し、Cookieを発行する。途中失敗は両方を戻す。失効・削除済みの鍵からセッションを作らない。

discoverable credential（ResidentKey=Required）とUserVerification=Requiredを必須にする。未対応端末へパスワード等で自動的に切り替えない。端末の生体情報・PIN・秘密鍵をAPIへ保存せず、公開鍵等はIdentity標準ストアで管理する。1アカウントに複数パスキーを登録できる。端末提供側の同期をアプリ側の保証とは扱わない。

## 登録コードと全失効

| 操作 | 処理 |
| --- | --- |
| 新規発行 | 全体管理者が人物を選ばず新規一般アカウントと初回コードを発行する。要求IDは管理者と作成先を固定し、同じ要求の再送で二重作成しない |
| 登録 | APIはコードと初回表示名を受け取る。画面ではコードを手入力せず、下記の招待リンクから取得する方針。標準検証成功時だけ表示名・鍵・有効化・コード消費を同じトランザクションで確定する。自動ログインしない |
| コード再発行 | 無効かつ鍵なしの既存アカウントが対象。一般・管理者を問わず同じ認証ID・表示名・ロールを保持し、旧未使用コードの失効と新コード保存を同時に行う |
| 鍵の追加 | ログイン中の同一アカウント・同一セッションと直近5分未満の本人確認を要求する。名前はアカウント自身の表示名を使う |
| 鍵の自己削除 | 直近本人確認が必要。最後の1件は拒否し、成功時はそのアカウントの全セッションを失効させる。残る鍵で再ログインする |
| 全失効 | 利用停止・紛失で同じ処理を使う。アカウントを無効化し、全鍵・全セッション・未使用コードを失効させる。コードは自動発行しない。人物・業務値・認証ID・表示名・ロール・旧対応は保持する |

状態は「アカウント未作成 → 登録待ち → 利用中 → 停止中 → 登録待ち → 利用中」。人物だけの登録はこの遷移に含めない。復旧では別操作でコードを発行し、本人の再登録成功時だけ有効にする。期限切れや発行だけでは利用中に戻らない。管理者が本人としてログインするセッションも作らない。

現在のコードは暗号学的乱数32バイト・発行から10分・1回限り。DBにはSHA-256ハッシュ・対象認証ID・用途・UTC期限・消費／取消状態を保存し、生コードを保存しない。発行成功時に一度だけ表示し、再送では再表示しない。クエリ・通常ログ・監査記録に生コードを含めず、登録画面からPOST本文で送る。Identityの2FA復旧コードとは別の仕組み。家計簿参加招待の条件は[家計簿招待](ledger-invitations.md)を参照する。

全失効のHTTP操作、Web管理画面、追加全体管理者の管理・権限変更は後続。無効・鍵なしの管理者には別の有効な管理者から再発行できる。最後のログイン可能な管理者の通常停止は拒否し、全員がログイン不能になった場合はサーバーの管理コマンドで明示的に緊急復旧する。停止と再発行は別操作のまま保つ。

### アカウント登録の招待リンク（DEC-050・未実装）

**招待制では**全体管理者がアカウント一覧から招待リンクを発行し、本人へ個別に渡す方式を採用する。リンクを開いた利用者は表示名だけ入力し、登録ボタンからパスキーを作成する。初回管理者もコマンドが出力する招待リンクから登録する方針とする。画面仕様は[58](ledger-onboarding.md#登録ログインの3画面dec-050未実装)を参照する。

リンク内部の推測困難な登録用トークンは、現在のコードと同じ暗号学的乱数32バイト・10分・1回限り・DBはSHA-256ハッシュのみの条件を維持する。リンクを持つ人が登録できるため、通常ログ・監査記録へリンク全体や生トークンを残さない。登録先アカウントは引き続きトークンで固定し、登録・消費の確定条件を緩めない。

現在のAPIは`code`を返し、管理コマンドは生コードを出力する。招待リンク生成・受け渡し・画面はまだ実装しておらず、[42の現行コマンド](42-api-foundation.md#db移行登録復旧コマンド)の出力が変更済みという意味ではない。URL内のトークンの持たせ方、ブラウザー履歴等への残留対策、CLIでの固定HTTPS URLの取得方法、APIの応答へリンクを追加するかは実装前に具体化する。


## 登録方式の段階的拡張（DEC-110・方針確認済み／未実装）

将来の不特定多数への提供に備え、**アカウントの登録方式を設定で「招待制／一般公開」に切り替えられる構造**とする。当面は招待制で運用する。設定キー名・値・反映手順はDEC-111で確定・実装したが、一般公開の自己登録API・画面は未実装であり、公開への切替は別途実装・検証してから行う。

| 項目 | 招待制（当面の運用） | 一般公開（将来の方式） |
| --- | --- | --- |
| 新規アカウント | 全体管理者が発行する登録招待から本人が登録 | 未ログインの本人が招待なしで登録 |
| 認証と登録後 | パスキー必須。登録後に明示ログイン | 同じくパスキー必須。登録後に明示ログイン |
| 初期権限 | 全体Adminを自動付与しない | 全体Adminを自動付与しない |
| 家計簿 | ログイン済みなら誰でも作成可。参加は家計簿招待 | 同左。アカウントの自由登録だけで他人の家計簿を閲覧できない |
| 運営管理 | 初期管理者コマンド・管理者による発行／復旧経路を保持 | 一般利用者の画面から独立した運営用権限を保持 |

アカウント、家計簿、家計簿内の人物を独立させる現行モデルは維持する。家計簿管理者権限と全体Admin権限は相互に付与されず、アカウント自己登録時に家計簿や人物を自動作成しない。一般利用者向けの全アカウント一覧・他人のアカウント編集は追加しない。全体管理者向け現行APIと管理コマンドはこの段階では削除しない。

### 自己登録の保存と認証（設計方針、API詳細は未確定）

- **一般公開のときだけ**未認証の自己登録開始・完了を許可する。招待制では同じ要求を拒否し、アカウント行や鍵を作らない。方式変更をまたいだ未完了チャレンジも、完了時に現在の方式を再確認する。
- 表示名は既存の初回登録条件を共用する。パスキーはIdentityの標準WebAuthn検証を使い、既存のOrigin・RP ID・本人確認・チャレンジの保護を弱めない。自己登録のためにパスワードやメール認証を追加しない。
- 未検証の登録開始だけで、利用可能なアカウントを永続化しない。**パスキーの検証成功を条件に、一般アカウント・鍵・有効化を同じDBトランザクションで確定する**案とする。途中失敗や同時完了による孤立アカウント・二重確定を防ぐ。識別子、未完了チャレンジ、再送や応答喪失の扱いはAPI実装前に具体化する。
- 登録成功では自動ログインせず、既存のログインへ進む。新規一般アカウントは全体Adminのロールを持たず、家計簿の参加者にもならない。家計簿作成・招待受領の既存APIによってのみ所属を作る。
- 管理者が先に作成した登録待ちアカウントのコード登録・再発行と、初期管理者のCLI登録経路は**別経路として維持**する。一般公開の自己登録を、停止アカウントの本人確認やパスキー喪失からの復旧経路として流用しない。

### 登録モードの設定（DEC-111・設定読込と検証は実装）

**API起動時に設定を読み取り、既定は招待制**とする。環境変数では階層区切りの`:`を`__`へ置き換えるため、Docker Composeでは`Registration__Mode`を指定する。

| 設定 | 設定としての動作 | 状態 |
| --- | --- | --- |
| `Registration:Mode` 未指定 | `InvitationOnly`を選択 | 実装 |
| `Registration:Mode=InvitationOnly` | 招待制を選択 | 実装 |
| `Registration:Mode=Public` | 一般公開モードを選択 | **設定読込のみ実装。匿名自己登録API・画面は未実装** |
| 空文字・未知の値 | 通常APIの起動を拒否 | 実装 |

- 通常起動時に設定を一度だけ読み込み、DIに固定する。変更はAPIコンテナの再作成／API再起動で反映する。起動中のホットリロードや登録方式変更APIは設けない。
- 管理コマンド`initialize-db`・`initialize-admin`・`issue-enrollment-code`等はこの設定の検証を要求しない。既存の管理者発行コードによる登録・ログイン・家計簿操作はどちらの値でも変更しない。
- **`Public`を指定しても、現時点では招待なし登録はできない。** 匿名登録用のoptions／verifyと画面、濫用対策・復旧設計の実装前に一般公開したと判断しない。公開前の条件と未決定事項は下記の通り。

### 自己登録の一括保存フロー（DEC-112・仕様確定／未実装）

1. `options`で公開モード・表示名・HTTPS・Origin・CSRF・回数制限を確認。既存の表示名の規則（前後空白を除く・100文字以内・空白のみ拒否・同名可）を共用する。
2. サーバーで候補の認証IDを生成し、WebAuthn作成オプションとチャレンジへ結びつける。**この時点ではアカウント・パスキー・セッションをDBに作らない。**
3. `verify`で同一ブラウザー・用途・候補ID・期限・未使用のチャレンジを検査し、現在もPublicか再確認する。Identity標準のWebAuthn検証を使用し、独自暗号検証は行わない。
4. 検証が成功した場合だけ、SQLiteの一つの書込トランザクションでアカウント（一般）、表示名、パスキーと有効化を確定する。全体Adminロール、家計簿参加、セッション、管理者用発行記録は作らない。
5. 途中のDB例外・同時確定・証明書検証失敗等では全体をロールバックする。成功後も自動ログインせず既存ログインへ誘導する。

既存の招待制登録チャレンジは5分・1回限り・ブラウザー固定・最大1024件・プロセス内保存を維持する。DEC-112の自己登録は用途別のCookie・格納領域で分離し、**同時最大128件・5分・1回限り**とする。用途の取り違え・再利用を防ぎ、再起動後の未完了分は無効とする。多重プロセス運用は別途設計する。

保存完了の応答が失われた場合、再度のアカウント作成を無条件に行わず、作成済みパスキーで通常ログインを試せる案内を検討する。既存の管理者招待・紛失復旧・家計簿参加の契約は変更しない。具体的な回数・保存・HTTP条件は次節を正本とする。

### 自己登録API・濫用防止の確定仕様（DEC-112・未実装）

DEC-110の自己登録方式とDEC-111の設定を前提に、**次のAPI実装で採用する仕様**を確定する。今回の文書更新は実装ではなく、`Public`でもAPIが既に利用できることを意味しない。実装範囲はAPIとDBマイグレーション・テストまで。登録画面、CAPTCHA、退会、パスキー全喪失時の自己復旧は別工程とする。

| 要素 | 確定仕様 |
| --- | --- |
| 利用モード | `Registration:Mode=Public`でだけ匿名の自己登録を開始・確定。招待制では両POSTを403で拒否し、状態を変更しない |
| API | `POST /auth/self-registration/options`、`POST /auth/self-registration/verify` |
| 入力 | optionsは`displayName`のみ。verifyは既存enrollmentと同形の`credential`オブジェクト。メール・電話・パスワードは使わない |
| 表示名 | 前後空白を除去、空欄・空白のみ・100文字超を拒否。同名を許可。認証IDには使わない |
| 登録成功 | 既存Identity標準WebAuthn検証成功後に、一般アカウント・表示名・パスキー・有効化を単一SQLiteトランザクションで確定 |
| 初期状態 | 全体Adminロールなし、家計簿・家計簿参加者・人物なし。Cookie／Bearerトークンを発行せず、明示ログインへ進む |
| 失敗時 | 検証・保存・回数制限失敗では利用可能なアカウント／鍵／セッションを作らない。保存失敗は必ず全体ロールバック |

**IP・チャレンジ・成功件数の制限**

| 制限 | 値と適用条件 |
| --- | --- |
| 既存認証API共通 | **20要求／1分／IP**を維持。新しい自己登録のoptions／verifyも同じ枠を消費 |
| 自己登録の開始 | **5要求／直近10分／IP**。`options`だけを追加で数え、6件目は429。入力不正も試行として数え、`verify`はここでは数えない |
| 自己登録成功数 | **サーバー全体で直近24時間に100件**。100件到達後の`verify`は429。成功した匿名自己登録だけ数える（管理者登録・パスキー追加は対象外） |
| 自己登録チャレンジ | **同時最大128件・5分・1回限り**。別用途Cookieと格納領域で招待制の登録チャレンジ（既存最大1024件）と分離。満杯は429、期限切れ・不一致・再利用は400 |
| 上限超過 | **HTTP 429**。待ち行列・自動再試行を設けず、拒否された操作でDBにアカウント・鍵を作らない |

自己登録の開始IP判定は`RemoteIpAddress`と既存の**信頼済みプロキシのみ**の転送ヘッダー処理を使用し、任意の`X-Forwarded-For`を信用しない。自己登録用のIP別状態はプロセス内で管理してよいが、**10分を過ぎた状態を掃除し、最大4096 IPキー**を保持する。有効キーで満杯なら新規IPは429で拒否し、無制限にメモリを消費しない。再起動時はIP別の回数枠がリセットされてもよいが、下記の成功件数はリセットされない。IPを成功件数のDBへ保存しない。

成功数の厳密な24時間は**UTCの直近24時間の移動窓（日時境界でのリセットなし）**とする。DBに自己登録成功の日時を保持する独立した記録（例：`auth_self_registration_completions`）を設け、管理者発行・復旧と分ける。記録はアカウントの将来の退会に伴って削除しない設計とし、IP・鍵・表示名は記録しない。48時間より古い成功件数記録はトランザクション内で削除可能とする。**24時間内件数の照合、100件未満の判定、アカウント／鍵／成功記録の追加を1つの排他的なSQLite書込トランザクション内**で実行し、同時要求でも100件を超えない。SQLiteのロック競合・DB障害では安全側に失敗させ、制限を迂回しない。開始側での残枠照合は任意の早期拒否にとどめ、必ず完了側で判定する。

**チャレンジとセキュリティ境界**

- `options`では暗号学的乱数の候補認証IDだけ生成し、DBにアカウントを作らない。候補ID・表示名・標準WebAuthnの検証状態を、同一ブラウザー・自己登録用途・5分有効・単回使用のサーバーチャレンジへ固定する。
- `verify`は同じ用途のCookie・候補IDを照合し、チャレンジを原子的に消費する。失敗や同時送信でも使い回せない。固定RP ID・Origin・UV等のIdentity標準WebAuthn検証、CSRF、固定HTTPS・本文64 KiBを既存より弱めない。
- `InvitationOnly`で両POSTを403。登録モードは起動時固定で、設定変更時はAPI再起動で未完了チャレンジが消える。再起動前に開始された匿名登録を招待制になった後で確定させない。
- 完了のHTTP応答が失われた場合、無条件で再登録しない。利用者には通常ログインを試す案内を検討する（画面は別工程）。登録コード方式、管理CLI、ログイン、Windows OAuth、家計簿操作は変更しない。
- 最初のAPI実装・運用は**単一APIプロセス**を前提とする。複数プロセス・複数ホスト配備ではメモリ内IP制限とチャレンジの共有／集中制御を設計し直す。DB側100件制限は再起動後も維持する。

**一般公開前の残作業**：パスキーを全て失った一般利用者の本人確認・自己復旧と、退会／共有家計簿の取り扱いはまだ未実装。この状態で不特定多数への本番一般公開を開始しない。実装PRでは匿名APIの有効化が`Public`によって直ちに可能になる旨を運用文書へ明記し、既存Composeの`InvitationOnly`を変更しない。

### 一般公開前に確定する事項（未決定）

- 登録モードの設定キー・起動時検証はDEC-111で確定・実装済み。未完了操作の扱いと、一般公開の有効化・停止手順、運営者だけが設定を変更できる配備上の権限境界は自己登録実装前に検証する。
- 自己登録API向け回数・件数・容量制限の数値はDEC-112で確定。ただし分散IP・BOT対策の運用評価と、多重プロセス環境への拡張は一般公開前に別途検証する。
- 自己登録APIのパス・基本DTO・エラー区分とチャレンジ・一括保存の主要条件はDEC-112で確定。応答文面・内部構造・HTTP失敗時の利用者向け復帰表示は実装・画面工程で詳細化する。
- パスキーを全て失った一般利用者の本人確認・復旧。現行の全体管理者による再発行を、不特定多数の通常サポートの唯一の前提にはしない。
- アカウント本人による退会、共有家計簿の履歴の保持・管理者引継ぎ・業務上の参照、運営による利用停止と復旧条件。退会API・画面はこの設計段階では追加しない。
