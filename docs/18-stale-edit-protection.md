# 18 古い編集内容の上書き防止

更新: 2026-10-19 / LEG-016。[PR #9時点の再現結果](17-concurrent-persistence-validation.md)を基に、レシート・振替・残高の更新と削除へ更新版照合を追加した。自動テストの件数・実行方法・最新CI結果は[tests/README.md](../tests/README.md)を参照する。

## 保存の契約

- 親3表の`revision_token`をモデルの内部プロパティ`RevisionToken`として読む。対象はレシート2経路・振替2経路・残高3経路。画面には表示しない。
- 登録と更新では新しいGUID（N形式）を発行する。更新は`seq`と読込時のトークンが一致する1行だけを変更し、成功後に子を入れ替える。トークンはCommit成功後にモデルへ反映する。
- 削除は書込トランザクション内で版を確認してから子→親の順に行い、親DELETEにも同じ版条件を付ける。
- 版が不明、行が削除済み、他の保存で版が変わった場合は`DBConcurrencyException`で中止する。親子・監査情報を含むDBの保存内容とモデルのトークンは保持する。途中失敗も既存トランザクションでRollbackする。
- 同じモデルの連続更新は新しい版で継続できる。流用は元の版を引き継がず新規登録する。削除後に同じseqが再利用されても、新規のGUIDが異なるため古い編集は適用できない。

更新日時や整数カウンターの初期値だけに依存せず、再登録時も別の識別子になる方式を採用した。採番・税計算・割引・支払メモの保存処理は維持する。

## 競合時の画面

通常の登録・更新・削除・即時流用の確認や操作は維持する。競合時だけ警告を表示し、画面と入力内容を保持して成功終了しない。閉じた後は一覧をDBから読み直すため、一覧から開き直すと最新内容を取得できる。競合した編集内容の自動マージ・強制上書き・自動再保存は行わない。

## DBへの適用

[更新版の移行SQL](migrations/20261019_01_revision_tokens.sql)を、税端数移行後のテスト用コピーに一回だけ適用する。対象は`t_receipts`・`t_transfers`・`t_balances`の3表で、`TEXT NOT NULL DEFAULT '0'`を1列ずつ追加する。既存行は初期版`'0'`として読み、新アプリの最初の保存からGUIDへ進む。既存の業務値・格納型・日時・税設定・割当、FKとuser_versionは変更しない。

元DDLは16表・90列・17FKの原本として保持する。税端数移行後は92列、更新版移行後は95列。適用前に3表の`PRAGMA table_info`で未追加を確認する。アプリを停止してバックアップと復元手順を確認し、旧アプリと新アプリで同じDBを同時に更新しない。利用者の実DBへの適用は未実施。

この保護は新アプリの保存経路を対象とする。旧バイナリやDBを直接書き換える処理は同じ契約に従わないため、併用対象に含めない。WAL・共有フォルダー・複数プロセスの画面E2Eは別途検証する。

## 回帰テスト

実DataAccess・製品SQLiteとFK ON/OFFで、先の保存後の更新／削除拒否、削除済み・ID再利用・不明版の拒否、全7読込、連続保存・流用、途中失敗時の版保持と再試行を検証する。拒否時はSQLite Updateイベントも監視し、子を含む書込が始まっていないことと全保存行不変を確認する。

3編集画面の通常成功と競合した更新／削除は、実際の確認・警告ダイアログを含めて検証する。画面の保持、入力不変、成功結果を返さないこと、閉じた後の再読込フラグを確認する。親一覧の全操作や利用者環境の手動操作を網羅した意味ではない。
