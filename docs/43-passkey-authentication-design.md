# 43 パスキー認証の設計

更新: 2026-10-24。**設計のみ。認証・DB接続・管理コマンドは未実装で、本番設定やDBは変更していない。** 現在のAPIは[42 APIの土台](42-api-foundation.md)の範囲。

## 決定事項と設計案

利用者確認済みの方針は、**パスキー中心でログインし、常設のパスワードを持たず、初回登録・全端末紛失時の復旧はサーバーの管理コマンドから期限付きコードを発行する**こと。以下の保存構成・API・時間設定は、その実現に向けた設計案としてレビューする。

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装しない。
- 同じHTTPSオリジンで、最小限のHTML・JavaScriptのログイン画面とAPIを提供する。ブラウザーからWebAuthn APIを呼び出す。業務画面のフレームワークは今回決めない。
- 認証アカウントと既存の`m_user`を分け、既存人物のうちログインを許可する人だけを1対1で紐付ける。公開の自己登録や、ログイン先の人物を自由に選ぶ入口は設けない。
- 共有範囲の初期案は、登録済みの利用者が1つの家計DB全体を共通権限で閲覧・編集するもの。**この共有範囲は利用者に確認中。** 支払方法の所有者・明細対象者をアクセス権とは扱わない。
- Windows版の認証切替、業務API、細かな権限、外部認証サービスとの連携は対象外とする。

## 普段のログイン

1. 固定したHTTPSのログイン画面で「パスキーでログイン」を選ぶ。
2. APIが認証チャレンジを発行し、ブラウザーが端末のパスキー選択・本人確認を行う。利用者コードやWindowsログイン名の入力は求めない。
3. APIがIdentityで応答を検証し、認証アカウントが有効で、人物への紐付けが存在することを確認する。
4. APIがログインセッションを作成してCookieを発行する。以後のAPIでは、そのセッションから利用者を解決する。

名前入力なしで認証できるよう、登録時はdiscoverable credential（ResidentKey=Required）と端末上の本人確認（UserVerification=Required）を必須にする。条件を満たさない端末へパスワード等で自動的に切り替えない。

端末の生体情報・PIN・パスキーの秘密鍵はAPIへ保存しない。APIはIdentityの標準ストアで公開鍵等を管理する。複数のパスキーを1アカウントに登録できるようにする。端末提供側の同期はアプリが実装するものではなく、別端末でも必ず使えるとはみなさない。

## 初回登録と復旧

管理操作はサーバーのローカルコマンドに限定し、Webの管理者権限や公開の管理APIは作らない。サーバーの管理権限を持つ運用担当者が対象人物を確認して実行する。コマンド名は実装時に決める。

| 操作 | 処理 |
| --- | --- |
| 初回登録コードの発行 | 未登録、または有効なパスキーがなく登録待ちの人物だけを対象にする。既存`m_user.code`を管理側で指定し、無効状態の認証アカウントと対応を作成する。登録待ちの再発行は同じアカウントを使い、古いコードを失効させる。有効なアカウントへの発行は拒否し、復旧コマンドを使う |
| 利用者による登録 | HTTPSの登録画面へコードを貼り付け、端末でパスキーを作成する。検証成功時だけ登録・アカウント有効化・コード消費を同じトランザクションで確定する |
| パスキーの追加 | ログイン済みで、直近5分以内にパスキーによる本人確認を済ませてから追加する。古いCookieだけでは追加できない |
| 紛失時の復旧コード発行 | 対象の既存パスキー・全ログインセッション・古いコードを即時失効させ、新しい再登録コードを発行する。復旧コマンドの途中失敗では全体を戻す |
| 復旧の完了 | 新しいパスキーの検証・保存とコード消費を原子的に確定する。人物への対応は変えず、旧端末は再び使えても認証できない |
| 利用停止 | 管理コマンドでアカウントと全セッションを無効化する。人物や業務データを削除しない |

登録・復旧コードは暗号学的乱数32バイト以上とし、DBにはハッシュ・対象認証ID・用途・有効期限・消費状態だけを保存する。有効期間は10分、1回限り。URLのクエリや通常ログには載せず、管理コマンドが必要時だけ表示し、登録画面からPOST本文で送る。期限切れは管理側で再発行する。

このコードはIdentityの2FA用復旧コードとは別の、パスキー登録専用の仕組みとする。コードだけでは家計APIを使えない。登録を終えた後、通常のパスキー認証でログインする。別人物への差し替え、使用済みコードの再送、登録の同時実行による二重成功を拒否する。最後のパスキーの自己削除は拒否し、削除操作にも直近の本人確認を求める。パスキー削除時は、そのアカウントの全セッションも失効させ、残ったパスキーで再ログインする。

## 人物との対応と保存先

既存SQLiteへ認証用テーブルを追加する案とする。DB間の外部キーや複数ファイルの同時復旧を持ち込まず、認証と人物の対応を一緒にバックアップする。認証用接続ではFKを有効にする。Windows版の接続設定は変えない。

SQLiteにはテーブル単位のアクセス権がないため、認証を含むDBファイルへの直接アクセスはサーバーに限定する。既存Windows版の直接接続と、このDBを本番で同時共有しない。認証の開発・検証は隔離した一時DBで進め、本番への適用はWindows版のAPI切替または並行利用をしない移行手順と合わせて判断する。今回その切替やDB移動は行わない。

| 保存対象 | 契約 |
| --- | --- |
| Identityの標準テーブル群 | 安定した認証ID、利用可否、パスキー等。パスワード・メールアドレスを必須にしない |
| `auth_user_links` | `auth_user_id TEXT NOT NULL PRIMARY KEY`、`user_code INTEGER NOT NULL UNIQUE`とし、認証アカウントと`m_user(code)`をFKで参照する。双方とも`ON DELETE RESTRICT`で、人物削除に連動して認証を消さない |
| `auth_sessions` | 推測できないセッションID、NOT NULLの認証IDとIdentityアカウントへのFK、発行日時・固定失効日時・取消状態・直近本人確認日時を保存する |
| 登録・復旧コードのテーブル | NOT NULLの対象認証IDとIdentityアカウントへのFK、用途、ハッシュ・有効期限・消費状態を管理する。生コードを保存しない |
| Data Protectionキー | Cookie等を保護するキーをコンテナ外の永続フォルダに保存する。アプリ識別子を固定し、非rootのアプリだけが読み書きできる権限を用意する |

`m_user.code`が人物のキーで、`name`・`account_name`には一意制約がない。表示名・Windowsログイン名・メールアドレスの一致で対応を自動作成しない。人物マスタに存在しても、認証アカウントがなければログインできない。

保護対象の各要求で、セッション、認証アカウントの利用可否、人物の存在と紐付けをサーバーで確認する。クライアントから送られた`user_code`で現在の本人を切り替えない。XMLへの利用者コード設定も追加しない。将来の業務入力で支払方法や対象者を選ぶ機能は、現在の本人の識別とは分ける。

## ログイン状態とHTTPの境界

- ログイン状態は最大14日、自動延長なしを初期案とする。Cookieに加え、サーバーのセッション台帳で固定失効日時・取消状態を確認する。Cookie更新があっても14日の期限を延ばさない。
- Cookieは`__Host-`接頭辞、Secure・HttpOnly・SameSite=Lax・Path=/を使い、Domainを設定しない。ブラウザーのlocalStorageへ認証トークンを保存せず、JWTや独自Bearerトークンも初期版へ追加しない。
- ログアウトは現在のセッションをDBで失効させてCookieを削除する。別のブラウザーは継続できる。利用停止・紛失復旧では全セッションを失効させ、以後の要求を拒否する。長期キャッシュで失効を遅らせない。
- Cookie認証を使うPOST・DELETE等は、ログイン・登録・ログアウトも含めCSRF対策を行う。同一オリジンで配信し、任意オリジンへの資格情報付きCORSは許可しない。
- チャレンジは5分、1回限り、ブラウザーと用途に結び付ける。消費は原子的に管理する。API再起動時には未完了チャレンジを無効にして操作をやり直す。
- 未認証・期限切れ・取消済みは401、認証後の人物対応不備は403として業務利用を拒否する。Cookieのログイン画面への302転送はAPIでは行わない。認証ストア障害も許可側に倒さない。
- 認証・コード受付にはレート制限を設け、無効・期限切れのコードや認証失敗から人物一覧を取得できない共通応答にする。Cookie・生コード・WebAuthn応答を通常ログへ記録しない。

## HTTPSと配備

パスキーの登録前に、固定HTTPSオリジンとRP ID、全端末で信頼できる証明書を決める。RP IDはドメイン、オリジンはスキーム・ホスト・ポートを含む別の値として検証する。RP IDやURLを利用者の端末ごと・接続IPごとに変えない。

実際のホスト名・接続先・鍵・コードはリポジトリへ記録せず、配備環境で設定する。証明書は管理可能なドメインの証明書、または全利用端末へ信頼を設定した内部CAを候補とし、具体的な取得方法は配備時に決める。未信頼の自己署名証明書を通常運用の前提にしない。

リバースプロキシでHTTPSを終端し、APIのポートは直接LANへ公開しない案とする。Host・転送ヘッダーは既知のプロキシと許可ホストだけを信頼する。現在のComposeはループバック公開のままで、この設計書だけではHTTPSや認証が有効にならない。

SQLiteの親フォルダとData Protectionキーを永続化し、認証テーブルを含むDBとキーを整合してバックアップする。通常のコンテナ再作成では登録したパスキーと有効なセッションを保持できる構成にする。

バックアップ復元では、復元したDBだけではバックアップ後の鍵の削除・失効を判断できない。**復元後は、人物対応を保持したまま全パスキー・セッション・コードを無効化し、管理コマンドによる再登録を済ませてから通常運用へ戻す。** 手元に残っている端末も再登録する。業務データを再計算・補正する処理は含めない。

## APIの初期契約案

| メソッド・パス | 用途と条件 |
| --- | --- |
| `GET /health` | 現行の稼働確認を維持。認証不要で、DBの正常性を示すものではない |
| `GET /auth/csrf` | 同じオリジンの画面へCSRFトークンを渡す。家計情報は返さない |
| `POST /auth/login/options` | 名前入力なしのパスキー認証オプションを発行 |
| `POST /auth/login/verify` | Identityで検証し、紐付け確認後にセッションとCookieを発行 |
| `POST /auth/enrollment/options` / `verify` | 登録・復旧コードによるパスキー登録。コードが示す認証IDに固定し、家計利用セッションは発行しない |
| `GET /auth/me` | 現在の認証IDと対応人物コード・表示名を返す。未認証は401 |
| `POST /auth/logout` | 現在のセッションを失効 |
| `GET /auth/passkeys` | 本人の登録パスキー一覧。秘密鍵等は返さない |
| `POST /auth/passkeys/options` / `verify` | 直近の本人確認を条件に、本人へパスキーを追加 |
| `DELETE /auth/passkeys/{id}` | 本人のパスキーを削除し、全セッションを失効。直近本人確認が必要で、最後の1件は拒否 |

同じログインフローによる本人再確認では対象認証IDを固定し、別人を認証したら本人確認済みにしない。ログインページ・必要な静的資産・上表の認証開始／登録・CSRF・稼働確認だけを未認証で公開し、今後の家計APIは認証必須を既定にする。具体的なJSONとIdentityの状態管理への接続は実装PRで固定する。

`MapIdentityApi`をそのまま公開してもパスキー用APIは揃わず、不要なメール・パスワード登録経路を開くため採用しない。Identityのパスキー機能へ薄いエンドポイントと画面を接続する。

## 実装順と確認条件

1. 一時DBで認証用の追加移行と人物対応を実装する。`EnsureCreated`や既存テーブルの再作成を使わず、既存の全業務行・`m_user.account_name`・過去の`update_user`・保存済み`receipt.total`を変更しない。
2. 固定HTTPSで最小のログイン／登録画面とWebAuthnの登録・認証を通す。管理コマンド、コードの失効・原子的消費、全端末紛失からの復旧を同じ段階で実装する。
3. Cookie・セッション・`me`・ログアウト・本人再確認・パスキー追加／削除、CSRF・期限・失効・コンテナ再作成を検証する。ここまでが最初の認証機能で、Windowsの接続切替や業務保存は含めない。
4. 認証が安定してからレシート、次に振替のAPIへ進む。将来APIから保存する更新者はサーバーが認証ID等の安定した識別子から決め、既存の更新者を一括変換しない。

自動テストには、重複人物対応、未登録・無効利用者、誤ったRP ID／オリジン／署名／チャレンジ、使用済み・期限切れ・同時送信、別人へのパスキー追加、Cookie期限・ログアウト・全端末失効、CSRF、移行前後の既存値保持を含める。プロトコルの自動検証と、実際のWindows Hello・スマートフォンでの操作確認を区別し、実データを要求しない。現在の実行済み件数・CIは[tests/README.md](../tests/README.md)を参照する。
