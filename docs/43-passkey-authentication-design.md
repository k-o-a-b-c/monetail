# 43 パスキー認証の設計

更新: 2026-10-24。**設計のみ。認証・DB接続・管理コマンドは未実装で、本番設定やDBは変更していない。** 現在のAPIは[42 APIの土台](42-api-foundation.md)の範囲。

## 決定事項と設計案

利用者確認済みの方針は、**パスキー中心でログインし、常設のパスワードを持たず、管理者がアカウントと期限付き登録コードを発行し、本人がパスキーを登録する**こと。ログイン状態はログインから14日・自動延長なし、管理操作とパスキー変更時の本人確認は直近5分以内とする方針も利用者が選択した。バックアップ復元後の全失効は、システム管理者が手動でコマンドを実行する。以下の保存構成・API等の詳細は、その実現に向けた設計案としてレビューする。

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装しない。
- 同じHTTPSオリジンで、最小限のHTML・JavaScriptのログイン画面とAPIを提供する。ブラウザーからWebAuthn APIを呼び出す。業務画面のフレームワークは今回決めない。
- 認証アカウントと既存の`m_user`を分け、ログインを許可する人物だけを1対1で紐付ける。人物だけを名前で登録でき、アカウントは後から同じ人物へ追加できる。人物1人にアカウントは0または1件で、アカウントには必ず1人の人物を対応させる。公開の自己登録や、ログイン先の人物を自由に選ぶ入口は設けない。
- 共有範囲の初期案は、登録済みの利用者が1つの家計DB全体を共通権限で閲覧・編集するもの。**この共有範囲は利用者に確認中。** 支払方法の所有者・明細対象者をアクセス権とは扱わない。
- アカウントを発行する管理者と一般利用者を区別する。家計データの細かな権限、Windows版の認証切替、業務API、外部認証サービスとの連携は対象外とする。

## 普段のログイン

1. 固定したHTTPSのログイン画面で「パスキーでログイン」を選ぶ。
2. APIが認証チャレンジを発行し、ブラウザーが端末のパスキー選択・本人確認を行う。利用者コードやWindowsログイン名の入力は求めない。
3. APIがIdentityで応答を検証し、認証アカウントが有効で、人物への紐付けが存在することを確認する。
4. APIがログインセッションを作成してCookieを発行する。以後のAPIでは、そのセッションから利用者を解決する。

名前入力なしで認証できるよう、登録時はdiscoverable credential（ResidentKey=Required）と端末上の本人確認（UserVerification=Required）を必須にする。条件を満たさない端末へパスワード等で自動的に切り替えない。

端末の生体情報・PIN・パスキーの秘密鍵はAPIへ保存しない。APIはIdentityの標準ストアで公開鍵等を管理する。複数のパスキーを1アカウントに登録できるようにする。端末提供側の同期はアプリが実装するものではなく、別端末でも必ず使えるとはみなさない。

## 初回登録と復旧

日常のアカウント発行・一般利用者の復旧は管理者のWeb画面から行う。管理者は既存人物を選んでアカウントと登録コードを発行し、本人へ渡す。パスキーは本人の端末で作成するため、管理者が本人の秘密鍵を作成・保管する方式にはしない。管理者画面では人物だけを追加でき、アカウントも同時に発行するかを選べるようにする。Windows版の汎用マスタメンテナンス画面は引き続き見送り、このWeb画面は人物追加とアカウント管理に限る。

新しい人物を追加する場合は表示名を入力し、「ログイン用アカウントも発行する」を選択できるようにする。人物だけの登録では、人物行だけを作り、認証アカウント・人物との認証用対応・パスキー・登録コードは作らない。ログインしない人でも明細対象者として使える。

アカウントも発行する場合は、人物・一般アカウント・人物との対応・登録コードを同じトランザクションで作成する。どちらの登録も途中失敗では全体を戻し、同じ要求の再送でも二重作成しない。後日アカウントが必要になった場合は、管理者がアカウント未登録の人物を明示的に選び、登録コードを発行する。既存の人物コードと過去の明細対象者・集計のつながりを維持し、名前一致で人物を作り直したり自動紐付けしたりしない。

`m_user.code`と表示順はサーバーで採番・設定する。新規人物の`account_name`は既存のNOT NULL制約を満たすため`api-person:<人物用ランダムID>`等の認証アカウントに依存しないサーバー生成値とし、Windowsログイン名を入力させない。この値を認証や人物対応のキーには使わない。既存人物の`account_name`は変更せず、後からアカウントを追加する際も書き換えない。

管理権限はIdentityの`Admin`ロールで認証アカウントに持たせる。人物の所有口座や明細対象者とは別で、家計データの共有範囲を決める権限ではない。一般利用者は自分のパスキーを管理できるが、他人のアカウントを発行・復旧できない。

最初の管理者はサーバーの管理コマンドから既存人物を指定して作成し、コードで本人のパスキーを登録する。最初の管理者が有効になるまで管理画面は利用できない。管理者の追加・権限変更・紛失復旧はローカルコマンドに限定し、管理画面で操作できる対象は一般アカウントだけとする。最後の有効な管理者の通常の停止・降格は拒否する。管理者もログインできない場合は、サーバーの管理権限を持つ運用担当者がローカルコマンドで復旧する。コマンド名は実装時に決める。

| 操作 | 処理 |
| --- | --- |
| 初回登録コードの発行 | 未登録、または有効なパスキーがなく登録待ちの人物だけを対象にする。既存`m_user.code`を管理者画面の人物選択または管理コマンドで指定し、無効状態の認証アカウントと対応を作成する。登録待ちの再発行は同じアカウントを使い、古いコードを失効させる。有効なアカウントへの発行は拒否し、復旧操作を使う |
| 利用者による登録 | HTTPSの登録画面へコードを貼り付け、端末でパスキーを作成する。検証成功時だけ登録・アカウント有効化・コード消費を同じトランザクションで確定する |
| パスキーの追加 | ログイン済みで、直近5分以内にパスキーによる本人確認を済ませてから追加する。古いCookieだけでは追加できない |
| 紛失時の復旧コード発行 | 対象の既存パスキー・全ログインセッション・古いコードを即時失効させ、新しい再登録コードを発行する。管理者画面・管理コマンドのどちらからでも同じ処理を使い、途中失敗では全体を戻す |
| 復旧の完了 | 新しいパスキーの検証・保存とコード消費を原子的に確定する。人物への対応は変えず、旧端末は再び使えても認証できない |
| 利用停止 | 管理者画面から一般アカウントと全セッションを無効化する。人物や業務データを削除しない |

登録・復旧コードは暗号学的乱数32バイト以上とし、DBにはハッシュ・対象認証ID・用途・有効期限・消費状態だけを保存する。有効期間は10分、1回限り。URLのクエリや通常ログには載せず、発行時に管理者画面または管理コマンドが一度だけ表示し、登録画面からPOST本文で送る。期限切れは管理側で再発行する。

管理画面のコード発行応答はキャッシュさせず、後から生コードを再表示できないようにする。再発行時は古いコードを失効させる。管理操作は認証ID・対象・操作・日時・結果を記録し、コード自体を監査記録へ残さない。

このコードはIdentityの2FA用復旧コードとは別の、パスキー登録専用の仕組みとする。コードだけでは家計APIを使えない。登録を終えた後、通常のパスキー認証でログインする。別人物への差し替え、使用済みコードの再送、登録の同時実行による二重成功を拒否する。最後のパスキーの自己削除は拒否し、削除操作にも直近の本人確認を求める。パスキー削除時は、そのアカウントの全セッションも失効させ、残ったパスキーで再ログインする。

## 既存Windows版DBからの移行

既存DBの人物・取引・対象者の関係をそのまま維持し、認証用テーブルを追加する。既存DBにパスキーはないため、ここでは**再登録ではなく初回登録**となる。

1. バックアップしたテスト用コピーで追加移行と既存値保持を確認する。本番切替は後述のファイルアクセス境界と合わせて行う。
2. 管理コマンドで既存の人物コードを指定し、その人物に認証アカウントと初回登録コードを発行する。最初の管理者もこの手順で作成する。
3. 本人が固定HTTPSの登録画面でコードを入力し、パスキーを登録する。人物を作り直したり、既存の所有者・対象者のコードを付け替えたりしない。
4. 他の人物も管理コマンドまたは管理者画面で同じように初回登録する。ログイン不要の人物にはアカウントを作らない。

移行コマンドの再実行で既存アカウントや対応を重複作成せず、既に有効なアカウントの鍵・セッションを初回登録扱いで失効させない。既存利用者の端末紛失やRP ID変更時には、用途を分けた再登録手続を使う。通常のサーバー移設では、同じRP ID・認証DB・Data Protectionキーを維持できればパスキーを再登録する必要はない。バックアップ復元後の全失効は、後述する別のケースとして扱う。

## 人物との対応と保存先

既存SQLiteへ認証用テーブルを追加する案とする。DB間の外部キーや複数ファイルの同時復旧を持ち込まず、認証と人物の対応を一緒にバックアップする。認証用接続ではFKを有効にする。Windows版の接続設定は変えない。

SQLiteにはテーブル単位のアクセス権がないため、認証を含むDBファイルへの直接アクセスはサーバーに限定する。既存Windows版の直接接続と、このDBを本番で同時共有しない。認証の開発・検証は隔離した一時DBで進め、本番への適用はWindows版のAPI切替または並行利用をしない移行手順と合わせて判断する。今回その切替やDB移動は行わない。

| 保存対象 | 契約 |
| --- | --- |
| Identityの標準テーブル群 | 安定した認証ID、利用可否、パスキー、管理者ロール等。パスワード・メールアドレスを必須にしない |
| `auth_user_links` | `auth_user_id TEXT NOT NULL PRIMARY KEY`、`user_code INTEGER NOT NULL UNIQUE`とし、認証アカウントと`m_user(code)`をFKで参照する。双方とも`ON DELETE RESTRICT`で、人物削除に連動して認証を消さない |
| `auth_sessions` | 推測できないセッションID、NOT NULLの認証IDとIdentityアカウントへのFK、発行日時・固定失効日時・取消状態・直近本人確認日時を保存する |
| 登録・復旧コードのテーブル | NOT NULLの対象認証IDとIdentityアカウントへのFK、用途、ハッシュ・有効期限・消費状態を管理する。生コードを保存しない |
| Data Protectionキー | Cookie等を保護するキーをコンテナ外の永続フォルダに保存する。アプリ識別子を固定し、非rootのアプリだけが読み書きできる権限を用意する |

`m_user.code`が人物のキーで、`name`・`account_name`には一意制約がない。表示名・Windowsログイン名・メールアドレスの一致で対応を自動作成しない。人物マスタに存在しても、認証アカウントがなければログインできない。

保護対象の各要求で、セッション、認証アカウントの利用可否、人物の存在と紐付けをサーバーで確認する。クライアントから送られた`user_code`で現在の本人を切り替えない。XMLへの利用者コード設定も追加しない。将来の業務入力で支払方法や対象者を選ぶ機能は、現在の本人の識別とは分ける。

## ログイン状態とHTTPの境界

- ログイン状態はログイン成功時から最大14日、自動延長なしとする（利用者決定）。Cookieに加え、サーバーのセッション台帳で固定失効日時・取消状態を確認する。Cookie更新があっても14日の期限を延ばさない。
- Cookieは`__Host-`接頭辞、Secure・HttpOnly・SameSite=Lax・Path=/を使い、Domainを設定しない。ブラウザーのlocalStorageへ認証トークンを保存せず、JWTや独自Bearerトークンも初期版へ追加しない。
- ログアウトは現在のセッションをDBで失効させてCookieを削除する。別のブラウザーは継続できる。利用停止・紛失復旧では全セッションを失効させ、以後の要求を拒否する。長期キャッシュで失効を遅らせない。
- Cookie認証を使うPOST・DELETE等は、ログイン・登録・ログアウトも含めCSRF対策を行う。同一オリジンで配信し、任意オリジンへの資格情報付きCORSは許可しない。
- チャレンジは5分、1回限り、ブラウザーと用途に結び付ける。消費は原子的に管理する。API再起動時には未完了チャレンジを無効にして操作をやり直す。
- 未認証・期限切れ・取消済みは401、認証後の人物対応不備は403として業務利用を拒否する。Cookieのログイン画面への302転送はAPIでは行わない。認証ストア障害も許可側に倒さない。
- 認証・コード受付にはレート制限を設け、無効・期限切れのコードや認証失敗から人物一覧を取得できない共通応答にする。Cookie・生コード・WebAuthn応答を通常ログへ記録しない。

## HTTPSと配備

パスキーの登録前に、固定HTTPSオリジンとRP ID、全端末で信頼できる証明書を決める。RP IDはドメイン、オリジンはスキーム・ホスト・ポートを含む別の値として検証する。RP IDやURLを利用者の端末ごと・接続IPごとに変えない。

実際のホスト名・接続先・鍵・コードはリポジトリへ記録せず、配備環境で設定する。URL・証明書の具体的な調達方法は運用側で扱い、本書には記載しない。設計では固定HTTPSオリジン・RP IDを設定から指定し、端末が証明書を信頼できることを前提とする。

HTTPS終端の配置は運用側で決め、APIへの接続と外部設定を整える。Host・転送ヘッダーは既知のプロキシと許可ホストだけを信頼する。現在のComposeはループバック公開のままで、この設計書だけではHTTPSや認証が有効にならない。

SQLiteの親フォルダとData Protectionキーを永続化し、認証テーブルを含むDBとキーを整合してバックアップする。通常のコンテナ再作成では登録したパスキーと有効なセッションを保持できる構成にする。

バックアップ復元では、復元したDBだけではバックアップ後の鍵の削除・失効を判断できない。**復元後は、人物対応を保持したまま全パスキー・セッション・コードを無効化し、管理コマンドによる再登録を済ませてから通常運用へ戻す。** 手元に残っている端末も再登録する。業務データを再計算・補正する処理は含めない。 システム管理者がサービスを停止した状態で手動の管理コマンドを実行し、全失効の完了後にサービスを再開する。その後、最初に管理者のパスキーを再登録し、管理者画面から他の利用者の再登録コードを発行する。バックアップの取得だけではリセットしない。

## APIの初期契約案

| メソッド・パス | 用途と条件 |
| --- | --- |
| `GET /health` | 現行の稼働確認を維持。認証不要で、DBの正常性を示すものではない |
| `GET /auth/csrf` | 同じオリジンの画面へCSRFトークンを渡す。家計情報は返さない |
| `POST /auth/login/options` | 名前入力なしのパスキー認証オプションを発行 |
| `POST /auth/login/verify` | Identityで検証し、紐付け確認後にセッションとCookieを発行 |
| `POST /auth/enrollment/options` / `verify` | 登録・復旧コードによるパスキー登録。コードが示す認証IDに固定し、家計利用セッションは発行しない |
| `GET /auth/me` | 現在の認証IDと対応人物コード・表示名を返す。未認証は401 |
| `POST /auth/logout` | 現在のセッションを失効 |
| `GET /auth/passkeys` | 本人の登録パスキー一覧。秘密鍵等は返さない |
| `POST /auth/passkeys/options` / `verify` | 直近の本人確認を条件に、本人へパスキーを追加 |
| `DELETE /auth/passkeys/{id}` | 本人のパスキーを削除し、全セッションを失効。直近本人確認が必要で、最後の1件は拒否 |

### 管理者画面とAPI

`/admin/accounts`で、既存人物・アカウント状態を確認し、新しい人物の追加、一般アカウントの発行・コード再発行・紛失復旧・利用停止を行う。管理者ロールの有無はサーバーで要求ごとに確認し、管理権限を取り消した古いCookieでは操作できない。変更操作は直近5分以内のパスキー本人確認とCSRF検証を必須にする。

| メソッド・パス | 管理者だけが行える処理 |
| --- | --- |
| `GET /admin/accounts` | 人物候補とアカウントの状態を取得。コードや鍵は返さない |
| `POST /admin/people` | 表示名から人物だけを登録。認証アカウントや登録コードは作らない |
| `POST /admin/accounts` | アカウント未登録の既存人物を選ぶか、新規人物と同時に一般アカウント・初回登録コードを発行。人物選択と新規追加は同時に指定できず、ロールの指定も受け付けない |
| `POST /admin/accounts/{id}/enrollment-code` | 登録待ちの一般アカウントのコードを再発行 |
| `POST /admin/accounts/{id}/recovery-code` | 一般アカウントの旧パスキー・全セッションを失効し、再登録コードを発行 |
| `POST /admin/accounts/{id}/disable` | 一般アカウントを利用停止し、全セッションと未使用コードを失効 |

アカウント発行や復旧によって、管理者本人が対象者としてログインするセッションは作らない。管理APIの対象ID・入力値から管理者ロールを付与する入口も設けない。

同じログインフローによる本人再確認では対象認証IDを固定し、別人を認証したら本人確認済みにしない。ログインページ・必要な静的資産・上表の認証開始／登録・CSRF・稼働確認だけを未認証で公開し、今後の家計APIは認証必須を既定にする。具体的なJSONとIdentityの状態管理への接続は実装PRで固定する。

`MapIdentityApi`をそのまま公開してもパスキー用APIは揃わず、不要なメール・パスワード登録経路を開くため採用しない。Identityのパスキー機能へ薄いエンドポイントと画面を接続する。

## 実装順と確認条件

1. 一時DBで認証用の追加移行、既存人物の初回登録コマンド、新規人物追加とアカウント発行を実装する。`EnsureCreated`や既存テーブルの再作成を使わず、既存の全業務行・既存人物の`m_user.account_name`・過去の`update_user`・保存済み`receipt.total`を変更しない。
2. 固定HTTPSで最小のログイン／登録画面とWebAuthnの登録・認証を通す。管理者のアカウント発行画面・APIと、初期管理者／緊急復旧の管理コマンド、コードの失効・原子的消費、全端末紛失からの復旧を同じ段階で実装する。
3. Cookie・セッション・`me`・ログアウト・本人再確認・パスキー追加／削除、CSRF・期限・失効・コンテナ再作成を検証する。ここまでが最初の認証機能で、Windowsの接続切替や業務保存は含めない。
4. 認証が安定してからレシート、次に振替のAPIへ進む。将来APIから保存する更新者はサーバーが認証ID等の安定した識別子から決め、既存の更新者を一括変換しない。

自動テストには、未認証・一般利用者による管理API拒否、直近本人確認の必須化、管理権限取消の即時反映、管理者アカウントへの管理画面からの操作拒否、最後の管理者保護、コードの非再表示、人物だけの登録と認証情報非作成、同じ人物への後日のアカウント追加と過去の対象者参照保持、新規人物・アカウント発行の原子性と再送時の二重作成防止、移行コマンドの再実行、重複人物対応、未登録・無効利用者、誤ったRP ID／オリジン／署名／チャレンジ、使用済み・期限切れ・同時送信、別人へのパスキー追加、Cookie期限・ログアウト・全端末失効、CSRF、移行前後の既存値保持を含める。プロトコルの自動検証と、実際のWindows Hello・スマートフォンでの操作確認を区別し、実データを要求しない。現在の実行済み件数・CIは[tests/README.md](../tests/README.md)を参照する。
