# 43 パスキー認証の設計

更新: 2026-10-27。**アカウント登録・ログイン・セッション・本人再確認・パスキー管理・全失効と、全体管理者のアカウント一覧・初回コード発行・再発行APIを実装。認証は人物との対応に依存しない。** Web管理画面、新規空DBの準備、家計簿の作成・参加・業務APIは未実装。本番設定・実データは変更していない。現在の検証結果は[tests/README.md](../tests/README.md)を参照する。

## アカウントと人物

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装せず、常設パスワードを持たない（DEC-026）。
- アカウントはMonetail全体で独立して新規作成する。人物の存在・選択・紐付けを登録・ログイン・セッション検証・復旧の条件にしない。人物名やWindows用`account_name`からアカウントを自動作成・統合しない（DEC-044・045）。
- アカウント自身の`DisplayName`は、初回パスキー登録時に本人が入力する。前後の空白を除き、空白のみ不可・100文字以内・同名可とする。上限は.NETの`string.Length`とHTMLの`maxlength`で扱う。復旧再登録では保存済み表示名を維持し、別の名前を送っても変更しない。名前変更APIは今回追加しない。
- 既存の人物名を表示名へコピーしたり、認証IDを仮の表示名として補完したりしない。既存認証行も削除・再作成しない。表示名未設定の旧アカウントは`null`のまま保持する。既存人物への対応は家計簿側で任意に設定する後続機能とする。
- 表示名は本人識別・ロール・家計簿権限の根拠にしない。認証ID、セッション、鍵の所有者で本人を確認する。人物の作成・名前変更・対応変更・削除はログイン可否へ影響しない。
- 家計簿内の任意のアカウント→人物→支払方法の対応は、その家計簿の管理者が設定する方針（DEC-044）。旧`auth_user_links`は履歴保持用であり、この家計簿対応の代用にはしない。

## 新規利用と実装範囲

新規利用を基本とする（DEC-037〜039、[56](56-new-user-onboarding-policy.md)）。目標の導線は「Docker起動 → 初期設定コマンドでDB準備・最初の管理者用コード発行 → 共通画面で表示名・パスキー登録 → 明示ログイン → 家計簿作成またはアカウント招待」。**新規空DBの準備は未実装**で、現在の`migrate-auth-db`は既存業務DBのコピーを要求する。

最初の全体管理者は、明示移行後に`initialize-admin`で人物を指定せず作成する。認証ID・Adminロール・無効状態・登録コードを原子的に保存する。管理者が既にいれば何も変更せず終了し、コードも再表示しない。コマンド例・再発行は[45](45-initial-admin-enrollment.md)、全失効・緊急復旧は[49](49-authentication-revocation-recovery.md)を参照する。

2人目以降の新規登録は全体管理者の招待を必須にする。全体管理者が`POST /admin/accounts`で無効な一般アカウントとコードを先に発行し、本人が登録画面で表示名とパスキーを登録して利用可能にする。通常の招待ではAdminを付与しない。登録だけで家計簿へ参加したことにせず、家計簿の参加招待とは別に扱う。公開登録や人物を自由に選んで本人確認を代替する入口は設けない。

アカウント一覧は全体管理者専用。家計簿管理者だけの権限では一覧・検索・存在照会を提供しない。管理画面は後続で、現在はAPIまで実装している。

## 認証コードの境界

別アプリのアカウントは独立させ、認証コードを流用しやすい構成を目指す（DEC-036、[52](52-reusable-authentication-boundaries.md)）。共通アカウント・共通ログインは採用しない。旧人物照合窓口`IAccountPersonLookup`とMonetail側の実装は不要となり削除した。[53](53-account-person-lookup.md)は過去の実装記録。`CurrentSession`とチャレンジも人物コードを保持しない。

互換性のため旧人物対応モデル・移行履歴・発行履歴の人物コード列は残す。新規空DBや家計簿データのスキーマは後続設計であり、認証基盤を別ライブラリにする作業は今回含めない。

## 普段のログイン

1. 固定HTTPSの`/auth/login`で「パスキーでログイン」を選ぶ。
2. APIがチャレンジを発行し、ブラウザーでパスキー選択・端末の本人確認を行う。利用者コードやWindowsログイン名は入力しない。
3. Identityが署名・Origin・RP ID・チャレンジ・UV・鍵の所有者等を検証し、有効なアカウントを確認する。
4. SQLiteの同じ書込トランザクションで鍵状態と新しいセッションを保存し、Cookieを発行する。途中失敗は両方を戻す。失効・削除済みの鍵からセッションを作らない。

discoverable credential（ResidentKey=Required）とUserVerification=Requiredを必須にする。未対応端末へパスワード等で自動的に切り替えない。端末の生体情報・PIN・秘密鍵をAPIへ保存せず、公開鍵等はIdentity標準ストアで管理する。1アカウントに複数パスキーを登録できる。端末提供側の同期をアプリ側の保証とは扱わない。

## 登録コードと全失効

| 操作 | 処理 |
| --- | --- |
| 新規発行 | 全体管理者が人物を選ばず新規一般アカウントと初回コードを発行する。要求IDは管理者と作成先を固定し、同じ要求の再送で二重作成しない |
| 登録 | `/auth/enroll`へコードと初回表示名を入力する。標準検証成功時だけ表示名・鍵・有効化・コード消費を同じトランザクションで確定する。自動ログインしない |
| コード再発行 | 無効かつ鍵なしの既存アカウントが対象。一般・管理者を問わず同じ認証ID・表示名・ロールを保持し、旧未使用コードの失効と新コード保存を同時に行う |
| 鍵の追加 | ログイン中の同一アカウント・同一セッションと直近5分未満の本人確認を要求する。名前はアカウント自身の表示名を使う |
| 鍵の自己削除 | 直近本人確認が必要。最後の1件は拒否し、成功時はそのアカウントの全セッションを失効させる。残る鍵で再ログインする |
| 全失効 | 利用停止・紛失で同じ処理を使う。アカウントを無効化し、全鍵・全セッション・未使用コードを失効させる。コードは自動発行しない。人物・業務値・認証ID・表示名・ロール・旧対応は保持する |

状態は「アカウント未作成 → 登録待ち → 利用中 → 停止中 → 登録待ち → 利用中」。人物だけの登録はこの遷移に含めない。復旧では別操作でコードを発行し、本人の再登録成功時だけ有効にする。期限切れや発行だけでは利用中に戻らない。管理者が本人としてログインするセッションも作らない。

現在のコードは暗号学的乱数32バイト・発行から10分・1回限り。DBにはSHA-256ハッシュ・対象認証ID・用途・UTC期限・消費／取消状態を保存し、生コードを保存しない。発行成功時に一度だけ表示し、再送では再表示しない。クエリ・通常ログ・監査記録に生コードを含めず、登録画面からPOST本文で送る。Identityの2FA復旧コードとは別の仕組み。将来の招待の有効期間は[56](56-new-user-onboarding-policy.md)で別に検討する。

全失効のHTTP操作、Web管理画面、追加全体管理者の管理・権限変更は後続。無効・鍵なしの管理者には別の有効な管理者から再発行できる。最後のログイン可能な管理者の通常停止は拒否し、全員がログイン不能になった場合はサーバーの管理コマンドで明示的に緊急復旧する。停止と再発行は別操作のまま保つ。

## 保存と移行

| 保存対象 | 契約 |
| --- | --- |
| Identity標準テーブル群 | 安定した認証ID、利用可否、パスキー、ロール等。パスワード・メールアドレスは必須にしない |
| `AspNetUsers.DisplayName` | アカウント自身の表示名。未登録・旧行はNULL、初回検証成功時に保存し、復旧時は維持 |
| `auth_user_links` | 旧版の1対1対応をそのまま保持する。NOT NULL・UNIQUE・FK・RESTRICTも維持するが、新規発行や認証では読み書きしない |
| `auth_account_creation_requests` | 要求ID・発行者ID・新規アカウントID・発行日時。旧`UserCode`はNULL許容へ移行し、新規発行はNULL、過去の値は保持する |
| `auth_sessions` | セッションIDのハッシュ、認証ID、発行・固定期限・取消・直近確認日時。タイムゾーンは保存しない |
| `auth_enrollment_codes` | ハッシュと登録用途・認証ID・UTC期限・消費／取消状態。生コードなし |
| Data Protectionキー | コンテナ外の永続フォルダへ保存し、アプリ識別子を固定する。非rootアプリのアクセス権を整える |

`20261026235549_AddIndependentAccounts`は表示名列の追加と発行履歴の人物コードのNULL許容化を行う。人物名のコピー、業務表の再作成、過去の更新者や`receipt.total`の再計算・補完はしない。明示的な`migrate-auth-db`で適用し、通常起動・HTTP要求で自動移行しない。人物未指定の発行履歴は旧版で表現できないため、旧版へ戻す必要がある場合は、書込停止と移行前バックアップからの復元を運用で判断する。

既存Windows版DBの移行は一度きりの運用手順・必要最小限のスクリプトで扱い、常設画面・APIは作らない。認証アカウントは新規作成し、本人が表示名とパスキーを登録する。既存人物・所有者・明細対象者の関係は保持し、後続の家計簿機能で必要な人物へ任意に紐付ける。名前一致によるコピー・自動統合は行わない。

## セッションとHTTPの境界

- 期限はログイン成功から13日（312時間）経過後、ログイン時の端末の地域で次に迎える午前2時（DEC-034）。日本時間で10月1日20時なら10月15日2時、10月1日1時なら10月14日2時。312時間後が午前2時ちょうどなら翌日とする。
- ブラウザーの`Intl.DateTimeFormat().resolvedOptions().timeZone`で得るIANA地域IDをサーバーで検証し、ログインチャレンジにだけ結び付ける。未取得・不正・非対応は`TimeZoneInfo.Local`へ補完する。端末時計やUTCオフセットを時刻の根拠にしない。
- 夏時間で午前2時が欠落する日は切替直後の最初の有効時刻、重複する日は早い方を候補とし、312時間後以前なら翌日の候補へ進む。通常は13日超〜14日だが時差変更の影響は生じる。
- ログイン時にUTC期限を保存し、Cookieも同じ日時で失効させる。地域はセッション・Cookieへ保存しない。旅行・端末地域・サーバー地域変更で既存期限を再計算しない。要求時は台帳を照合し、期限以上なら定時バッチを待たず拒否する。
- 再確認は同じアカウント・セッションの`VerifiedAtUtc`だけを更新し、固定期限を延ばさない。通常操作も滑動延長しない。重要操作は直近5分未満かつ未来でない確認日時を要求する。残り1日の再ログイン案内は設けない。
- Cookieは`__Host-`、Secure・HttpOnly・SameSite=Lax・Path=/・Domainなし。localStorageのトークン、JWT、独自Bearerは追加しない。ログアウトは現在セッションだけ、全失効や鍵削除では全セッションを失効させる。
- 各保護要求でセッション・有効アカウント・最新ロールを検証する。人物コードを送って本人を切り替えず、XMLの利用者コード設定も採用しない。未認証・失効・利用停止は401、権限不足・重要操作の確認期限切れは403、認証DB障害は503。人物未対応を403にする経路は削除した。302転送しない。
- 同じHTTPSオリジンから配信し、POST・DELETE等は登録・ログイン・ログアウトもCSRFを検証する。資格情報付きの任意CORSを許可しない。本文64 KiB、認証更新を合わせてIPごと1分20回、待ち行列なし。GET一覧はこの更新枠を消費しない。
- チャレンジは5分・1回限り・ブラウザー／用途固定。再開始で置換し、再起動で未完了分を破棄する。再確認と鍵追加はアカウントID・開始セッションのハッシュでも固定する。Cookie・生コード・WebAuthn応答を通常ログに出さない。
- 将来の業務入力では、入力途中の失効でも画面に入力を保持し、再ログイン後に本人が確認して登録する。自動再送や別アカウントへの引継ぎはしない。ブラウザーストレージの永続化は前提にしない。

## API契約

| メソッド・パス | 用途・応答 |
| --- | --- |
| `GET /health` | 未認証の稼働確認。DBの正常性は示さない |
| `GET /auth/csrf` | 同一OriginへCSRFトークンを返す |
| `POST /auth/login/options` / `verify` | 名前入力なしの標準認証、開始時に地域IDを受け取り、成功時にセッションとCookieを発行 |
| `POST /auth/enrollment/options` / `verify` | optionsへ`code`と初回`displayName`、verifyへ標準資格情報を送る。登録先はコードで固定し、自動ログインしない |
| `GET /auth/me` | `authUserId`、アカウントの`displayName`、`expiresAtUtc`、`verifiedAtUtc`。人物コードは返さない |
| `POST /auth/logout` | 現在セッションを失効 |
| `POST /auth/reauthentication/options` / `verify` | 有効セッションの本人を再確認。期限は延ばさない |
| `GET /auth/passkeys` | 本人の鍵メタデータだけを返す |
| `POST /auth/passkeys/options` / `verify` | 直近本人確認後に本人へ鍵を追加 |
| `DELETE /auth/passkeys/{id}` | 最後の鍵を拒否し、削除成功時は全セッションを失効 |
| `GET /admin/accounts` | 全体Admin専用。アカウントID順の`authUserId`・`displayName`・`isEnabled`。人物行は含めない（[51](51-admin-account-list.md)） |
| `POST /admin/accounts` | 全体Admin・直近本人確認・CSRFが必要。`requestId`だけを受け取り、新規一般アカウントとコードを発行（[54](54-admin-account-creation.md)） |
| `POST /admin/accounts/{id}/enrollment-code` | 同じ条件で無効・鍵なしの一般／Adminへ再発行（[55](55-admin-enrollment-code-reissue.md)） |

メール・パスワード登録を開く`MapIdentityApi`は使わず、標準パスキー機能へ薄い受付と画面を接続する。既定は`/health`だけ、固定HTTPS設定を指定したときに認証・管理者APIを公開する。管理者の全失効HTTP経路・権限変更は未実装であり、この表に含めない。人物の追加は家計簿側の後続機能とする。

## HTTPS・バックアップ

固定HTTPSオリジン（スキーム・ホスト・ポート）とRP ID（ドメイン）、端末で信頼できる証明書を運用側で用意する。具体的な調達方法・接続先・秘密は文書へ記録しない。HTTPS終端は配備側で決め、Hostと転送ヘッダーは既知プロキシ・許可ホストだけを信頼する。現在のComposeはループバック公開で、自動的にHTTPSを用意しない。

Dockerの地域は既定`Etc/UTC`、Composeの`TZ`で変更できる。ホスト地域の自動引継ぎを前提にせず、地域データを含むイメージで.NETの解決結果を起動ログとコンテナ検証で確認する。

DB親フォルダとData Protectionキーを永続化し、整合したバックアップを取る。通常のコンテナ再作成では鍵・有効セッションを保持する。同じRP ID・DB・Data Protectionキーを維持する通常移設は再登録不要。RP IDを変える場合は再登録を計画する。

バックアップ復元後は、サービス停止中にシステム管理者が手動で全失効コマンドを実行する（[49](49-authentication-revocation-recovery.md)）。認証ID・表示名・ロール・旧人物対応・業務データは保持する。手元にある鍵も再登録し、まず管理者を復旧してから他利用者へコードを発行する。バックアップ取得だけではリセットしない。DB自体の暗号化は今回含めない（DEC-030）。

## 後続の家計簿・検証

家計簿は全登録利用者が作成でき、同じアカウントが複数参加できる。家計簿管理者が参加を招待し、招待受領者はログインして参加を確定する。人物・業務マスタ・取引は家計簿ごとに管理し、SQLite 1ファイルを家計簿IDで区分する（DEC-035・039〜041）。

参加直後は閲覧者。編集者・家計簿管理者と区別し、全体Adminを家計簿権限の代用にしない。編集者の支払方法編集は任意の人物対応から自分のものを判定し、振替は両側の編集権限を確認する（DEC-043・044）。件数制約・具体スキーマ・作成時の管理者割当・取引の詳細権限は[57](57-ledger-data-ownership.md)で後続設計する。新規入力者／更新者はログインIDからサーバーで記録する方針で、既存保存値は一括変換しない。

自動検証は標準Identityの合成EC署名・実SQLite・Cookieを使い、人物なしの登録／認証／管理、表示名の上限・同名・復旧維持、権限・期限・失効・競合・保存失敗のRollback・移行前後の既存全保存値を確認する。実Windows Hello／スマートフォンと本番配備は別の未実施確認として扱う。認証安定後は新規初期化と家計簿基盤を整え、レシート入力、次に振替へ進む。
