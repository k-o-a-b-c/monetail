# 43 パスキー認証の設計

更新: 2026-10-28。**認証と全体アカウント管理APIの現行契約。認証は人物との対応に依存しない。招待リンクによる登録画面は未実装。** DB準備・運用は[42](42-api-foundation.md)、家計簿のAPIと後続設計は[58](58-ledger-foundation-design.md)、検証結果は[tests/README](../tests/README.md)を正本とする。

## アカウントと人物

- ASP.NET Core 10 Identityのパスキー登録・検証とCookie認証を使う。暗号検証を独自実装せず、常設パスワードを持たない（DEC-026）。
- アカウントはMonetail全体で独立して新規作成する。人物の存在・選択・紐付けを登録・ログイン・セッション検証・復旧の条件にしない。人物名やWindows用`account_name`からアカウントを自動作成・統合しない（DEC-044・045）。
- アカウント自身の`DisplayName`は、初回パスキー登録時に本人が入力する。前後の空白を除き、空白のみ不可・100文字以内・同名可とする。上限は.NETの`string.Length`とHTMLの`maxlength`で扱う。復旧再登録では保存済み表示名を維持し、別の名前を送っても変更しない。名前変更APIは今回追加しない。
- 既存の人物名を表示名へコピーしたり、認証IDを仮の表示名として補完したりしない。既存認証行も削除・再作成しない。表示名未設定の旧アカウントは`null`のまま保持する。既存人物への対応は家計簿側で任意に設定する後続機能とする。
- 表示名は本人識別・ロール・家計簿権限の根拠にしない。認証ID、セッション、鍵の所有者で本人を確認する。人物の作成・名前変更・対応変更・削除はログイン可否へ影響しない。
- 家計簿内の任意のアカウント→人物→支払方法の対応は、その家計簿の管理者が設定する方針（DEC-044）。認証アカウントの登録・ログインの必須条件にはしない。

## 実装と導入の境界

この文書は認証と全体アカウント管理APIを扱う。起動設定と管理コマンドは[42](42-api-foundation.md)、新規利用と家計簿の設計は[58](58-ledger-foundation-design.md)を正本とする。

## 認証コードの境界

別アプリのアカウントは独立させ、認証コードを流用しやすい構成を目指す（DEC-036、[構成](04-architecture.md)）。共通アカウント・共通ログインは採用しない。`CurrentSession`とチャレンジはアカウントの識別情報を扱う。

全体のアカウント管理APIは`Features/Accounts`、発行要求の保存モデルは`Authentication`に配置し、認証基盤から家計簿機能への参照を持たせない。APIのURL・入出力・認証条件は維持する。

APIは未リリースであり、過去の開発案との互換モデル・旧コマンド専用の処理は持たせない。空DBの初期定義はEFで管理し、家計簿データのスキーマは後続設計とする。

## 普段のログイン

1. 固定HTTPSのログイン画面で「ログイン」を選ぶ。画面自体は未実装で、表示・遷移は[58](58-ledger-foundation-design.md#登録ログインの3画面dec-050未実装)を正本とする。
2. APIがチャレンジを発行し、ブラウザーでパスキー選択・端末の本人確認を行う。利用者コードやWindowsログイン名は入力しない。
3. Identityが署名・Origin・RP ID・チャレンジ・UV・鍵の所有者等を検証し、有効なアカウントを確認する。
4. SQLiteの同じ書込トランザクションで鍵状態と新しいセッションを保存し、Cookieを発行する。途中失敗は両方を戻す。失効・削除済みの鍵からセッションを作らない。

discoverable credential（ResidentKey=Required）とUserVerification=Requiredを必須にする。未対応端末へパスワード等で自動的に切り替えない。端末の生体情報・PIN・秘密鍵をAPIへ保存せず、公開鍵等はIdentity標準ストアで管理する。1アカウントに複数パスキーを登録できる。端末提供側の同期をアプリ側の保証とは扱わない。

## 登録コードと全失効

| 操作 | 処理 |
| --- | --- |
| 新規発行 | 全体管理者が人物を選ばず新規一般アカウントと初回コードを発行する。要求IDは管理者と作成先を固定し、同じ要求の再送で二重作成しない |
| 登録 | APIはコードと初回表示名を受け取る。画面ではコードを手入力せず、下記の招待リンクから取得する方針。標準検証成功時だけ表示名・鍵・有効化・コード消費を同じトランザクションで確定する。自動ログインしない |
| コード再発行 | 無効かつ鍵なしの既存アカウントが対象。一般・管理者を問わず同じ認証ID・表示名・ロールを保持し、旧未使用コードの失効と新コード保存を同時に行う |
| 鍵の追加 | ログイン中の同一アカウント・同一セッションと直近5分未満の本人確認を要求する。名前はアカウント自身の表示名を使う |
| 鍵の自己削除 | 直近本人確認が必要。最後の1件は拒否し、成功時はそのアカウントの全セッションを失効させる。残る鍵で再ログインする |
| 全失効 | 利用停止・紛失で同じ処理を使う。アカウントを無効化し、全鍵・全セッション・未使用コードを失効させる。コードは自動発行しない。人物・業務値・認証ID・表示名・ロール・旧対応は保持する |

状態は「アカウント未作成 → 登録待ち → 利用中 → 停止中 → 登録待ち → 利用中」。人物だけの登録はこの遷移に含めない。復旧では別操作でコードを発行し、本人の再登録成功時だけ有効にする。期限切れや発行だけでは利用中に戻らない。管理者が本人としてログインするセッションも作らない。

現在のコードは暗号学的乱数32バイト・発行から10分・1回限り。DBにはSHA-256ハッシュ・対象認証ID・用途・UTC期限・消費／取消状態を保存し、生コードを保存しない。発行成功時に一度だけ表示し、再送では再表示しない。クエリ・通常ログ・監査記録に生コードを含めず、登録画面からPOST本文で送る。Identityの2FA復旧コードとは別の仕組み。家計簿参加招待の条件は[家計簿設計](58-ledger-foundation-design.md)を参照する。

全失効のHTTP操作、Web管理画面、追加全体管理者の管理・権限変更は後続。無効・鍵なしの管理者には別の有効な管理者から再発行できる。最後のログイン可能な管理者の通常停止は拒否し、全員がログイン不能になった場合はサーバーの管理コマンドで明示的に緊急復旧する。停止と再発行は別操作のまま保つ。

### アカウント登録の招待リンク（DEC-050・未実装）

全体管理者がアカウント一覧から招待リンクを発行し、本人へ個別に渡す方式を採用する。リンクを開いた利用者は表示名だけ入力し、登録ボタンからパスキーを作成する。初回管理者もコマンドが出力する招待リンクから登録する方針とする。画面仕様は[58](58-ledger-foundation-design.md#登録ログインの3画面dec-050未実装)を参照する。

リンク内部の推測困難な登録用トークンは、現在のコードと同じ暗号学的乱数32バイト・10分・1回限り・DBはSHA-256ハッシュのみの条件を維持する。リンクを持つ人が登録できるため、通常ログ・監査記録へリンク全体や生トークンを残さない。登録先アカウントは引き続きトークンで固定し、登録・消費の確定条件を緩めない。

現在のAPIは`code`を返し、管理コマンドは生コードを出力する。招待リンク生成・受け渡し・画面はまだ実装しておらず、[42の現行コマンド](42-api-foundation.md#db移行登録復旧コマンド)の出力が変更済みという意味ではない。URL内のトークンの持たせ方、ブラウザー履歴等への残留対策、CLIでの固定HTTPS URLの取得方法、APIの応答へリンクを追加するかは実装前に具体化する。

## 保存と移行

| 保存対象 | 契約 |
| --- | --- |
| Identity標準テーブル群 | 安定した認証ID、利用可否、パスキー、ロール等。パスワード・メールアドレスは必須にしない |
| `AspNetUsers.DisplayName` | アカウント自身の表示名。未登録はNULL、初回検証成功時に保存し、復旧時は維持 |
| `auth_account_creation_requests` | 要求ID・発行者ID・新規アカウントID・発行日時。人物コードを含めない |
| `auth_sessions` | セッションIDのハッシュ、認証ID、発行・固定期限・取消・直近確認日時。タイムゾーンは保存しない |
| `auth_enrollment_codes` | ハッシュと登録用途・認証ID・UTC期限・消費／取消状態。生コードなし |
| Data Protectionキー | コンテナ外の永続フォルダへ保存し、アプリ識別子を固定する。非rootアプリのアクセス権を整える |

認証ストアは人物テーブル・旧人物リンク・人物コードへのFKを持たない。新規DBの準備・再実行は[42](42-api-foundation.md#db移行登録復旧コマンド)、既存DBの一度きりのSQL移行と保存値保持は[58](58-ledger-foundation-design.md#新規利用と既存dbの境界)を参照する。

## セッションとHTTPの境界

- パスキーによるログイン成功時の期限は、その時点から13日（312時間）経過後、ログイン時の端末の地域で次に迎える午前2時（DEC-034）。日本時間で10月1日20時なら10月15日2時、10月1日1時なら10月14日2時。312時間後が午前2時ちょうどなら翌日とする。
- ブラウザーの`Intl.DateTimeFormat().resolvedOptions().timeZone`で得るIANA地域IDをサーバーで検証し、ログインチャレンジにだけ結び付ける。未取得・不正・非対応は`TimeZoneInfo.Local`へ補完する。端末時計やUTCオフセットを時刻の根拠にしない。
- 夏時間で午前2時が欠落する日は切替直後の最初の有効時刻、重複する日は早い方を候補とし、312時間後以前なら翌日の候補へ進む。通常は13日超〜14日だが時差変更の影響は生じる。
- ログイン時にUTC期限を保存し、Cookieも同じ日時で失効させる。地域はセッション・Cookieへ保存しない。旅行・端末地域・サーバー地域変更で既存期限を再計算しない。要求時は台帳を照合し、期限以上なら定時バッチを待たず拒否する。
- 再確認は同じアカウント・セッションの`VerifiedAtUtc`だけを更新し、固定期限を延ばさない。通常操作も滑動延長しない。重要操作は直近5分未満かつ未来でない確認日時を要求する。残り1日の再ログイン案内は設けない。
- WebのCookieは`__Host-`、Secure・HttpOnly・SameSite=Lax・Path=/・Domainなし。Web画面へlocalStorageのトークンを追加しない。Windows版には下記の標準OAuthによるBearer認証を追加する。ログアウトは現在セッションだけ、全失効や鍵削除では全セッションを失効させる。
- 各保護要求でセッション・有効アカウント・最新ロールを検証する。人物コードを送って本人を切り替えず、XMLの利用者コード設定も採用しない。未認証・失効・利用停止は401、権限不足・重要操作の確認期限切れは403、認証DB障害は503。人物未対応を403にする経路は削除した。302転送しない。
- 同じHTTPSオリジンから配信し、POST・DELETE等は登録・ログイン・ログアウトもCSRFを検証する。資格情報付きの任意CORSを許可しない。本文64 KiB、認証更新を合わせてIPごと1分20回、待ち行列なし。GET一覧はこの更新枠を消費しない。
- チャレンジは5分・1回限り・ブラウザー／用途固定。再開始で置換し、再起動で未完了分を破棄する。再確認と鍵追加はアカウントID・開始セッションのハッシュでも固定する。Cookie・生コード・WebAuthn応答を通常ログに出さない。
- 将来の業務入力では、入力途中の失効でも画面に入力を保持し、再ログイン後に本人が確認して登録する。自動再送や別アカウントへの引継ぎはしない。ブラウザーストレージの永続化は前提にしない。

## Windows版のOAuth認証（DEC-051）

OpenIddict 7.7.2のサーバー・検証機能を使い、外部ブラウザーでのパスキー認証後に認可コード＋PKCEでWindows版へAPI利用権限を渡す。Windowsクライアントの実装・実ブラウザーからの復帰は後続で、サーバーのHTTP経路を実装した段階。公開条件・証明書の準備は[42](42-api-foundation.md#windows版向けoauthの有効化)を参照する。

| 経路 | 契約 |
| --- | --- |
| `GET /.well-known/openid-configuration` | 固定HTTPSオリジンに対応する標準メタデータを公開する |
| `GET /connect/authorize` | 登録済みWindowsクライアント・認可コード・PKCE S256を検証。未ログインなら既存のログイン画面を経由し、元の認可要求へ戻す |
| `POST /connect/token` | `application/x-www-form-urlencoded`で認可コード＋verifier、または更新トークンを交換する。Cookie・Origin・CSRFではなく標準のコード／トークン検証を使う |

- 公式の公開クライアントIDは`monetail-windows`。利用者の認証IDとは別で、共有のクライアント秘密鍵をWindowsアプリへ埋め込まない。APIスコープは`monetail-api`、更新を利用する場合は`offline_access`も要求する。他のスコープを今回の受付から付与しない。
- 復帰先は`http://127.0.0.1/callback/`のループバック。応答はquery方式とする。標準ライブラリのNativeクライアント検証で実行時のポート変更を認め、それ以外のホスト・パスへの復帰を許可しない。サーバー側の認可・交換・API通信は引き続きHTTPSとする。
- 認可コードは1分・単回。アクセストークンは最大15分で、元のセッションの残り時間が短ければそれを上限にする。更新トークンも元の絶対期限までとし、更新で期限・直近本人確認時刻を延ばさない。
- 既にブラウザーでログイン済みなら再度のパスキー認証を要求しない。Windows用に独立した`auth_sessions`行を作り、ブラウザーのUTC期限と直近本人確認時刻を引き継ぐ。残り2日ならWindowsも残り2日。WindowsのログアウトはそのWindowsセッションだけを失効させ、ブラウザーはログアウトさせない。
- APIトークンは署名・暗号化した標準トークンを使い、検証後も毎回DBのセッション・利用可否・現在の全体ロールを確認する。期限切れ・失効・利用停止はアクセスと更新の両方を拒否する。保護APIは引き続き現在の家計簿参加・役割を確認し、トークンだけで家計簿権限を固定しない。
- CookieとBearerは認証時に分ける。Authorizationヘッダーがある場合はWindows用の標準検証を選び、不正なBearerから有効なCookieへ切り替えない。有効なBearerで認証できたAPI要求だけをCookie用のOrigin・CSRF検証から除外する。Cookie要求の検証は維持する。
- OAuthの認可・交換と既存パスキー操作は、検証途中の早期拒否を含め同じIP単位の1分20回を共有する。家計簿のアカウント別枠も、Cookie／Windowsセッションを問わず共有する。保存先の障害は503とし、HTTP経由でDBを自動作成・修復しない。
- `OpenIddictApplications`・`OpenIddictAuthorizations`・`OpenIddictScopes`・`OpenIddictTokens`は標準ライブラリの保存モデル。既存の初回EF定義に含め、Windowsクライアントの公開登録だけを初期データにする。アカウント・家計簿・人物は自動作成しない。
- 認可コード・更新／アクセストークンを通常ログへ残さない。OpenIddictの詳細ログを抑制し、ブラウザーの戻り先も同じオリジンの認可エンドポイントに限定する。

### Windows版の認証情報保存（未実装）

Windows版のアクセス／更新トークンは、WindowsのDPAPI（`DataProtectionScope.CurrentUser`）で暗号化し、`%LOCALAPPDATA%\Monetail`内の専用ファイルへ保存する。接続先URLの`settings.json`とは分け、平文のトークンを設定ファイル・一時ファイル・通常ログへ残さない。暗号鍵の管理はWindowsに任せ、復号用パスワードの入力は追加しない。認証情報を別PC・別Windowsユーザーへ持ち運んで使う運用は前提にしない。

復元後もサーバーで有効性を確認し、保存・読込・トークン更新によって元のログイン期限を延ばさない。ファイル形式・更新と削除の具体的な処理、復号できない場合の画面操作は実装前に具体化する。今回確定したのは保護方式と保存先で、Windowsクライアントの保存処理はまだ実装していない。

## API契約

| メソッド・パス | 用途・応答 |
| --- | --- |
| `GET /health` | 未認証の稼働確認。DBの正常性は示さない |
| `GET /auth/csrf` | 同一OriginへCSRFトークンを返す |
| `POST /auth/login/options` / `verify` | 名前入力なしの標準認証、開始時に地域IDを受け取り、成功時にセッションとCookieを発行 |
| `POST /auth/enrollment/options` / `verify` | optionsへ`code`と初回`displayName`、verifyへ標準資格情報を送る。登録先はコードで固定し、自動ログインしない |
| `GET /auth/me` | `authUserId`、アカウントの`displayName`、`expiresAtUtc`、`verifiedAtUtc`。人物コードは返さない |
| `POST /auth/logout` | 現在セッションを失効 |
| `POST /auth/reauthentication/options` / `verify` | 有効セッションの本人を再確認。期限は延ばさない |
| `GET /auth/passkeys` | 本人の鍵メタデータだけを返す |
| `POST /auth/passkeys/options` / `verify` | 直近本人確認後に本人へ鍵を追加 |
| `DELETE /auth/passkeys/{id}` | 最後の鍵を拒否し、削除成功時は全セッションを失効 |
| `GET /admin/accounts` | 全体Admin専用。アカウントID順の`authUserId`・`displayName`・`isEnabled`。人物行は含めない |
| `POST /admin/accounts` | 全体Admin・直近本人確認・CSRFが必要。`requestId`だけを受け取り、新規一般アカウントとコードを発行 |
| `POST /admin/accounts/{id}/enrollment-code` | 同じ条件で無効・鍵なしの一般／Adminへ再発行 |

メール・パスワード登録を開く`MapIdentityApi`は使わず、標準パスキー機能へ薄い受付と画面を接続する。通常起動はCookie認証・OAuth・管理者APIを常に公開し、必須設定が不備なら起動しない。設定と管理コマンドの扱いは[42](42-api-foundation.md#認証の必須設定)を参照する。管理者の全失効HTTP経路・権限変更は未実装であり、この表に含めない。人物の追加は家計簿側の後続機能とする。

## 運用と家計簿の境界

固定HTTPS・既知プロキシ・永続化・バックアップ・全失効後の復旧は[42](42-api-foundation.md)。ログイン成功を家計簿の利用許可とは扱わない。家計簿の参加・権限・人物との任意対応は[58](58-ledger-foundation-design.md)で管理する。

## 管理APIの再送と対象条件

`POST /admin/accounts`は空でないUUIDの`requestId`だけを受け取り、人物・名前・ロール等の追加項目は400。初回201で`authUserId`・`code`・`expiresAtUtc`を返す。同じ管理者・要求IDの再送は200で同じIDを返し、コードと期限はnull。別管理者が同じ要求IDを使う場合は409。別要求IDは別の新規アカウントとなる。

再発行は対象アカウントがなければ404、有効または鍵が残る場合は409。停止中のAdminにも別の有効Adminから発行でき、表示名・ロールを維持する。初回発行・再発行とも最新Admin・有効セッション・直近5分未満の本人確認・Origin・CSRFを保存前後で検証し、途中失敗は全変更を戻す。再発行の同時成功は最後に確定したコードだけを有効とする。

`GET /admin/accounts`は登録待ち・停止中・人物未対応を含むアカウントID順。公開項目はID・表示名・利用可否だけで、参照に直近本人確認・CSRFを要求しない。名前だけの人物は含めず、役割・鍵・セッション・コード等を公開しない。
