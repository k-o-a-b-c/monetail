# 41 明細税率へのコピーDB移行

[40の設計](40-detail-tax-unified-design.md)のうち、コピーDBの移行を実装した。**[42の新Windows版](42-detail-tax-application.md)が移行後構造へ対応した。旧Windows版では移行コピーを開かない。** 新版のWindows自動検証は完了し、手動確認と実期間データ確認を残す。 利用者の実DBには適用していない。

## 実行方法

既存アプリと同じVB.NET・.NET Framework 4.8・System.Data.SQLite 1.0.113.1を使う。Python等の追加ランタイムは不要。Windowsで実行する。

```powershell
dotnet build tools/DetailTaxMigration/DetailTaxMigration.vbproj
& ./tools/DetailTaxMigration/bin/Debug/net48/DetailTaxMigration.exe C:/data/backup.sqlite C:/data/detail-tax-test.sqlite C:/data/detail-tax-comparison.csv
```

元DBはアプリを閉じてバックアップしたものを指定する。読取専用で開き、SQLiteのバックアップAPIでWAL内の確定済みデータも含むコピーを作る。コピー・CSVは新規パスが必須。同じパス・既存ファイルを拒否し、失敗時は今回作成した出力だけを削除する。終了コードは成功0、移行失敗1、引数不足2。

アプリ起動時の自動移行には接続していない。税率の適用履歴は実データ確認前なので空で作成し、将来の1%などを推測で登録しない。初期区分は通常・既存軽減・対象外を作り、旧フラグから分類を対応付ける。区分は追加可能。

## 実データを共有しない確認手順

2026-10-23の利用者方針により、実DB・レシートは共有しない。以下は利用者のWindows内で行い、DB・比較CSV・画面画像・結果ファイルをアップロードする必要はない。

1. アプリを閉じ、元DBをバックアップする。バックアップ・移行コピー・比較CSVはGit作業フォルダーの外の、利用者だけが扱うローカルフォルダーへ置く。
2. 必要な旧移行の適用状況を[Windows確認手順](../tests/README.md#windowsで画面を手動確認する手順利用者環境では未実施)で確認し、上記CLIでバックアップから別名の移行コピーと比較CSVを作る。元DBを新Windows版の接続先にしない。
3. 比較CSVの全差分を確認し、移行コピーの対象者・メモ・明細と手元のレシートを照合する。旧Double誤差の修正で差が出る例は下記を参照する。実際の分類と区分の対応・適用開始日・税率も手元で確認して移行コピーへ設定する。
4. [起動設定](19-database-startup-settings.md)に従って新Windows版を移行コピーへ接続し、Windows確認手順の画面操作と普段の操作を確認する。確認が終わるまで移行コピーを本番利用しない。

未実施の項目は[tests/README](../tests/README.md#未完了テストまとめて実施するもの)に残す。合成データによる自動検証と、実データ・利用者環境での確認を分けて扱う。

## 変更と記録

- 明細の`tax_code`へ旧親税率コードをコピーし、旧`tax_target=0`は新しく採番した対象外コードへ移す。旧0%課税とは区別する。
- 同一レシート・分類のグループを最小の元seqへ統合し、明細を元group_seq・seq順に再採番する。空グループ、異なる親の同一番号、全対象者割当を保持する。
- 単一グループのメモはNULL・空文字も保持。統合時は空でないメモを番号付きで連結し、空白・同文も残す。全NULLならNULL、それ以外に有効なメモがなければ空文字。
- 割引率はSQLiteの実際の格納型を読み、INTEGERは正確に、REALはInvariantCultureの往復可能な文字列からDecimalへ変換する。宣言型による小数切捨・日付変換を避ける。新割引率列はTEXTで、文字列は`Decimal.TryParse`（`NumberStyles.Float`・InvariantCulture）で変換する。書式不正・範囲超過は拒否し、多桁・微小な値の扱いは標準変換に委ねる。2桁への制限・丸めは追加しない。
- `ExactMoney`は割引率をDecimalで保持し、乗除算の中間値・端数判定をBigIntegerの係数・商・余りで計算する。税率別に合算した税額をfloor／half_upで丸め、最終会計・収入・支出はInt32範囲を検証。手入力金額値引と率値引のCeilingという業務ルールは維持する。
- `t_receipts.total`は仕様変更時に差分を確認する比較基準として、NULLを含む元の保存値・格納型を保持する。再計算値は監査テーブルと比較CSVだけへ記録する。構造変更に伴うレシートの更新版は新しくする。その他のヘッダー項目と元の更新者・更新日時、ポイント・振替・残高・支払メモ等は変更しない。

| 記録先 | 内容 |
| --- | --- |
| `detail_tax_group_map` | 元→新のグループ番号、元のメモ・税率コード |
| `detail_tax_detail_map` | 元→新の明細複合キー、元の課税フラグ |
| `detail_tax_receipt_audit` | 全レシートの旧保存total・旧再計算・新計算、収支、旧新版 |
| `detail_tax_migration` | 移行IDと完了UTC。再適用を拒否 |
| 比較CSV | 全レシートの旧新合計・差額・収支・更新版。旧保存totalがNULLなら保存差額も空欄 |

旧Double式は比較値の記録専用。新金額には使わない。10%課税−100円＋対象外1,000円は890円、負額単独は旧−111円→新−110円、10,000円の0.14%値引は旧15円→新14円となる。元明細から求めた期待値と移行後明細の再計算を照合する。両者は同じ正確な演算ヘルパーを使うため、数式自体の正しさは別の固定期待値で検証する。

## 失敗時と対応範囲

接続のFK設定を記録し、トランザクション外で一時OFFにして`BEGIN IMMEDIATE`。中間表へ全件生成し、子から旧表を削除、親から最終名へ変更する。FK・整合性・件数・金額を検査してCommitし、途中の例外はDDLごとRollbackする。FKは終了後に戻す。呼出元の既存トランザクションは開始を拒否し、その変更をRollbackしない。`user_version`を保持し、SQLite 3.32で使えない`DROP COLUMN`等は使わない。

旧税端数・更新版移行が前提。元のFK違反、税率コード欠損、不正な格納型・フラグ・税設定、整数範囲超過、Decimal変換に失敗する率は中止する。独自列・トリガー・ビュー・再構築対象の独自CHECK／UNIQUE制約・未知の明細参照は事前確認を求めて拒否。明示索引は再作成し、廃止列依存などで再作成不能なら全体を戻す。独自構造を自動削除しない。

検証範囲と結果は[tests/README](../tests/README.md)。Windowsアプリの全経路と参考集計は42で切替済み。Windowsの手動確認と実期間データの確認・設定を残す。旧列へのフォールバックや過去専用モードは追加しない。
