# 参加者API・業務契約

**参加者APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：家計簿の参加者一覧取得・役割と人物対応の更新・除外。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：認証アカウント自体、人物マスタの操作、招待による参加、家計簿自体の操作。
- 関連契約：[家計簿API](ledgers.md)、[人物API](persons.md)、[参加者管理](../../../ledger-participants.md)、[人物・参加者DB](../../../ledger-person-db.md)、[招待API](invitations.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[共通HTTP境界・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /members` | 参加者一覧を取得 | Admin | 200 |
| `PATCH /members/{accountId}` | 役割・人物対応を更新 | Admin | 200 |
| `DELETE /members/{accountId}` | 参加者を除外 | Admin | 200 |

- APIは各要求で認証・対象家計簿への現在の参加・Admin権限を検証する。全体管理者の権限は家計簿Adminの権限を代替しない。家計簿に参加しない全体管理者にもアクセスを認めない。
- 本人は認証済みアカウントIDで判定する。本人の役割の実値変更・除外は禁止し、本人の人物対応の編集は許可する。書込時の整合性は第7節に従う。

## 3. 参加者の値・業務制約

| 項目 | 契約 |
| --- | --- |
| `accountId` | 参加者の認証アカウントID |
| `displayName` | 登録済みアカウントの表示名（[認証仕様](../../../auth-passkeys.md)に従う） |
| `role` | `Admin`・`Editor`・`Viewer` のいずれかと完全一致する |
| `personId` | 同一家計簿の人物IDまたは`null`。人物対応は任意で、1アカウントにつき最大1人物、1人物につき最大1アカウント。他の参加者に対応済みの人物を奪わない。有効期間外の人物も対応候補とする |
| 人物対応の変更 | 旧対応の解除と新対応の設定を原子的に行う。アカウント表示名と人物名は同期せず、人物の業務記録・支払方法の所有者を移さない。人物対応の変更は本人判定・本人所有分の操作権限に反映される |
| 除外 | 参加者行と人物対応を取り除き、アカウント・人物・過去の業務記録を保持する。本人の退会操作は設けず、他のAdminによる除外に統一する。最後の有効なAdminを保護する |
| 追加・再参加 | 家計簿作成時は作成者がAdminとして参加する。それ以外の参加者の追加は招待で行い、Viewer・人物未設定とする。再参加も同様とし、以前の役割・人物対応は復活させない。参加者行の新規作成時（再参加を含む）は新しい `revision` を発行する |

## 4. リクエスト

パスの `ledgerId`・`accountId` はUUID（N・D・B・P・X形式。URL上で適切にエンコードする）。UUID値として照合し、UUIDとして解釈できないパスはルーティングの404とする。全桁ゼロのUUIDもパスではUUIDとして扱い、第6節の認可・存在確認に従う。

GETには要求本文を必要としない。書込2操作（PATCH・DELETE）はJSONオブジェクトを送る。Content-Typeは `application/json` または `+json` サフィックスを持つJSONメディアタイプを受け付ける。

本文のUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。全桁ゼロのUUIDは本文では不正とし、UUIDのバージョンによる入力制限は設けない。

| JSON項目 | 型 | PATCH | DELETE |
| --- | --- | --- | --- |
| `role` | 文字列 | 任意 | — |
| `personId` | UUID文字列または`null` | 任意 | — |
| `revision` | UUID文字列 | 必須 | 必須 |

- 「任意」はキーの省略を許す。「—」は送信不可。キー名は大文字・小文字を区別する。`null`は表で明記した`personId`だけに許す。入力不備のエラーと検証の優先順位は第6節に従う。
- PATCHの省略項目は変更しない。`personId`の明示的な`null`は対応解除を表す。

## 5. 成功応答・識別と並び順

全3操作の成功応答は共通の参加者一覧JSONオブジェクトを返す。各JSONオブジェクトは以下の表に列挙した項目のみで構成し、すべて必須キーとする。`null`は表で明記した項目だけに許す。読み取りの整合性・再送時の応答は第7節に従う。

| トップレベル項目 | 型 | 内容 |
| --- | --- | --- |
| `members` | オブジェクト配列 | 対象家計簿の全参加者 |

| `members[]` の項目 | 型 | 内容 |
| --- | --- | --- |
| `accountId` | UUID文字列 | 参加者の認証アカウントID |
| `displayName` | 文字列 | 登録済みアカウントの表示名（[認証仕様](../../../auth-passkeys.md)に従う） |
| `role` | 文字列 | 家計簿内の役割 |
| `personId` | UUID文字列または`null` | 対応する人物ID。未対応なら`null` |
| `revision` | UUID文字列 | 参加者単位の更新版 |

UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。更新版はAPIが生成するUUID v4とし、一致のみで照合する。

配列順は次のとおり。

1. 操作者本人。
2. 本人以外の人物対応済み参加者を[人物マスタの共通順](persons.md#5-成功応答識別と並び順)で並べる（順位値が同じ場合は人物ID昇順）。
3. 本人以外の人物未対応参加者を参加日時昇順、同日時ならアカウントID昇順で並べる。

クライアントは認証済みアカウントIDで本人を識別し、操作者の権限・本人対応は[家計簿API](ledgers.md)で管理する。対応人物名と選択候補は人物APIの全人物と参加者一覧を人物IDで照合して求める。画面操作は[参加者管理](../../../ledger-participants.md)に従う。

## 6. 競合・失敗応答

### エラー本文

参加者APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列または`null` | 対象のJSON項目名。個別項目を特定しない場合は`null` |
| `latest` | オブジェクトまたは`null` | 更新版競合時の最新情報。形式は後述。それ以外は`null` |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。GETは共有参照枠、PATCH・DELETEは共有書込枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | Content-Typeの欠落・JSON非対応、JSON形式・オブジェクト形式の不備、未知・重複キー | `null` |
| 400 | `invalid_input` | 個別項目の型・値・必須キーの欠落、空UUIDなどの不備 | 該当項目名 |
| 400 | `invalid_input` | PATCHで指定した人物が同一家計簿に存在しない（他家計簿の人物を含む） | `personId` |
| 403 | `forbidden` | Admin権限がない | `null` |
| 403 | `self_role_change` | 本人の役割の実値変更 | `null` |
| 403 | `self_exclusion` | 本人の除外 | `null` |
| 404 | `not_found` | 家計簿不在・未参加、または権限確認後の対象参加者不在 | `null` |
| 409 | `person_already_assigned` | 別の参加者に対応済みの人物を指定 | `personId` |
| 409 | `revision_conflict` | 更新版の不一致 | `null` |
| 503 | `store_unavailable` | 業務処理の保存先障害等 | （キーなし） |

家計簿の不存在と未参加を区別する情報、内部例外・DBの詳細を応答に公開しない。

### 検証の優先順位

[共通の検証原則](../../../ledger-core-api.md#共通の検証原則)に従う。全操作で受付時の認証を含む共通HTTP境界を適用し、第4節でJSON本文を定義した操作ではJSONメディアタイプ・構文・トップレベルのオブジェクト／許可キーを検証してから、下表の業務処理に進む。

矢印はエラーの優先順位を示す。同一段階の項目は列挙順を要求しない。業務処理は受付時に認証済みのアカウントを使用する。書込と競合時の `latest` の返却に必要な認可・整合性は書込トランザクション内で保証する。内部処理やクラス構成は指定しない。

| 操作 | 検証・処理の流れ |
| --- | --- |
| GET | 家計簿参加・Admin権限 → 参加者一覧取得 → 応答 |
| PATCH | 家計簿参加・Admin権限 → `revision`・`role`・`personId` の必須項目／型／UUID形式（空UUIDの拒否を含む） → 対象参加者の存在 → 更新版の一致 → 役割の許容値 → 本人の役割の実値変更禁止 → 対応人物の実在 → 重複対応 → 更新 → 原子的な確定・応答 |
| DELETE | 家計簿参加・Admin権限 → 本人の除外禁止 → `revision` の型／形式 → 対象参加者の存在 → 更新版の一致 → 除外・一覧順序版の更新 → 原子的な確定・応答 |

DELETEの本人除外禁止は認可条件であり、トップレベルのJSON構造・許可キーの検証とAdmin権限確認後、`revision` の必須・型・UUID形式、対象参加者の存在、版の一致より先に確認する。本人除外と `revision` の形式不備が重なる場合は403 `self_exclusion` とする。PATCHの本人役割変更禁止は役割の許容値の検証後とし、対応人物の実在・重複対応より先に確認する。

### 更新版競合

- PATCH・DELETEの `revision` は対象参加者の `revision` と原子的に照合する。
- 参加者単位の `revision` は役割・人物対応の実値変更時だけ更新する。
- 入力の正規化後に実値が変わらないPATCH（`revision` だけを指定した場合を含む）は、権限・版・業務制約の検証を通れば無変更成功（200）とし、行版を維持する。
- 409 `revision_conflict` の `latest` は最新の対象参加者1件（第5節の `members[]` と同じ項目）を返す。

409の `latest` は書込トランザクション内で当該操作に必要な参加・権限を確認した場合に限り返す。未参加なら404、権限不足なら403を優先する。

## 7. 整合性・再送

### 原子性と認可

- 書込2操作は、業務制約・更新版の照合、当該操作に伴う変更を一つのトランザクションで確定する。トランザクションの確定前に処理が失敗した場合は当該操作の変更をすべて戻し、別の確定済み操作まで取り消さない。確定後の通信断・応答喪失はロールバックの根拠にならず、クライアントから保存結果を断定できない。
- 成功応答の参加者一覧は同じトランザクションの整合した状態を返す。書込時は変更後の状態を返す。
- GETでは取得前に当該操作に必要な参加・権限を確認する。取得障害時も参加者情報を返さない。
- 当該操作に必要な参加・権限は同一書込トランザクション内で確認し、確定まで保証する。認可条件を満たさない場合は変更をすべて戻す。
- 競合する人物割り当ては先に確定した対応を維持する。同時除外・降格でも現在の操作者の権限を検証し、最後の有効なAdminの保護を維持する。
- 除外時は対象アカウントの家計簿一覧からの除外・順序版の更新を同じ書込トランザクションで確定する。残りの家計簿の相対順と最終選択の扱いは[家計簿API](ledgers.md)に従う。役割・人物対応の変更だけでは家計簿一覧の順序版を変更しない。
- 人物マスタの行版・順序版、家計簿編集版、既存業務記録、他家計簿の参加者を変更しない。
### 再送

- 書込の再送には第6節の更新版照合を適用する。PATCH・DELETEは専用の成功再送記録を作成せず、`requestId`を要求しない。現在の認証・参加・Admin権限を確認した上で、対象参加者が既に除外され不在の場合は404 `not_found` とする。
