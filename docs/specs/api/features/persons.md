# 人物API・業務契約

**人物APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：家計簿に属する人物の5操作。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：参加者の役割と人物IDの対応付け、認証アカウント自体、科目・支払方法・レシートの固有操作。
- 関連契約：[人物の画面動作・業務ルール](../../../ledger-persons.md)、[参加者API](../../../ledger-person-api-contract.md)、[参加者仕様](../../../ledger-participants.md)、[人物DB](../../../ledger-person-db.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[家計簿API・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /people` | 人物一覧を取得 | 現在の家計簿参加者（Admin・Editor・Viewer） | 200 |
| `POST /people` | 人物1人を作成 | Admin | 初回201、同一の成功要求の再送200 |
| `PATCH /people/{personId}` | 人物名・有効期間を更新 | Adminは全項目。Editor・Viewerは本人に対応する人物の名前のみ | 200 |
| `DELETE /people/{personId}` | 人物を削除 | Admin | 200 |
| `PUT /people/order` | 全人物の共通順を一括保存 | Admin | 200 |

Admin以外が本人をPATCHするときは、日付項目を省略する。日付項目を送信した場合は、nullや現在値と同じ値であっても403 `forbidden` とする。

- APIは各要求で認証・対象家計簿への**現在の参加**と操作権限を検証する。家計簿に参加しない全体管理者にもアクセスを認めない。確定前の再検証は第7節に従う。
- 本人判定はログインアカウントが**その家計簿で対応付けられた人物ID**で行う。人物名で同一人物と判定しない。対応なしでも人物閲覧は可能だが、管理者以外は本人に該当する名前変更の権限を得ない。

## 3. 人物の値・業務制約

| 項目 | 契約 |
| --- | --- |
| `personId` | APIが生成するUUID v4。名前・順序と独立し、名前変更でIDを変えない |
| `name` | `.NET string.Trim()`で前後の空白を除去し、**1～100 UTF-16コード単位（.NET `string.Length`）**の名前として保存する。APIは上限超過を切り詰めない |
| 同名判定 | **同一家計簿内のTrim後の完全一致**を禁止。大文字/小文字、全角/半角、Unicode正規化の差は同一視しない |
| `validFrom` / `validTo` | `YYYY-MM-DD` 形式の実在する暦日または `null`。時刻・タイムゾーンは持たない。各 `null` はその側の制限なし。両端を含み、両方がある場合は開始日≦終了日 |
| 有効期間の意味 | 認証アカウントのログイン期限ではなく、**記録対象日**に人物が利用できる範囲。期間終了後でも対象日が範囲内なら利用可能 |
| 既存データとの整合 | 既存の人物参照を範囲外にする期間変更は拒否。新規の業務記録の保存側でも各業務の対象日・所有者を検証する |
| 削除 | 人物への参照が1件でも残れば拒否。参加者の人物対応、支払方法の所有、取引などを自動解除・連鎖削除しない |

対象家計簿における期間検証の参照元・基準日は次のとおり。

| 業務 | 対象人物 | 基準日 |
| --- | --- | --- |
| レシート | 支払方法の所有者、明細の対象人物 | レシートの取引日 |
| 振替 | 移動元・移動先の支払方法の所有者 | 振替の取引日 |
| 残高 | 支払方法の所有者 | 残高の登録日 |

同一家計簿で人物を使用するその他の業務についても、各業務APIの契約で定める対象日を適用する。操作日・登録処理時刻では判定しない。支払方法の所有や参加者との対応自体は日付付きの業務記録ではないが、削除制限の対象となる。

## 4. リクエスト

パスの `ledgerId`・`personId` はUUID。GETには要求本文を必要としない。書込4操作（DELETEを含む）は `Content-Type: application/json` のJSONオブジェクトを送る。

本文のUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。全桁ゼロのUUIDは本文では不正とする。UUIDのバージョンによる入力制限は設けない。

| JSON項目 | 型 | POST | PATCH | DELETE | 共通順PUT |
| --- | --- | --- | --- | --- | --- |
| `requestId` | UUID文字列 | 必須 | — | — | — |
| `name` | 文字列 | 必須 | 任意 | — | — |
| `validFrom` | 日付文字列またはnull | 任意 | 任意 | — | — |
| `validTo` | 日付文字列またはnull | 任意 | 任意 | — | — |
| `revision` | UUID文字列 | — | 必須 | 必須 | 必須 |
| `personIds` | UUID文字列の配列 | — | — | — | 必須 |

- 「任意」はキーの省略を許す。「—」は送信不可。キー名は大文字・小文字を区別する。nullは表に明記した日付項目だけに許す。入力不備のエラーと検証の優先順位は第6節に従う。
- POSTの省略された日付はnullと同じ。PATCHの省略項目は変更せず、日付の明示的なnullはその側の制限解除。名前・日付の値は第3節に従う。
- 共通順PUTの `personIds` は有効期間外を含む当該家計簿の全人物IDを各1回、保存する順に並べる。他家計簿の人物ID・重複・欠落を認めず、人物0件の場合は空配列を指定する。

## 5. 成功応答・識別と並び順

全5操作の成功応答は共通の人物一覧JSONオブジェクトを返す。以下の項目はすべて必須キーで、nullは表で明記した項目だけに許す。読み取りの整合性・再送時の応答は第7節に従う。

| トップレベル項目 | 型 | 内容 |
| --- | --- | --- |
| `people` | オブジェクト配列 | 有効期間外を含む全人物。0件なら空配列 |
| `orderRevision` | UUID文字列 | 共通順全体の更新版。人物0件でも返す |

| `people[]` の項目 | 型 | 内容 |
| --- | --- | --- |
| `personId` | UUID文字列 | 人物ID |
| `name` | 文字列 | 保存済みの人物名 |
| `validFrom` | 日付文字列またはnull | 有効開始日 |
| `validTo` | 日付文字列またはnull | 有効終了日 |
| `displayOrder` | 整数（Int32） | 共通表示順 |
| `revision` | UUID文字列 | 人物単位の更新版 |

UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。更新版はAPIが生成するUUID v4とし、大小や時系列ではなく一致で照合する。日付は第3節の形式に従う。

- `people` は `displayOrder` 昇順、同値の場合は `personId` の文字列昇順で返す。
- 新規人物は共通順の末尾（最大の `displayOrder` + 1、人物0件なら0）に追加する。実際に共通順を変更したときは要求配列の順で0から連番を設定する。人物削除時は残った人物の順序値を詰めないため、欠番を許容する。

## 6. 競合・失敗応答

### エラー本文

人物APIの業務エラーは以下の4項目を持つJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列またはnull | 対象のJSON項目名。個別項目を特定しない場合はnull |
| `latest` | オブジェクトまたはnull | 更新版競合時の最新情報。形式は後述。それ以外はnull |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。GETは共有参照枠、POST・PATCH・DELETE・PUTは共有書込枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | JSON形式・オブジェクト形式の不備、未知・重複キー | null |
| 400 | `invalid_input` | 個別項目の型・値・必須キーの欠落、空UUID、存在しない日付などの不備 | 該当項目名 |
| 400 | `invalid_input` | 開始日が終了日より後 | `validTo` |
| 400 | `invalid_input` | 共通順の配列・要素・全人物ID集合の不備 | `personIds` |
| 401 | `authentication_changed` | 業務処理中の認証再検証で失効・停止等を検出 | null |
| 403 | `forbidden` | 操作に必要な権限がない | null |
| 404 | `not_found` | 家計簿不在・未参加、または権限確認後の対象人物不在 | null |
| 409 | `duplicate_person_name` | 同名人物の登録・更新 | `name` |
| 409 | `person_referenced` | 参照が残る人物の削除 | null |
| 409 | `person_period_conflict` | 既存の人物参照を期間外にする期間変更 | `validFrom` または `validTo` |
| 409 | `revision_conflict` | 更新版の不一致 | null |
| 409 | `request_conflict` | 要求IDを異なる内容で再利用 | null |
| 409 | `created_result_deleted` | 作成済み人物の削除後に同じ要求を再送 | null |
| 503 | `store_unavailable` | 業務処理の保存先障害等 | （キーなし） |

有効な開始日・終了日の指定が既存参照と両側で衝突するときは `validFrom` を優先する。参照制約による削除拒否と保存先障害を区別し、内部例外・DBの詳細を応答に公開しない。未認証等の受付前401、制限超過429等の状態コードは共通契約に従う。

### 検証の優先順位

受付・JSONオブジェクト／許可キーの検証を通過した要求では、現在の認証・家計簿参加・操作権限を業務データの検証より先に確認する。以下は複数の不備が重なったときの業務エラーの優先順位であり、内部処理の構成を指定するものではない。

| 操作 | 優先順位（先に該当したエラーを返す） |
| --- | --- |
| POST | 名前・日付・期間・要求IDの入力検証 → 再送照合（内容不一致・作成結果の削除） → 同名判定。成功済みの同一要求は現在の一覧を返し、新規作成としての同名判定を行わない |
| PATCH | 対象人物の存在 → 要求の更新版の妥当性・一致 → 名前・日付・期間の入力検証 → 同名判定 → 既存参照との期間衝突 |
| DELETE | 対象人物の存在 → 要求の更新版の妥当性・一致 → 参照による削除制限 |
| 共通順PUT | 要求の更新版の妥当性・一致 → `personIds` の検証 |

認証・参加・操作権限が失われた場合の最新情報の返却制限は、次の更新版競合の規定に従う。

### 更新版競合

- PATCH・DELETEの要求の`revision`は対象人物の`revision`、共通順PUTの要求の`revision`は共通順全体の`orderRevision`と原子的に照合する。
- 人物単位の`revision`は名前・期間の実値変更時だけ更新する。共通順だけの変更でも人物の行版を変えない。入力の正規化後に実値が変わらないPATCH（`revision`だけを指定した場合を含む）も、権限・版・業務制約の検証を通れば成功し、行版を維持する。人物の編集・並べ替えと、参加者の役割・人物対応の更新版は独立する。
- `orderRevision`は人物の追加・削除・共通順の変更時に更新する。共通順PUTで人物ID順が変わらない場合は、人物0件の空配列も含めて無変更成功（200）とし、`displayOrder`・`orderRevision`を維持する。無変更時も更新版・全人物ID集合を検証し、古い`revision`は409を返す。
- 409 `revision_conflict`の`latest`には、PATCH/DELETEなら最新の人物1件（`people[]`と同じ6項目）、共通順PUTなら最新の人物一覧応答（`people`・`orderRevision`）を返す。いずれも現在の権限で閲覧可能な情報に限る（[競合・権限喪失](../../../ledger-person-conflicts.md)）。
- 409の`latest`に情報を返す前にも現在の認証・家計簿参加・操作権限を検証し、認証失効なら401、未参加なら404、権限不足なら403を優先する。閲覧できない他参加者の情報・過去の閲覧権限による情報を返さない。

## 7. 整合性・作成の再送

### 原子性と認可

- 書込4操作は、業務制約・更新版の照合、人物・順序・更新版・作成成功記録の当該操作に伴う変更を一つのトランザクションで確定する。失敗時は当該操作の変更をすべて戻し、別の確定済み操作まで取り消さない。
- 成功応答の人物一覧と共通順の更新版は同じトランザクションの整合した状態を返す。書込時は変更後の状態を返す。
- 成功の確定直前にも現在の認証・家計簿参加・当該要求の操作権限を検証する。書込中に必要な権限・本人対応・認証を失った場合は成功とせず、変更をすべて戻す。変更された権限でも当該操作が許可される場合は拒否しない。
- 同時操作でも同名登録、参照切れ、期間外の記録、更新版による競合検出のすり抜けを許さない。人物期間の変更と日付付き業務記録の書込は双方で制約を検証する。人物の名前・期間・共通順の変更は、参加者の対応や役割、既存業務記録そのものを変更しない。

### 作成の再送

- POST /peopleでは、サーバー発行の人物IDとは別に、クライアントが発行した `requestId` で同一作成要求を識別する。[共通再送](../../../ledger-operation-retries.md)の規定に従い、人物作成は `person.create` として扱う。
- 同一性は操作者・操作種類・家計簿・正規化後の名前・開始日・終了日で判定する。同じUUIDの表記差、名前の前後空白、日付の省略とnullの差は同一視する。成功記録のある要求IDを異なる内容に使う場合は `request_conflict`。
- **同じ成功要求の再送で重複作成しない。** 現在も作成権限があり、元の作成人物が残っていれば、改名・期間変更・順序変更後であっても200で現在の人物一覧を返す。人物・更新版・順序・成功記録を変更しない。
- 元の作成人物が削除されていれば同じ要求で再作成せず `created_result_deleted` を返す。要求記録の原子的な確定と無期限保持は共通再送の規定に従う。
- 保存結果が不明なPOSTは同じ要求ID・同じ内容で再送する。成功記録が存在しない要求IDは再送照合上の新規要求として扱う。PATCH・DELETE・共通順PUTの競合は第6節の更新版照合に従う。
