# 振替API・業務契約

**振替の一覧・詳細取得・保存・削除APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：振替の参照・作成・更新・削除の5操作。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：履歴候補・自動補完（[振替履歴API](transfer-history.md)）、マスタ管理、画面操作、残高API。
- 関連契約：[家計簿API](ledgers.md)、[人物API](persons.md)、[支払方法API](payment-methods.md)、[振替DB](../../../ledger-transfer-db.md)、[振替画面](../../../ledger-transfer-ui.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[共通HTTP境界・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /transfers` | 一覧取得 | Admin・Editor・Viewer | 200 |
| `GET /transfers/{transferId}` | 詳細取得 | Admin・Editor・Viewer | 200 |
| `POST /transfers` | 作成（流用登録を含む） | Admin・Editor（下記） | 201 |
| `PUT /transfers/{transferId}` | 更新 | Admin・Editor（下記） | 204 |
| `DELETE /transfers/{transferId}` | 削除 | Admin・Editor（下記） | 204 |

各要求で現在の認証と対象家計簿への参加・操作権限を検証する。全体管理者の権限は家計簿Adminを代替しない。参加者は家計簿内の全振替を閲覧できる。新規書込要求ではAdminは家計簿内の全振替を書き込める。Editorは振替元・振替先の両方が本人対応人物の所有する支払方法の場合のみ書込可。PUTでは変更前と変更後の両側について検証する。本人対応がないEditorは新規書込不可。Adminは本人対応なしでも書込可。作成者で権限を判定しない。成功済み要求の再送は第7節に従う。

## 3. 振替の値・業務制約

振替は同一家計簿内の異なる支払方法間の資金移動。振替元の残高から金額を減算し、振替先に加算する。収入・支出には計上しない。

| 項目 | 契約 |
| --- | --- |
| ID・更新版 | 振替IDはAPIがUUID v7を生成。更新版はUUID v4。削除済みIDは再利用しない |
| 取引日時 | 実在するローカル日時 `yyyy-MM-ddTHH:mm:ss`（オフセット・小数秒なし）。期間照合は日付部分を使用 |
| 振替名 | 1〜100 UTF-16コード単位。空白文字だけの値は不可。前後空白・元文字列を保持し、Trimや表記正規化をしない |
| 振替元・振替先 | 両方必須、異なる支払方法ID。同一家計簿内に存在すること |
| 金額 | 1以上のInt32（最大2,147,483,647）のJSON整数 |
| メモ | 100 UTF-16コード単位以内、1行、改行不可、`null` 可。空文字を`null`に正規化し、空白のみの文字列は保持。Trimしない |

保存時、両支払方法とそれぞれの所有人物は同一家計簿に存在し、取引日が各有効期間内（両端含む、`null` の端は制限なし）であることを検証する。保存済みの値が未変更でも検証し、自動で代替値に変更しない。メモの改行文字はCR・LF・VT・FF・NEL・Unicode行区切り・段落区切りを含む。

## 4. リクエスト

パスの `ledgerId`・`transferId` はUUID（N・D・B・P・X形式。URL上で適切にエンコードする）。UUID値として照合し、UUIDとして解釈できないパスはルーティングの404とする。全桁ゼロのUUIDもパスではUUIDとして扱い、第6節の認可・存在確認に従う。

GETには要求本文を必要としない。書込3操作（DELETEを含む）はJSONオブジェクトを送る。Content-Typeは `application/json` または `+json` サフィックスを持つJSONメディアタイプを受け付ける。

本文とクエリのUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。全桁ゼロのUUIDは本文・クエリでは不正とする。UUIDのバージョンによる入力制限は設けない。

### 4.1 一覧GET

| クエリ | 必須 | 値・意味 |
| --- | --- | --- |
| `month` | 必須 | 実在する `YYYY-MM`（0001〜9999年）または `all` |
| `ownerPersonId` | 任意 | 振替元または振替先の支払方法の所有人物ID |
| `paymentMethodId` | 任意 | 振替元または振替先の支払方法ID |
| `q` | 任意 | 振替名の部分一致検索語。省略・空文字は絞り込みなし |
| `cursor` | 全期間の場合のみ任意 | APIが発行した不透明な継続位置 |

表に列挙したクエリのみを各1値で受け付ける。クエリ名は大文字・小文字を区別する。全検索条件をANDで適用する。人物条件と支払方法条件は独立に判定し、それぞれ異なる側に一致しても該当する。UUIDとして有効な人物・支払方法IDに一致する振替がなければ0件とする。振替名の照合は[振替履歴APIの検索正規化](transfer-history.md#3-履歴候補自動補完の値業務制約)に従う。検索語の独自文字数上限は設けない。

`cursor` は `month=all` の場合に限り指定可能。一覧GET以外の操作にクエリは定義しない。

### 4.2 POST・PUT・DELETE

| JSON項目 | 型 | POST | PUT | DELETE |
| --- | --- | --- | --- | --- |
| `requestId` | UUID文字列 | 必須 | 必須 | 必須 |
| `revision` | UUID文字列 | — | 必須 | 必須 |
| `transactionAt` | 日時文字列 | 必須 | 必須 | — |
| `name` | 文字列 | 必須 | 必須 | — |
| `fromPaymentMethodId` | UUID文字列 | 必須 | 必須 | — |
| `toPaymentMethodId` | UUID文字列 | 必須 | 必須 | — |
| `amount` | 整数 | 必須 | 必須 | — |
| `memo` | 文字列または`null` | 必須 | 必須 | — |

「—」は送信不可。キー名は大文字・小文字を区別する。`null`は表で明記した項目だけに許し、そのキーも必須とする。整数はJSON整数であり、小数・文字列では代用できない。入力表現の範囲と業務値の検証は第6節に従う。

## 5. 成功応答・並び順

応答のUUIDは小文字のN形式（ハイフンなし32桁）。各JSONオブジェクトは列挙した項目のみを必須キーとして返し、`null`は明記した項目だけに許す。旧保存値の空文字メモは`null`として扱う。

### 5.1 一覧GET

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `transfers` | オブジェクト配列 | 振替要約。月指定は該当全件、全期間は0〜100件 |
| `nextCursor` | 文字列または`null` | 後続取得用の不透明なカーソル。月指定または後続なしは`null` |

振替要約の項目：

| 項目 | 型 |
| --- | --- |
| `transferId` | UUID文字列 |
| `transactionAt` | 日時文字列 |
| `name` | 文字列 |
| `fromPaymentMethodId` | UUID文字列 |
| `toPaymentMethodId` | UUID文字列 |
| `amount` | 整数 |
| `memo` | 文字列または`null` |

全件に条件を適用し、取引日時降順・同日時は振替IDのBINARY降順で返す。月指定では件数を制限せず該当全件を返す。全期間では最大100件とし、カーソル指定時は直前ページの末尾より後方を取得する。全期間で後続が存在する場合のみ `nextCursor` を発行する。0件は `{"transfers":[],"nextCursor":null}`。

全期間のカーソルは家計簿・検索条件（`month=all`・所有人物ID・支払方法ID・送信された検索語（省略と空文字を区別））に結び付け、改ざんを検出する。継続取得は同じ条件でカーソルをそのまま送る。レシート用カーソルは使用できない。独自の有効期限やアカウント固定は設けず、検証可能なカーソルはAPI再起動後も継続利用できる。各要求で現在のアクセス権限を確認する。ページ間の取引日時変更等による重複・取りこぼしの完全防止は保証しない。

### 5.2 詳細GET

一覧の振替要約7項目に `revision`（UUID文字列）を加えた8項目のJSONオブジェクトを直接返す。支払方法・所有人物の表示名はマスタを参照する。

### 5.3 書込

POSTは201 Created、本文なし。必須の `Location: /ledgers/{ledgerId}/transfers/{transferId}` ヘッダーで作成された振替の詳細URLを返す。PUT・DELETEは204 No Content、本文なし。更新版は次回の詳細GETで取得する。

## 6. 競合・失敗応答

### エラー本文

振替APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けの説明。具体的な文言は実装側で管理し、処理分岐には使用しない |
| `field` | 文字列または`null` | 対象のJSON項目名またはクエリ名。特定しない場合は`null` |
| `latest` | オブジェクトまたは`null` | 更新版競合時の最新振替。それ以外は`null` |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP境界に従う。業務エラー本文を一律には要求しない。GETは共有参照枠、書込は共有書込枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | Content-Typeの欠落・JSON非対応、JSON構文・トップレベルのオブジェクト形式の不備、未知・重複JSONキー | `null` |
| 400 | `invalid_input` | 個別項目の型・必須キー・値・入力制約の不備、同一家計簿に存在しない指定支払方法ID（他家計簿を含む） | 該当項目名 |
| 400 | `invalid_input` | 未知・重複クエリ、不正な検索条件、月指定でのcursor指定 | 該当クエリ名 |
| 400 | `invalid_cursor` | カーソル不正・改ざん・検証不能または家計簿・条件不一致 | cursor |
| 400 | `master_changed` | 下記のマスタ不整合 | 該当する支払方法ID項目名 |
| 403 | `forbidden` | 書込権限不足 | `null` |
| 404 | `not_found` | 家計簿不存在・未参加、対象振替の不在（他家計簿を含む） | `null` |
| 409 | `revision_conflict` | 更新版不一致 | `null` |
| 409 | `request_conflict` | 要求IDの不一致再使用 | `null` |
| 503 | `store_unavailable` | 保存先障害等 | （キーなし） |

内部例外・DBの詳細を応答に公開しない。同一支払方法の指定は `invalid_input`（`field=toPaymentMethodId`）。支払方法または所有人物の期間不整合は該当する `fromPaymentMethodId` または `toPaymentMethodId` を返す。

`master_changed` はPUTで取引日の日付部分と該当支払方法IDが保存済みと同じで、現行マスタとの期間不整合を確認できる場合に限る。取引日や該当IDを変更した場合、判断不能、参照先の不存在、POSTは通常の `invalid_input`。マスタ版の送信は要求しない。画面でのマスタ再取得は[振替画面](../../../ledger-transfer-ui.md)に従う。

### 検証の優先順位

[共通の検証原則](../../../ledger-core-api.md#共通の検証原則)に従う。全操作で受付時の認証を含む共通HTTP境界を適用し、書込ではJSONメディアタイプ・構文・トップレベルのオブジェクト／許可キーを検証してから下表の業務処理に進む。同一段階の個別項目の列挙順は要求しない。書込と競合応答に必要な認可・整合性は書込トランザクション内で保証する。

| 操作 | 検証・処理の流れ |
| --- | --- |
| 一覧GET | 家計簿参加 → 許可クエリ・重複・必須項目・年月／UUID・組み合わせの検証 → 全期間のカーソル検証 → 一覧取得 → 応答 |
| 詳細GET | 家計簿参加 → 未知クエリの検証 → 対象の存在・詳細取得 → 応答 |
| POST | 家計簿参加・書込ロール → 未知クエリ・必須項目・型・UUID・日時・整数の形式／表現可能性の検証、同一性の正規化 → 再送照合 → 新規要求のみ両支払方法の実在・所有者権限 → 全入力値・マスタ検証 → 作成 → 原子的な確定・応答 |
| PUT | 家計簿参加・書込ロール → 未知クエリ・必須項目・型・UUID・日時・整数の形式／表現可能性の検証、同一性の正規化 → 再送照合 → 新規要求のみ対象の存在・旧／新の両支払方法の実在と所有者権限 → 更新版の一致 → 全入力値・マスタ検証 → 更新または無変更 → 原子的な確定・応答 |
| DELETE | 家計簿参加・書込ロール → 未知クエリ・requestId／revisionの型／UUID形式の検証 → 再送照合 → 新規要求のみ対象の存在・両支払方法の所有者権限 → 更新版の一致 → 削除 → 原子的な確定・応答 |

整数入力はJSON整数としてInt64で解釈できることを版照合前に検証する。Int32の正値範囲・文字数・空白のみ・改行・元先同一・有効期間等の業務制約は版照合後に検証する。版照合のないPOSTでは版照合段階を省略する。入力支払方法の不存在は400とする。成功済み同一要求は第7節の契約に従い新規要求の処理へ進まない。

### 更新版競合

PUT・DELETEの `revision` は対象振替の現行版と原子的に照合する。一致のみで判定する。409 `revision_conflict` の `latest` は詳細GETと同じ8項目。書込トランザクション内で当該操作に必要な認可を確認した場合のみ返す。未参加・対象不在なら404、権限不足なら403を優先する。画面での権限再取得・入力保持・競合処理は[振替画面](../../../ledger-transfer-ui.md)に従う。

## 7. 整合性・再送

### 原子性と認可

- 参照前に参加を確認し、対象家計簿に限定する。取得障害時は部分データを成功応答として返さない。
- 新規書込は第6節に従い、必要な参加・所有者権限・参照整合性・マスタ・版を同一書込トランザクション内で確認し、確定まで保証する。
- 振替・監査情報・更新版・成功再送記録を単一トランザクションで原子的に確定する。確定前の失敗は当該操作全体をロールバックする。確定後の通信断はロールバックの根拠とならず、保存結果を断定できない。
- 無変更PUTも通常の権限・版・入力検証を行う。業務入力6項目が同じなら204、更新版・監査情報・振替行を変更せず成功記録だけ残す。同値判定は日時・UUID値・金額、元の振替名、メモの空文字から`null`への正規化（保存済み空文字も同値）を用いる。実変更時は新しいUUID v4の版と更新監査情報を発行する。作成監査情報は保持する。

### 書込の再送

- POST・PUT・DELETEではクライアントが新規操作ごとにUUID v4の `requestId` を生成する。APIの受理形式は第4節に従う。共通再送記録は無期限保持し、操作者・操作種別（transfer.create／transfer.update／transfer.delete）・家計簿・対象振替・版・正規化した入力を照合する。JSONキー順・UUID表記差・メモの空文字と`null`の差は同じ内容として扱う。
- 成功済み同一要求は現在の認証・参加・AdminまたはEditorロールを確認して元の成功応答を返す。POSTは同じ振替IDのLocationを再現する。支払方法の所有人物・マスタ・対象行の存在・版を再検証せず、業務処理も再実行しない。異なる操作者・操作・内容での同一ID再使用は409。現在の未参加は404、Viewerは403。
- 結果不明時は同一要求ID・同一内容を再送する。確定エラーを修正して保存する場合は新規要求IDを使用し、更新版を勝手に変更しない。
