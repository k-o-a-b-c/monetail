# 支払方法API・業務契約

**支払方法APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：家計簿に属する支払方法の5操作。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：人物・参加者の管理、レシート・振替・残高・支払メモの固有操作。
- 関連契約：[支払方法DB・評価額](../../../ledger-core-schema.md)、[人物API](persons.md)、[レシートAPI](../../../ledger-receipt-api.md)、[振替API](../../../ledger-transfer-api.md)、[残高API](../../../ledger-balance-api.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[家計簿API・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /payment-methods` | 支払方法一覧を取得 | 現在の家計簿参加者（Admin・Editor・Viewer） | 200 |
| `POST /payment-methods` | 支払方法1件を作成 | Adminは任意の同一家計簿人物、Editorは本人対応人物を所有者とする場合のみ | 初回201、同一の成功要求の再送200 |
| `PATCH /payment-methods/{paymentMethodId}` | 名前・有効期間・評価額属性を更新 | Adminは全所有者分、Editorは本人所有分のみ | 200 |
| `DELETE /payment-methods/{paymentMethodId}` | 支払方法を削除 | Adminは全所有者分、Editorは本人所有分のみ | 200 |
| `PUT /payment-methods/order` | 1人物の全支払方法の共通順を保存 | Adminは任意の同一家計簿人物、Editorは本人対応人物の所有分のみ | 200 |

- APIは各要求で認証・対象家計簿への現在の参加と操作権限を検証する。全体管理者の権限は家計簿Adminの権限を代替しない。確定直前の再検証は第7節に従う。
- 本人判定はログインアカウントがその家計簿で対応付けられた人物IDで行う。人物未対応のEditorとViewerには書込権限を認めない。Admin自身の人物対応は不要。GETは所有者・本人対応・有効期間で絞らず全件を返す。
- 支払方法の管理権限と、レシートなどでの利用権限は別とし、各業務APIの契約に従う。

## 3. 支払方法の値・業務制約

| 項目 | 契約 |
| --- | --- |
| `paymentMethodId` | APIが生成するUUID v4。名前・順序・期間から独立し、編集しても変わらない |
| `ownerPersonId` | 同一家計簿に存在する人物1人のID。必須かつ作成後変更不可。アカウント対応の有無を問わない。人物0件では作成できない |
| `name` | .NET `string.Trim()` で前後の空白を除去し、1～100 UTF-16コード単位（.NET `string.Length`）として保存する。上限超過を切り詰めない |
| 同名判定 | 同一家計簿・同一所有者内の別支払方法とのTrim後の完全一致を禁止。更新対象自身は除く。有効期間外も対象とする。所有者が異なる場合の同名は許可する。大文字/小文字、全角/半角、Unicode正規化の差は同一視しない |
| `validFrom` / `validTo` | `YYYY-MM-DD` 形式の実在する暦日またはnull。時刻・タイムゾーンは持たない。各nullはその側の制限なし。両端を含み、両方がある場合は開始日≦終了日 |
| `hasValuation` | 評価額の登録対象かを表すJSON boolean。trueなら評価額のみの登録も可能、falseなら評価額の登録不可。新規作成時の省略値はfalse。残高履歴の有無に関係なくfalse→trueを許可する。true→falseは非NULL評価額の保存済み記録（0円を含む）が1件でもあれば拒否する。残高のみの記録は拒否理由としない |
| 有効期間の意味 | 記録対象日に支払方法が利用できる範囲。期間終了後でも対象日が範囲内なら利用可能 |
| 既存データとの整合 | 既存の日付付き業務記録を範囲外にする期間変更は拒否。各業務の登録・更新側でも対象日の支払方法の有効期間を検証する |
| 削除 | 保存済み業務データからの参照が1件でも残れば削除不可。金額0・日付なしの参照も含む。参照の自動解除・付け替え・連鎖削除を行わない。作成成功記録は処理履歴であり、削除制限の対象ではない |

対象家計簿における期間検証の参照元・基準日は次のとおり。

| 業務 | 対象支払方法 | 基準日 |
| --- | --- | --- |
| レシート | レシートの支払方法 | レシートの取引日 |
| 振替 | 移動元・移動先の支払方法 | 振替の取引日 |
| 残高・評価額 | 残高または評価額の記録の支払方法（どちらか一方だけの登録、両方の登録、0円を含む） | 記録の登録日 |
| 支払メモ | メモの支払方法 | 日付付き記録のチェック日 |

- 所有者の誤登録は、未使用なら削除して正しい人物を所有者とする新規作成で訂正する。新しいUUIDを発行する。使用済みの場合は所有者の変更も削除もできない。支払方法が残る人物は削除できない。
- 期間変更・名前変更は保存済み取引・残高等を自動変更せず、過去の履歴を保持する。解約等は有効終了日で管理する。
- 評価額属性を変更しても残高・評価額を転記・代用・自動削除しない。集計・残高入力の業務制約は[支払方法の評価額と残高連携](../../../ledger-core-schema.md#支払方法の評価額と残高連携dec-305347未実装)に従う。

## 4. リクエスト

パスの `ledgerId`・`paymentMethodId` はUUID（N・D・B・P・X形式。URL上で適切にエンコードする）。UUID値として照合し、UUIDとして解釈できないパスはルーティングの404とする。全桁ゼロのUUIDもパスではUUIDとして扱い、第6節の認可・存在確認に従う。

GETには要求本文を必要としない。書込4操作（DELETEを含む）はJSONオブジェクトを送る。Content-Typeは `application/json` または `+json` サフィックスを持つJSONメディアタイプを受け付ける。

本文のUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。全桁ゼロのUUIDは本文では不正とする。UUIDのバージョンによる入力制限は設けない。

| JSON項目 | 型 | POST | PATCH | DELETE | 所有者別順PUT |
| --- | --- | --- | --- | --- | --- |
| `requestId` | UUID文字列 | 必須 | — | — | — |
| `ownerPersonId` | UUID文字列 | 必須 | — | — | 必須 |
| `name` | 文字列 | 必須 | 任意 | — | — |
| `validFrom` | 日付文字列またはnull | 任意 | 任意 | — | — |
| `validTo` | 日付文字列またはnull | 任意 | 任意 | — | — |
| `hasValuation` | boolean | 任意 | 任意 | — | — |
| `revision` | UUID文字列 | — | 必須 | 必須 | 必須 |
| `paymentMethodIds` | UUID文字列の配列 | — | — | — | 必須 |

- 「任意」はキーの省略を許す。「—」は送信不可。キー名は大文字・小文字を区別する。nullは表に明記した日付項目だけに許す。
- POSTの省略された日付はnull、`hasValuation`はfalseと同じ。`hasValuation`はJSONのtrue/falseのみ受け付け、null・数値・文字列は不正とする。PATCHの省略項目は変更せず、日付の明示的なnullはその側の制限を解除する。
- 所有者別順PUTの `paymentMethodIds` は指定人物が所有する有効期間外を含む全支払方法IDを各1回、保存する順に並べる。他家計簿・他所有者・未知ID・重複・欠落を認めず、対象人物の支払方法0件の場合は空配列を指定する。複数人物を一括で並び替えたり所有者間で移動させたりしない。

## 5. 成功応答・識別と並び順

全5操作の成功応答は同じ支払方法一覧JSONオブジェクトを返す。各JSONオブジェクトは以下の表に列挙した項目のみで構成し、すべて必須キーとする。nullは表で明記した項目だけに許す。

| トップレベル項目 | 型 | 内容 |
| --- | --- | --- |
| `paymentMethods` | オブジェクト配列 | 有効期間外を含む全支払方法。0件なら空配列 |
| `ownerOrderRevisions` | オブジェクト配列 | 全人物の所有者別順序版。支払方法0件の人物も含む。人物0件なら空配列 |

| `paymentMethods[]` の項目 | 型 | 内容 |
| --- | --- | --- |
| `paymentMethodId` | UUID文字列 | 支払方法ID |
| `ownerPersonId` | UUID文字列 | 所有者人物ID |
| `name` | 文字列 | 保存済みの支払方法名 |
| `validFrom` | 日付文字列またはnull | 有効開始日 |
| `validTo` | 日付文字列またはnull | 有効終了日 |
| `hasValuation` | boolean | 評価額あり／なし |
| `displayOrder` | 整数（Int32） | 非負の所有者内の共通表示順 |
| `revision` | UUID文字列 | 支払方法単位の更新版 |

| `ownerOrderRevisions[]` の項目 | 型 | 内容 |
| --- | --- | --- |
| `ownerPersonId` | UUID文字列 | 所有者人物ID |
| `orderRevision` | UUID文字列 | その人物の支払方法共通順の更新版 |

UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。更新版はAPIが生成するUUID v4とし、大小や時系列ではなく一致で照合する。日付は第3節の形式に従う。

- `paymentMethods` は `ownerPersonId`、`displayOrder`、`paymentMethodId` の順にそれぞれ昇順で返す。所有者間で順位値を比較しない。
- `ownerOrderRevisions` は人物マスタの共通順（人物の `displayOrder` 昇順、同値なら人物ID昇順）で返す。人物作成時に所有者別順序版を初期化し、支払方法0件でも保持する。
- 新規支払方法は最新の対象所有者の共通順の末尾（最大の `displayOrder` + 1、0件なら0）に追加する。最大値がInt32上限なら作成を拒否する。実際に所有者内の共通順を変更したときは要求順に0から連番を設定する。削除時は残った支払方法の順序値を詰めない。欠番・同順位を許容する。

## 6. 競合・失敗応答

### エラー本文

支払方法APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列またはnull | 対象のJSON項目名。個別項目を特定しない場合はnull |
| `latest` | オブジェクトまたはnull | 更新版競合時の最新情報。形式は後述。それ以外はnull |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。GETは共有参照枠、POST・PATCH・DELETE・PUTは共有書込枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | Content-Typeの欠落・JSON非対応、JSON形式・オブジェクト形式の不備、未知・重複キー | null |
| 400 | `invalid_input` | 個別項目の型・値・必須キーの欠落、空UUID、存在しない日付などの不備 | 該当項目名 |
| 400 | `invalid_input` | POSTの新規要求で同一家計簿の所有者が存在しない | `ownerPersonId` |
| 400 | `invalid_input` | 開始日が終了日より後 | `validTo` |
| 400 | `invalid_input` | 並び順の配列・要素・全ID集合の不備 | `paymentMethodIds` |
| 400 | `invalid_input` | 新規支払方法の表示順がInt32上限を超える | null |
| 401 | `authentication_changed` | 業務処理中の認証再検証で失効・停止等を検出 | null |
| 403 | `forbidden` | 操作に必要な権限がない | null |
| 404 | `not_found` | 家計簿不在・未参加、または権限確認後の対象支払方法・PUT対象人物不在 | null |
| 409 | `duplicate_payment_method_name` | 同一所有者内の同名登録・更新 | `name` |
| 409 | `payment_method_referenced` | 参照が残る支払方法の削除 | null |
| 409 | `payment_method_period_conflict` | 既存の支払方法参照を期間外にする期間変更 | `validFrom` または `validTo` |
| 409 | `payment_method_valuation_conflict` | 非NULL評価額の保存済み記録がある支払方法のtrue→false変更 | `hasValuation` |
| 409 | `revision_conflict` | 更新版の不一致 | null |
| 409 | `request_conflict` | 成功記録のある要求IDの再利用で、第7節の同一性条件を満たさない | null |
| 409 | `created_result_deleted` | 第7節の同一作成要求の再送で、作成結果の支払方法が削除済み | null |
| 503 | `store_unavailable` | 業務処理の保存先障害等 | （キーなし） |

有効な開始日・終了日の指定が既存参照と両側で衝突するときは `validFrom` を優先する。参照制約による削除拒否と保存先障害を区別し、内部例外・DBの詳細を応答に公開しない。

### 検証の優先順位

受付・JSONオブジェクト／許可キーの検証後、現在の認証・家計簿参加・書込可能な役割を確認する。対象所有者に対する操作権限も検証する。

| 操作 | 優先順位（先に該当したエラーを返す） |
| --- | --- |
| POST | 所有者IDの入力検証・所有者に対する権限 → 名前・日付・期間・評価額属性・要求IDの入力検証 → 再送照合（第7節） → 新規要求の場合のみ所有者の存在 → 同名判定 → 表示順上限 |
| PATCH | 対象支払方法の存在・所有者に対する権限 → 更新版の妥当性・一致 → 名前・日付・期間・評価額属性の入力検証 → 同名判定 → 評価額属性の変更制限 → 既存参照との期間衝突 |
| DELETE | 対象支払方法の存在・所有者に対する権限 → 更新版の妥当性・一致 → 参照による削除制限 |
| 所有者別順PUT | 所有者IDの入力検証・所有者に対する権限・対象人物の存在 → 更新版の妥当性・一致 → `paymentMethodIds` の検証 |

### 更新版競合

- PATCH・DELETEの `revision` は対象支払方法の行版、所有者別順PUTの `revision` は対象人物の `orderRevision` と原子的に照合する。
- 名前・期間・評価額属性の実値変更時だけ支払方法の行版を更新する。入力の正規化後に実値が変わらないPATCH（`revision`だけを指定した場合を含む）は、権限・版・業務制約の検証を通れば無変更成功（200）とし、行版を維持する。属性編集で表示順や所有者別順序版は変更しない。
- 所有者別順序版は対象所有者の追加・削除・共通順の変更時に更新する。所有者別順序版の照合は所有者別順PUTだけで行う。追加・削除では最新の構成・順序に対して操作し、順序版の旧値を条件にせず、新しい順序版を同一書込トランザクション内で設定する。
- 所有者別順PUTで対象人物の支払方法ID順が変わらない場合は、0件・1件の場合も含めて無変更成功（200）とし、欠番・同順位があっても `displayOrder`・`orderRevision` を維持する。無変更時も更新版・全ID集合を検証し、古い `revision` は409を返す。支払方法自体の行版や人物の編集版・人物共通順版・他所有者の順序版は変更しない。
- 409 `revision_conflict` の `latest` は行版競合なら最新の支払方法1件（第5節の`paymentMethods[]` と同じ項目）、所有者別順PUTの版競合なら以下の3項目を返す。

| 所有者別順PUTの `latest` の項目 | 型 | 内容 |
| --- | --- | --- |
| `ownerPersonId` | UUID文字列 | 対象人物ID |
| `orderRevision` | UUID文字列 | 対象人物の最新順序版 |
| `paymentMethods` | オブジェクト配列 | 対象人物の最新の全支払方法（第5節の`paymentMethods[]` と同じ項目）。`displayOrder`、`paymentMethodId` の順に昇順。0件なら空配列。他所有者分は含めない |

409の `latest` に情報を返す前にも現在の認証・家計簿参加・当該所有者への操作権限を検証し、認証失効なら401、未参加なら404、権限不足なら403を優先する。

## 7. 整合性・作成の再送

### 原子性と認可

- 書込4操作は、業務制約・更新版の照合、支払方法・順序・更新版・作成成功記録の当該操作に伴う変更を一つのトランザクションで確定する。確定前の失敗では当該操作の変更をすべて戻し、別の確定済み操作まで取り消さない。確定後の通信断・応答喪失はロールバックの根拠とならず、クライアントから保存結果を断定できない。
- 成功応答の支払方法一覧と所有者別順序版は同じトランザクションの整合した状態を返す。書込時は変更後の状態を返す。
- 成功の確定直前にも現在の認証・家計簿参加・当該要求の操作権限（本人対応・所有者を含む）を検証する。必要な権限を失った場合は成功とせず全変更を戻す。変更された権限でも当該操作が許可される場合は拒否しない。
- PATCHは省略項目と現在値を組み合わせた変更後の期間全体と既存の日付付き業務記録を同一書込トランザクション内で照合する。true→falseの変更制限も同一書込トランザクション内で最新の非NULL評価額記録を照合する。残高・評価額の登録・更新側も同一書込トランザクション内で対象日の有効期間と現在の評価額属性を検証し、並行する業務記録の保存・削除でも第3節の参照整合性と第6節の更新版照合を維持する。評価額の登録と属性のオフへの変更が競合しても両方が不整合な状態で成功しない。支払方法の操作は人物の行版・人物共通順版、他所有者の順序版、既存業務記録そのものを変更しない。

### 作成の再送

- POST /payment-methodsでは、サーバー発行の支払方法IDとは別にクライアントが発行した `requestId` で同一作成要求を識別する。[共通再送](../../../ledger-operation-retries.md)に従い、支払方法作成は `payment_method.create` として扱う。
- 同一性は操作者・操作種類・家計簿・所有者ID・正規化後の名前・開始日・終了日・評価額属性で判定する。同じUUIDの表記差、名前の前後空白、日付の省略とnull、`hasValuation`の省略とfalseの差は同一視する。
- 現在の認証・参加・作成権限と所有者に対する権限を先に検証し、再送記録を照合する。所有者の実在確認は成功記録のない新規要求で行う。
- 同じ成功要求の再送では重複作成しない。元の支払方法が残っていれば、改名・期間変更・評価額属性変更・順序変更後でも新規作成としての同名判定を行わず、現在の一覧・所有者別順序版を返す。支払方法・更新版・順序・成功記録は変更しない。
- 成功記録のある要求IDで異なる操作者・操作・家計簿・正規化入力を送れば `request_conflict`。元の作成結果が削除されていれば、所有者の人物も削除されていた場合を含め、同じ要求で再作成せず `created_result_deleted` を返す。要求記録の原子的な確定と無期限保持は共通再送に従う。
- 保存結果が不明なPOSTは同じ要求ID・同じ内容で再送する。成功記録が存在しない要求IDは再送照合上の新規要求として扱う。PATCH・DELETE・所有者別順PUTの競合は第6節の更新版照合に従う。
