# 科目API・業務契約

**科目APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：家計簿に属する科目の5操作。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：共通税区分・税率履歴の取得、レシートの入力・保存・計算。
- 関連契約：[科目DB](../../../ledger-core-schema.md#category-master)、[共通税区分・税率履歴](../../../ledger-core-schema.md#shared-tax-history)、[レシートAPI](../../../ledger-receipt-api.md)、[科目とレシートの接続](../../../ledger-core-schema.md#category-receipt-handoff)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[家計簿API・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /categories` | 科目一覧を取得 | 現在の家計簿参加者（Admin・Editor・Viewer） | 200 |
| `POST /categories` | 科目1件を作成 | Admin | 初回201、同一の成功要求の再送200 |
| `PATCH /categories/{categoryId}` | 名前・有効期間・収支区分・初期税区分を更新 | Admin | 200 |
| `DELETE /categories/{categoryId}` | 科目を削除 | Admin | 200 |
| `PUT /categories/order` | 全科目の共通順を一括保存 | Admin | 200 |

- APIは各要求で認証・対象家計簿への現在の参加と操作権限を検証する。全体管理者の権限は家計簿Adminの権限を代替しない。家計簿に参加しない全体管理者にもアクセスを認めない。確定前の再検証は第7節に従う。

## 3. 科目の値・業務制約

| 項目 | 契約 |
| --- | --- |
| `categoryId` | APIが生成するUUID v4。名前・順序・期間から独立し、編集しても変わらない |
| `name` | .NET `string.Trim()` で前後の空白を除去し、1～100 UTF-16コード単位（.NET `string.Length`）として保存する。上限超過を切り詰めない |
| 同名判定 | 同一家計簿内の別科目とのTrim後の完全一致を禁止。更新対象自身は同名判定から除く。有効期間外も対象とする。大文字/小文字、全角/半角、Unicode正規化の差は同一視しない。収支区分によって分けない |
| `validFrom` / `validTo` | `YYYY-MM-DD` 形式の実在する暦日または`null`。時刻・タイムゾーンを持たない。各`null`はその側の制限なし。両端を含み、両方がある場合は開始日≦終了日 |
| `incomeExpense` | `Income`（収入）または `Expense`（支出）の完全一致。レシートグループから参照されている科目では実値の変更を禁止する |
| `taxCategoryCode` | `Standard`（標準）、`ReducedFood`（食品軽減）、`ReducedNewspaper`（新聞軽減）、`Exempt`（非課税）の完全一致。新規明細の税率初期選択に使用する |
| 有効期間の意味 | 記録対象日に科目が利用できる範囲。期間終了後でも対象日が範囲内なら利用可能 |
| 既存データとの整合 | 期間検証対象の既存記録を範囲外にする期間変更は拒否。対象業務の登録・更新側でも対象日の科目の有効期間を検証する |
| 削除 | 参照が1件でも残れば、有効期間にかかわらず削除不可。参照の自動解除・付け替え・連鎖削除を行わない。作成成功記録は処理履歴であり、削除制限の対象ではない |

対象家計簿における期間検証の参照元・基準日は次のとおり。

| 業務 | 対象科目 | 基準日 |
| --- | --- | --- |
| レシート | レシートグループの科目 | レシートの取引日 |

操作日・登録処理時刻では判定しない。

- 属性の変更は既存業務記録を書き換えない。過去の表示・集計では科目IDから現在の名前を参照する。
- 使用済み科目とは、同一家計簿の保存済みレシートグループに当該科目の参照が1件以上ある科目をいう。収支区分を同じ値で指定すること、名前・初期税区分を変更することは許可する。
- 科目別の収支分類は科目の収支区分を使用し、実際の収入・支出の金額符号とは独立する。レシート側の詳細は第1節の関連契約に従う。

## 4. リクエスト

パスの `ledgerId`・`categoryId` はUUID（N・D・B・P・X形式。URL上で適切にエンコードする）。UUID値として照合し、UUIDとして解釈できないパスはルーティングの404とする。全桁ゼロのUUIDもパスではUUIDとして扱い、第6節の認可・存在確認に従う。

GETには要求本文を必要としない。書込4操作（DELETEを含む）はJSONオブジェクトを送る。Content-Typeは `application/json` または `+json` サフィックスを持つJSONメディアタイプを受け付ける。

本文のUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。全桁ゼロのUUIDは本文では不正とする。UUIDのバージョンによる入力制限は設けない。

| JSON項目 | 型 | POST | PATCH | DELETE | 共通順PUT |
| --- | --- | --- | --- | --- | --- |
| `requestId` | UUID文字列 | 必須 | — | — | — |
| `name` | 文字列 | 必須 | 任意 | — | — |
| `validFrom` | 日付文字列または`null` | 任意 | 任意 | — | — |
| `validTo` | 日付文字列または`null` | 任意 | 任意 | — | — |
| `incomeExpense` | 文字列 | 必須 | 任意 | — | — |
| `taxCategoryCode` | 文字列 | 必須 | 任意 | — | — |
| `revision` | UUID文字列 | — | 必須 | 必須 | 必須 |
| `categoryIds` | UUID文字列の配列 | — | — | — | 必須 |

- 「任意」はキーの省略を許す。「—」は送信不可。キー名は大文字・小文字を区別する。`null`は表で明記した日付項目だけに許す。入力不備のエラーと検証の優先順位は第6節に従う。
- POSTの省略された日付は`null`と同じ。PATCHの省略項目は変更せず、日付の明示的な`null`はその側の制限を解除する。片方だけの期間変更でも現在値と組み合わせて第3節の制約を検証する。
- 共通順PUTの `categoryIds` は有効期間外・収入・支出を含む当該家計簿の全科目IDを各1回、保存する順に並べる。他家計簿の科目ID・未知ID・重複・欠落を認めず、科目0件の場合は空配列を指定する。

## 5. 成功応答・識別と並び順

全5操作の成功応答は共通の科目一覧JSONオブジェクトを返す。各JSONオブジェクトは以下の表に列挙した項目のみで構成し、すべて必須キーとする。`null`は表で明記した項目だけに許す。読み取りの整合性・再送時の応答は第7節に従う。

| トップレベル項目 | 型 | 内容 |
| --- | --- | --- |
| `categories` | オブジェクト配列 | 有効期間外を含む全科目。0件なら空配列 |
| `orderRevision` | UUID文字列 | 共通順全体の更新版。科目0件でも返す |

| `categories[]` の項目 | 型 | 内容 |
| --- | --- | --- |
| `categoryId` | UUID文字列 | 科目ID |
| `name` | 文字列 | 保存済みの科目名 |
| `validFrom` | 日付文字列または`null` | 有効開始日 |
| `validTo` | 日付文字列または`null` | 有効終了日 |
| `incomeExpense` | 文字列 | 収支区分 |
| `taxCategoryCode` | 文字列 | 初期税区分 |
| `displayOrder` | 整数（Int32） | 非負の共通表示順 |
| `revision` | UUID文字列 | 科目単位の更新版 |

UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。更新版はAPIが生成するUUID v4とし、大小や時系列ではなく一致で照合する。日付は第3節の形式に従う。

- `categories` は収入・支出を分けず `displayOrder` 昇順、同値の場合は `categoryId` の文字列昇順で返す。
- 新規科目は書込トランザクション内の最新の全期間の共通順の末尾（最大の `displayOrder` + 1、科目0件なら0）に追加する。最大値がInt32上限なら作成を拒否する。
- 実際に共通順を変更したときは要求配列の順に0から連番を設定する。削除時は残った科目の順序値を詰めない。欠番・同順位を許容する。

## 6. 競合・失敗応答

### エラー本文

科目APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列または`null` | 対象のJSON項目名。個別項目を特定しない場合は`null` |
| `latest` | オブジェクトまたは`null` | 更新版競合時の最新情報。形式は後述。それ以外は`null` |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。GETは共有参照枠、POST・PATCH・DELETE・PUTは共有書込枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | Content-Typeの欠落・JSON非対応、JSON形式・オブジェクト形式の不備、未知・重複キー | `null` |
| 400 | `invalid_input` | 個別項目の型・値・必須キーの欠落、空UUID、存在しない日付などの不備 | 該当項目名 |
| 400 | `invalid_input` | 開始日が終了日より後 | `validTo` |
| 400 | `invalid_input` | 共通順の配列・要素・全科目ID集合の不備 | `categoryIds` |
| 400 | `invalid_input` | 新規科目の表示順がInt32上限を超える | `null` |
| 401 | `authentication_changed` | 業務処理中の認証再検証で失効・停止等を検出 | `null` |
| 403 | `forbidden` | 操作に必要な権限がない | `null` |
| 404 | `not_found` | 家計簿不在・未参加、または権限確認後の対象科目不在 | `null` |
| 409 | `duplicate_category_name` | 同名科目の登録・更新 | `name` |
| 409 | `category_referenced` | 参照が残る科目の削除 | `null` |
| 409 | `category_income_expense_conflict` | 使用済み科目の収支区分の実値変更 | `incomeExpense` |
| 409 | `category_period_conflict` | 期間検証対象の既存記録を範囲外にする期間変更 | `validFrom` または `validTo` |
| 409 | `revision_conflict` | 更新版の不一致 | `null` |
| 409 | `request_conflict` | 成功記録のある要求IDの再利用で、第7節の同一性条件を満たさない | `null` |
| 409 | `created_result_deleted` | 第7節の同一作成要求の再送で、作成結果の科目が削除済み | `null` |
| 503 | `store_unavailable` | 業務処理の保存先障害等 | （キーなし） |

有効な開始日・終了日の指定が既存参照と両側で衝突するときは `validFrom` を優先する。参照制約による削除拒否と保存先障害を区別し、内部例外・DBの詳細を応答に公開しない。

### 検証の優先順位

受付・JSONオブジェクト／許可キーの検証を通過した要求では、現在の認証・家計簿参加・操作権限を業務データの検証より先に確認する。以下は複数の不備が重なったときの業務エラーの優先順位であり、内部処理の構成を指定するものではない。

| 操作 | 優先順位（先に該当したエラーを返す） |
| --- | --- |
| POST | 名前・日付・期間・収支区分・初期税区分・要求IDの入力検証 → 再送照合（第7節） → 新規要求の場合のみ同名判定 → 表示順上限 |
| PATCH | 対象科目の存在 → 更新版の妥当性・一致 → 名前・日付・期間・収支区分・初期税区分の入力検証 → 同名判定 → 使用済み科目の収支区分の変更制限 → 既存参照との期間衝突 |
| DELETE | 対象科目の存在 → 更新版の妥当性・一致 → 参照による削除制限 |
| 共通順PUT | 更新版の妥当性・一致 → `categoryIds` の検証 |

### 更新版競合

- PATCH・DELETEの `revision` は対象科目の `revision`、共通順PUTの `revision` は共通順全体の `orderRevision` と原子的に照合する。`orderRevision` の照合は共通順PUTだけで行う。追加・削除では最新の構成・順序に対して操作し、順序版の旧値を条件にせず、新しい順序版を同一書込トランザクション内で設定する。
- 科目単位の `revision` は名前・期間・収支区分・初期税区分の実値変更時だけ更新する。属性編集は表示順・順序版を変更しない。
- 入力の正規化後に実値が変わらないPATCH（`revision` だけを指定した場合を含む）は、権限・版・業務制約の検証を通れば無変更成功（200）とし、行版を維持する。
- `orderRevision` は科目の追加・削除・共通順の変更時に更新する。並び替えは科目の行版や属性を変えない。
- 共通順PUTで科目ID順が変わらない場合は、科目0件の空配列や1件の場合も含めて無変更成功（200）とし、欠番・同順位があっても `displayOrder`・`orderRevision` を維持する。無変更時も更新版・全科目ID集合を検証し、古い `revision` は409を返す。
- 409 `revision_conflict` の `latest` は行版競合なら最新の科目1件（第5節の `categories[]` と同じ項目）、共通順PUTの版競合なら以下の2項目を返す。

| 共通順PUTの `latest` の項目 | 型 | 内容 |
| --- | --- | --- |
| `categories` | オブジェクト配列 | 最新の全科目（第5節の `categories[]` と同じ項目）。第5節の並び順に従う。0件なら空配列 |
| `orderRevision` | UUID文字列 | 共通順全体の最新順序版 |

409の `latest` に情報を返す前にも現在の認証・家計簿参加・操作権限を検証し、認証失効なら401、未参加なら404、権限不足なら403を優先する。現在の権限で認められない情報は返さない。

## 7. 整合性・作成の再送

### 原子性と認可

- 書込4操作は、業務制約・更新版の照合、科目・順序・更新版・作成成功記録の当該操作に伴う変更を一つのトランザクションで確定する。トランザクションの確定前に処理が失敗した場合は当該操作の変更をすべて戻し、別の確定済み操作まで取り消さない。確定後の通信断・応答喪失はロールバックの根拠とならず、クライアントから保存結果を断定できない。
- 成功応答の科目一覧と共通順の更新版は同じトランザクションの整合した状態を返す。書込時は変更後の状態を返す。
- 成功の確定直前にも現在の認証・家計簿参加・当該要求の操作権限を検証する。書込中に必要な権限・認証を失った場合は成功とせず、変更をすべて戻す。変更された権限でも当該操作が許可される場合は拒否しない。
- PATCHでは日付項目の省略や実値変更の有無にかかわらず、変更後の期間全体と第3節の期間検証対象の既存記録を同一書込トランザクション内で照合する。並行する業務記録の保存・削除でも第3節の業務制約と第6節の更新版照合を維持する。
- 収支区分を実値変更する場合も、同一書込トランザクション内で最新のレシートグループからの参照を照合する。収支区分の変更とレシートの登録・更新が競合しても、第3節の業務制約に反する状態で両方が成功しない。
- 科目の操作は家計簿編集版、他家計簿、共通税率履歴を変更しない。人物・支払方法の行版・順序版、既存業務記録そのものを変更しない。

### 作成の再送

- POST /categoriesでは、サーバー発行の科目IDとは別にクライアントが発行した `requestId` で同一作成要求を識別する。[共通再送](../../../ledger-operation-retries.md)に従い、科目作成は `category.create` として扱う。
- 同一性は操作者・操作種類・家計簿・正規化後の名前・開始日・終了日・収支区分・初期税区分で判定する。同じUUIDの表記差、名前の前後空白、日付の省略と`null`の差は同一視する。
- 現在の認証・家計簿参加・作成権限を先に検証し、再送記録を照合する。
- 同じ成功要求の再送では重複作成しない。元の作成科目が残っていれば、改名・期間変更・収支区分・初期税区分の変更・順序変更後でも、新規作成としての同名判定を行わず、現在の科目一覧・順序版を返す。科目・更新版・順序・成功記録を変更しない。
- 成功記録のある要求IDで異なる操作者・操作・家計簿・正規化入力を送れば `request_conflict`。元の作成科目が削除されていれば同じ要求で再作成せず `created_result_deleted` を返す。要求記録の原子的な確定と無期限保持は共通再送に従う。
- 保存結果が不明なPOSTは同じ要求ID・同じ内容で再送する。成功記録が存在しない要求IDは再送照合上の新規要求として扱う。PATCH・DELETE・共通順PUTの競合は第6節の更新版照合に従う。
