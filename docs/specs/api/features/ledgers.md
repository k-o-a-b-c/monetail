# 家計簿API・業務契約

**家計簿APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：参加中の家計簿の一覧・個別参照、作成して開く、指定／最後の家計簿を開く、家計簿名の変更、アカウント別並び順の保存、家計簿の削除。
- Clientの操作者情報の再取得：[画面共通処理](../../../ledger-person-conflicts.md)。
- 関連契約：[家計簿共通前提](../../../ledger-core-principles.md)、[家計簿DB](../../../ledger-core-schema.md)、[参加者API](../../../ledger-person-api-contract.md)、[招待](../../../ledger-invitations.md)、[人物API](persons.md)、[科目API](categories.md)、[支払方法API](payment-methods.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[共通HTTP境界・回数制限](../../../ledger-core-api.md)、[共通再送](../../../ledger-operation-retries.md)。

## 2. エンドポイントと権限

| メソッド・パス | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /ledgers` | 自分が参加する家計簿一覧を取得 | 有効な認証アカウント | 200 |
| `GET /ledgers/{id}` | 対象家計簿と本人の参加情報を取得 | 対象家計簿の参加者 | 200 |
| `POST /ledgers` | 家計簿を作成して開く | 有効な登録アカウント | 初回201、同一成功要求の再送200 |
| `POST /ledgers/{id}/open` | 指定家計簿を開き、最終選択を保存 | 対象家計簿の参加者 | 200 |
| `POST /ledgers/open-last` | 最後の家計簿を開く | 有効な認証アカウント | 200 |
| `PATCH /ledgers/{id}` | 家計簿名を変更 | 対象家計簿のAdmin | 200 |
| `PUT /ledgers/order` | 自分の家計簿一覧の順序を保存 | 有効な認証アカウント | 200 |
| `DELETE /ledgers/{id}` | 家計簿を削除 | 対象家計簿のAdmin | 200 |

- 参加者の役割は Viewer・Editor・Admin。全体Adminの権限は家計簿の参加・役割の確認を免除しない。別アカウントのIDを入力から受け取らない。
- 一覧・個別GETは最終選択を変更しない。作成・指定／最後の家計簿を開く操作は成功時に最終選択を更新する。最終選択はアカウント単位で端末間共有する。
- GETと2つの開くPOSTは共有参照枠、作成POST・PATCH・並び順PUT・DELETEは共有書込枠を使用する。

## 3. 家計簿の値・業務制約

| 項目 | 制約 |
| --- | --- |
| `ledgerId` | APIが生成するUUID v4。家計簿名・順序から独立 |
| `name` | .NET `string.Trim()` で前後の空白を除去し、1～100 UTF-16コード単位（.NET `string.Length`）として保存する。上限超過を切り詰めない。同名を認め、名前で統合しない |
| `role` | ログイン中のアカウントの対象家計簿内の役割。Viewer・Editor・Adminのいずれか |
| `myPersonId` | ログイン中の参加者に対応する同一家計簿の人物ID。未設定ならnull |
| 作成 | 作成者がAdminとして参加する。人物・科目・支払方法・招待は自動作成しない。直近のパスキー本人確認は要求しない |
| 名前変更 | 作成と同じ名前の制約を適用する。業務記録の有無にかかわらず変更できる |
| 並び順 | アカウント単位の任意の順序。端末間で共有し、新規作成・招待参加は末尾に追加する。参加解除された家計簿は一覧から除く |
| 削除 | レシート・残高（評価額のみの登録を含む）・振替・支払メモが1件でも残る家計簿は削除不可。業務記録が0件の場合は物理削除する。有効な認証と対象家計簿のAdmin権限を要求し、直近のパスキー本人確認は要求しない |

人物とアカウントの対応は[参加者API](../../../ledger-person-api-contract.md)で管理する。同一家計簿では1アカウント0〜1人物、1人物0〜1アカウント。人物対応の有無を管理権限の条件にしない。

## 4. リクエスト

パスの `id` はUUID（N・D・B・P・X形式。URL上で適切にエンコードする）。UUID値として照合し、UUIDとして解釈できないパスはルーティングの404とする。全桁ゼロのUUIDもパスではUUIDとして扱い、第6節の認可・存在確認に従う。

GETおよび2つの開くPOSTには要求本文を必要としない。開くPOSTの対象はパスまたは認証中のアカウントの最終選択から決まる。本文が送られても対象の決定には使用せず、共通HTTP境界は適用する。

作成POST・PATCH・並び順PUT・DELETEはJSONオブジェクトを送る。Content-Typeは `application/json` または `+json` サフィックスを持つJSONメディアタイプを受け付ける。

| JSON項目 | 型 | 作成POST | PATCH | 並び順PUT | DELETE |
| --- | --- | --- | --- | --- | --- |
| `name` | 文字列 | 必須 | 任意 | — | — |
| `requestId` | UUID文字列 | 必須 | — | — | — |
| `revision` | UUID文字列 | — | 必須 | 必須 | 必須 |
| `ledgerIds` | UUID文字列の配列 | — | — | 必須 | — |

- キー名は大文字・小文字を区別する。未知・重複キー、必須キーの欠落、null、全桁ゼロのUUIDを認めない。「—」の項目は送信不可。
- 本文のUUID文字列は.NET `Guid.TryParse` で解釈できる形式（N・D・B・P・X）を受け付け、同じUUID値として照合する。UUIDのバージョンによる入力制限は設けない。
- 「任意」はキーの省略を許す。PATCHで `name` を省略した場合は現在の名前を維持する。明示的な `null` は認めない。
- 並び順PUTの `ledgerIds` は現在参加している全家計簿のIDを保存する順に各1回指定する。未参加・未知ID、重複・欠落を認めない。0件の場合は空配列。

## 5. 成功応答・識別と並び順

家計簿オブジェクトは以下の5項目のみを含み、すべて必須キーとする。nullは表で明記した項目だけに許す。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `ledgerId` | UUID文字列 | 家計簿ID |
| `name` | 文字列 | 保存済みの家計簿名 |
| `role` | 文字列 | 本人の現在の役割 |
| `revision` | UUID文字列 | 家計簿自身の更新版 |
| `myPersonId` | UUID文字列またはnull | 本人の対応人物ID。未設定・新規作成直後はnull |

UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。更新版はAPIが生成するUUID v4で、一致により照合する。

| 操作 | 応答 |
| --- | --- |
| 一覧GET・並び順PUT・DELETE | 下表の一覧オブジェクト。書込時は変更後の状態 |
| 個別GET・指定して開くPOST | 家計簿オブジェクト |
| PATCH | 更新後の家計簿オブジェクト |
| 作成POST | 家計簿オブジェクト。初回201では Location: /ledgers/{id} |
| 最後の家計簿を開くPOST | `{"ledger": 家計簿オブジェクトまたはnull}`。履歴なし・現在未参加ならnull |

| 一覧オブジェクトの項目 | 型 | 内容 |
| --- | --- | --- |
| `ledgers` | オブジェクト配列 | 現在参加中の全家計簿を本人の保存順で返す。0件なら空配列 |
| `orderRevision` | UUID文字列 | 本人の家計簿一覧の構成・順序の更新版。0件でも返す |

## 6. 競合・失敗応答

### エラー本文

業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けの説明。処理分岐には使用しない |
| `field` | 文字列またはnull | 対象のJSON項目名。個別項目を特定しない場合はnull |
| `latest` | オブジェクトまたはnull | 更新版競合時の最新情報。それ以外はnull |

受付前の認証・認証ストア障害・Origin／CSRF・本文上限・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP境界に従い、業務エラー本文を一律には要求しない。

### HTTP状態・エラーコード

| HTTP | code | 条件 | field |
| --- | --- | --- | --- |
| 400 | `invalid_input` | Content-Type・JSONオブジェクト形式・未知／重複キーの不備 | null |
| 400 | `invalid_input` | 個別項目の型・値・必須キー等の不備 | 該当項目名 |
| 400 | `invalid_input` | 並び順の配列・要素・全家計簿ID集合の不備 | `ledgerIds` |
| 401 | `authentication_changed` | 業務処理中の認証再検証で失効・停止等を検出 | null |
| 403 | `forbidden` | 名前変更・削除に必要な家計簿Admin権限がない | null |
| 404 | `not_found` | 指定家計簿の不存在・未参加、作成再送時に現在の参加がない | null |
| 409 | `request_conflict` | 成功記録のある要求IDの再利用で第7節の同一性条件を満たさない | null |
| 409 | `revision_conflict` | 更新版の不一致 | null |
| 409 | `ledger_referenced` | 業務記録が残る家計簿の削除 | null |
| 503 | `store_unavailable` | 業務処理の保存先障害等、作成確定前に作成者のAdmin参加が失われた場合 | （キーなし） |

不存在と未参加を区別する情報や内部例外・DBの詳細は返さない。

### 検証の優先順位

受付・JSONオブジェクト／許可キーの検証を通過した要求では、現在の認証と、対象家計簿を指定する操作では現在の参加・操作権限を業務データの検証より先に確認する。以下は複数の不備が重なったときの業務エラーの優先順位であり、内部処理の構成を指定するものではない。

| 操作 | 優先順位（先に該当したエラーを返す） |
| --- | --- |
| 作成POST | 名前・要求IDの入力検証 → 再送照合（第7節） → 同一成功要求の場合は現在の参加確認 |
| PATCH | 対象家計簿の存在・参加・Admin権限 → 更新版の妥当性・一致 → 名前の入力検証 |
| 並び順PUT | 更新版の妥当性・一致 → `ledgerIds` の検証 |
| DELETE | 対象家計簿の存在・参加・Admin権限 → 更新版の妥当性・一致 → 参照による削除制限 |

### 更新版競合

- 並び順PUTの `revision` は本人の `orderRevision`、PATCH・DELETEの `revision` は対象家計簿の更新版と原子的に照合する。
- `orderRevision` は参加家計簿の追加・除外・順序の変更時に更新する。追加・除外では旧順序版を条件とせず、現在の順序に対して操作する。並び替えは家計簿自身の更新版・他アカウントの順序・最終選択を変更しない。同じ順序のPUTは版と全ID集合の照合を通れば無変更成功とし、版を維持する。
- 家計簿自身の `revision` は名前の実値変更時に更新する。入力の正規化後に実値が変わらないPATCH（`revision` だけを指定した場合を含む）は、権限・更新版・入力検証を通れば無変更成功（200）とし、更新版を維持する。役割・本人対応の変更は家計簿自身の `revision` を変更しない。
- 409 `revision_conflict` の `latest` は並び順PUTでは最新の一覧オブジェクト、PATCH・DELETEでは対象家計簿オブジェクトとする。返却前に現在の認証を、対象家計簿の行版競合では現在の参加・Admin権限も再確認する。認証失効なら401、未参加なら404、権限不足なら403を優先し、現在の権限で認められない情報は返さない。

## 7. 整合性・作成の再送

### 原子性と認可

- 取得前と結果確定前に現在の認証を検証する。指定家計簿の操作は現在の参加状態と必要な役割を確認する。取得に失敗したときは取得済みのデータを返さない。順序版と一覧は整合した同一状態を返す。
- 書込操作は成功の確定直前にも現在の認証・当該操作に必要な参加と権限を検証する。確定前に処理が失敗した場合は当該操作の変更をすべて戻す。確定後の通信断・応答喪失はロールバックの根拠とならない。DELETEの参加・Admin権限の確認は同一書込トランザクション内の関連データ削除前に行い、自身の削除処理による参加者行の消滅を権限喪失と扱わない。
- 作成して開く・指定して開く・最後の家計簿を開くはそれぞれ1回の要求で完了する。最終選択を含む操作の変更は単一トランザクションで確定し、確定前の失敗・認証喪失は全変更を戻して以前の選択を維持する。開く操作で参加を失った場合、指定は404、最後はnull応答とする。履歴なし・未参加の最終選択は変更しない。
- 複数端末の最終選択は最後に確定した操作を保存する。確定後の通信断・応答喪失はロールバックの根拠とならず、同じ家計簿を開き直せる。
- 並び順保存は全ID集合と順序版を検証し、順序と更新版を同じトランザクションで確定する。家計簿作成・招待参加・参加解除による構成変更と順序版の更新も当該操作と原子的に確定する。

### 名前変更

- 現在の認証・参加・Admin権限、家計簿の更新版、変更後の名前の制約を同一書込トランザクション内で検証し、実値変更時は名前と新版を原子的に確定する。
- 家計簿ID、全アカウントの並び順・順序版、参加者・人物対応、最終選択、マスタ・業務記録は変更しない。

### 削除

- 業務記録の参照確認、権限・更新版の照合、全関連データの削除を一つの書込トランザクションで行う。削除前に同じ書込トランザクション内で現在の参加・Admin権限を確認し、確定前にも認証を再検証する。参照があれば業務記録もマスタも変更せず拒否する。削除可否の事前確認APIは設けない。家計簿自体の削除は、参加者の降格・除外における最後の有効なAdminの保護の対象外とする。
- 削除対象家計簿の人物・科目・支払方法、参加者・招待を削除する。関連する全アカウントの一覧から対象家計簿を除き、参加構成が変わるアカウントの順序版を更新する。対象家計簿を指す最終選択を除去する（過去の参加者分も含む）。他の家計簿を指す最終選択は維持する。成功応答は削除後の操作者の家計簿一覧と順序版を同一トランザクションの整合した状態で返す。
- 認証アカウント、共通税率履歴、要求成功記録、他家計簿の業務データは維持する。RESTRICTによる参照整合性を維持し、業務記録の連鎖削除を行わない。失敗時は全変更を戻す。
- DELETEは専用の成功再送記録を作成せず、`requestId`を要求しない。削除済みの家計簿への再送は404 `not_found` とする。削除した家計簿IDは再利用しない。

### 作成の再送

- 作成者のAdmin参加・家計簿・成功要求記録・本人の最終選択・一覧への追加と順序版を一つのトランザクションで確定する。確定前に現在の認証と作成者のAdmin参加を確認する。
- 保存結果が不明な作成POSTは同じ `requestId` と同じ名前で再送する。同一操作者・操作・要求ID・正規化済みの名前が成功記録と一致すれば、現在の参加を確認して同じ家計簿を開く。家計簿や参加を再作成せず、現在の家計簿オブジェクトを200で返し、最終選択を更新する。順序を末尾へ移さない。
- UUIDの表記差や名前の前後空白の差は同一視する。異なる操作者・操作・正規化済みの名前との要求ID競合は409とし、元の家計簿情報を返さない。別の要求IDは別操作として扱う。
- 現在の参加を失った場合は404とし、削除済みの家計簿も成功記録から復活させない。要求成功記録は共通再送契約に従って無期限保持する。
