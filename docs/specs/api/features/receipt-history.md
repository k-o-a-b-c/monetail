# レシート履歴候補・基本情報自動補完API・業務契約

**レシート履歴候補検索・基本情報自動補完APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：保存済みレシートからの店名・所在地・品名候補の検索、および店名確定時のレシート基本情報の取得の2操作。全パスは `/ledgers/{ledgerId}` の下。
- 関連契約：[レシートAPI](receipts.md)、[人物](persons.md)、[科目](categories.md)、[支払方法](payment-methods.md)、[家計簿](ledgers.md)、[レシートDB](../../../ledger-receipt-schema.md)、[候補入力・自動補完画面](../../../ledger-receipt-suggestions.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[共通HTTP境界・回数制限](../../../ledger-core-api.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /receipts/suggestions` | 履歴候補検索 | Admin・Editor・Viewer | 200 |
| `GET /receipts/autofill` | 基本情報自動補完 | Admin・Editor・Viewer | 200 |

各要求で現在の認証と対象家計簿への参加を検証する。全体管理者であっても未参加の家計簿にはアクセスできない。候補と所在地・税設定は参加者全員が参照可能。補完する支払方法だけは第5節の本人・権限制約を適用する。

<a id="3-値業務制約"></a>

## 3. 履歴候補・自動補完の値・業務制約

- 同一家計簿の保存済みレシートのみを検索する。画面の未保存入力・他家計簿は含めない。
- 部分一致検索は検索語と候補文字列の双方にUnicode NFKC、かな種統一、言語非依存の英字大小文字非区別を適用する。濁点・空白を除去せず、元の文字列・保存値は変更しない。
- 検索範囲の店名は元文字列の完全一致（BINARY）。候補の重複除去も元文字列の完全一致で行う。表記差が検索上同値でも別候補とする。
- `null`、空文字、空白だけの文字列は候補検索の対象外。その他の候補の前後空白は保持する。自動補完は候補検索とは別に最新履歴の値を取得するため、所在地が未入力でも古い非空値へ置換しない。

## 4. リクエスト

GETには要求本文を必要としない。パスとクエリのUUIDは[レシートAPI第4節](receipts.md#4-リクエスト)に従う。許可したクエリのみ各1値を受け付ける。両APIの `shopName`・`q` に独自の文字数上限は設けず、共通HTTP境界に従う。

### 4.1 履歴候補検索

`kind` は検索する候補の種類を指定する必須クエリパラメータであり、次の3値のみを許容する。

| `kind` の値 | 検索範囲 | 追加の必須クエリ |
| --- | --- | --- |
| `shopName` | 家計簿内の全レシートの店名 | なし |
| `shopLocation` | 同じ店名のレシートの所在地 | `shopName` |
| `itemName` | 同じ店名・科目の明細の品名 | `shopName`・`categoryId` |

`kind` と表に定義された追加クエリ、および任意の `q` のみを許容する。不要なクエリを送信した場合は400 `invalid_input` とする。

`shopName` は空文字不可。`categoryId` はUUID。`q` はすべての種類で任意とし、省略・空文字なら絞り込みなし、指定時は部分一致で絞り込む。

### 4.2 基本情報自動補完

| クエリ | 必須 | 値 |
| --- | --- | --- |
| `shopName` | 必須 | 確定店名（空文字不可） |
| `transactionDate` | 必須 | 実在するローカル取引日（YYYY-MM-DD） |

表の2クエリのみを受け付ける。本人対応人物は現在の参加情報からAPIが特定する。

## 5. 成功応答・並び順

HTTP 200の成功応答はJSONオブジェクトを返す。各JSONオブジェクトは表に列挙した項目のみで構成し、すべて必須キーとする。UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。

### 5.1 履歴候補検索

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `suggestions` | 文字列配列 | 元の文字列、0〜100件 |
| `hasMore` | 真偽値 | 条件一致・重複除去後の候補が100件を超える場合のみ`true` |

全対象履歴に検索条件と空候補の除外を適用し、元文字列で重複除去した後、候補に該当するレシートの最終更新UTC日時の最大値降順、同日時は元文字列のBINARY昇順で最大100件を返す。品名も明細ではなく親レシートの更新日時を使用する。金額やメモの変更でも候補順位は上がり得る。0件は `{"suggestions":[],"hasMore":false}`。`categoryId` がUUIDとして有効でも一致する履歴がなければ同じ0件応答とする。

### 5.2 基本情報自動補完

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `shopLocation` | 文字列または`null` | 所在地 |
| `paymentMethodId` | UUID文字列または`null` | 支払方法ID |
| `taxInclusionMode` | 整数または`null` | 0（税込）・1（税抜） |
| `taxRoundingMode` | 文字列または`null` | `floor`・`half_up` |

店名の完全一致履歴から、次の2集合それぞれで最終更新UTC日時降順、同日時はレシートIDのBINARY降順の最新1件を選ぶ。

- 所在地・税込／税抜・税端数方式：同一家計簿の全人物の同名店レシート。3項目は同じレシートから取得する。所在地は最新レシートに保存された値をそのまま返す。`null`なら`null`、空文字なら空文字を返し、空白のみの文字列も変換しない。いずれの場合も古い所在地を探さない。
- 支払方法：本人対応人物が所有する支払方法を利用した同名店レシートのうち、リクエストの `transactionDate`（現在入力中のレシートの取引日）が支払方法・所有人物双方の有効期間内（両端含む）であり、現在のロールがAdminまたはEditorのもの。本人対応なし・Viewer・利用可能な履歴なしなら`null`。Adminも他人物の支払方法へフォールバックしない。

いずれも該当履歴なしならその集合の全項目を`null`とする。別表記・部分一致の店名へフォールバックしない。画面での適用・手動値保護は[候補入力・自動補完画面](../../../ledger-receipt-suggestions.md)に従う。

## 6. 失敗応答

### エラー本文

レシート履歴APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列または`null` | 対象のクエリ名。個別項目を特定しない場合は`null` |
| `latest` | `null` | 更新版競合は対象外 |

受付前の認証・認証ストア障害・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。2操作とも共有参照枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | `kind`不正、必須項目欠落、空の店名、不正UUID・日付、未知・重複クエリ | 該当クエリ名 |
| 401 | `authentication_changed` | 業務処理中の認証再検証で失効・停止等を検出 | `null` |
| 404 | `not_found` | 家計簿不存在・未参加 | `null` |
| 503 | `store_unavailable` | 保存先障害等 | （キーなし） |

内部例外・DBの詳細を応答に公開しない。

### 検証の優先順位

[共通の検証原則](../../../ledger-core-api.md#共通の検証原則)に従う。全操作で受付時の認証を含む共通HTTP境界を適用し、第4節でJSON本文を定義した操作ではJSONメディアタイプ・構文・トップレベルのオブジェクト／許可キーを検証してから、下表の業務処理に進む。

矢印はエラーの優先順位を示す。同一段階の項目は列挙順を要求しない。成功応答・競合時の `latest` の返却前、および書込確定前の再検証も含める。内部処理やクラス構成は指定しない。

| 操作 | 検証・処理の流れ |
| --- | --- |
| 履歴候補GET | 現在の認証・家計簿参加 → `kind`・許可クエリ・重複・必須項目・店名／UUIDの検証 → 全対象履歴から候補検索・重複除去・並び替え・件数制限 → 認証・参加の再検証 → 応答 |
| 基本情報自動補完GET | 現在の認証・家計簿参加 → 許可クエリ・重複・必須項目・店名／取引日の検証 → 同名店履歴から所在地・税設定と本人所有支払方法を取得 → 認証・参加・本人対応／ロールの再検証 → 応答（第7節） |

応答確定前の認可変化の扱いは第7節に従う。

<a id="7-整合性再送"></a>

## 7. 整合性・認可

- 参照専用であり、レシートや更新日時を変更しない。検索・結合は対象家計簿に限定する。
- 取得前と応答確定前に認証・参加を検証し、認証失効時は401、非参加時は404として補完値・候補を返さない。
- 自動補完では開始時から本人対応人物（未対応との切替を含む）またはロールが変化した場合、取得済み支払方法IDを破棄して`null`を返す。新しい人物・ロールで再検索せず、所在地・税設定の取得結果は維持する。
