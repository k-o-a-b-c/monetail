# レシート履歴候補・基本情報自動補完API・業務契約

**レシート履歴候補検索・基本情報自動補完APIの外部契約の正本。**

## 1. 対象・関連契約

- 対象：保存済みレシートからの店名・所在地・品名候補の検索、および店名確定時のレシート基本情報の取得の2操作。全パスは `/ledgers/{ledgerId}` の下。
- 対象外：レシートの保存・削除、マスタの管理、画面での候補表示・補完値の適用。
- 関連契約：[レシートAPI](receipts.md)、[人物API](persons.md)、[科目API](categories.md)、[支払方法API](payment-methods.md)、[家計簿API](ledgers.md)、[レシートDB](../../../ledger-receipt-schema.md)、[候補入力・自動補完画面](../../../ledger-receipt-suggestions.md)。
- 共通契約：[認証API](../../../auth-api-contract.md)、[セッション保護](../../../auth-session-security.md)、[Windows認証](../../../auth-windows-oauth.md)、[共通HTTP境界・回数制限](../../../ledger-core-api.md)。

## 2. エンドポイントと権限

| メソッド・パス（家計簿相対） | 動作 | 権限 | HTTP成功コード |
| --- | --- | --- | --- |
| `GET /receipts/suggestions` | 履歴候補検索 | Admin・Editor・Viewer | 200 |
| `GET /receipts/autofill` | 基本情報自動補完 | Admin・Editor・Viewer | 200 |

各要求で現在の認証と対象家計簿への参加を検証する。全体管理者であっても未参加の家計簿にはアクセスできない。履歴候補・税設定は参加者全員が参照可能。自動補完の所在地・支払方法は第5節の本人所有履歴に限定し、支払方法には書込ロールの制約も適用する。

<a id="3-値業務制約"></a>

## 3. 履歴候補・自動補完の値・業務制約

- 同一家計簿の保存済みレシートのみを検索する。画面の未保存入力・他家計簿は含めない。
- 部分一致検索は検索語と候補文字列の双方にUnicode NFKC、かな種統一、言語非依存の英字大小文字非区別を適用する。濁点・空白を除去せず、元の文字列・保存値は変更しない。
- 検索範囲の店名は元文字列の完全一致（BINARY）。候補の重複除去も元文字列の完全一致で行う。表記差が検索上同値でも別候補とする。
- `null`、空文字、空白だけの文字列は候補検索の対象外。その他の候補の前後空白は保持する。

## 4. リクエスト

GETには要求本文を必要としない。パスとクエリのUUIDは[レシートAPI第4節](receipts.md#4-リクエスト)に従う。許可したクエリのみ各1値を受け付ける。両APIの `shopName`・`q` に独自の文字数上限は設けず、共通HTTP境界に従う。

### 4.1 履歴候補検索

`kind` は検索する候補の種類を指定する必須クエリパラメータであり、次の3値のみを許容する。

| `kind` の値 | 検索範囲 | 追加の必須クエリ |
| --- | --- | --- |
| `shopName` | 家計簿内の全レシートの店名 | なし |
| `shopLocation` | 同じ店名のレシートの所在地 | `shopName` |
| `itemName` | 同じ店名・科目の明細の品名 | `shopName`・`categoryId` |

`kind` と表に定義された追加クエリ、および任意の `q` のみを許容する。不要なクエリを送信した場合は400 `invalid_input` とする。

`shopName` は空文字不可。`categoryId` はUUID。`q` はすべての種類で任意とし、省略・空文字なら絞り込みなし、指定時は部分一致で絞り込む。

### 4.2 基本情報自動補完

| クエリ | 必須 | 値 |
| --- | --- | --- |
| `shopName` | 必須 | 確定店名（空文字不可） |

`shopName` のみを受け付ける。本人対応人物は現在の参加情報からAPIが特定する。

## 5. 成功応答・並び順

HTTP 200の成功応答はJSONオブジェクトを返す。各JSONオブジェクトは表に列挙した項目のみで構成し、すべて必須キーとする。`null`は表で明記した項目だけに許す。UUIDの応答形式は小文字のN形式（ハイフンなし32桁）。

### 5.1 履歴候補検索

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `suggestions` | 文字列配列 | 元の文字列、0〜100件 |
| `hasMore` | 真偽値 | 条件一致・重複除去後の候補が100件を超える場合のみ`true` |

全対象履歴に検索条件と空候補の除外を適用し、元文字列で重複除去した後、候補に該当するレシートの最終更新UTC日時の最大値降順、同日時は元文字列のBINARY昇順で最大100件を返す。品名も明細ではなく親レシートの更新日時を使用する。金額やメモの変更でも候補順位は上がり得る。0件は `{"suggestions":[],"hasMore":false}`。`categoryId` がUUIDとして有効でも一致する履歴がなければ同じ0件応答とする。

### 5.2 基本情報自動補完

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `shopLocation` | 文字列または`null` | 所在地。未入力は`null` |
| `paymentMethodId` | UUID文字列または`null` | 支払方法ID |
| `taxInclusionMode` | 文字列または`null` | `Inclusive`（税込）・`Exclusive`（税抜） |
| `taxRoundingMode` | 文字列または`null` | `Floor`（切り捨て）・`HalfUp`（四捨五入） |

店名の完全一致履歴から、次の2集合それぞれで最終更新UTC日時降順、同日時はレシートIDのBINARY降順の最新1件を選ぶ。有効期間による絞り込みは行わない。

- 所在地・支払方法：本人対応人物が所有する支払方法を使用したレシートの最新1件から取得する。本人対応なしの場合は両項目を`null`とする。所在地は[レシートAPIの値の契約](receipts.md#3-レシートの値業務制約)に従う。支払方法IDはAdmin・Editorの場合のみ返し、Viewerの場合は`null`とする。
- 税込／税抜・税端数方式：同一家計簿の全人物のレシートの最新1件から取得する。

該当履歴がない場合はその集合の全項目を`null`とする。取得した値が空欄または利用不可でも、古い履歴・他人物の履歴（本人所有履歴の取得時）・別表記や部分一致の店名へフォールバックしない。画面での適用・有効期間判定・手動値保護は[候補入力・自動補完画面](../../../ledger-receipt-suggestions.md)に従う。

## 6. 失敗応答

### エラー本文

レシート履歴APIの業務エラーは以下の4項目のみで構成するJSONオブジェクトを返す。ただし、保存障害の503 `store_unavailable` は `code`・`message` の2項目とする。

| 項目 | 型 | 内容 |
| --- | --- | --- |
| `code` | 文字列 | エラーコード |
| `message` | 文字列 | 利用者向けのエラーの説明。具体的な文言は実装側で管理し、クライアントの処理分岐には使用しない |
| `field` | 文字列または`null` | 対象のクエリ名。個別項目を特定しない場合は`null` |
| `latest` | `null` | 更新版競合は対象外 |

受付前の認証・認証ストア障害・回数制限等の拒否、およびルーティング段階のエラーは第1節の共通HTTP契約・HTTP境界に従う。業務エラー本文を一律には要求しない。2操作とも共有参照枠を使用する。

### HTTP状態・エラーコード

| HTTP | `code` | 条件 | `field` |
| --- | --- | --- | --- |
| 400 | `invalid_input` | `kind`不正、必須項目欠落、空の店名、不正UUID、未知・重複クエリ | 該当クエリ名 |
| 404 | `not_found` | 家計簿不存在・未参加 | `null` |
| 503 | `store_unavailable` | 保存先障害等 | （キーなし） |

内部例外・DBの詳細を応答に公開しない。

### 検証の優先順位

[共通の検証原則](../../../ledger-core-api.md#共通の検証原則)に従う。両操作で受付時の認証を含む共通HTTP境界を適用してから、下表の業務処理に進む。

矢印はエラーの優先順位を示す。同一段階の項目は列挙順を要求しない。業務処理は受付時に認証済みのアカウントを使用する。内部処理やクラス構成は指定しない。

| 操作 | 検証・処理の流れ |
| --- | --- |
| 履歴候補GET | 家計簿参加 → `kind`・許可クエリ・重複・必須項目・店名／UUIDの検証 → 全対象履歴から候補検索・重複除去・並び替え・件数制限 → 応答 |
| 基本情報自動補完GET | 家計簿参加 → 許可クエリ・重複・必須項目・店名の検証 → 本人所有の最新同名店履歴から所在地・支払方法を取得し、支払方法の返却可否をロールで判定、全人物の最新同名店履歴から税設定を取得 → 応答 |


<a id="7-整合性再送"></a>

## 7. 整合性・認可

- 参照専用であり、レシートや更新日時を変更しない。検索・結合は対象家計簿に限定する。
- 取得前に参加を確認する。非参加なら404として補完値・候補を返さない。自動補完は取得時に確認した参加情報・本人対応人物・ロールに基づき第5節の候補を取得する。候補は取得時点の値であり、レシート保存の権限・有効性は保存要求で検証する。
