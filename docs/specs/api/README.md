# API契約の機能別整理・実装台帳

**対象：サーバーAPI。** 機能別にAPI契約の参照先・文書移行状況・実装状況・確定仕様との未対応差分を管理する。

**本書はAPIの実装状況・文書移行の台帳であり、外部契約の正本ではない。** API仕様は第3節の参照先、WinUIの実装状況は[画面台帳](../../screen-inventory.md)、開発の優先順位は[ロードマップ](../../07-roadmap.md)、検証・CIは[テスト台帳](../../../tests/README.md)で管理する。

**新たに確定した応答責務の変更は未実装。** 操作者の`role`・`myPersonId`を[家計簿API](features/ledgers.md)に集約し、人物・科目・支払方法の成功応答・版競合の`latest`から`currentRole`・`myPersonId`を除く。家計簿・人物・科目・支払方法・共通税区分／税率履歴APIの業務エラー本文は`code`・`message`・`field`・`latest`の4項目とし（保存先障害は2項目）、操作者の`permissions`を返さない。Clientは人物・科目・支払方法APIの403/404検知時に家計簿APIで状態を再取得する。共通税区分・税率履歴APIは有効な認証を要求する独立した共通マスタAPIとし、家計簿参加確認を行わない。その他のHTTP成功コード、業務制約、サーバー側の認可、再送・更新版・保存の原子性は維持する。実装とAPIテスト・Windows Clientの切替が完了するまでは、新しいJSON契約と現行実装を混同しない。

## 1. API仕様書の記載範囲

- HTTPメソッド・パス・クエリ・ヘッダー、認証と認可、リクエスト・レスポンスのJSON、ステータスコード・エラーコード。
- 入力値の制約、業務ルール、検索・並び順・計算、保存の原子性、更新版照合、再送の保証など**APIが受け付け、返し、保証する内容**。
- **機能別API正本は確定した最終契約だけを記載する。** 現行コードが未対応でも、承認済みの契約を正本とし、現行との差分・実装状況・移行手順は本台帳で管理する。提案・未決定事項は正本と分離し、承認前に契約へ混入させない。
- 旧仕様・変更理由・判断経緯・実装履歴を本文に残さない。確定した要求・応答項目を漏れなく列挙し、廃止済み項目を「含めない」と列挙し直さない。ただし不正入力の拒否、禁止操作、権限制約など、最終契約として意味のある否定条件は維持する。
- 物理DBの列・索引・トリガー・運用CLIの手順は関連する正本を参照し、API仕様へ複製しない。認証・セキュリティの共通契約も別の正本を参照する。
- 実装クラスや工程・PR履歴を契約と混同しない。APIの外部契約として観測できない内部処理手順は記載しない。
- 文書移行で業務制約、API/DB、認証・セキュリティ、データ整合性、JSONの省略/null、再送・版競合の確定済み契約を変えない。

**更新ルール**：API契約の確定・変更、またはAPI実装の追加・完了に伴って状態／未対応差分が変わるとき、同じPRで本表の該当行だけ更新する。実装変更がなく文書だけ移行した場合は文書移行列だけを更新する。実装済みの判定はコードと必要なテストを確認し、未確認事項を完了扱いしない。文書移行やPRの進捗、テスト件数、実行ログを実装状況として転記しない。

**共通税区分・税率履歴の確定契約と現行との差分**：`GET /tax-rates`を有効な認証アカウント向けの共通マスタAPIとし、家計簿の指定・参加確認を不要とすることを利用者確認済み（2026-11-25）。現行の`GET /ledgers/{ledgerId}/tax-rates`を置き換え、旧ルートは残さない。`LedgerManagementEndpoints.cs`・`TaxRateManagement.cs`の家計簿依存を解消し、`Program.cs`の`MapPasskeyWeb`の保護対象に新ルートを追加し、既存の共通HTTP境界（固定HTTPS・ホスト検証・no-store・認証・障害応答）とアカウント単位の共有参照枠を適用する。業務エラー本文は4項目とし、現行`LedgerApiSupport.cs`の5項目形式に含まれる`permissions`を廃止する。家計簿不在・未参加を理由とする404は対象外とする。`TaxRateTransport.cs`の`ListTaxRatesAsync`・`TaxRateRequestException`と`TaxRateHistoryCache.cs`の`TaxRatesWorkspace`から不要な家計簿ID・権限情報依存を除き、呼出元とテストも整合させる。税率取得失敗を家計簿参加喪失として扱わない。Decimal文字列は同値表記を許容し、`null`と課税0%を区別する（利用者確認済み）。現行のInvariantCulture出力に正規化処理は不要。401の既存認証復帰、取得前・確定前の認証再検証、503の2項目形式、失敗時の履歴非公開・非キャッシュ、読取非変更、[Clientキャッシュ契約](../../ledger-core-schema.md#共通税率履歴の全件getメモリキャッシュ)を維持する。API・Clientのテストで、家計簿未参加・未作成でも有効な認証で取得可能、役割によらず同一全履歴、旧ルートのルーティング404、未認証・認証失効・停止の拒否、共通HTTP境界（HTTPS・ホスト・no-store）、回数制限、JSONの必須キー・型・NULL許容、Decimal同値・精度・`null`、失敗時の取得結果非キャッシュを確認する。他機能の認可・契約、DB・CLI・保存時の税率検証は変更しない。

**人物の表示順契約と現行との差分**：科目と同じ非負のInt32表示順・上限時の400 `invalid_input`（field=null）を利用者確認済み（2026-11-24）。現行`PeopleManagement.cs`は`checked`による加算で上限を超えると例外となり、明示的な400拒否は未実装。`LedgerModel.cs`の人物表には表示順の非負CHECKがない。実装時は科目と同様の非負CHECKを初期DB定義に追加し、上限直前の成功・上限時の新規作成拒否・既存成功要求の再送・拒否時の行／順序版／再送記録の保持を検証する。Migrationは追加しない。

**人物・科目の順序版の責務**：順序版を照合するのは共通順PUTのみとする（利用者確認済み）。追加・削除では最新の構成に対し書込トランザクション内で末尾への追加・対象行の削除と順序版の更新を原子的に行い、旧順序版を更新条件にしない。現行`CategoryManagement.cs`の`AdvanceCategoryOrderAsync`には旧順序版条件付きUPDATEがあり、`PeopleManagement.cs`は追跡中の家計簿を更新するため`LedgerModel.cs`の順序版・家計簿行版の同時実行トークンが更新条件に影響する。対象列だけの更新等、既存のSQLite書込トランザクションによる直列化を維持して不要な条件を除く。共通順PUTの原子的な版照合、DELETEの行版照合、再送・業務制約・認可・ロールバックは維持する。`CategoryApiTests.cs`の内部順序版CAS失敗を409とする期待値は見直し、順序版更新自体の保存失敗は503で全変更を戻すことを検証する。Clientは追加・削除用の順序版競合分岐を設けない。実際の並び替え・追加・削除の同時操作、末尾追加、欠番保持、古い順序版のPUT拒否、古い行版のDELETE拒否、無関係な版の保持と全変更の原子性を検証する。支払方法の所有者別順序版についても同じ責務とする（下記）。

**人物・科目の削除可否・対象不在時の画面処理**：参照による削除可否の事前判定・表示は行わず、削除時にAPIで検証する。PATCH・DELETEの404では家計簿APIで現在の参加・権限を再確認し、必要な権限がある場合は該当マスタの一覧を再取得する（利用者確認済み）。APIの404・409契約は変更しない。[共通画面処理](../../ledger-person-conflicts.md#編集削除対象不在時の処理)に従ってClient・WinUIを整合させ、参照による拒否、対象不在、権限喪失、取得失敗、入力保持、選択解除、自動保存なしを検証する。事前照会API・応答項目・DBフラグは追加しない。

**科目の確定契約と現行との差分・確認事項**：旧科目CRUD契約では使用済み科目の収支区分変更は409で拒否すると明記されていたが、`CategoryManagement.cs`は400 `invalid_input`（`field=incomeExpense`）、`ReceiptApiSafetyTests.cs`も400を期待する。業務上の変更禁止はDEC-147で確定している。409 `category_income_expense_conflict`（`field=incomeExpense`、`latest=null`）を利用者確認済み（2026-11-24）。API・テスト・Clientを確定契約に整合させる。実レシート参照がある科目の収支変更拒否、同値指定・未使用科目の変更許可、拒否時のデータと版の維持を検証する。画面は事前の使用済み判定・入力無効化を行わず保存時のAPI拒否を用いる（利用者確認済み）。収支区分のエラー表示・入力保持を検証し、使用済み照会API・一覧項目・DBフラグは追加しない。`CategoryPeriodApiTests.cs`の参照プローブは実レシートグループではなく、実際の使用済み判定を覆す根拠ではない。操作者情報の集約に伴う成功応答・エラー本文の切替も未対応。POSTの初回成功・再送成功は他の4操作と同じ一覧応答に統一することを利用者確認済み（2026-11-24）。現行APIのトップレベル`categoryId`とClientの`CategoryCreationInfo`は切替対象。科目一覧内のIDと再送記録の`result_id`は維持し、API・Client・関連テストを整合させる。既存取引を期間外にする科目の期間変更を拒否することも利用者確認済み（2026-11-24）。現行`CategoryManagement.cs`は期間の前後関係のみを検証し、既存レシートの取引日との照合は未実装。エラー形式も利用者確認済み（2026-11-24）。確定契約は[科目API第6節](features/categories.md#6-競合失敗応答)を参照。実レシート参照、両端日、null、片側変更、同時保存、拒否時のデータ・版保持を実装時に検証する。共通順PUTは人物APIと同様に、ID順が変わらない場合は表示順値と順序版を維持することを利用者確認済み（2026-11-24）。現行`CategoryOrderManagement.cs`は同順・0件でも順序版更新と連番設定を行う。変更後は同順（欠番・同順位を含む）・0件・1件で版と値を維持し、無変更でも古い版・不正な全ID集合を拒否すること、実際の順変更では連番・新順序版となり行版を維持することを検証する。`revision`のみのPATCHも人物APIと同じ無変更成功に統一することを利用者確認済み（2026-11-24）。現行`CategoryManagement.cs`とClientの`CategoryChanges`は変更項目なしを拒否する。API・Client・関連テストを整合させ、正しい版で200・行版と順序版の維持、古い版で409、権限・存在・業務制約の検証維持を確認する。PATCHの検証優先順位も人物APIと同じく入力検証→同名判定→既存参照に伴う制約とすることを利用者確認済み（2026-11-24）。科目固有の収支変更制限は期間競合の前に判定する。POSTとPATCHの属性入力順は名前・日付・期間・収支区分・税区分に揃える（利用者確認済み）。現行`CategoryManagement.cs`の検証順を変更し、複数不備が同時にある場合のエラー優先順位をテストする。人物・科目のPATCHは日付項目の省略・実値変更の有無にかかわらず変更後の期間全体と既存参照を照合する。科目の画面エラー処理はHTTP状態だけでなくcode・latestの形式で区別し、人物と同様に業務エラーでは入力を保持する。API・Client・WinUIの関連テストで確認する。実装・テストの変更は文書移行の対象外。

**支払方法の確定契約と現行との差分・確認事項**：人物・科目との6項目の統一を利用者確認済み（2026-11-24）。確定契約は[支払方法API](features/payment-methods.md)を参照。

- 操作者情報の集約は上記の確定方針に従う。POST初回・再送の成功応答も他の4操作と同じ一覧応答に統一する。現行`PaymentMethodManagement.cs`のトップレベル作成IDとClientの作成応答DTO・参照箇所を切り替える。行ID・共通再送記録の`result_id`は維持し、再送時の重複作成防止・削除後再送・権限検証を維持する。
- 現行`PaymentMethodManagement.cs`は変更項目なしのPATCHを400で拒否する。正しい版でのrevisionのみのPATCHは無変更成功（200）とし、行版・順序版を維持する。古い版・権限不足・対象不在・既存参照の期間検証は維持する。PATCHの検証順は入力検証→同名判定→評価額属性の変更制限→期間競合に統一する（利用者確認済み）。現行は期間競合を先に判定する。POST・PATCHの属性入力順は名前・日付・期間・評価額属性とし、科目と同様に共通属性を固有属性より先に検証する（利用者確認済み）。所有者ID・権限・更新版等の先行検証は正本に従う。複数不備が重なる場合の優先順位と、日付項目の省略・実値変更の有無にかかわらず変更後の期間全体を検証することを確認する。
- 現行`PaymentMethodOrderManagement.cs`は同順・0件・1件でも順序版更新と連番設定を行う。同順では欠番・同順位も含め版と表示順値を維持し、古い版・不正な全ID集合は拒否する。実際の順変更では連番・新順序版となり、行版・人物版・他所有者の版を維持する。`PaymentMethodOrderApiTests.cs`の同順成功期待値を更新する。
- 現行`AdvancePaymentOrderAsync`の追加・削除時の旧順序版条件を廃止する。対象所有者の最新構成に対する末尾追加・削除と新版設定を同一トランザクションで確定する。PUTの版照合とDELETEの行版照合は維持する。`PaymentMethodApiTests.cs`の内部順序版CAS失敗を409とする期待値を見直し、順序版更新の保存失敗は503で全変更を戻すことを検証する。Clientは追加・削除専用の順序版競合分岐を設けない。同時操作、独立した所有者の版、欠番、再送記録の原子性を確認する。
- 既存参照との期間競合は409 `payment_method_period_conflict`（field=validFromまたはvalidTo、latest=null）に統一する。現行`PaymentMethodManagement.cs`・`PaymentMethodPeriodTests.cs`・`ReceiptApiSafetyTests.cs`は400を使用する。日付の形式・前後関係の不備は400のまま。実レシート・振替両側、両端日・null・片側変更・同時保存、拒否時の行と版の保持を検証する。Client・画面はcodeとlatestの形式で業務エラーを区別する。
- 所有者別順PUTの版競合の`latest`は`ownerPersonId`・`orderRevision`・`paymentMethods`の3項目とする（利用者確認済み）。現行の重複する`paymentMethodIds`を応答から除き、Clientは最新一覧の配列順と各行IDを用いる。要求側の`paymentMethodIds`は維持する。成功応答の`ownerOrderRevisions[]`の所有者ID項目名も`personId`から`ownerPersonId`に統一する（利用者確認済み）。人物APIの`personId`は変更しない。`ownerOrderRevisions`の配列順も`paymentMethods`の所有者順と同じ`ownerPersonId`の文字列昇順に統一する（利用者確認済み）。API・Client・関連テストで0件、欠番・同順位、他所有者情報の除外、最新順への切替、応答キーの一致、人物の設定順変更が支払方法APIの配列順・順序版に影響しないことを検証する。

- 残高API実装時に、評価額のみ・残高のみ・両方（0円を含む）の記録について人物（支払方法の所有者）・支払方法双方の有効期間と削除制約を適用し、人物APIの期間変更で対象記録が期間外になる場合は409 `person_period_conflict` とする。人物側も残高保存との同時操作・両端日・null・拒否時の版保持を検証する。支払方法側はtrue→falseの非NULL評価額記録による拒否（409 `payment_method_valuation_conflict`）を実装する。残高のみならオフへの変更可。評価額履歴のない状態でオフへの変更、評価額記録削除後の変更、オフ→オン、期間競合と評価額競合が同時にある場合の評価額競合優先、評価額保存とオフ変更・期間変更の同時操作での整合性・ロールバックを検証する。残高側のHTTP詳細は残高APIの設計で確定する。支払メモは人物・支払方法の期間検証の対象外とする（利用者確認済み）。当該API実装時に、確認日が期間外でもメモの保存・マスタの期間変更を拒否せず、メモを自動削除しないこと、支払方法への参照による削除制限を維持することを検証する。実装・テストの変更は文書移行の対象外。

### 家計簿APIの未対応差分

- 現行の `LedgerResponse`・Clientの `LedgerInfo` は4項目。全家計簿オブジェクトの `myPersonId` 追加とClient共通状態の切替、人物・科目・支払方法APIからの操作者情報の除去が必要。

- 作成POSTの現行DTOは未知キーを拒否するが、キーの大文字小文字・重複の検証、要求IDのN・D・B・P・X形式の受付は確定契約に未対応。UUID表記差で同一要求と判定し、空UUIDを本文で拒否することを検証する。業務400/401/404/409/503の本文統一も未対応。受付前の共通HTTP境界は変更しない。
- 作成POSTを開く操作から分離し、初回201・再送200を維持し、いずれも一覧と順序版を返す契約に統一する（利用者確認済み）。現行のLocationヘッダーは廃止し、API・Client・関連テストを整合させる。現行の作成・再送による最終選択更新を廃止し、Clientの作成成功後の遷移・一覧更新は[画面仕様](../../ledger-onboarding.md#所属0件の家計簿作成画面)に従う。作成後のopen失敗は確定済み作成を取り消さない。作成・再送時の最終選択維持、同時作成、作成確定後のopen失敗、管理画面での非切替を検証する。初回作成画面では初回成功・再送成功ともに一覧1件の場合の自動openと、複数件の場合の選択画面への遷移を検証する。
- PATCH未実装。成功時は200で更新後の操作者の家計簿一覧・順序版を返す（無変更成功を含む）。Admin限定の名前変更、名前の正規化・同名許容、行版照合・実値変更時のみ新版設定・`revision`のみのPATCHを含む無変更成功、競合時の最新家計簿オブジェクト、業務記録の有無によらない改名、順序版等の非変更を検証する。

### マスタAPIの配列順と表示順値の責務

家計簿・人物・科目・支払方法はサーバーで保存順に整列した配列を返し、配列順をClientの基準とする（利用者確認済み）。人物・科目・支払方法の現行応答および行版競合の `latest` に含まれる `displayOrder` は廃止する。順序版競合の配列も同じ応答形式に統一する。DBの表示順値・採番・上限・欠番・同順位の扱いと順序版、全ID配列による保存は維持する。家計簿にも表示順管理の共通規則を適用し、具体的なテーブル構成は別途設計する。

- APIのDTO・投影とClientの `PersonInfo`・`CategoryInfo`・`PaymentMethodInfo` および各Transportのパース・検証を切り替える。Clientのキャッシュと各画面で受信配列順を保持し、`DisplayOrder` による再ソートを除く。本人優先は安定した並び替え、絞り込みは相対順の保持、支払方法の所有者グループ順は人物配列の順に基づく。並び順編集は全期間の保存順を使用し、画面固有の表示順をそのまま書き戻さない。
- API・Client・表示関連テストで、成功／再送／版競合のJSON項目、保存順と同順位時のID順、追加・削除・並び替え、空配列、本人優先・有効期間フィルター、所有者別の順序と版の独立性を検証する。DBの順位値を検証するテストは維持する。参加者APIの `personDisplayOrder` は別契約のため、今回変更しない。

## 6. 機能単位の移行

1. 既存正本と現行API実装・APIテストを照合し、メソッド・パス・要求・応答・制約・権限・エラー・更新版・再送・原子性の欠落を探す。確定/提案/未決定、実装/未実装を分ける。
2. 機能別正本に確定した最終API契約だけを整理する。共通の外部契約はリンクし、推測で新しい値や規則を追加しない。現行との差分や実装状況は本台帳へ記載する。
3. 旧文書の節と新文書の節との対応を確認し、未移行の契約や食い違いを台帳に記録する。正本のレビューでは、確定事項の欠落・意味の変更・重複・旧仕様や実装状況の混入・参照切れがないことを確認する。
4. 承認後に**対象機能の正本だけ切り替える**。[文書INDEX](../../INDEX.md)の契約参照先を更新し、旧文書の当該API契約の重複を案内に置き換える。
5. 第3節の文書移行列を更新する。実装状況は実際のAPI実装と確定契約の差分が変わった場合だけ更新する。API/DBの実装変更を伴わない文書整理では、ビルドやAPIテストの未実施を未実施と報告する。

**家計簿API**（8操作）、**人物API・科目API・支払方法API**（GET/POST/PATCH/DELETE・順序PUT）、**共通税区分・税率履歴API**（全件GET）は移行済み。次の機能も確定した契約を照合してから移行する。参加者API・共通の認証・再送契約・物理DBは各正本を維持する。
