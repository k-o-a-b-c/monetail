# API契約の機能別整理・実装台帳

**対象：サーバーAPI。** 機能別にAPI契約の参照先・文書移行状況・実装状況・確定仕様との未対応差分を管理する。

**本書はAPIの実装状況・文書移行の台帳であり、外部契約の正本ではない。** API仕様は第3節の参照先、WinUIの実装状況は[画面台帳](../../screen-inventory.md)、開発の優先順位は[ロードマップ](../../07-roadmap.md)、検証・CIは[テスト台帳](../../../tests/README.md)で管理する。

**新たに確定した応答責務の変更は未実装。** 操作者の`role`・`myPersonId`を[家計簿API](features/ledgers.md)に集約し、人物・科目・支払方法の成功応答・版競合の`latest`から`currentRole`・`myPersonId`を除く。家計簿・人物・科目・支払方法・共通税区分／税率履歴・参加者・招待／参加受諾・レシート・履歴候補APIの業務エラー本文は`code`・`message`・`field`・`latest`の4項目とし（保存先障害は2項目）、操作者の`permissions`を返さない。Clientは人物・科目・支払方法・参加者・招待管理・レシート書込APIの403/404検知時に家計簿APIで状態を再取得する。共通税区分・税率履歴APIは有効な認証を要求する独立した共通マスタAPIとし、家計簿参加確認を行わない。その他のHTTP成功コード、業務制約、サーバー側の認可、再送・更新版・保存の原子性は維持する。実装とAPIテスト・Windows Clientの切替が完了するまでは、新しいJSON契約と現行実装を混同しない。

## 1. API仕様書の記載範囲

- HTTPメソッド・パス・クエリ・ヘッダー、認証と認可、リクエスト・レスポンスのJSON、ステータスコード・エラーコード。
- 入力値の制約、業務ルール、検索・並び順・計算、保存の原子性、更新版照合、再送の保証など**APIが受け付け、返し、保証する内容**。
- **機能別API正本は確定した最終契約だけを記載する。** 現行コードが未対応でも、承認済みの契約を正本とし、現行との差分・実装状況・移行手順は本台帳で管理する。提案・未決定事項は正本と分離し、承認前に契約へ混入させない。
- 旧仕様・変更理由・判断経緯・実装履歴を本文に残さない。確定した要求・応答項目を漏れなく列挙し、廃止済み項目を「含めない」と列挙し直さない。ただし不正入力の拒否、禁止操作、権限制約など、最終契約として意味のある否定条件は維持する。
- 物理DBの列・索引・トリガー・運用CLIの手順は関連する正本を参照し、API仕様へ複製しない。認証・セキュリティの共通契約も別の正本を参照する。
- 実装クラスや工程・PR履歴を契約と混同しない。APIの外部契約として観測できない内部処理手順は記載しない。
- 検証の優先順位は[共通の検証原則](../../ledger-core-api.md#共通の検証原則)を参照しつつ、第6節に操作別の具体的な検証・処理の流れを記載する。共通原則へのリンクだけで省略せず、適用する認可・型検証・再送・対象・版・業務制約・応答／確定前再検証を明示する。同一段階内の個別項目順・実装構造は規定しない。
- 文書移行で業務制約、API/DB、認証・セキュリティ、データ整合性、JSONの省略/null、再送・版競合の確定済み契約を変えない。

**更新ルール**：API契約の確定・変更、またはAPI実装の追加・完了に伴って状態／未対応差分が変わるとき、同じPRで本表の該当行だけ更新する。実装変更がなく文書だけ移行した場合は文書移行列だけを更新する。実装済みの判定はコードと必要なテストを確認し、未確認事項を完了扱いしない。文書移行やPRの進捗、テスト件数、実行ログを実装状況として転記しない。

**共通税区分・税率履歴の確定契約と現行との差分**：`GET /tax-rates`を有効な認証アカウント向けの共通マスタAPIとし、家計簿の指定・参加確認を不要とすることを利用者確認済み（2026-11-25）。現行の`GET /ledgers/{ledgerId}/tax-rates`を置き換え、旧ルートは残さない。`LedgerManagementEndpoints.cs`・`TaxRateManagement.cs`の家計簿依存を解消し、`Program.cs`の`MapPasskeyWeb`の保護対象に新ルートを追加し、既存の共通HTTP境界（固定HTTPS・ホスト検証・no-store・認証・障害応答）とアカウント単位の共有参照枠を適用する。業務エラー本文は4項目とし、現行`LedgerApiSupport.cs`の5項目形式に含まれる`permissions`を廃止する。家計簿不在・未参加を理由とする404は対象外とする。`TaxRateTransport.cs`の`ListTaxRatesAsync`・`TaxRateRequestException`と`TaxRateHistoryCache.cs`の`TaxRatesWorkspace`から不要な家計簿ID・権限情報依存を除き、呼出元とテストも整合させる。税率取得失敗を家計簿参加喪失として扱わない。Decimal文字列は同値表記を許容し、`null`と課税0%を区別する（利用者確認済み）。現行のInvariantCulture出力に正規化処理は不要。401の既存認証復帰、取得前・確定前の認証再検証、503の2項目形式、失敗時の履歴非公開・非キャッシュ、読取非変更、[Clientキャッシュ契約](../../ledger-core-schema.md#共通税率履歴の全件getメモリキャッシュ)を維持する。API・Clientのテストで、家計簿未参加・未作成でも有効な認証で取得可能、役割によらず同一全履歴、旧ルートのルーティング404、未認証・認証失効・停止の拒否、共通HTTP境界（HTTPS・ホスト・no-store）、回数制限、JSONの必須キー・型・NULL許容、Decimal同値・精度・`null`、失敗時の取得結果非キャッシュを確認する。他機能の認可・契約、DB・CLI・保存時の税率検証は変更しない。

**人物の表示順契約と現行との差分**：科目と同じ非負のInt32表示順・上限時の400 `invalid_input`（field=null）を利用者確認済み（2026-11-24）。現行`PeopleManagement.cs`は`checked`による加算で上限を超えると例外となり、明示的な400拒否は未実装。`LedgerModel.cs`の人物表には表示順の非負CHECKがない。実装時は科目と同様の非負CHECKを初期DB定義に追加し、上限直前の成功・上限時の新規作成拒否・既存成功要求の再送・拒否時の行／順序版／再送記録の保持を検証する。Migrationは追加しない。

**人物・科目の順序版の責務**：順序版を照合するのは共通順PUTのみとする（利用者確認済み）。追加・削除では最新の構成に対し書込トランザクション内で末尾への追加・対象行の削除と順序版の更新を原子的に行い、旧順序版を更新条件にしない。現行`CategoryManagement.cs`の`AdvanceCategoryOrderAsync`には旧順序版条件付きUPDATEがあり、`PeopleManagement.cs`は追跡中の家計簿を更新するため`LedgerModel.cs`の順序版・家計簿行版の同時実行トークンが更新条件に影響する。対象列だけの更新等、既存のSQLite書込トランザクションによる直列化を維持して不要な条件を除く。共通順PUTの原子的な版照合、DELETEの行版照合、再送・業務制約・認可・ロールバックは維持する。`CategoryApiTests.cs`の内部順序版CAS失敗を409とする期待値は見直し、順序版更新自体の保存失敗は503で全変更を戻すことを検証する。Clientは追加・削除用の順序版競合分岐を設けない。実際の並び替え・追加・削除の同時操作、末尾追加、欠番保持、古い順序版のPUT拒否、古い行版のDELETE拒否、無関係な版の保持と全変更の原子性を検証する。支払方法の所有者別順序版についても同じ責務とする（下記）。

**人物・科目の削除可否・対象不在時の画面処理**：参照による削除可否の事前判定・表示は行わず、削除時にAPIで検証する。PATCH・DELETEの404では家計簿APIで現在の参加・権限を再確認し、必要な権限がある場合は該当マスタの一覧を再取得する（利用者確認済み）。APIの404・409契約は変更しない。[共通画面処理](../../ledger-person-conflicts.md#編集削除対象不在時の処理)に従ってClient・WinUIを整合させ、参照による拒否、対象不在、権限喪失、取得失敗、入力保持、選択解除、自動保存なしを検証する。事前照会API・応答項目・DBフラグは追加しない。

### マスタAPIの配列順と表示順値の責務

家計簿・人物・科目・支払方法はサーバーで保存順に整列した配列を返し、配列順をClientの基準とする（利用者確認済み）。人物・科目・支払方法の現行応答および行版競合の `latest` に含まれる `displayOrder` は廃止する。順序版競合の配列も同じ応答形式に統一する。DBの表示順値・採番・上限・欠番・同順位の扱いと順序版、全ID配列による保存は維持する。家計簿にも表示順管理の共通規則を適用し、具体的なテーブル構成は別途設計する。

- APIのDTO・投影とClientの `PersonInfo`・`CategoryInfo`・`PaymentMethodInfo` および各Transportのパース・検証を切り替える。Clientのキャッシュと各画面で受信配列順を保持し、`DisplayOrder` による再ソートを除く。本人優先は安定した並び替え、絞り込みは相対順の保持、支払方法の所有者グループ順は人物配列の順に基づく。並び順編集は全期間の保存順を使用し、画面固有の表示順をそのまま書き戻さない。
- API・Client・表示関連テストで、成功／再送／版競合のJSON項目、保存順と同順位時のID順、追加・削除・並び替え、空配列、本人優先・有効期間フィルター、所有者別の順序と版の独立性を検証する。DBの順位値を検証するテストは維持する。参加者APIの応答・配列順の変更は上記の参加者APIの未対応差分で扱う。

- 成功済みPOST／PUT／DELETEの再送は現在の認証・参加・書込ロールと同一性だけを検証し、既存処理を繰り返さない。現行 `ReceiptManagement.cs` の再送分岐はこの方式。所有者変更・Viewer・参加喪失・対象削除後の成功再送、異内容の409、成功記録と業務データの原子性を回帰確認する。

- `ReceiptHistoryQuery.cs` の自動補完空店名を400へ、候補検索の空文字・空白のみを除外へ変更する。履歴候補検索・基本情報自動補完の `shopName`・`q` の100 UTF-16コード単位制限を廃止する。保存時の店名・所在地・品名の制限は維持する。関連テストでは100単位超の検索語・店名が文字数だけを理由に400にならないことを確認する。所在地は最新の全人物同名店履歴の保存値を補完応答に追加する。`null`・空文字・空白のみの値をそのまま返し、履歴なしは`null`、古い非空値へフォールバックしないことを検証する。支払方法・税設定の選定基準と権限は維持する。Client DTOと画面の所在地適用・古い応答破棄・手動操作保護を整合させる。追加DB列やAPIは不要。

## 6. 機能単位の移行

1. 既存正本と現行API実装・APIテストを照合し、メソッド・パス・要求・応答・制約・権限・エラー・更新版・再送・原子性の欠落を探す。確定/提案/未決定、実装/未実装を分ける。
2. 機能別正本に確定した最終API契約だけを整理する。共通の外部契約はリンクし、推測で新しい値や規則を追加しない。現行との差分や実装状況は本台帳へ記載する。
3. 旧文書の節と新文書の節との対応を確認し、未移行の契約や食い違いを台帳に記録する。正本のレビューでは、確定事項の欠落・意味の変更・重複・旧仕様や実装状況の混入・参照切れがないことを確認する。
4. 承認後に**対象機能の正本だけ切り替える**。[文書INDEX](../../INDEX.md)の契約参照先を更新し、旧文書の当該API契約の重複を案内に置き換える。
5. 第3節の文書移行列を更新する。実装状況は実際のAPI実装と確定契約の差分が変わった場合だけ更新する。API/DBの実装変更を伴わない文書整理では、ビルドやAPIテストの未実施を未実施と報告する。

**家計簿API**（8操作）、**人物API・科目API・支払方法API**（GET/POST/PATCH/DELETE・順序PUT）、**共通税区分・税率履歴API**（全件GET）は移行済み。次の機能も確定した契約を照合してから移行する。**参加者API**（3操作）、**招待・参加受諾API**（5操作）、**レシートAPI**（5操作）、**レシート履歴API**（2操作）も移行済み。共通の認証・再送契約・物理DBは各正本を維持する。
