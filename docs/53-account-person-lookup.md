# 53 認証からの人物照合・表示名取得の分離

**登録・ログイン・セッション検証・本人再確認・本人のパスキー管理の人物照合を、Monetail側の専用処理へ分離した。** [52 認証処理の再利用方針](52-reusable-authentication-boundaries.md)を引き継ぎ、URL・JSON・認証条件・保存値は維持する。

## 境界

認証側の`IAccountPersonLookup.FindAsync(authUserId, token)`が、アカウントに対応する人物コードと表示名を`AccountPerson`で受け取る。対応または人物がなければ`null`を返す。認証側からMonetailの人物テーブルを直接読む代わりに、この窓口へ依頼する。

`Features/Monetail/Accounts/MonetailAccountPersonLookup`が`auth_user_links`と`m_user`を内部結合し、パラメーター化した1回のSELECTで現在の人物コードと名前を取得する。名前やWindows用`account_name`からの推測対応は行わず、エンティティの追跡・キャッシュ・DB更新も行わない。DB障害は握りつぶさず既存の認証エラー処理へ伝える。

`Program.cs`でスコープ単位に実装を登録する。呼び出す認証サービスと同じ`AuthDbContext`を使い、書込トランザクション中の人物照合も同じ接続・トランザクションへ参加する。

## 維持する確認順序

| 呼出元 | 確認と取得の位置 |
| --- | --- |
| 登録 | 開始時と、確定時の書込トランザクション内で登録待ちアカウントの人物を確認。作成オプションの名前も取得結果を使う |
| ログイン | 署名検証後、鍵状態更新・セッション保存前の書込トランザクション内で人物を確認 |
| セッション検証 | 各要求で有効セッション・アカウントを確認後、現在の人物と名前を取得し、現在のロールも読み直す |
| 本人再確認 | 署名検証後、鍵状態・確認日時の保存前に開始時と同じ人物であることを確認 |
| パスキー追加・削除 | 有効アカウント・セッション・直近5分を確認したうえで現在の人物を照合し、保存後の再確認も維持。追加時の名前も取得結果を使う |

パスキー管理では、従来1つのSELECTで行っていたアカウント・セッションと人物の照合を、認証側のSELECTと人物照合のSELECTへ分ける。書込中は同じトランザクションであり、最後の鍵の保護・削除と全端末失効の原子性・途中失敗のRollbackを維持する。

人物不在・対応不備・処理中の人物変更は従来の条件で拒否する。人物なしのログイン、別人への鍵登録、セッションの復活、Cookieや固定期限の延長を許可する変更は含まない。

## 残る依存と範囲

新規導入ではアカウントと人物を別管理にする（DEC-039、[56](56-new-user-onboarding-policy.md)）。本書の人物照合必須は現在の実装の説明であり、新規導入はアカウントをMonetail全体、人物を家計簿ごとに管理する方針が確定した（DEC-040、[57](57-ledger-data-ownership.md)）。新規導入では人物との直接紐付けを持たず、アカウント自身の表示名を使う（DEC-042）。人物を要件としない認証・表示名取得への具体的な改修は後続設計で決める。今回の文書更新では照合の削除やアクセス条件の変更を行わない。

`CurrentSession`やチャレンジは人物コードを保持し、認証DBの`AuthUserLink`・`LegacyPerson`とEF移行、人物指定の管理コマンド・全失効処理も現行構成を維持する。今回で認証全体が別アプリへそのまま流用できる状態にはならない。

別アプリでは独立したアカウントを持つ方針を維持し、共通アカウント・SSO・認証データ共有は追加しない。ライブラリ化や残るDBモデル・管理コマンドの分離は必要時に検討する。

EF移行・依存パッケージの追加は不要。Windows版・業務値・保存済み`receipt.total`・本番設定・実データは変更しない。検証結果・件数・CIは[tests/README.md](../tests/README.md)を参照する。
