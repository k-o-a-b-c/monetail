計算テストは .NET 8 SDK を使い、実アプリの VB ソースを直接コンパイルします。JSON の全11ケース、税率別合算、旧 `floor` の負数・浮動小数点境界、手入力値引・率値引、収入／支出、人別参考配分、残高推算、内税／外税・端数方式を指定した合計プレビューでReceiptの状態を変更しないことを検証します。残高推算の入出力だけをメモリ上で供給し、計算処理は製品コードを実行します。

マイグレーションテストは Python 標準ライブラリの SQLite で実際のスキーマと移行 SQL を実行し、既存行・割当・合計の保持、2列だけの追加、既定値・制約、PRAGMA の保持、再実行拒否を検証します。

Windows と .NET Framework 4.8 がある環境では次も実行します。

```powershell
dotnet run --project tests/PersistenceTests/PersistenceTests.vbproj
```

こちらは実際の `DataAccess`、SQLite プロバイダー（製品と同じ 1.0.113.1）、登録画面、独自コントロールを直接コンパイルします。一時DBで新規保存／編集、一覧・残高用の両読込、店舗別の直近方式、同日時の順序、利用者ごとの履歴、手動選択の保持、内税／外税と端数方式のラジオグループの独立性、編集中・確認取消時にReceiptの両設定・合計が変わらないこと、登録確認後の選択値の反映、更新失敗時のロールバック、新規／編集取消／流用の画面状態を検証します。確認ダイアログを開かない画面操作は実際のイベント処理を呼び出します。流用は確認ダイアログを含め、ボタン操作後の即時保存・画面終了と取消を検証します。既存DBは使用しません。

レシートの外部キー回帰テストもWindowsの同じプロジェクトで実行します。実際のDataAccess接続の外部キーをON/OFFそれぞれに設定し、子を入れ替える更新、親子の削除、別レシートの保持、更新途中・親削除時の失敗からのDB復元を検証します。外部キーの設定はテスト用接続だけに指定し、製品側の既定値は変更しません。

NULL文字列の回帰テストでは、レシートの所在地・タグ、グループと明細のタグを個別にNULLへ設定します。一覧・残高の両読込経路、子の再読込、画面の取消・同じレシートの再表示を実行し、NULLを空文字で扱えること、既存の空文字・日本語・空白や金額・対象者割当が保持されることを確認します。読込・画面取消ではDBのNULLを更新しません。後で明示的に保存した場合は、既存の保存処理により画面上の空文字が保存されます。

小数割引率の回帰は新規・更新の2チェックです。率0%／3%／2.5%／2.6%、`floor`／`half_up`それぞれで、単価103円・単価値引3円・数量2・外税8%を保存し、一覧・残高・子再読込の3経路で率と合計を検証します。整数率はINTEGER、小数率はREALで格納され、読込では率・値引・数量・保存合計等を更新しないことも確認します。旧`GetInt32`がREAL値で`InvalidCastException`になることは、[修正前CI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39125787720)で再現しています。製品修正は共通読込の`GetDouble`への変更だけで、DDL・保存・計算・入力操作は従来どおりです。[PR #5](https://github.com/k-o-a-b-c/monetail-legacy/pull/5)。

支払メモ一括保存は、成功、末尾行のINSERT／UPDATE失敗時の巻き戻しと同じDataAccessでの再保存、空リストの3チェックに成功しました。FK ON/OFFで実際のDataAccessを使い、追加と更新の混在、NULL日付／タグ・空文字・日時・引用符／改行を含むメモ、対象外行・読込時の保存値の保持を確認します。[旧処理のCI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39158731495)では成功・空リストがPASSする一方、FK ONで末尾INSERTを失敗させると先行する1行目の更新と2行目の追加が残ることを再現しました。末尾失敗はテスト専用トリガーで起こし、その前に先行2行の変更が実行されたことも確認します。修正後は末尾INSERT／UPDATE失敗の両方をFK ON/OFFで通しています。製品の保存SQL・保存順・NULL仕様は維持し、画面の空メモは従来どおり空文字です。画面の確認・終了操作や実DBでの障害復旧を検証したものではありません。[PR #6](https://github.com/k-o-a-b-c/monetail-legacy/pull/6)。

GitHub Actions の `Tests` は上記テストと、Windows で既存ソリューションの NuGet 復元・ビルドを実行します。

## Windowsで画面を手動確認する手順（利用者環境では未実施）

1. 確認対象の作業ブランチ（mainへの取り込み後は `main`）をチェックアウトし、READMEの開発手順で既存ソリューションをビルドします。
2. DBをバックアップしてテスト用コピーを作り、`PRAGMA table_info` で店舗・レシートの `tax_rounding_mode` 列の有無を確認します。未適用のコピーにだけ `docs/migrations/20261017_01_shop_tax_rounding.sql` を一度適用し、適用済みなら再実行しません。`App.config` の接続先をそのコピーに変更して起動します。
3. 未登録の店舗名で新規レシートを作成し、「外税」、税率10%、19円の明細2件を入力します。「税端数」のラジオボタンを切り替え、切り捨て41円／四捨五入42円を確認します。端数を切り替えても「外税」が選択されたままで、「内税」に切り替えても端数の選択が保持されることを確認します。
4. 四捨五入で保存して開き直し、方式と42円が保持されることを確認します。店名を変えても方式が変わらないことを確認します。「内税」と別の端数方式へ変更して保存せず閉じ、同じレシートを再度開くと元の「外税」と方式・合計に戻ることを確認します。「内税」から「外税」への取消も同様です。保存した場合には変更後の設定が保持されます。編集中の選択は画面側だけで保持され、Receiptの両設定は登録確認後に転記されます。
5. 同じ店舗の新規レシートを開き、候補を選ぶか店名を入力して別の欄へ移動すると、直近の四捨五入が初期選択されることを確認します。その店舗で切り捨てのレシートを後の日付で保存すると、次の新規入力は切り捨てになります。履歴のない店舗は切り捨てです。レシートで方式を手動選択した後は、店舗を変えても選択を保持します。
6. 既存レシートを開き、必要なら画面上の税端数を変更して「流用」を押します。従来の確認後に新しいレシートが保存され、画面が閉じることを確認します。「登録」の押し直しは不要です。元レシートのDB上の内容は変わらず、流用先には画面上の端数方式が保存されます。流用確認で「いいえ」を選ぶと、画面は開いたままで追加保存されません。
7. 税込入力で方式を変えても合計が変わらないことと、既存レシートの金額・オーケーの手入力割引に変化がないことを確認します。
8. 外税8%、単価103円・単価値引3円・数量2・値引率2.5%で保存し、開き直して率と合計（切り捨て210円／四捨五入211円）が保持されることを確認します。率を2.6%へ更新して再表示し、切り捨て209円／四捨五入210円を確認します。0%・3%の整数率も従来どおり保存・再表示できることを確認します。

旧アプリと新アプリで同じDBを同時に使わないでください。
