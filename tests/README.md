# 計算・保存・外部キーの自動テスト

リポジトリのルートで実行します。

現在の自動テスト構成です。各チェック内の値・モード・経路の組合せは、件数へ重複加算しません。

最新結果は[この改修ブランチのTests](https://github.com/k-o-a-b-c/monetail-legacy/actions/workflows/tests.yml?query=branch%3Afix%2Fdetail-input-validation)で確認します。各実行のコミットを確認し、全ジョブ完了後の結果を採用します。Windowsでは既存ソリューションのNuGet復元・ビルドも行います。実データや利用者環境での手動操作は検証対象に含めません。

```sh
dotnet run --project tests/CalculationTests/CalculationTests.vbproj
python3 -m unittest discover -s tests -p 'test_*migration.py' -v
```

計算テストは .NET 8 SDK を使い、実アプリの VB ソースを直接コンパイルします。JSON の全11ケース、税率別合算、旧 `floor` の負数・浮動小数点境界、手入力値引・率値引、収入／支出、人別参考配分、残高推算、内税／外税・端数方式を指定した合計プレビューでReceiptの状態を変更しないことを検証します。残高推算の入出力だけをメモリ上で供給し、計算処理は製品コードを実行します。

人別集計は、対象者なし・1〜3名と無関係な選択者を含む全16選択集合、完全一致／部分一致、按分あり／なし、内税／外税、両端数方式を固定値で比較します。2人／3人の正負按分、8%／10%、課税／非課税混在、グループ内合算・空グループ・分類／日時の保持も確認します。Userの参照一致を現行挙動として記録し、各呼出前後でレシートの値・会計合計／収入／支出と選択者の値・参照順序が変わらないことを検証します。製品コードやDBは変更しません。[22 検証範囲と残る仕様判断](../docs/22-person-group-statistics.md)参照。

マイグレーションテストは Python 標準ライブラリの SQLite で実際のスキーマと移行 SQL を実行し、既存行・割当・合計の保持、税端数2列と更新版3列だけの追加、既定値・制約、PRAGMA の保持、再実行拒否を検証します。

Windows と .NET Framework 4.8 がある環境では次も実行します。

```powershell
dotnet run --project tests/PersistenceTests/PersistenceTests.vbproj
```

残高の日付境界は、製品DataAccessで保存した一時DBをFK ON/OFFで両AutoBalanceから読み、日末残高の仕様の固定期待値と比較します。起点なし／0円／収入・口座の絞り込み、最新起点と同日残高、残高日の翌日から対象日末までの半開区間、1tick・小数秒ゼロのTEXT表記、月末・年末・うるう日、時刻付き残高、DateTimeの最小日／最終日を対象とします。一般の3引数読込の両端包含も維持します。全保存値・格納型・版・スキーマ・FK／user_versionの不変と書込イベント0回を確認します。推算は`Calculation`へ共通化し、共有DataAccessが未設定／別DBでもインスタンス側が自身のDBを読み、共有設定を変更しない回帰を追加しています。[21 現行仕様](../docs/21-end-of-day-balance.md)、[20 修正前の記録](../docs/20-balance-date-boundaries.md)参照。

明細入力の回帰は、製品の登録画面と実SQLiteのFK ON/OFFで、数量の不正値は1、率の不正値は0・100%超は100に通知ダイアログなしで補正することを確認します。実際に欄を離れたときの補正と明細／DBの不変、イベントを経由しない追加／更新時の補正と反映を比較します。数量1・複数・型の上限（単価と値引額0）、率の空欄／空白・0%・100%・2.5%、負の単価の正常操作を両端数方式で保存・再読込します。既存の数量0／−2・率125%／150%は読込・計算・表示・取消を維持します。[23 仕様](../docs/23-detail-input-validation.md)参照。

起動設定の回帰では、実.NET設定プロバイダーと製品SQLiteで既定値の一致、exe基準の相対パス、接続オプション、未作成の保持、不正DB・必要構造／各移行列不足、追加列の許容、拒否時のファイル内容・ハンドル解放、エラー通知と修正後の再接続を検証します。DBの実データ監査やメイン画面のエラー表示・終了操作のE2Eは含みません。[19 設定契約](../docs/19-database-startup-settings.md)参照。

こちらは実際の `DataAccess`、SQLite プロバイダー（製品と同じ 1.0.113.1）、登録画面、独自コントロールを直接コンパイルします。一時DBで新規保存／編集、一覧・残高用の両読込、店舗別の直近方式、同日時の順序、利用者ごとの履歴、手動選択の保持、内税／外税と端数方式のラジオグループの独立性、編集中・確認取消時にReceiptの両設定・合計が変わらないこと、登録確認後の選択値の反映、更新失敗時のロールバック、新規／編集取消／流用の画面状態を検証します。確認ダイアログを開かない画面操作は実際のイベント処理を呼び出します。流用は確認ダイアログを含め、ボタン操作後の即時保存・画面終了と取消を検証します。既存DBは使用しません。

レシートの外部キー回帰テストもWindowsの同じプロジェクトで実行します。実際のDataAccess接続の外部キーをON/OFFそれぞれに設定し、子を入れ替える更新、親子の削除、別レシートの保持、更新途中・親削除時の失敗からのDB復元を検証します。外部キーの設定はテスト用接続だけに指定し、製品側の既定値は変更しません。

残高削除は、成功と親DELETE失敗からの復元・再削除の2論理チェックです。実際の`DataAccess.DeleteBalance`と製品と同じSQLiteのFK ON/OFFで、削除成功は子0／2件、親DELETE失敗からの復元・再削除は子2件を検証します。対象の親子だけが消えること、他の残高と無関係な全テーブルが変わらないことを確認します。テスト専用トリガーで親DELETEを失敗させ、先行する子DELETEもRollbackされること、トリガー解除後に同じDataAccessで再削除できることを確認します。製品修正は`t_balance_groups`→`t_balances`へのDELETE順変更だけで、既存トランザクション・製品のFK設定・DDL・画面操作を維持します。残高の登録・更新や、確認ダイアログ・エラー後の画面状態・実DBの復旧を検証したものではありません（LEG-027）。

NULL文字列の回帰テストでは、レシートの所在地・タグ、グループと明細のタグを個別にNULLへ設定します。一覧・残高の両読込経路、子の再読込、画面の取消・同じレシートの再表示を実行し、NULLを空文字で扱えること、既存の空文字・日本語・空白や金額・対象者割当が保持されることを確認します。読込・画面取消ではDBのNULLを更新しません。後で明示的に保存した場合は、既存の保存処理により画面上の空文字が保存されます。

残高・振替のNULLタグ回帰は、残高ヘッダー、支払方法別残高、振替の3チェックに成功しました（LEG-028）。対象は`t_balances.tag`・`t_balance_groups.tag`・`t_transfers.tag`の3列・6読込箇所です。`GetBalances`・`GetLastBalance`・`GetLastValuationAmount`と`GetTransfers`・`GetPaymentTransfers`で、NULLだけを空文字へ変換し、空文字・通常文字・日本語／引用符・タブ／全角空白を保持することを確認します。最新残高と最新評価額が異なる2履歴、評価額NULL／負額、振替の出金／入金・別口座・翌月行も使い、日時・金額・支払方法・関連8表の全保存行が読込前後で変わらないことを比較します。対象の文字列がすべてNULLの統合では、両AutoBalanceが口座ごとに1114円／−214円／9円となることも固定します。DB移行・保存処理・金額計算・画面操作は変更しません。

[残高・振替タグの修正前CI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39167506376)では、既存22件がPASSし、追加3チェックだけがSQL NULLの`GetString`による`InvalidCastException`で失敗しました。非NULL入力の失敗はありませんでした。[PR #8](https://github.com/k-o-a-b-c/monetail-legacy/pull/8)。

小数割引率の回帰は新規・更新の2チェックです。率0%／3%／2.5%／2.6%、`floor`／`half_up`それぞれで、単価103円・単価値引3円・数量2・外税8%を保存し、一覧・残高・子再読込の3経路で率と合計を検証します。整数率はINTEGER、小数率はREALで格納され、読込では率・値引・数量・保存合計等を更新しないことも確認します。旧`GetInt32`がREAL値で`InvalidCastException`になることは、[修正前CI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39125787720)で再現しています。製品修正は共通読込の`GetDouble`への変更だけで、DDL・保存・計算・入力操作は従来どおりです。[PR #5](https://github.com/k-o-a-b-c/monetail-legacy/pull/5)。

支払メモ一括保存は、成功、末尾行のINSERT／UPDATE失敗時の巻き戻しと同じDataAccessでの再保存、空リストの3チェックに成功しました。FK ON/OFFで実際のDataAccessを使い、追加と更新の混在、NULL日付／タグ・空文字・日時・引用符／改行を含むメモ、対象外行・読込時の保存値の保持を確認します。[旧処理のCI](https://github.com/k-o-a-b-c/monetail-legacy/actions/runs/39158731495)では成功・空リストがPASSする一方、FK ONで末尾INSERTを失敗させると先行する1行目の更新と2行目の追加が残ることを再現しました。末尾失敗はテスト専用トリガーで起こし、その前に先行2行の変更が実行されたことも確認します。修正後は末尾INSERT／UPDATE失敗の両方をFK ON/OFFで通しています。製品の保存SQL・保存順・NULL仕様は維持し、画面の空メモは従来どおり空文字です。画面の確認・終了操作や実DBでの障害復旧を検証したものではありません。[PR #6](https://github.com/k-o-a-b-c/monetail-legacy/pull/6)。

採番・更新競合は、同じ一時DBへの2接続とFK ON/OFFで登録の直列化・ロック失敗と再試行・古い編集の拒否を検証します。更新版の回帰は、更新／削除、削除済み／ID再利用／不明版、全7読込、連続保存／流用、Commit後の版反映と途中失敗後の再試行を対象にします。3画面の通常成功と競合した更新／削除は確認・警告ダイアログを含めて検証し、画面と入力、再読込フラグを比較します。[保存契約・移行手順](../docs/18-stale-edit-protection.md)。上書きを再現した旧版の結果は[PR #9の履歴](../docs/17-concurrent-persistence-validation.md)に保持しています。

GitHub Actions の `Tests` は上記テストと、Windows で既存ソリューションの NuGet 復元・ビルドを実行します。

## Windowsで画面を手動確認する手順（利用者環境では未実施）

1. 確認対象の作業ブランチ（mainへの取り込み後は `main`）をチェックアウトし、READMEの開発手順で既存ソリューションをビルドします。
2. DBをバックアップしてテスト用コピーを作ります。税端数の2列が未追加なら`docs/migrations/20261017_01_shop_tax_rounding.sql`を一度適用します。次にレシート・振替・残高の3表を`PRAGMA table_info`で確認し、`revision_token`が未追加なら`docs/migrations/20261019_01_revision_tokens.sql`を一度適用します。適用済みの移行は再実行しません。`App.config`の接続先をそのコピーに変更して起動します。
3. 未登録の店舗名で新規レシートを作成し、「外税」、税率10%、19円の明細2件を入力します。「税端数」のラジオボタンを切り替え、切り捨て41円／四捨五入42円を確認します。端数を切り替えても「外税」が選択されたままで、「内税」に切り替えても端数の選択が保持されることを確認します。
4. 四捨五入で保存して開き直し、方式と42円が保持されることを確認します。店名を変えても方式が変わらないことを確認します。「内税」と別の端数方式へ変更して保存せず閉じ、同じレシートを再度開くと元の「外税」と方式・合計に戻ることを確認します。「内税」から「外税」への取消も同様です。保存した場合には変更後の設定が保持されます。編集中の選択は画面側だけで保持され、Receiptの両設定は登録確認後に転記されます。
5. 同じ店舗の新規レシートを開き、候補を選ぶか店名を入力して別の欄へ移動すると、直近の四捨五入が初期選択されることを確認します。その店舗で切り捨てのレシートを後の日付で保存すると、次の新規入力は切り捨てになります。履歴のない店舗は切り捨てです。レシートで方式を手動選択した後は、店舗を変えても選択を保持します。
6. 既存レシートを開き、必要なら画面上の税端数を変更して「流用」を押します。従来の確認後に新しいレシートが保存され、画面が閉じることを確認します。「登録」の押し直しは不要です。元レシートのDB上の内容は変わらず、流用先には画面上の端数方式が保存されます。流用確認で「いいえ」を選ぶと、画面は開いたままで追加保存されません。
7. 税込入力で方式を変えても合計が変わらないことと、既存レシートの金額・オーケーの手入力割引に変化がないことを確認します。
8. 外税8%、単価103円・単価値引3円・数量2・値引率2.5%で保存し、開き直して率と合計（切り捨て210円／四捨五入211円）が保持されることを確認します。率を2.6%へ更新して再表示し、切り捨て209円／四捨五入210円を確認します。0%・3%の整数率も従来どおり保存・再表示できることを確認します。

旧アプリと新アプリで同じDBを同時に使わないでください。
